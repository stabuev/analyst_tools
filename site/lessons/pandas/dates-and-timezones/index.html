Проблема

Одна строка времени отвечает сразу на несколько разных вопросов

В таблице заказов хранится значение:

text
2026-02-01T23:30:00Z

Оно может понадобиться аналитику как минимум в трёх ролях:

  1. Сравнить этот заказ с другим событием на общей временной шкале.
  2. Посчитать, сколько времени прошло до оплаты или доставки.
  3. Определить, к какому рабочему дню отнести заказ в конкретной стране.

Это не одна и та же операция. Для Москвы данный момент выглядит так:

text
2026-02-02 02:30:00+03:00

Значит, UTC-дата заказа — 1 февраля, а московский календарный день — 2 февраля. Если взять первые десять символов исходной строки, дневная метрика попадёт не в тот день.

Видимая разность часов не равна прошедшей длительности

Рассмотрим обслуживание заказа в Берлине в ночь перехода на летнее время:

Событие Записанное локальное время Соответствующий UTC-момент
Начало 2026-03-29T01:30:00+01:00 2026-03-29T00:30:00Z
Конец 2026-03-29T03:30:00+02:00 2026-03-29T01:30:00Z

По показаниям часов между 01:30 и 03:30 будто бы прошло два часа. На общей шкале времени прошёл только один: местные часы перескочили через несуществующий час.

Если аналитик вычитает только локальные часы или отбросит offsets, он может получить правдоподобную, но неверную длительность. Ошибка затем попадёт в срок обслуживания (SLA), среднее время доставки, воронку или поиск аномалий.

Строка может выглядеть как дата, но ещё не быть временем

Значения ниже похожи, но несут разные контракты:

text
2026-02-01T10:00:00Z       # момент с нулевым offset
2026-02-01T13:00:00+03:00  # тот же момент с другим представлением
2026-02-01T10:00:00        # локальные часы без указания зоны

Первые два значения можно однозначно поместить на временную шкалу. Третье — нельзя, пока источник не скажет, в какой зоне были эти часы. Молчаливо принять их за UTC — не техническое преобразование, а недокументированное бизнес-предположение.

Концепция

Четыре сущности, которые нельзя смешивать

Полезно держать в голове такую цепочку:

text
строка источника
    -> aware-момент в UTC
        -> отображение в локальной timezone -> календарный день
        -> вычитание другого момента        -> прошедшая длительность Timedelta
Сущность На какой вопрос отвечает Пример в pandas
Строка Как значение записал источник? "2026-02-01T23:30:00Z"
Момент Где событие находится на временной шкале? Timestamp, datetime64[..., UTC]
Длительность Сколько времени прошло между моментами? Timedelta, timedelta64[...]
Календарное представление Какой это день и час в выбранной зоне? aware timestamp после tz_convert

Строки нужны для обмена данными, но сравнивать и вычитать следует типизированные моменты. Число часов удобно показывать в отчёте, но вычисление лучше хранить как Timedelta: тип сохраняет смысл и не заставляет помнить, записано число в секундах, минутах или часах.

Timestamp — точка, Timedelta — расстояние

В pandas одиночный момент обычно представлен pd.Timestamp, а столбец моментов — datetime-dtype. Одиночная длительность представлена pd.Timedelta, а столбец длительностей — timedelta64 с некоторой точностью хранения.

Основная арифметика следует смыслу величин:

Операция Результат Смысл
end - start Timedelta Прошедшее время между двумя моментами
moment + duration Timestamp Новый момент после фиксированной длительности
duration > threshold bool Превышен ли временной порог
duration / other_duration число Во сколько раз одна длительность больше другой

Например:

python
start = pd.Timestamp("2026-02-01T10:00:00Z")
end = pd.Timestamp("2026-02-01T12:30:00Z")

duration = end - start

assert duration == pd.Timedelta("2h 30min")
assert end == start + duration
assert duration > pd.Timedelta("2h")

Timedelta — не оформление числа. Пока результат имеет этот тип, выражение duration > pd.Timedelta("2h") само документирует единицы обеих сторон.

NaT — временной пропуск

Для datetime- и timedelta-значений pandas использует NaT — not a time. Он играет ту же роль неизвестного значения, что pd.NA в nullable-типах:

text
известный конец - неизвестное начало -> NaT

Это не нулевая длительность. Если время начала отсутствует, мы не знаем, сколько прошло, и не должны подставлять 0 часов без предметного правила.

Как и в 03/02, пустое значение и неразбираемое непустое значение различаются:

  • пустое поле может быть допустимым пропуском;
  • 2026-13-99T10:00:00Z — повреждённое значение, которое должно остановить расчёт.

Naive и aware описывают полноту временного контракта

Naive timestamp содержит дату и показания часов, но не содержит информации, как связать их с UTC. Пример: 2026-10-25 02:30.

Timezone-aware timestamp уже связан с временной шкалой через offset или timezone. Пример: 2026-10-25T02:30:00+03:00.

Слово naive не означает «плохое значение». Иногда источник действительно хранит местное время отдельно от названия зоны. Но тогда эти два поля образуют единый контракт, и зону нужно назначить явно. Без такого контракта додумывать её нельзя.

UTC, offset и timezone — не синонимы

UTC — общая шкала, относительно которой удобно сравнивать моменты.

Offset — числовое смещение от UTC в конкретный момент, например +03:00. Оно позволяет восстановить момент, но само по себе не содержит исторических и будущих правил.

Timezone — именованный набор календарных правил, например Europe/Berlin или Europe/Moscow. Одна зона в разные даты может иметь разные offsets.

Поэтому в аналитическом процессе обычно нужны обе стороны:

text
UTC                         -> сравнение, сортировка, длительность
именованная бизнес-timezone -> день, час, неделя и границы отчётного периода

Offset, пришедший в строке события, помогает найти момент. Именованная бизнес-зона определяет, как этот момент попадёт в календарный отчёт.

tz_localize и tz_convert решают разные задачи

tz_localize отвечает на вопрос:

В какой зоне были записаны эти naive-часы?

Операция назначает временную зону локальным показаниям. На переходах летнего времени могут возникнуть:

  • nonexistent time — местные часы, которые были пропущены при переводе вперёд;
  • ambiguous time — местные часы, которые повторились при переводе назад.

Политики nonexistent= и ambiguous= нельзя выбирать случайно: они должны следовать контракту источника.

tz_convert отвечает на другой вопрос:

Как уже известный aware-момент выглядит в другой зоне?

Он меняет календарное представление, но сохраняет сам момент. Поэтому обычный путь для событий с явными offsets выглядит так:

text
строка с offset -> parse в UTC -> tz_convert в бизнес-зону

Удаление зоны через tz_localize(None) не является переводом между зонами: оно оставляет показания часов, но выбрасывает связь с временной шкалой.

Длительность и календарный сдвиг — разные виды арифметики

pd.Timedelta(days=1) означает фиксированные 24 прошедших часа. Но фраза «то же местное время на следующий календарный день» описывает календарное правило. На переходе DST (сезонного перевода часов) эти результаты могут различаться:

python
local_noon = pd.Timestamp("2026-03-28 12:00", tz="Europe/Berlin")

after_24_hours = local_noon + pd.Timedelta(days=1)
next_calendar_day = local_noon + pd.DateOffset(days=1)

assert str(after_24_hours) == "2026-03-29 13:00:00+02:00"
assert str(next_calendar_day) == "2026-03-29 12:00:00+02:00"

Первое выражение сохраняет прошедшую длительность, второе — положение на местных часах. Месяц или квартал тоже нельзя выразить одним фиксированным Timedelta: их длина зависит от календаря. Для таких правил нужны календарные offsets. Здесь достаточно увидеть границу Timedelta; полный каталог offsets не является пререквизитом курса.

В основном артефакте урока DateOffset не нужен: он показан как граница применимости Timedelta, а не как ещё один API для заучивания.

Series вычитаются по меткам индекса

Из 03/01 мы знаем, что pandas сначала выравнивает Series по labels. Это правило действует и для времени:

python
start = pd.Series(["2026-01-01T10:00:00Z"], index=["A"])
end = pd.Series(["2026-01-01T11:00:00Z"], index=["B"])

Если независимо разобрать эти Series и вычесть их, pandas построит объединение индексов A и B. Получатся две строки с NaT, а не одна длительность в час. Такой результат легко принять за пропуски источника.

Вычитать два столбца одного проверенного DataFrame безопаснее: они уже относятся к одним строкам. Переиспользуемая функция всё равно должна проверить точное совпадение индексов, потому что её могут вызвать с двумя независимо подготовленными Series. Это необходимая, но не достаточная проверка: два независимо сброшенных RangeIndex могут совпасть формально. Надёжная пара start/end должна происходить из одной таблицы с проверенным grain и ключом.

Соберите это

Сначала решим центральную задачу без pandas. Цель — увидеть преобразования, которые готовый API затем выполнит векторно.

Шаг 1. Поместите два представления на общую шкалу

Даны значения:

text
A = 2026-02-01T13:00:00+03:00
B = 2026-02-01T10:00:00Z

Offset +03:00 означает, что локальные часы опережают UTC на три часа. Вычтем его:

text
A -> 13:00 - 03:00 -> 10:00 UTC
B -> 10:00 + 00:00 -> 10:00 UTC

После нормализации A == B. Сравнение исходных строк такого вывода не даёт.

Шаг 2. Выведите локальный календарный день

Возьмём момент заказа:

text
2026-02-01T23:30:00Z

В феврале 2026 года московское представление имеет offset +03:00:

text
23:30 UTC + 03:00 = 02:30 следующего дня

Следовательно:

text
UTC-момент:          2026-02-01 23:30Z
московское время:    2026-02-02 02:30+03:00
московский день:     2026-02-02 00:00+03:00

Сначала выбрана зона, и только после этого извлечена календарная граница.

Шаг 3. Рассчитайте прошедшую длительность

Вернёмся к берлинскому примеру:

text
start = 2026-03-29T01:30:00+01:00 -> 00:30Z
end   = 2026-03-29T03:30:00+02:00 -> 01:30Z

Теперь вычтем моменты на общей шкале:

text
01:30Z - 00:30Z = 1 час

Предскажите типы до запуска кода:

text
start_utc, end_utc -> datetime64[..., UTC]
end_utc - start_utc -> timedelta64[...]

Если получился обычный float, единица измерения была отброшена слишком рано.

Используйте это

1. Объявите контракт входа

ISO 8601 — распространённый стандарт текстовой записи даты и времени. В учебном наборе допустимы:

  • ISO 8601 строки с Z или явным offset вида +03:00;
  • пустое поле как неизвестный момент.

Непустая неразбираемая строка и timestamp без offset считаются ошибками контракта. Функция parse_aware_utc сочетает строгий разбор с отдельной проверкой явного offset:

python
utc = pd.to_datetime(
    source,
    format="ISO8601",
    errors="coerce",
    utc=True,
)

Здесь errors="coerce" — внутренний диагностический механизм, а не разрешение терять данные. После разбора функция находит непустые исходные значения, превратившиеся в NaT, и поднимает TimeContractError.

Отдельная проверка naive-значений принципиальна: utc=True способен молча принять naive timestamp за UTC. Технически код выполнится, но аналитический смысл будет выдуман. Для aware-строк с разными offsets тот же utc=True, наоборот, нужен: он переводит каждый момент на общую шкалу и даёт столбцу единый aware datetime-dtype.

Этот контракт намеренно не является «универсальным парсером всего». Если другой источник хранит Unix time — количество единиц от общей начальной точки — целыми числами, единица должна быть объявлена отдельно:

python
occurred_at_ms = pd.Series([1770000000000], dtype="Int64")
occurred_at_utc = pd.to_datetime(
    occurred_at_ms,
    unit="ms",
    origin="unix",
    utc=True,
)

Без unit="ms" числовой аргумент по умолчанию означает наносекунды от origin, а не миллисекунды. Не смешивайте ISO-строки и числа Unix time в одном столбце: сначала примените контракт конкретного источника.

Отдельно храните календарную дату без времени, если источник действительно сообщает только день, например дату рождения. Такая дата — календарное значение, а не событие в полночь UTC; превращение её в момент требует нового предположения.

2. Вычислите бизнес-календарь после нормализации

python
utc = parse_aware_utc(orders["ordered_at"])
local = utc.dt.tz_convert("Europe/Moscow")

orders = orders.assign(
    ordered_at_utc=utc,
    ordered_at_local=local,
    local_day=local.dt.normalize(),
    local_hour=local.dt.hour.astype("Int64"),
)

dt.normalize() устанавливает часы в полночь, сохраняя выбранную timezone. В результате local_day остаётся временным dtype, а не превращается в произвольные Python-объекты или строки. Его можно использовать как календарный ключ дневной агрегации.

Эти столбцы являются производными признаками той же строки заказа. Число строк, индекс и grain таблицы не должны меняться.

3. Сохраняйте разность как Timedelta

python
start_utc = parse_aware_utc(deliveries["started_at"])
end_utc = parse_aware_utc(deliveries["finished_at"])

elapsed_time = end_utc - start_utc

Не переводите результат в часы в той же строке. Сначала проверьте временной контракт:

python
from pandas.api.types import is_timedelta64_dtype

assert is_timedelta64_dtype(elapsed_time.dtype)

negative = elapsed_time.dropna() < pd.Timedelta(0)
if negative.any():
    raise ValueError("end precedes start")

Пока значение остаётся Timedelta, порог SLA тоже можно записать с явной единицей:

python
is_late = (
    elapsed_time.gt(pd.Timedelta("2h"))
    .astype("boolean")
    .mask(elapsed_time.isna(), pd.NA)
)

Простое сравнение NaT > threshold возвращает обычный False. Для SLA это опасно: неизвестная длительность стала бы выглядеть как «срок не нарушен». Поэтому после сравнения мы явно восстанавливаем pd.NA там, где длительность неизвестна.

Пропущенная граница даёт NaT; отрицательная известная длительность означает нарушение порядка событий; известная длительность даёт True или False. Это три разных состояния и требуют разных решений.

4. Переводите длительность в число только на границе отчёта

Если графику или внешней системе нужен числовой столбец часов:

python
elapsed_hours = elapsed_time.dt.total_seconds() / 3600

Используйте именно total_seconds(). Атрибут .dt.seconds возвращает только остаток секунд после выделения целых дней:

python
duration = pd.Series([pd.Timedelta("49h")])

assert duration.dt.total_seconds().iloc[0] / 3600 == 49
assert duration.dt.seconds.iloc[0] / 3600 == 1

Второй результат синтаксически корректен и особенно опасен: длительности меньше суток будут выглядеть правильно, а длинные — незаметно обрежутся.

5. Создавайте Timedelta с явной единицей

Одиночный порог удобно задать скаляром:

python
sla = pd.Timedelta(hours=2)
# или
sla = pd.Timedelta("2h")

Для целого столбца используйте pd.to_timedelta. Числовому источнику обязательно укажите единицу:

python
sla_minutes = pd.Series([90, 120, None], dtype="Float64")
sla_duration = pd.to_timedelta(sla_minutes, unit="m")

Без unit="m" числовые значения по умолчанию будут прочитаны как наносекунды, а не минуты. Имя столбца sla_minutes полезно, но не заменяет исполняемый dtype-контракт.

Публичный контракт артефакта:

python
parse_aware_utc(series) -> Series[datetime64[..., UTC]]

add_business_calendar(frame, column=..., timezone=...) -> DataFrame

elapsed_time(start, end) -> Series[timedelta64[...]]

Главное решение артефакта — не терять временную семантику раньше времени:

text
строка -> aware Timestamp -> UTC
два UTC-момента -> Timedelta
UTC-момент + бизнес-zone -> локальный календарный признак
Timedelta -> число часов только для конкретного потребителя

Такой контракт можно встроить в pandas pipeline уроков 03/11–03/12: он сможет добавлять временные признаки без повторного разбора строк и без скрытого предположения о зоне.

Что сознательно остаётся за границей урока

Этот урок даёт временной минимум для аналитических проектов, но не превращается в курс по временным рядам. Здесь не нужны:

  • временной индекс и восстановление частоты наблюдений;
  • resample, rolling- и expanding-окна;
  • лаги, сезонность и прогнозирование;
  • полный каталог календарных offsets и праздничных календарей;
  • преобразование периодов (Period) и интервальных индексов;
  • исторические особенности всех timezone.

В фазе 14 появятся временной индекс, частота, resampling, окна, лаги, сезонность и прогнозирование — тогда единица анализа действительно станет временным рядом. Period, интервальные индексы и расширенный каталог offsets не являются обязательными пререквизитами курса и изучаются по необходимости. Сейчас достаточно надёжно отвечать на три вопроса: когда произошло событие, сколько времени прошло и к какому локальному дню оно относится.

Дополнительное чтение

  • Time series / date functionality — начните с разделов Overview, Time stamps vs. time spans и DateOffset objects: они связывают Timestamp, Timedelta, Period и календарные смещения в одну модель.
  • pandas.to_datetime — используйте как точный справочник по format, errors, utc, unit и origin; отдельно проверьте, что именно происходит с naive-значением при utc=True.
  • datetime — основные типы даты и времени — русскоязычный перевод документации Python; прочитайте введение про aware и naive объекты, а затем разделы datetime и timedelta, чтобы увидеть основу, на которой строится модель pandas.
  • zoneinfo — поддержка часовых поясов IANA — русскоязычный перевод документации Python; полезны начало страницы и пример с fold, показывающий, почему часовой пояс — это набор правил, а не постоянное смещение от UTC.
  • Типы даты и времени в PostgreSQL — сопоставьте timestamp with time zone, timestamp without time zone и interval; разделы о часовых поясах и интервалах помогают перенести модель урока в будущую работу с SQL.
  • Time deltas — прочитайте разделы Parsing, Operations и Attributes: они показывают, как создавать длительности, считать разности и разбирать результат на компоненты.
  • pandas.to_timedelta — справочник по безопасному преобразованию длительностей; обратите внимание на unit, errors и неоднозначность единиц месяцев и лет.
  • Series.dt.total_seconds — короткая, но важная страница о переводе полной длительности в секунды; сравните результат с отдельными компонентами .dt.seconds и .dt.components.
  • Time zone handling — разберите примеры tz_localize и tz_convert, а также параметры ambiguous и nonexistent: именно здесь проявляются переходы на летнее и зимнее время.
  • DateOffset objects — прочитайте сравнение Timedelta и DateOffset вокруг перехода DST: оно закрепляет разницу между фиксированной длительностью и календарным правилом.

Ответьте после практики. Объяснение появится сразу после выбора.

01

Источник прислал 2026-02-01 10:00:00 без offset и без отдельного поля timezone. Как безопасно поступить?

Naive-часы нельзя однозначно связать с UTC. Молчаливый выбор зоны создаёт момент, которого источник не объявлял.

02

В какой последовательности следует получить московский календарный день из aware-события?

Календарная граница зависит от зоны. Сначала сохраняем и переводим момент, затем вычисляем локальный день.

03

Почему длительность лучше сначала сохранить как Timedelta, а не сразу как Float64 часов?

Timedelta делает единицу частью типа операции. В число часы переводят только тогда, когда этого требует отчёт или внешний интерфейс.

04

Интервал длится 49 часов. Как получить полное число часов без потери целых дней?

seconds содержит остаток после целых дней и дал бы 1 час. total_seconds учитывает всю длительность и даёт 49.

05

Почему + Timedelta(days=1) и + DateOffset(days=1) могут дать разное местное время?

При смене DST фиксированная длительность и следующий локальный календарный день отвечают на разные вопросы.

06

Начало интервала имеет индекс A, а конец — индекс B. Почему функция урока останавливается до вычитания?

Совпадающая позиция не доказывает принадлежность одной сущности. Проверка меток блокирует явное рассогласование; надёжнее всего брать оба столбца из одной таблицы с проверенным grain.

class TimeNormalizerTest(unittest.TestCase):
    def test_equivalent_offsets_become_same_utc_instant(self) -> None:
        parsed = TIME.parse_aware_utc(
            pd.Series(["2026-01-01T10:00:00+03:00", "2026-01-01T07:00:00Z"])
        )

        self.assertEqual(parsed.iloc[0], parsed.iloc[1])
        self.assertEqual(str(parsed.dt.tz), "UTC")

    def test_naive_timestamp_is_rejected_instead_of_assumed_utc(self) -> None:
        with self.assertRaisesRegex(TIME.TimeContractError, "no explicit UTC offset"):
            TIME.parse_aware_utc(pd.Series(["2026-01-01T10:00:00"]))

    def test_invalid_nonempty_timestamp_is_rejected(self) -> None:
        with self.assertRaisesRegex(TIME.TimeContractError, "cannot parse"):
            TIME.parse_aware_utc(pd.Series(["not-a-date"]))

    def test_empty_and_null_timestamps_remain_missing(self) -> None:
        parsed = TIME.parse_aware_utc(pd.Series(["  ", None]))

        self.assertTrue(parsed.isna().all())

    def test_business_day_is_derived_after_timezone_conversion(self) -> None:
        frame = pd.DataFrame({"ts": ["2026-01-01T22:30:00Z"]})

        result = TIME.add_business_calendar(
            frame,
            column="ts",
            timezone="Europe/Moscow",
        )

        self.assertEqual(result.loc[0, "ts_local"].hour, 1)
        self.assertEqual(str(result.loc[0, "local_day"]), "2026-01-02 00:00:00+03:00")
        self.assertEqual(str(result["local_day"].dt.tz), "Europe/Moscow")

    def test_calendar_enrichment_preserves_input_grain_index_and_object(self) -> None:
        frame = pd.DataFrame(
            {"ts": ["2026-01-01T00:00:00Z", None]},
            index=["O2", "O1"],
        )
        before = frame.copy(deep=True)

        result = TIME.add_business_calendar(
            frame,
            column="ts",
            timezone="Europe/Moscow",
        )

        pd.testing.assert_frame_equal(frame, before)
        self.assertIsNot(result, frame)
        self.assertEqual(result.index.tolist(), ["O2", "O1"])
        self.assertEqual(len(result), len(frame))

    def test_invalid_timezone_is_rejected(self) -> None:
        with self.assertRaisesRegex(TIME.TimeContractError, "invalid timezone"):
            TIME.add_business_calendar(

            pd.Series([None], index=["D1"]),
            pd.Series(["2026-03-29T03:30:00+02:00"], index=["D1"]),

        self.assertTrue(pd.isna(duration.loc["D1"]))

        self.assertEqual(hours.iloc[0], 49.0)
        self.assertTrue(pd.isna(hours.iloc[1]))
        self.assertEqual(str(hours.dtype), "Float64")

        with self.assertRaisesRegex(TIME.TimeContractError, "timedelta64"):
            TIME.duration_to_hours(pd.Series([1.5]))

from __future__ import annotations

import pandas as pd
from pandas.api.types import is_timedelta64_dtype

EXPLICIT_OFFSET_PATTERN = r"(?:Z|[+-]\d{2}:\d{2})$"


class TimeContractError(ValueError):
    """Raised when temporal data violates the declared source contract."""


def _require_series(value: object, *, name: str) -> pd.Series:
    if not isinstance(value, pd.Series):
        raise TimeContractError(f"{name} must be a pandas Series")
    return value


def parse_aware_utc(series: pd.Series) -> pd.Series:
    """Parse ISO 8601 timestamps with explicit offsets onto the UTC timeline."""

    series = _require_series(series, name="series")
    source = series.astype("string").str.strip()
    missing = source.isna() | source.eq("").fillna(False)
    parsed = pd.to_datetime(
        source.mask(missing),
        format="ISO8601",
        errors="coerce",
        utc=True,
    )
    invalid = ~missing & parsed.isna()
    if invalid.any():
        raise TimeContractError(f"cannot parse {int(invalid.sum())} timestamps")

    has_offset = source.str.contains(EXPLICIT_OFFSET_PATTERN, regex=True, na=False)
    naive = ~missing & ~has_offset
    if naive.any():
        raise TimeContractError(
            f"{int(naive.sum())} timestamps have no explicit UTC offset"
        )
    return parsed


def add_business_calendar(
    frame: pd.DataFrame,
    *,
    column: str,
    timezone: str,
) -> pd.DataFrame:
    """Add UTC, local timestamp, local day, and local hour without changing grain."""

    if not isinstance(frame, pd.DataFrame):
        raise TimeContractError("frame must be a pandas DataFrame")
    if column not in frame.columns:
        raise TimeContractError(f"missing timestamp column: {column}")
    if not isinstance(timezone, str) or not timezone.strip():
        raise TimeContractError("timezone must be a non-empty named zone")

    result = frame.copy()
    utc = parse_aware_utc(result[column])
    try:
        local = utc.dt.tz_convert(timezone)
    except (TypeError, ValueError, KeyError) as error:
        raise TimeContractError(f"invalid timezone: {timezone}") from error

    result[f"{column}_utc"] = utc
    result[f"{column}_local"] = local
    result["local_day"] = local.dt.normalize()
    result["local_hour"] = local.dt.hour.astype("Int64")
    return result


def elapsed_time(start: pd.Series, end: pd.Series) -> pd.Series:
    """Return non-negative elapsed time between index-aligned aware moments."""

    start = _require_series(start, name="start")
    end = _require_series(end, name="end")
    if not start.index.equals(end.index):
        raise TimeContractError("start and end indexes must match exactly")

    start_utc = parse_aware_utc(start)
    end_utc = parse_aware_utc(end)
    duration = (end_utc - start_utc).rename("elapsed_time")
    if duration.dropna().lt(pd.Timedelta(0)).any():
        raise TimeContractError("end timestamp precedes start timestamp")
    return duration


def duration_to_hours(duration: pd.Series) -> pd.Series:
    """Convert a Timedelta Series to reporting hours without losing whole days."""

    duration = _require_series(duration, name="duration")
    if not is_timedelta64_dtype(duration.dtype):
        raise TimeContractError("duration must have a timedelta64 dtype")
    hours = duration.dt.total_seconds().div(3600).astype("Float64")
    return hours.rename("elapsed_hours")
