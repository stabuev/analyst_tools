Проверка перед уроком

Ответьте до чтения: результат поможет заметить исходные предположения.

01

Есть таблица с grain «одна строка на заказ». Что произойдет с grain после GROUP BY user_id?

GROUP BY user_id сворачивает заказы пользователя в одну группу и меняет grain результата. Оконная функция, напротив, может добавить расчет к каждой строке заказа.

02

Зачем поместить промежуточный расчет в CTE, если затем нужно отфильтровать его результат?

CTE создает именованный этап запроса. Следующий SELECT видит его вычисленные столбцы и может фильтровать их, но CTE сам по себе не обещает дедупликацию, материализацию или однократное выполнение.

Оконные функции: разделы, порядок и соседние строки

Оконная функция не сворачивает заказы в группы: она сначала определяет для каждой строки ее раздел и место в нем, а затем добавляет результат к той же строке.

Тип: Build Треки: Core Пререквизиты: 04/06 Время: ~90 минут Результат: сохраняет grain заказов, задает независимые разделы и детерминированный порядок строк, различает row_number, rank и dense_rank, получает соседние строки через lag и lead и отбирает результат окна через CTE.

Цели обучения

После урока вы сможете:

  • объяснить, почему оконный расчет сохраняет одну строку на заказ, а GROUP BY обычно создает новый grain;
  • перевести рабочий вопрос в две разные части оконного контракта: PARTITION BY и ORDER BY;
  • задать однозначную последовательность через содержательный ключ порядка и tie-breaker;
  • выбрать между row_number, rank и dense_rank, не разрушив равенство значений;
  • получить предыдущую и следующую строку через lag и lead;
  • отличить границу раздела от неизвестного значения в соседней строке;
  • не путать порядок расчета внутри OVER с порядком строк итоговой таблицы;
  • вычислить оконный столбец в CTE и отфильтровать его на следующем этапе.

На что опирается урок

Оконные функции здесь не начинаются «с чистого листа». Они соединяют уже пройденные идеи:

Что уже известно Где пройдено Как используется сейчас
grain отвечает на вопрос «что означает одна строка» 03/01, 04/01 проверяем, что окно не размножило и не свернуло order_id
SELECT, выражения, WHERE и финальный ORDER BY 04/02 выбираем популяцию оплаченных заказов и отдельно сортируем выдачу
NULL означает неизвестное значение 04/03 не подменяем неизвестную сумму нулем и различаем два источника NULL после lag
GROUP BY создает новый grain 04/04 противопоставляем свертку группы оконному расчету на строках
суммы разных валют нельзя бездумно сравнивать 04/04, 04/05 ранжируем amount только внутри одной currency
CTE — именованный этап с собственными population и grain 04/06 сначала вычисляем номер строки, затем фильтруем его во внешнем SELECT
timestamp должен быть типизирован и сопоставим 03/09 принимаем ordered_at как готовый TIMESTAMPTZ, не обучаясь здесь разбору дат

Последний пункт — важная граница. Учебная инфраструктура уже передает запросу типизированный ordered_at. Как разбирать строковые даты, выбирать бизнес-часовой пояс и строить календарные периоды, будет подробно разобрано в отдельном уроке о времени в SQL. Для текущей задачи достаточно понимать: значения уже обозначают сравнимые моменты времени.

Проблема

У нас есть таблица заказов с grain:

text
одна строка = один order_id

Нужно ответить на вопросы, которые относятся не к отдельному заказу, а к его положению среди других строк:

  1. Какая по счету это оплаченная покупка пользователя?
  2. Какой оплаченный заказ был у него предыдущим?
  3. Какой заказ будет следующим?
  4. Какое место занимает сумма покупки среди сумм в той же валюте?
  5. Как оставить только последний оплаченный заказ каждого пользователя?

Умение выбрать строки и вычислить выражение для одной строки уже есть. Но здесь значение зависит от других строк.

Почему обычный GROUP BY не решает задачу

Такой запрос действительно посчитает число покупок пользователя:

sql
SELECT
    user_id,
    count(*) AS paid_order_count
FROM orders
WHERE status = 'paid'
GROUP BY user_id;

Но результат имеет другой grain:

text
вход:  одна строка на order_id
выход: одна строка на user_id

Из результата исчезли отдельные order_id, их суммы и даты. Мы узнали итог пользователя, но уже не можем подписать каждый заказ его порядковым номером.

Можно попытаться вернуть агрегат к заказам через JOIN, но для нумерации и соседних строк это громоздко, а иногда приводит к fanout. Нужен механизм, который видит связанные строки, но оставляет результат на исходном grain.

Как выглядит нужный результат

Для двух оплаченных заказов U001:

order_id ordered_at amount user_order_number previous_order_id next_order_id
O1001 2026-01-05 1200 RUB 1 NULL O1005
O1005 2026-02-05 1500 RUB 2 O1001 NULL

Обе строки сохранились. Новые значения описывают положение каждой строки в последовательности пользователя.

Ошибки здесь особенно опасны тем, что результат выглядит правдоподобно:

  • без разделения по пользователю первый заказ U003 может получить номер 3;
  • без однозначного tie-breaker две покупки в одну секунду могут менять порядок;
  • уникальный order_id, добавленный в рейтинг сумм, может незаметно уничтожить общий ранг равных покупок;
  • ORDER BY внутри окна может быть принят за гарантию порядка выдачи;
  • NULL из lag(amount) можно ошибочно принять за отсутствие предыдущего заказа, хотя предыдущий заказ существует, а неизвестна только его сумма.

Поэтому цель урока — не запомнить несколько имен функций. Нужно научиться формулировать и проверять контракт последовательности.

Концепция

1. Окно добавляет контекст, не меняя grain

Оконная функция вычисляет значение с учетом набора связанных строк и записывает его в текущую строку:

text
строка заказа
-> определить ее независимый раздел
-> определить ее место внутри раздела
-> применить функцию относительно этого места
-> добавить значение к той же строке заказа

Минимальная форма выглядит так:

sql
row_number() OVER (
    PARTITION BY user_id
    ORDER BY ordered_at, order_id
)

row_number() — функция. OVER (...) — описание контекста, в котором она работает.

Если оплаченных заказов было девять, корректный оконный запрос должен вернуть девять строк. Это не доказывает правильность всех значений, но подтверждает первый инвариант: grain не был изменен.

Сравните:

Механизм Что происходит со строками Типичный результат
GROUP BY user_id строки пользователя сворачиваются одна строка на пользователя
row_number() OVER (...) строки сохраняются одна строка на заказ плюс номер
lag(amount) OVER (...) строки сохраняются одна строка на заказ плюс соседнее значение

Фраза «окно сохраняет grain» не означает, что любой запрос с окном безопасен. JOIN до окна уже мог размножить заказы, а фильтр после окна может сократить строки. Поэтому grain входного отношения все равно нужно проверить.

2. PARTITION BY отвечает: какие последовательности независимы

В этом уроке partition будем называть независимым разделом строк. Для каждого пользователя нумерация должна начинаться заново:

sql
PARTITION BY user_id

Упрощенная картина:

text
U001: O1001 -> O1005
U002: O1007
U003: O1003 -> O1011
...

При переходе от U001 к U002 состояние функции сбрасывается.

Если убрать PARTITION BY user_id, все оплаченные заказы станут одной общей последовательностью:

text
O1001 -> O1003 -> O1006 -> ...

Это может быть синтаксически корректно и даже полезно для другого вопроса — например, «какой по счету была покупка во всем магазине». Но для вопроса о покупках конкретного пользователя это другая аналитическая задача.

Следовательно, PARTITION BY выбирают не «потому что так принято», а по независимой единице сравнения:

Вопрос Возможный раздел
номер покупки пользователя user_id
место суммы среди покупок в одной валюте currency
номер обращения внутри тикета ticket_id
порядок события внутри сессии session_id

Partition не обязан совпадать с grain. Grain остается order_id, а user_id только объединяет несколько заказов в контекст расчета.

3. ORDER BY внутри OVER отвечает: что значит «раньше» или «выше»

После выбора раздела нужно определить порядок строк:

sql
ORDER BY ordered_at, order_id

Здесь два ключа выполняют разные роли:

  • ordered_at выражает содержательный смысл — хронологию покупки;
  • order_id разрешает случай, когда два заказа имеют одинаковый ordered_at.

Второй ключ называют tie-breaker — правилом разрешения равенства. Для детерминированной нумерации полный набор ключей должен однозначно упорядочивать строки.

Одного ordered_at недостаточно, если возможны два заказа в один момент:

order_id ordered_at
O1005 2026-02-05 11:00
O1005A 2026-02-05 11:00

Без дополнительного правила SQL не обязан выбирать одну из этих строк первой. Сегодня номера могут выглядеть стабильно из-за текущего плана выполнения, а после изменения данных или движка поменяться.

Хороший tie-breaker:

  • заполнен для всех строк целевой популяции;
  • вместе с предыдущими ключами уникален;
  • имеет понятное постоянное правило;
  • не меняет бизнес-смысл сравнения.

Для хронологической нумерации уникальный order_id подходит. Но последнее условие важно: для рейтинга равных сумм он уже может быть неправильным. К этому вернемся ниже.

При одинаковом ordered_at такой tie-breaker задает воспроизводимую договоренность: какую строку показывать первой. Он не доказывает, что один из двух одновременных заказов в действительности произошел раньше. Если бизнес-вопрос требует истинной очередности, источник должен поставлять более точное время, монотонный sequence number или другой содержательный признак порядка.

4. Порядок окна и порядок выдачи — два разных контракта

В запросе могут быть два независимых ORDER BY:

sql
SELECT
    order_id,
    row_number() OVER (
        PARTITION BY user_id
        ORDER BY ordered_at, order_id
    ) AS user_order_number
FROM orders
ORDER BY user_id, ordered_at, order_id;

Первый ORDER BY находится внутри OVER:

  • определяет номера;
  • определяет предыдущую и следующую строку;
  • является частью вычисления.

Второй ORDER BY находится в конце запроса:

  • определяет порядок строк, которые увидит читатель или получатель выгрузки;
  • не меняет уже вычисленные номера.

Если финального ORDER BY нет, порядок результата не гарантирован. Даже если движок случайно вернул строки в порядке окна, опираться на это нельзя.

И обратная ошибка тоже возможна. Такой финальный порядок:

sql
ORDER BY amount DESC

переставит строки результата, но не заставит lag искать предыдущую строку по сумме. Для этого порядок суммы должен находиться внутри соответствующего OVER.

5. row_number: уникальная позиция в последовательности

row_number() присваивает строкам номера 1, 2, 3, ...:

sql
row_number() OVER (
    PARTITION BY user_id
    ORDER BY ordered_at, order_id
) AS user_order_number

Для каждого пользователя ровно одна строка получит номер 1, одна — номер 2 и так далее.

Это подходит, когда нужна именно уникальная позиция:

  • первая или последняя покупка;
  • последние N обращений;
  • выбор одной строки из нескольких кандидатов по явному правилу;
  • последовательный номер события.

Чтобы отметить последний заказ номером 1, меняют направление порядка:

sql
row_number() OVER (
    PARTITION BY user_id
    ORDER BY ordered_at DESC, order_id DESC
) AS latest_order_number

Для U001:

order_id хронологический номер номер от последнего
O1001 1 2
O1005 2 1

Это две разные координаты одной строки. Ни одна из них не требует удалить другой заказ.

6. Peers: строки, равные по ключам оконного порядка

Для рейтинга часто нужно сохранить равенство. Допустим, внутри RUB есть суммы:

order_id amount
O1005 1500
O1013 1500
O1001 1200

Строки с суммой 1500 равны по ключу amount DESC. Такие строки называются peers — равными по всем выражениям ORDER BY данного окна.

Важно: peers определяются не равенством всей строки и не совпадением order_id, а только ключами порядка конкретного окна.

7. row_number, rank и dense_rank отвечают на разные вопросы

На значениях 1500, 1500, 1200, 1000 функции дадут:

amount row_number rank dense_rank
1500 1 или 2 1 1
1500 2 или 1 1 1
1200 3 3 2
1000 4 4 3

Различие:

  • row_number всегда дает уникальные последовательные номера;
  • rank дает peers одинаковый ранг и оставляет после них пропуск;
  • dense_rank дает peers одинаковый ранг, но не оставляет пропусков.

Выбор определяется смыслом:

  • «оставить ровно одну последнюю строку» — row_number;
  • «место в соревновании, где после двух первых идет третье» — rank;
  • «номер уникального уровня суммы» — dense_rank.

Почему tie-breaker нельзя копировать во все окна

Для хронологической нумерации мы использовали:

sql
ORDER BY ordered_at, order_id

Можно по привычке написать рейтинг так:

sql
rank() OVER (
    PARTITION BY currency
    ORDER BY amount DESC, order_id
)

Но уникальный order_id делает полный набор ключей различным для каждой строки. Две покупки по 1500 больше не peers и получат разные ранги.

Корректное окно рейтинга суммы:

sql
rank() OVER (
    PARTITION BY currency
    ORDER BY amount DESC NULLS LAST
)

Здесь однозначная перестановка равных строк не нужна: равенство и есть часть ответа. Если позже требуется детерминированно показать строки с одинаковым рангом, используйте order_id в финальном ORDER BY, не меняя оконный контракт ранга.

8. Ранжировать деньги можно только в совместимых единицах

Сравнить 1500 RUB, 900 EUR и 75 USD как числа — значит проигнорировать единицы. Поэтому в артефакте рейтинг разделен по валюте:

sql
PARTITION BY currency
ORDER BY amount DESC NULLS LAST

Результат означает «место суммы среди оплаченных заказов в той же валюте», а не «самая дорогая покупка вообще».

NULLS LAST задает явную политику для неизвестной суммы. Строка не исчезает: она сохраняется на grain заказа, но неизвестная сумма располагается после известных. Это правило не превращает NULL в ноль и не делает неизвестную сумму «самой маленькой». Поэтому артефакт использует техническую позицию для работы окна, но через CASE оставляет amount_rank_in_currency и amount_dense_rank_in_currency равными NULL:

sql
CASE
    WHEN amount IS NOT NULL
    THEN rank() OVER currency_amount_peers
END AS amount_rank_in_currency

Числовой ранг появляется только там, где значение действительно можно сравнить.

9. lag и lead: обратиться к соседней строке

lag возвращает выражение из предыдущей строки окна:

sql
lag(order_id) OVER (
    PARTITION BY user_id
    ORDER BY ordered_at, order_id
) AS previous_order_id

lead возвращает выражение из следующей:

sql
lead(order_id) OVER (
    PARTITION BY user_id
    ORDER BY ordered_at, order_id
) AS next_order_id

Ключевое слово «предыдущая» не имеет смысла без оконного порядка. lag не знает, что для бизнеса означает раньше: это определяет автор запроса.

Для первой строки раздела предыдущей строки нет, поэтому lag возвращает NULL. Для последней строки lead также возвращает NULL.

Функции могут принимать смещение и значение по умолчанию, но в основном запросе мы используем расстояние в одну строку и не подменяем границу искусственным значением. Прозрачный NULL легче проверить.

10. Один NULL после lag может означать две разные ситуации

Посмотрите только на:

sql
lag(amount) OVER user_chronology AS previous_amount

Если previous_amount равен NULL, возможны два объяснения:

  1. текущая строка первая, поэтому предыдущего заказа нет;
  2. предыдущий заказ есть, но его amount неизвестен.

По одному previous_amount различить случаи нельзя. Поэтому артефакт сохраняет и идентификатор:

sql
lag(order_id) OVER user_chronology AS previous_order_id,
lag(amount)   OVER user_chronology AS previous_amount

Интерпретация:

previous_order_id previous_amount Смысл
NULL NULL строка находится на границе раздела; предыдущего заказа нет
O1013 NULL предыдущий заказ существует, но его сумма неизвестна
O1001 1200 предыдущий заказ и его сумма известны

Это продолжение трехзначной логики из 04/03: неизвестное значение не следует автоматически подменять нулем или фразой «строки не было».

11. Именованное окно сокращает повторение одного контракта

Если несколько функций используют одну и ту же последовательность, ее можно назвать:

sql
SELECT
    row_number()   OVER user_chronology AS user_order_number,
    lag(order_id)  OVER user_chronology AS previous_order_id,
    lead(order_id) OVER user_chronology AS next_order_id
FROM paid_orders
WINDOW user_chronology AS (
    PARTITION BY user_id
    ORDER BY ordered_at, order_id
);

Имя полезно не только из-за краткости. Оно показывает, что три столбца намеренно используют один контракт соседства.

Но разные аналитические вопросы требуют разных окон. В артефакте есть:

  • user_chronology — последовательность пользователя от раннего к позднему;
  • user_reverse_chronology — та же сущность от позднего к раннему;
  • currency_amount_peers — рейтинг сумм внутри валюты с сохранением равенства.

Не нужно насильно объединять их в одно окно.

12. Оконный результат фильтруют на следующем этапе

Хочется написать:

sql
SELECT
    order_id,
    user_id,
    row_number() OVER (
        PARTITION BY user_id
        ORDER BY ordered_at DESC, order_id DESC
    ) AS latest_order_number
FROM orders
WHERE status = 'paid'
  AND latest_order_number = 1;

Но WHERE этого уровня формирует строки до вычисления оконного выражения. Алиас latest_order_number еще не является столбцом входного отношения для данного WHERE.

Переносимая форма продолжает механизм из 04/06:

sql
WITH paid_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount
    FROM orders
    WHERE status = 'paid'
),
numbered_orders AS (
    SELECT
        *,
        row_number() OVER (
            PARTITION BY user_id
            ORDER BY ordered_at DESC, order_id DESC
        ) AS latest_order_number
    FROM paid_orders
)
SELECT
    order_id,
    user_id,
    ordered_at,
    currency,
    amount
FROM numbered_orders
WHERE latest_order_number = 1;

Контракты этапов:

Этап Population Grain
paid_orders оплаченные заказы одна строка на order_id
numbered_orders те же оплаченные заказы одна строка на order_id
финальный результат последний оплаченный заказ пользователя одна строка на user_id

Обратите внимание: окно само сохранило grain. Grain изменился по смыслу только после фильтра — мы сознательно оставили одну строку на пользователя.

Некоторые SQL-движки, включая DuckDB, поддерживают QUALIFY для более короткой записи. Он полезен, но не нужен для понимания механизма. CTE переносим между большим числом диалектов и напрямую продолжает предыдущий урок, поэтому остается основной формой.

13. Входной контракт важнее красивого окна

Основной SQL ожидает таблицу orders:

Поле Контракт для текущей задачи
order_id непустой уникальный ключ всех заказов
status заполнен и входит в канонический словарь cancelled, paid, pending, refunded
user_id заполнен для оплаченных заказов
ordered_at заполненный TIMESTAMPTZ для оплаченных заказов
currency заполнена для оплаченных заказов
amount DECIMAL(18, 2); может быть неизвестна

Почему проверки стоят до окна:

  • повторный order_id даст две правдоподобные позиции одной сущности;
  • пустой user_id соберет несвязанные покупки в один раздел NULL;
  • пустой ordered_at не позволяет определить хронологию;
  • пустая currency создаст раздел без понятной единицы сравнения;
  • неканонический status вроде Paid молча изменил бы популяцию, поэтому reference runner отклоняет значение до оконного расчета.

Артефакт не читает CSV и не исправляет эти состояния. Загрузка данных, очистка строк и управление соединением не входят в результат текущего урока.

Что сознательно остается для второго урока

Оконные агрегаты требуют еще одного самостоятельного шага. В этом уроке нет:

  • sum(...) OVER (...), avg(...) OVER (...) и других оконных агрегатов;
  • накопительных итогов;
  • скользящих средних;
  • рамок окна — window frames;
  • различия ROWS и RANGE;
  • неявной рамки по умолчанию;
  • first_value и last_value, поведение которых особенно зависит от рамки.

Во втором уроке мы сохраним уже построенную модель раздела и порядка, но добавим третий вопрос: какие строки относительно текущей входят в расчет агрегата. Смешивать его с рангами и соседними строками сейчас не нужно.

Также за границей текущего минимального маршрута остаются ntile, percent_rank, cume_dist, сложные временные rolling windows и sessionization. Они не являются скрытыми пререквизитами следующих уроков.

Шаг 1. Зафиксируйте population и grain

Берем только:

text

Ожидаем:

9 уникальных order_id
grain = одна строка на оплаченный order_id

Оконные столбцы не должны изменить эти числа.

Шаг 2. Вручную постройте последовательность U001

Исходные строки:

order_id user_id ordered_at amount
O1001 U001 2026-01-05 1200 RUB
O1005 U001 2026-02-05 1500 RUB

Сортируем по ordered_at, order_id:

text

Теперь можно заполнить:

order_id user_order_number latest_order_number previous_order_id next_order_id
O1001 1 2 NULL O1005
O1005 2 1 O1001 NULL

Проверьте каждую колонку вопросом:

  • какой раздел? U001;
  • какой порядок? ordered_at, order_id;
  • от какого края считаем номер?;
  • существует ли соседняя строка в этом разделе?

Шаг 3. Вручную сравните три ранга

Добавим мысленный заказ O1013 на 1500 RUB:

order_id amount row_number rank dense_rank
O1005 1500 1 или 2 1 1
O1013 1500 2 или 1 1 1
O1001 1200 3 3 2

Здесь row_number без tie-breaker не отвечает, какая из равных строк первая. Для rank и dense_rank это не проблема: обе суммы должны остаться равными.

Шаг 4. Сформулируйте три разных оконных контракта

До SQL заполните таблицу:

Выходной столбец Раздел Порядок Почему
user_order_number user_id ordered_at, order_id уникальная хронологическая позиция
latest_order_number user_id ordered_at DESC, order_id DESC последний заказ получает 1
amount_rank_in_currency currency amount DESC NULLS LAST одинаковые суммы остаются peers

Эта таблица важнее механического копирования синтаксиса. Она не позволяет случайно использовать один порядок для трех разных вопросов.

Шаг 5. Предскажите результат до выполнения

На учебных данных:

  • U001: O1001 затем O1005;
  • U003: O1003 затем O1011;
  • U007: O1009 затем O1012;
  • у пользователей с одной оплаченной покупкой оба номера равны 1;
  • в RUB O1005 имеет ранг 1, O1001 — 2;
  • последними заказами U001 и U007 являются O1005 и O1012;
  • всего остается девять строк.

Он состоит из двух этапов:

text

-> paid_orders
-> sequenced_orders
-> явный SELECT и финальный ORDER BY

Этап 1. Выбрать популяцию

sql
WITH paid_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount

paid_orders не очищает и не типизирует вход. Он только фиксирует популяцию, знакомым механизмом из предыдущего урока.

Этап 2. Добавить оконные столбцы

Сокращенный фрагмент:

sql
sequenced_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount,
        row_number() OVER user_chronology AS user_order_number,
        row_number() OVER user_reverse_chronology AS latest_order_number,
        CASE WHEN amount IS NOT NULL
            THEN rank() OVER currency_amount_peers
        END AS amount_rank_in_currency,
        CASE WHEN amount IS NOT NULL
            THEN dense_rank() OVER currency_amount_peers
        END AS amount_dense_rank_in_currency,
        lag(order_id) OVER user_chronology AS previous_order_id,
        lag(amount) OVER user_chronology AS previous_amount,
        lead(order_id) OVER user_chronology AS next_order_id
    FROM paid_orders
    WINDOW
        user_chronology AS (
            PARTITION BY user_id
            ORDER BY ordered_at, order_id
        ),
        user_reverse_chronology AS (
            PARTITION BY user_id
            ORDER BY ordered_at DESC, order_id DESC
        ),
        currency_amount_peers AS (
            PARTITION BY currency
            ORDER BY amount DESC NULLS LAST
        )
)

Population и grain не меняются:

text
до sequenced_orders:    9 оплаченных order_id
после sequenced_orders: 9 оплаченных order_id

    ...

ORDER BY user_id, ordered_at, order_id;

Сломайте это

Ошибка 1. Убрать PARTITION BY user_id

Неверный контракт:

sql
row_number() OVER (
    ORDER BY ordered_at, order_id
)

Нумерация станет общей для магазина. У первого заказа нового пользователя номер уже не обязан быть 1.

Как заметить:

  • для каждого пользователя минимум user_order_number должен быть 1;
  • номера внутри пользователя должны образовывать 1..N без пропусков.

Ошибка 2. Оставить неуникальный порядок для row_number

Хрупкий контракт:

sql
row_number() OVER (
    PARTITION BY user_id
    ORDER BY ordered_at
)

Добавьте пользователю два заказа с одинаковым timestamp. Если бизнес-правило не говорит, какой первый, номер зависит от произвольного порядка peers.

Исправление:

sql
ORDER BY ordered_at, order_id

Но сначала убедитесь, что order_id заполнен и уникален.

Ошибка 3. Добавить уникальный tie-breaker в рейтинг

Неверно для общего ранга равных сумм:

sql
rank() OVER (
    PARTITION BY currency
    ORDER BY amount DESC, order_id
)

Две покупки по 1500 получат разные ранги, потому что полный набор ключей больше не равен.

Как заметить:

  • добавьте fixture с равной суммой в той же валюте;
  • проверьте, что у peers одинаковый rank и dense_rank;
  • проверьте пропуск после peers у rank и отсутствие пропуска у dense_rank.

Ошибка 4. Принять оконный порядок за порядок результата

Запрос вычисляет корректные номера, но не содержит финального ORDER BY. В маленьком примере строки могут выглядеть отсортированными. Это побочный эффект исполнения, а не контракт.

Как заметить: откройте сам SQL и проверьте наличие обоих порядков — внутри окна и в конце выдачи.

Ошибка 5. Фильтровать оконный алиас в том же WHERE

Попытка:

sql
SELECT
    ...,
    row_number() OVER (...) AS latest_order_number
FROM paid_orders
WHERE latest_order_number = 1;

Проблема не в функции row_number. WHERE этого уровня формирует строки раньше, чем появляется оконный алиас.

Исправление: вычислить столбец в CTE и фильтровать во внешнем SELECT.

Ошибка 6. Перепутать границу и неизвестное значение

Если сохранить только:

sql
lag(amount) OVER user_chronology AS previous_amount

то NULL неоднозначен.

Исправление: переносить вместе previous_order_id и previous_amount, а при необходимости еще единицу измерения previous_currency.

Ошибка 7. Сравнивать суммы разных валют

Неверный рейтинг:

sql
rank() OVER (ORDER BY amount DESC)

Он поставит числа из RUB, EUR, USD и KZT в один список без конвертации.

Исправление текущего урока:

sql
PARTITION BY currency

Это не валютная конвертация, а честное ограничение сравнения совместимыми единицами.

Ошибка 8. Пытаться «починить» пустой timestamp сортировкой NULLS LAST

NULLS LAST может сделать запрос исполнимым, но не отвечает на вопрос, где заказ без времени находится в хронологии пользователя.

Для текущей задачи оплаченный заказ без ordered_at отклоняется входным контрактом. Политики восстановления и нормализации времени относятся к следующему уроку о датах.

Ошибка 9. Запустить окно после размножающего JOIN

Если перед окном одна строка заказа размножена по товарным позициям, row_number пронумерует строки позиций, хотя столбец может называться user_order_number.

Как заметить:

  • до окна проверить число строк и уникальность order_id;
  • если источник имеет grain позиции, сначала вернуть его к grain заказа знакомой агрегацией из 04/04 и безопасным JOIN из 04/05.

В рейтинге сумм внутри валюты две покупки имеют одинаковый amount. Почему нельзя бездумно добавить уникальный order_id в ORDER BY этого же окна?

Для rank равенство определяется всеми выражениями ORDER BY окна. Уникальный order_id полезен для детерминированной нумерации, но в рейтинге сумм он разрушает нужную группу peers.

У второй покупки previous_amount равен NULL, но previous_order_id заполнен. Что это означает?

previous_order_id подтверждает существование предыдущей строки. NULL в previous_amount тогда относится к самому значению суммы, а не к границе раздела.

Запрос использует ORDER BY ordered_at внутри OVER, но не содержит финального ORDER BY. Что можно утверждать о порядке строк результата?

ORDER BY внутри OVER определяет, какую строку считать предыдущей и какой номер присвоить. Порядок выдачи задается отдельным финальным ORDER BY.

def _schema(connection: duckdb.DuckDBPyConnection, relation: str) -> dict[str, str]:
    return {
        row[0]: str(row[1])
        for row in connection.execute(f"DESCRIBE {relation}").fetchall()

def _require_columns(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    required: dict[str, str],
) -> None:
    actual = _schema(connection, relation)
    for column, expected_type in required.items():
        if column not in actual:
            raise ValueError(f"{relation} is missing required column {column}")
        if actual[column] != expected_type:
            raise ValueError(
                f"{relation}.{column} must be {expected_type}, got {actual[column]}"
            )


def _require_populated_text(
    connection: duckdb.DuckDBPyConnection,
    column: str,
    *,
    where: str = "TRUE",
) -> None:
    missing = connection.execute(
        f"""
        SELECT count(*)
        FROM orders
        WHERE ({where})
          AND ({column} IS NULL OR trim({column}) = '')
        """
    ).fetchone()[0]
    if missing:
        raise ValueError(
            f"orders.{column} contains {missing} NULL or blank values where {where}"
        )


def validate_input(connection: duckdb.DuckDBPyConnection) -> None:
    _require_columns(
        connection,
        "orders",
        {
            "order_id": "VARCHAR",
            "user_id": "VARCHAR",
            "ordered_at": "TIMESTAMP WITH TIME ZONE",
            "status": "VARCHAR",
            "currency": "VARCHAR",
            "amount": "DECIMAL(18,2)",
        },
    )

    _require_populated_text(connection, "order_id")
    _require_populated_text(connection, "status")

    placeholders = ", ".join("?" for _ in CANONICAL_ORDER_STATUSES)
    unknown_statuses = [
        row[0]
        for row in connection.execute(
            f"""
            SELECT DISTINCT status
            FROM orders
            WHERE status NOT IN ({placeholders})
            ORDER BY status
            """,
            list(CANONICAL_ORDER_STATUSES),
        ).fetchall()
    ]
    if unknown_statuses:
        raise ValueError(
            "orders.status must use canonical values "
            f"{CANONICAL_ORDER_STATUSES}, got {unknown_statuses}"
        )

    duplicate = connection.execute(
        """
        SELECT order_id
        FROM orders
        GROUP BY order_id
        HAVING count(*) > 1
        LIMIT 1
        """
    ).fetchone()
    if duplicate is not None:
        raise ValueError(f"orders grain violation for order_id: {duplicate[0]}")

    _require_populated_text(connection, "user_id", where="status = 'paid'")
    _require_populated_text(connection, "currency", where="status = 'paid'")

    missing_ordered_at = connection.execute(
        """
        SELECT count(*)
        FROM orders
        WHERE status = 'paid' AND ordered_at IS NULL
        """
    ).fetchone()[0]
    if missing_ordered_at:
        raise ValueError(
            "paid orders require ordered_at before a chronological window can be built"
        )


def execute_sql(
    connection: duckdb.DuckDBPyConnection,
    query_path: Path,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    relation = connection.execute(query_path.read_text(encoding="utf-8"))
    columns = [column[0] for column in relation.description]
    types = [str(column[1]) for column in relation.description]
    return columns, types, relation.fetchall()


def execute_sequence(
    connection: duckdb.DuckDBPyConnection,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    return execute_sql(connection, SEQUENCE_SQL_PATH)


def execute_latest(
    connection: duckdb.DuckDBPyConnection,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:

def validate_sequence(
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
) -> None:
    if columns != EXPECTED_SEQUENCE_COLUMNS:
        raise ValueError(
            f"sequence columns must be {EXPECTED_SEQUENCE_COLUMNS}, got {columns}"
        )
    if types != EXPECTED_SEQUENCE_TYPES:
        raise ValueError(
            f"sequence types must be {EXPECTED_SEQUENCE_TYPES}, got {types}"
        )

    order_id_at = columns.index("order_id")
    user_id_at = columns.index("user_id")
    user_number_at = columns.index("user_order_number")
    latest_number_at = columns.index("latest_order_number")
    previous_order_at = columns.index("previous_order_id")
    next_order_at = columns.index("next_order_id")

    order_ids = [row[order_id_at] for row in rows]
    if len(order_ids) != len(set(order_ids)):
        raise ValueError("sequence result changed the one-row-per-order_id grain")

    users: dict[str, list[tuple[Any, ...]]] = {}
    for row in rows:
        users.setdefault(row[user_id_at], []).append(row)

    for user_id, user_rows in users.items():
        count = len(user_rows)
        actual_forward = [row[user_number_at] for row in user_rows]
        if actual_forward != list(range(1, count + 1)):
            raise ValueError(f"user {user_id} has a broken chronological sequence")
        actual_reverse = [row[latest_number_at] for row in user_rows]
        if actual_reverse != list(range(count, 0, -1)):
            raise ValueError(f"user {user_id} has a broken reverse sequence")

        for position, row in enumerate(user_rows):
            expected_previous = (
                None if position == 0 else user_rows[position - 1][order_id_at]
            )
            expected_next = (
                None
                if position == count - 1
                else user_rows[position + 1][order_id_at]
            )
            if row[previous_order_at] != expected_previous:
                raise ValueError(f"user {user_id} has an incorrect previous_order_id")
            if row[next_order_at] != expected_next:
                raise ValueError(f"user {user_id} has an incorrect next_order_id")


def _json_value(value: Any) -> Any:
    if isinstance(value, Decimal):
        return str(value)
    if isinstance(value, datetime):
        return value.isoformat()
    return value


def run_example() -> dict[str, Any]:
    with duckdb.connect() as connection:
        prepare_orders(connection)
        validate_input(connection)
        columns, types, rows = execute_sequence(connection)
        validate_sequence(columns, types, rows)
        latest_columns, _, latest_rows = execute_latest(connection)

    return {
        "grain": ["order_id"],
        "population": "orders where status = 'paid'",
        "columns": columns,
        "rows": [
            {
                column: _json_value(value)
                for column, value in zip(columns, row, strict=True)
            }
            for row in rows
        ],
        "latest_paid_orders": [
            {
                column: _json_value(value)
                for column, value in zip(latest_columns, row, strict=True)
            }
            for row in latest_rows
        ],
    }


def main() -> None:
    print(json.dumps(run_example(), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

-- Input contract:
-- orders has grain one row per unique non-NULL order_id;
-- status is one of cancelled, paid, pending or refunded for every order;
-- paid orders have non-NULL user_id, ordered_at TIMESTAMPTZ and currency;
-- amount is DECIMAL(18, 2) and may be NULL.
--
-- Output contract:
-- one row per paid order_id; window functions add columns without changing grain.
-- Unknown amount keeps both rank columns NULL: a technical NULLS LAST position is not
-- a business rank.

WITH paid_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount
    FROM orders
    WHERE status = 'paid'
),
sequenced_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount,
        row_number() OVER user_chronology AS user_order_number,
        row_number() OVER user_reverse_chronology AS latest_order_number,
        CASE
            WHEN amount IS NOT NULL
            THEN rank() OVER currency_amount_peers
        END AS amount_rank_in_currency,
        CASE
            WHEN amount IS NOT NULL
            THEN dense_rank() OVER currency_amount_peers
        END AS amount_dense_rank_in_currency,
        lag(order_id) OVER user_chronology AS previous_order_id,
        lag(currency) OVER user_chronology AS previous_currency,
        lag(amount) OVER user_chronology AS previous_amount,
        lead(order_id) OVER user_chronology AS next_order_id
    FROM paid_orders
    WINDOW
        user_chronology AS (
            PARTITION BY user_id
            ORDER BY ordered_at, order_id
        ),
        user_reverse_chronology AS (
            PARTITION BY user_id
            ORDER BY ordered_at DESC, order_id DESC
        ),
        currency_amount_peers AS (
            PARTITION BY currency
            ORDER BY amount DESC NULLS LAST
        )
)
SELECT
    order_id,
    user_id,
    ordered_at,
    currency,
    amount,
    user_order_number,
    latest_order_number,
    amount_rank_in_currency,
    amount_dense_rank_in_currency,
    previous_order_id,
    previous_currency,
    previous_amount,
    next_order_id
FROM sequenced_orders
ORDER BY user_id, ordered_at, order_id;
