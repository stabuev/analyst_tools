Проверка перед уроком

Ответьте до чтения: результат поможет заметить исходные предположения.

01

В orders одна строка на заказ, а в order_items — одна строка на товарную позицию. Каким станет grain после прямого JOIN по order_id?

Каждая позиция получает данные своего заказа, поэтому результат имеет grain товарной позиции. Поля заказа могут повториться.

02

Почему оплаченные суммы нельзя сверять одним итогом, если в orders одновременно лежат RUB, USD, EUR и KZT?

Числа в разных валютах нельзя складывать и сравнивать без отдельного правила конвертации. Сверку нужно проводить внутри валюты.

Joins без размножения метрик

До JOIN нужно предсказать, какие пары строк он создаст. После JOIN нужно доказать, что результат сохранил задуманный grain, нужные строки и единицы измерения метрик.

Тип: Case Треки: Core Пререквизиты: 04/04 Время: ~105 минут Результат: перед JOIN фиксирует grain, ключ, ожидаемое число совпадений и политику unmatched-строк, а после проверяет целевой grain и сохранение метрик в их исходных единицах.

Зачем этот урок аналитику

Аналитические данные редко находятся в одной таблице. Заказ хранится отдельно от пользователя, товарных позиций, платежей и обращений в поддержку. Чтобы ответить на рабочий вопрос, аналитик соединяет эти факты.

Синтаксически правильный JOIN при этом может вернуть правдоподобный, но неверный результат:

  • строк стало больше, и сумма заказа повторилась на каждой товарной позиции;
  • строк стало меньше, потому что часть ключей не нашлась в справочнике;
  • две таблицы соединили по неполному составному ключу;
  • NULL в ключе приняли за обычное совпадающее значение;
  • дубликат в справочнике превратил ожидаемую связь many-to-one в fanout;
  • денежные итоги сверили одним числом, хотя в данных несколько валют.

База данных не знает, является ли это ошибкой. Она честно создаёт все пары строк, которые удовлетворяют условию ON. Поэтому безопасность соединения — часть аналитической методологии, а не свойство ключевого слова JOIN.

Цели обучения

После урока вы сможете:

  • до запроса назвать grain обеих сторон, ключ соединения и целевой grain;
  • предсказать число строк по частотам ключей;
  • отличить multiplicity совпадений от покрытия ключей;
  • осознанно выбрать INNER, LEFT, SEMI или ANTI JOIN;
  • понять, почему LEFT JOIN тоже может размножить строки;
  • предварительно агрегировать дочернюю таблицу до grain родителя;
  • отличить отсутствующую ссылку от ссылки на несуществующую строку;
  • проверить unmatched-ключи в обоих направлениях;
  • сверить метрики после соединения, не смешивая валюты и не теряя NULL;
  • диагностировать fanout по данным, а не по ощущению от запроса.

В pandas ожидание cardinality можно было выразить параметром validate. У обычного SQL нет встроенного параметра с таким контрактом. До соединения аналитик самостоятельно проверяет уникальность и частоты ключа, а после — grain, покрытие и контрольные метрики. Это и есть новая часть урока.

CTE и подзапросы пока не требуются. В этом уроке два шага хранятся как два отдельных SQL-запроса. В 04/06 вы научитесь собирать такие шаги в один читаемый SQL-pipeline.

Проблема

Нужно построить витрину с grain:

одна строка на заказ.

В ней нужны:

  • сведения из orders;
  • число и сумма товарных позиций из order_items;
  • признак того, найден ли пользователь в users;
  • состояние сверки orders.amount и суммы позиций.

Исходные таблицы имеют разные grain:

Relation Grain Ключ
orders одна строка на заказ order_id
order_items одна строка на товарную позицию заказа (order_id, product_id)
users одна строка на пользователя user_id

Наивный запрос выглядит естественно:

sql
SELECT
    o.order_id,
    o.currency,
    o.amount,
    i.product_id
FROM orders AS o
INNER JOIN order_items AS i
    ON o.order_id = i.order_id;

Но результат уже имеет grain товарной позиции. Для заказа O1001 есть две позиции:

text
orders
order_id  amount
O1001     1200.00

order_items
order_id  product_id  line amount
O1001     P01          1000.00
O1001     P02           200.00

После соединения:

text
order_id  product_id  amount
O1001     P01          1200.00
O1001     P02          1200.00

Сумма orders.amount для этого заказа стала 2400.00, хотя сам заказ не изменился. Ошибка появилась не в SUM. Она появилась раньше, когда метрику grain заказа перенесли на grain позиции.

Концепция

JOIN создаёт пары строк

Для каждого значения ключа SQL берёт все подходящие строки слева и все подходящие строки справа. Затем создаёт все пары между ними.

Если для ключа K:

  • слева L(K) строк;
  • справа R(K) строк;

то INNER JOIN создаст:

text
L(K) × R(K)

строк для этого ключа.

Пример:

text
слева 2 строки с K
справа 3 строки с K
результат 2 × 3 = 6 строк

Это не случайное «размножение базы данных». Это точное следствие условия совпадения.

Для LEFT JOIN каждая левая строка:

  • создаёт по одной строке на каждое совпадение справа;
  • остаётся одной строкой с правыми NULL, если совпадений нет.

Поэтому для одного ключа число строк можно записать так:

text
L(K) × max(R(K), 1)

Главное следствие:

LEFT JOIN гарантирует, что левая строка не исчезнет, но не гарантирует, что она останется единственной.

Четыре разных вопроса перед соединением

Перед каждым JOIN ответьте на четыре вопроса отдельно:

Вопрос Пример ответа
Каков grain каждой стороны? заказ и товарная позиция заказа
По какому полному ключу сопоставляются строки? order_id
Сколько совпадений допустимо для одной строки? справа может быть много позиций
Каков целевой grain результата? одна строка на заказ

Тип LEFT или INNER не отвечает на остальные три вопроса. Он задаёт только политику для строк без пары.

Cardinality зависит от направления

Одну и ту же связь можно описать по-разному в зависимости от того, откуда мы смотрим:

Левая сторона Правая сторона Ожидание среди совпавших строк
orders order_items one-to-many
order_items orders many-to-one
orders item_totals one-to-one среди совпавших строк; справа может не быть строки
orders users many-to-one

Фраза one-to-one или many-to-one описывает multiplicity — сколько строк может совпасть. Она не обещает, что совпадение вообще существует.

Например, users.user_id может быть уникальным, но заказ O1010 с user_id = 'U999' всё равно не найдёт пользователя. Поэтому отдельно проверяются:

  1. Uniqueness: не больше ли одного совпадения там, где ожидается одно.
  2. Coverage: нашлась ли хотя бы одна пара там, где она нужна.

Target grain выбирает аналитик

Прямой orders JOIN order_items не является неправильным сам по себе. Он корректен, если нужен результат «одна строка на товарную позицию».

Ошибка возникает, когда:

  1. нужен grain заказа;
  2. соединение создаёт grain позиции;
  3. поля и метрики заказа продолжают использовать так, словно они остались уникальными.

Для нашей витрины нужен grain заказа. Значит, order_items сначала надо привести к одной строке на order_id:

text
order_items
одна строка на (order_id, product_id)

        GROUP BY order_id
                ↓

item_totals
одна строка на order_id

После этого у одного заказа справа будет не более одной строки.

Деньги сохраняют единицу измерения

В orders одновременно находятся RUB, USD, EUR и KZT. Числа:

text
2700 RUB
180 USD
1625 EUR
500 KZT

нельзя сложить в один осмысленный денежный итог без курса и правила конвертации. Поэтому fanout проверяется отдельно внутри каждой валюты.

Для исходных данных:

Валюта Оплаченная сумма в orders После прямого JOIN к позициям Лишнее из-за fanout
EUR 1625.00 1625.00 0.00
KZT 500.00 500.00 0.00
RUB 2700.00 5400.00 2700.00
USD 180.00 180.00 0.00

Разница появилась только в RUB: оплаченные заказы O1001 и O1005 имеют по две позиции. Общие числа 5005 и 7705 здесь не публикуются, потому что смешивают валюты.

ON и USING

Если ключи называются одинаково, короткая запись допустима:

sql
FROM orders
LEFT JOIN item_totals USING (order_id)

Более явная запись:

sql
FROM orders AS o
LEFT JOIN item_totals AS i
    ON o.order_id = i.order_id

В учебном артефакте используется ON, потому что в нём видны:

  • левая и правая стороны;
  • точные столбцы;
  • все части составного условия.

Для составного ключа нужно перечислить каждую часть:

sql
FROM order_lines AS l
LEFT JOIN prices AS p
    ON l.order_id = p.order_id
   AND l.product_id = p.product_id

Если оставить только order_id, каждая позиция заказа может совпасть с ценой другой позиции того же заказа.

Не используйте NATURAL JOIN в аналитической модели. Он выбирает одноимённые столбцы неявно, поэтому добавление нового одноимённого поля способно изменить смысл запроса.

Основные типы JOIN

INNER JOIN: нужны только совпавшие пары

sql
SELECT
    o.order_id,
    u.plan
FROM orders AS o
INNER JOIN users AS u
    ON o.user_id = u.user_id;

Заказ O1010 исчезнет, потому что U999 отсутствует в users. Это подходит, только если бизнес-вопрос действительно требует отбросить unmatched-заказы. Для аудита качества такое исчезновение опасно.

LEFT JOIN: сохраняем левую population

sql
SELECT
    o.order_id,
    u.plan
FROM orders AS o
LEFT JOIN users AS u
    ON o.user_id = u.user_id;

O1010 останется, а u.plan будет NULL. Это делает проблему наблюдаемой. Но если U001 окажется в users дважды, все его заказы повторятся дважды.

SEMI JOIN: оставить строки, для которых существует пара

sql
SELECT o.order_id
FROM orders AS o
SEMI JOIN users AS u
    ON o.user_id = u.user_id;

SEMI JOIN возвращает только столбцы и строки левой стороны. Даже если справа несколько совпадений, левая строка возвращается один раз. Он полезен для вопроса:

Какие заказы ссылаются на существующего пользователя?

ANTI JOIN: оставить строки, для которых пары нет

sql
SELECT
    o.order_id,
    o.user_id
FROM orders AS o
ANTI JOIN users AS u
    ON o.user_id = u.user_id
WHERE o.user_id IS NOT NULL;

Это прямой аудит orphan-ссылок. Условие WHERE o.user_id IS NOT NULL отделяет orphan от отсутствующей ссылки:

  • user_id IS NULL — ссылка не заполнена;
  • непустой user_id, которого нет в users — orphan reference.

RIGHT JOIN симметричен LEFT JOIN: обычно запрос проще прочитать, если поменять стороны местами. FULL OUTER JOIN полезен для двусторонней сверки, но в основной практике этого урока достаточно двух ANTI JOIN — слева направо и справа налево.

Как ведёт себя NULL в ключе

Из 04/03 известно:

sql
NULL = NULL

возвращает UNKNOWN, а не TRUE. Значит, при обычном условии:

sql
ON left.key = right.key

две строки с NULL не совпадут.

Не надо автоматически заменять это на:

sql
ON left.key IS NOT DISTINCT FROM right.key

Такое условие считает два NULL совпавшими, но отсутствующие идентификаторы обычно не означают одну и ту же сущность. Используйте его только при явном бизнес-правиле, которое действительно приравнивает отсутствующие значения.

Соберите это

Шаг 1. Запишите план соединения

До SQL заполните маленькую таблицу:

Поле решения orders + позиции orders + пользователи
Левая population все заказы все заказы
Grain слева order_id order_id
Grain справа до подготовки (order_id, product_id) user_id
Ключ соединения order_id user_id
Допустимые совпадения справа много до агрегации, не более одного после не более одного
Политика без пары заказ сохранить заказ сохранить и пометить
Целевой grain order_id order_id

Здесь видно, что прямое соединение с позициями несовместимо с целевым grain. Его нужно подготовить.

Шаг 2. Предскажите число строк вручную

В orders каждый order_id встречается один раз. В order_items:

  • O1001 встречается два раза;
  • O1005 встречается два раза;
  • остальные десять заказов — по одному разу.

Для прямого INNER JOIN:

text
1 × 2
+ 1 × 2
+ 10 × 1
= 14 строк

Это ожидаемый результат, а не проверка после факта. Если SQL вернёт другое число, предположение о данных неверно или изменилось покрытие ключей.

Шаг 3. Верните позиции к grain заказа

Из 04/04 уже известен GROUP BY:

sql
SELECT
    order_id,
    count(*) AS item_rows,
    count(quantity * unit_price) AS known_item_amount_rows,
    sum(quantity * unit_price) AS item_total,
    count(*) = count(quantity * unit_price) AS item_amount_complete
FROM order_items
GROUP BY order_id
ORDER BY order_id;

Результат называется item_totals и имеет одну строку на order_id.

Контрольные строки:

text
order_id  item_rows  known rows  item_total  complete
O1001     2          2           1200.00     true
O1005     2          2           1500.00     true

known_item_amount_rows сохраняет знаменатель суммы. Если у позиции неизвестны quantity или unit_price, выражение quantity * unit_price станет NULL, а SUM пропустит его. Числовой item_total тогда является только суммой известных частей. Признак item_amount_complete не позволяет назвать такую частичную сумму полной.

Важно: предварительная агрегация не является универсальным рецептом. Она правильна сейчас, потому что итоговая витрина должна иметь grain заказа и нам нужны именно число позиций и их сумма. Если аналитический вопрос требует категорию каждой позиции, агрегировать её без отдельного правила нельзя.

Шаг 4. Опишите состояния до запроса

Одного булева matched = true/false недостаточно. Для пользователя нужны три состояния:

Состояние Смысл
matched ссылка заполнена и пользователь найден
missing_reference orders.user_id IS NULL
orphan_reference ссылка заполнена, но пользователя нет

Для сверки суммы нужны отдельные состояния:

Состояние Смысл
matches обе суммы известны и равны
differs обе суммы известны, но различаются
order_amount_missing сумма заказа неизвестна
item_total_missing позиции заказа не найдены
item_total_incomplete позиции есть, но сумма хотя бы одной позиции неизвестна
both_missing неизвестны обе стороны

Так NULL не исчезает из проверки и не превращается автоматически в «расхождений нет».

Используйте это

1. Выполните предварительную агрегацию

Запрос находится в:

text
outputs/item_totals.sql

Учебный runner предоставляет его результат следующему запросу как relation item_totals. Техническое связывание двух запросов не является результатом урока. Именованные CTE и композицию шагов вы построите в 04/06.

2. Соберите витрину на grain заказа

Основной артефакт:

sql
SELECT
    o.order_id,
    o.user_id,
    o.status,
    o.currency,
    o.amount,
    i.item_rows,
    i.known_item_amount_rows,
    i.item_total,
    i.item_amount_complete,
    CASE
        WHEN i.order_id IS NULL THEN 'no_items'
        ELSE 'matched'
    END AS item_match_state,
    CASE
        WHEN o.user_id IS NULL THEN 'missing_reference'
        WHEN u.user_id IS NULL THEN 'orphan_reference'
        ELSE 'matched'
    END AS user_match_state,
    CASE
        WHEN i.order_id IS NULL AND o.amount IS NULL THEN 'both_missing'
        WHEN i.order_id IS NULL THEN 'item_total_missing'
        WHEN NOT i.item_amount_complete THEN 'item_total_incomplete'
        WHEN o.amount IS NULL THEN 'order_amount_missing'
        WHEN o.amount = i.item_total THEN 'matches'
        ELSE 'differs'
    END AS amount_reconciliation_state
FROM orders AS o
LEFT JOIN item_totals AS i
    ON o.order_id = i.order_id
LEFT JOIN users AS u
    ON o.user_id = u.user_id
ORDER BY o.order_id;

Почему здесь нет SELECT *:

  • одинаковые имена перестают быть неоднозначными;
  • схема результата не меняется при добавлении столбца в источник;
  • видно, какие значения относятся к заказу, позициям и пользователю;
  • тип и смысл каждого выходного поля можно проверить.

3. Прочитайте результат как evidence

Несколько показательных строк:

order_id amount item rows known rows item total complete user state amount state
O1001 1200.00 2 2 1200.00 true matched matches
O1004 NULL 1 1 50.00 true matched order_amount_missing
O1008 NULL 1 1 80.00 true matched order_amount_missing
O1010 60.00 1 1 60.00 true orphan_reference matches

O1004 и O1008 не являются расхождениями известных сумм, но их нельзя объявить совпавшими. Состояние order_amount_missing сохраняет эту разницу.

Если числовой item_total случайно совпадёт с orders.amount, но одна из позиций не вошла в сумму из-за NULL, состояние всё равно будет item_total_incomplete, а не matches.

4. Проверьте unmatched-ключи в обе стороны

Заказы без позиций:

sql
SELECT o.order_id
FROM orders AS o
ANTI JOIN order_items AS i
    ON o.order_id = i.order_id;

Позиции без заказа:

sql
SELECT
    i.order_id,
    i.product_id
FROM order_items AS i
ANTI JOIN orders AS o
    ON i.order_id = o.order_id;

Нулевая первая проверка не доказывает нулевую вторую. Покрытие связи нужно смотреть в обоих направлениях, если обе стороны должны быть согласованы.

Сломайте это

Поломка 1. Сумма после прямого JOIN

sql
SELECT
    o.currency,
    sum(o.amount) FILTER (WHERE o.status = 'paid') AS paid_amount
FROM orders AS o
INNER JOIN order_items AS i
    ON o.order_id = i.order_id
GROUP BY o.currency;

Запрос синтаксически корректен, но RUB завышен с 2700.00 до 5400.00. Проверка одного общего денежного числа скрыла бы ещё одну ошибку — смешение валют.

Поломка 2. Дубликат в users

Пусть U001 появился в справочнике дважды. У него два заказа: O1001 и O1005. Обычный LEFT JOIN создаст по две строки для каждого из них. Число строк вырастет с 12 до 14.

Поэтому до many-to-one JOIN проверяется правый ключ:

sql
SELECT
    user_id,
    count(*) AS rows_per_key
FROM users
GROUP BY user_id
HAVING count(*) > 1;

Ожидаемый результат — ноль строк.

Поломка 3. INNER JOIN скрывает плохую ссылку

Если соединить orders с users через INNER JOIN, заказ O1010 исчезнет. Итог станет аккуратнее, но ошибка качества данных пропадёт из наблюдения.

Сначала определите политику:

  • сохранить и пометить;
  • исключить с измеримым числом исключений;
  • остановить расчёт.

Молчаливое исчезновение политикой не является.

Поломка 4. DISTINCT amount

Иногда fanout пытаются исправить так:

sql
sum(DISTINCT o.amount)

Это неверно. Два разных заказа могут иметь одинаковую сумму:

text
O1  100.00
O2  100.00

Правильная сумма равна 200.00, а sum(DISTINCT amount) вернёт 100.00. Исправлять нужно grain входа в агрегацию, а не совпадение числовых значений.

Поломка 5. Неполный составной ключ

Если grain таблицы цен равен (order_id, product_id), условие только по order_id соединит позицию с ценами всех позиций того же заказа:

sql
-- Недостаточно
ON l.order_id = p.order_id

Нужно:

sql
ON l.order_id = p.order_id
AND l.product_id = p.product_id

Ключ соединения выбирается из смысла сущности, а не из первого похожего имени.

Поломка 6. NULL приняли за совпавший ключ

Две отсутствующие ссылки не доказывают, что строки относятся к одной сущности. При обычном = они не совпадут. Не заменяйте эту семантику на null-safe equality без явного предметного правила.

Quiz · 5 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

Справа в users случайно появились две строки с одним user_id. Что произойдет с заказами этого пользователя после LEFT JOIN?

LEFT JOIN сохраняет строку без совпадения, но не ограничивает число совпадений справа. Дубли правого ключа создают fanout.

02

Как сохранить одну строку на заказ и добавить сумму его товарных позиций?

Предварительная агрегация возвращает позиции к grain заказа. После этого справа ожидается не более одной строки на order_id.

03

Как получить заказы, user_id которых отсутствует в справочнике users, не размножая строки совпавшими пользователями?

ANTI JOIN возвращает строки левой стороны, для которых справа не нашлось совпадения, и не добавляет правые столбцы.

04

В обеих таблицах join key равен NULL. Совпадут ли строки при условии left.key = right.key?

Обычное равенство с NULL не дает TRUE, поэтому такие ключи не совпадают. Политику отсутствующих ключей нужно задавать отдельно.

05

Почему SELECT DISTINCT amount не является исправлением суммы после fanout?

DISTINCT удалит не только копии, созданные JOIN, но и одинаковые значения разных заказов. Исправлять нужно grain соединения.

    def setUp(self) -> None:
        self.connection = duckdb.connect()
        JOIN.prepare_relations(self.connection)

        self.connection.close()

        columns, types, rows = JOIN.execute_safe_mart(self.connection)

        return columns, types, rows

        columns, _, rows = self.safe_mart()
        return columns, {row[columns.index("order_id")]: row for row in rows}

    def test_item_preaggregation_returns_one_row_per_order(self) -> None:
        rows = self.connection.execute(
            """
            SELECT
                order_id,
                item_rows,
                known_item_amount_rows,

                item_amount_complete

            ORDER BY order_id

        self.assertEqual(

            ("O1001", 2, 2, Decimal("1200.00"), True),
        )
        self.assertEqual(

            ("O1005", 2, 2, Decimal("1500.00"), True),
        )

        self.assertEqual(len(rows), 12)

def _schema(connection: duckdb.DuckDBPyConnection, relation: str) -> dict[str, str]:
    return {
        row[0]: str(row[1])
        for row in connection.execute(f"DESCRIBE {relation}").fetchall()
    }


def _require_columns(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    required: dict[str, str],
) -> None:
    actual = _schema(connection, relation)
    for column, expected_type in required.items():
        if column not in actual:
            raise ValueError(f"{relation} is missing required column {column}")
        if actual[column] != expected_type:
            raise ValueError(
                f"{relation}.{column} must be {expected_type}, got {actual[column]}"
            )


def _validate_grain(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    key: tuple[str, ...],
) -> None:
    key_sql = ", ".join(key)
    missing_condition = " OR ".join(
        f"{column} IS NULL OR trim({column}) = ''" for column in key
    )
    missing = connection.execute(
        f"SELECT count(*) FROM {relation} WHERE {missing_condition}"
    ).fetchone()[0]
    if missing:
        raise ValueError(f"{relation} grain {key} contains NULL or blank values")

    duplicate = connection.execute(
        f"""
        SELECT {key_sql}
        FROM {relation}
        GROUP BY {key_sql}
        HAVING count(*) > 1
        LIMIT 1
        """
    ).fetchone()
    if duplicate is not None:
        raise ValueError(f"{relation} grain violation for {key}: {duplicate}")


def validate_input(connection: duckdb.DuckDBPyConnection) -> None:
    _require_columns(
        connection,
        "orders",

            "order_id": "VARCHAR",
            "user_id": "VARCHAR",

            "quantity": "INTEGER",

def execute_safe_mart(
    connection: duckdb.DuckDBPyConnection,
    query_path: Path = SAFE_MART_QUERY,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    relation = connection.execute(query_path.read_text(encoding="utf-8"))
    columns = [column[0] for column in relation.description]
    types = [str(column[1]) for column in relation.description]
    return columns, types, relation.fetchall()


def validate_safe_mart(
    connection: duckdb.DuckDBPyConnection,
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
) -> None:
    if columns != EXPECTED_COLUMNS:
        raise ValueError(
            f"safe mart columns must be {EXPECTED_COLUMNS}, got {columns}"
        )
    if types != EXPECTED_TYPES:
        raise ValueError(f"safe mart types must be {EXPECTED_TYPES}, got {types}")

    positions = {column: index for index, column in enumerate(columns)}
    order_ids = [row[positions["order_id"]] for row in rows]
    source_order_ids = [
        row[0]
        for row in connection.execute(
            "SELECT order_id FROM orders ORDER BY order_id"
        ).fetchall()
    ]
    if order_ids != source_order_ids:
        raise ValueError("safe mart must preserve every order exactly once")

    allowed_item_states = {"matched", "no_items"}
    allowed_user_states = {"matched", "missing_reference", "orphan_reference"}
    allowed_amount_states = {
        "both_missing",
        "order_amount_missing",
        "item_total_missing",
        "item_total_incomplete",
        "matches",
        "differs",
    }
    for row in rows:
        if row[positions["item_match_state"]] not in allowed_item_states:
            raise ValueError("unknown item_match_state")
        if row[positions["user_match_state"]] not in allowed_user_states:
            raise ValueError("unknown user_match_state")
        if (
            row[positions["amount_reconciliation_state"]]
            not in allowed_amount_states
        ):
            raise ValueError("unknown amount_reconciliation_state")


def fanout_by_currency(
    connection: duckdb.DuckDBPyConnection,
) -> list[dict[str, Any]]:
    source_rows = connection.execute(
        """
        SELECT
            currency,
            sum(amount) FILTER (WHERE status = 'paid') AS source_paid_amount
        FROM orders
        GROUP BY currency
        ORDER BY currency ASC NULLS LAST
        """
    ).fetchall()
    naive_rows = connection.execute(
        """
        SELECT
            o.currency,
            sum(o.amount) FILTER (WHERE o.status = 'paid') AS joined_paid_amount
        FROM orders AS o
        INNER JOIN order_items AS i
            ON o.order_id = i.order_id
        GROUP BY o.currency
        ORDER BY o.currency ASC NULLS LAST
        """
    ).fetchall()
    naive_by_currency = {currency: amount for currency, amount in naive_rows}

    result = []
    for currency, source_amount in source_rows:
        joined_amount = naive_by_currency.get(currency)
        extra = (
            None
            if source_amount is None or joined_amount is None
            else joined_amount - source_amount
        )
        result.append(
            {
                "currency": currency,
                "source_paid_amount": source_amount,
                "joined_paid_amount": joined_amount,
                "fanout_extra": extra,
            }
        )
    return result


def coverage_counts(
    connection: duckdb.DuckDBPyConnection,
) -> dict[str, int]:
    return {
        "orders_with_missing_user_id": connection.execute(
            "SELECT count(*) FROM orders WHERE user_id IS NULL"

                ON o.user_id = u.user_id
            WHERE o.user_id IS NOT NULL
            """
        ).fetchone()[0],
        "orders_without_items": connection.execute(
            """
            SELECT count(*)
            FROM orders AS o
            ANTI JOIN order_items AS i
                ON o.order_id = i.order_id
            """
        ).fetchone()[0],
        "item_rows_without_order": connection.execute(
            """
            SELECT count(*)
            FROM order_items AS i
            ANTI JOIN orders AS o
                ON i.order_id = o.order_id
            """
        ).fetchone()[0],
    }


def _json_value(value: Any) -> Any:
    if isinstance(value, Decimal):
        return format(value, "f")
    return value


def rows_as_dicts(
    columns: list[str],
    rows: list[tuple[Any, ...]],
) -> list[dict[str, Any]]:
    return [
        {
            column: _json_value(value)
            for column, value in zip(columns, row, strict=True)
        }
        for row in rows
    ]


def run_example(
    users_path: Path = USERS_PATH,
    orders_path: Path = ORDERS_PATH,
    items_path: Path = ITEMS_PATH,
) -> dict[str, Any]:
    connection = duckdb.connect()
    try:
        prepare_relations(connection, users_path, orders_path, items_path)
        validate_input(connection)
        direct_join_rows = connection.execute(
            """
            SELECT count(*)
            FROM orders AS o
            INNER JOIN order_items AS i
                ON o.order_id = i.order_id
            """
        ).fetchone()[0]
        prepare_item_totals(connection)
        columns, types, rows = execute_safe_mart(connection)
        validate_safe_mart(connection, columns, types, rows)
        fanout = fanout_by_currency(connection)
        coverage = coverage_counts(connection)
    finally:
        connection.close()

    amount_state_position = columns.index("amount_reconciliation_state")
    amount_states: dict[str, int] = {}
    for row in rows:
        state = row[amount_state_position]
        amount_states[state] = amount_states.get(state, 0) + 1

    return {
        "input_grains": {
            "orders": ["order_id"],
            "order_items": ["order_id", "product_id"],
            "users": ["user_id"],
        },
        "output_grain": ["order_id"],
        "row_counts": {
            "orders": len(rows),
            "direct_orders_to_items_join": direct_join_rows,
            "safe_order_mart": len(rows),
        },
        "coverage": coverage,
        "amount_reconciliation_states": amount_states,
        "fanout_by_currency": [
            {key: _json_value(value) for key, value in row.items()}
            for row in fanout
        ],
        "safe_order_mart": rows_as_dicts(columns, rows),
    }


def main() -> None:
    print(json.dumps(run_example(), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

    o.order_id,
    o.user_id,
    o.status,
    o.currency,
    o.amount,

    i.item_total,

        ELSE 'matched'

        WHEN o.user_id IS NULL THEN 'missing_reference'
        WHEN u.user_id IS NULL THEN 'orphan_reference'
        ELSE 'matched'

        WHEN i.order_id IS NULL THEN 'item_total_missing'
        WHEN NOT i.item_amount_complete THEN 'item_total_incomplete'
        WHEN o.amount IS NULL THEN 'order_amount_missing'
        WHEN o.amount = i.item_total THEN 'matches'
        ELSE 'differs'
    END AS amount_reconciliation_state
FROM orders AS o
LEFT JOIN item_totals AS i
    ON o.order_id = i.order_id
LEFT JOIN users AS u
    ON o.user_id = u.user_id
ORDER BY o.order_id;
