Проверка перед уроком

Ответьте до чтения: результат поможет заметить исходные предположения.

01

Два SQL-запроса должны рассчитывать одну витрину. Что необходимо проверить до обсуждения различий их выполнения?

Из предыдущих уроков уже известно: оптимизировать можно только тот же аналитический результат. Совпадение одной итоговой суммы не заменяет проверку grain, схемы, типов, порядка и всех значений.

02

SELECT содержит два независимых scalar subquery, и каждый читает одну relation для своего агрегата. Что можно обоснованно сказать до просмотра физического плана?

Scalar subquery и форма его результата изучены в 04/06. По SQL видны две логические ветви, но оптимизатор может перестроить выполнение, поэтому физические scans подтверждаются планом.

Планы запросов и стоимость

План выполнения показывает не то, как написан SQL, а какую работу движок решил выполнить: откуда прочитать строки, как их преобразовать и сколько данных прошло через каждый оператор.

Тип: Learn Треки: Core Пререквизиты: 04/11 Время: ~90 минут Результат: для двух эквивалентных SELECT читает структурированные EXPLAIN и EXPLAIN ANALYZE снизу вверх, сопоставляет оценки с фактическими строками и находит повторное чтение или неожиданный рост данных без вывода о скорости по одному запуску.

Цели обучения

После урока вы сможете:

  • объяснить план как дерево физических операторов, а не как пересказ SQL-текста;
  • читать дерево от источников к результату и узнавать минимальный набор операторов: scan, filter, projection, aggregate, join и sort;
  • различать оценённое число строк, фактический выход оператора и число прочитанных строк;
  • объяснить, почему EXPLAIN не выполняет запрос, а EXPLAIN ANALYZE выполняет;
  • до сравнения планов проверить точное равенство результата, его колонок, порядка и dtypes;
  • найти две независимые scan-ветви и сравнить их с одним чтением того же входа;
  • использовать JSON-план DuckDB вместо разбора изменчивого текстового оформления;
  • отделить диагностику формы плана от полноценного benchmarking, который появится в фазе 12.

Проблема

После 04/11 у нас есть типизированная таблица месячной когортной активности. Одна строка означает один наблюдаемый период одной когорты:

text
grain -> (cohort_month, period_index)

Для январской когорты нужны два контрольных числа:

  • сколько периодов присутствует в таблице;
  • какова сумма месячных значений active_users по этим периодам.

Вторую величину мы намеренно называем active_user_period_sum, а не «числом уникальных пользователей». Один пользователь мог быть активен в нескольких месяцах, а агрегированная когортная таблица уже не содержит user_id. Название метрики сохраняет её единицу: пользователь-периоды.

Первый запрос выглядит естественно: каждая метрика вычисляется отдельным scalar subquery.

sql
SELECT
    (
        SELECT count(*)
        FROM cohort_activity
        WHERE cohort_month = $cohort_month::DATE
    ) AS cohort_period_rows,
    (
        SELECT sum(active_users)::BIGINT
        FROM cohort_activity
        WHERE cohort_month = $cohort_month::DATE
    ) AS active_user_period_sum;

Он возвращает правильный результат:

cohort_period_rows active_user_period_sum
4 9

Второй запрос получает те же числа из одной relation:

sql
SELECT
    count(*) FILTER (
        WHERE cohort_month = $cohort_month::DATE
    ) AS cohort_period_rows,
    CAST(
        sum(active_users) FILTER (
            WHERE cohort_month = $cohort_month::DATE
        ) AS BIGINT
    ) AS active_user_period_sum
FROM cohort_activity;

По результату запросы неразличимы. По SQL-тексту можно предположить, что первый читает вход дважды, а второй один раз. Но предположение о работе движка ещё не является наблюдением. Оптимизатор может перестроить выражения, объединить или разделить этапы.

Нужен способ ответить на три разных вопроса:

  1. Возвращают ли запросы один и тот же результат?
  2. Какой физический план выбрал DuckDB для каждого запроса?
  3. Что фактически произошло при выполнении?

Концепция

Между SQL и результатом есть план

SQL описывает желаемый результат декларативно. Мы говорим, какие строки и столбцы нужны, но обычно не задаём точный алгоритм выполнения.

Упрощённая цепочка выглядит так:

text
SQL-текст
-> логические операции
-> оптимизированный физический план
-> выполнение операторов
-> результат

Для этого урока достаточно различать три уровня.

Уровень Главный вопрос Пример
SQL-текст Что попросил автор? два scalar subquery
Физический план Как движок решил это выполнить? два scan или один scan
Профиль выполнения Что произошло на этих данных? прочитано 7 строк, оператор вернул 4

Мы не изучаем все промежуточные стадии компилятора SQL. Термин «логический» здесь нужен только для контраста: WHERE, JOIN и GROUP BY описывают смысл операций, а PANDAS_SCAN, HASH_JOIN и UNGROUPED_AGGREGATE — выбранные DuckDB физические операторы.

План — дерево движения данных

У дерева есть:

  • листья — источники данных, обычно scan-операторы;
  • промежуточные узлы — фильтры, проекции, соединения, агрегаты и сортировки;
  • корень — оператор, после которого получается итог запроса.

Текстовый план DuckDB рисуется корнем сверху, но смысл удобнее восстанавливать снизу вверх:

text
PANDAS_SCAN
-> FILTER
-> PROJECTION
-> UNGROUPED_AGGREGATE
-> итоговая строка

Читаем это как историю:

  1. взять строки из pandas relation;
  2. проверить условие;
  3. оставить или вычислить нужные выражения;
  4. свернуть строки в один итог;
  5. вернуть результат.

Если у узла два ребёнка, у операции два входа. Так устроены, например, join и объединение двух независимых scalar subquery.

Минимальный словарь операторов

Названия зависят от движка и версии. Запоминать полный каталог не нужно. Важно узнавать роль оператора.

Семейство Человеческий смысл Что проверить
*_SCAN Прочитать relation, таблицу или файл сколько входов и строк прочитано
FILTER Оставить строки по условию сколько строк вошло и вышло
PROJECTION Выбрать или вычислить выражения не изменился ли смысл столбцов
*_AGGREGATE Свернуть строки до нового grain ожидаемое ли число групп или итоговых строк
*_JOIN Сопоставить две ветви не выросло ли число строк неожиданно
ORDER_BY / SORT Установить порядок действительно ли downstream нужен этот порядок
CROSS_PRODUCT Сочетать строки двух входов ожидалось ли такое сочетание

PROJECTION может появляться несколько раз, даже если в SQL один SELECT. Оптимизатор создаёт технические выражения и перестраивает дерево. Это не ошибка само по себе.

Одна строка SQL не равна одному оператору

Нельзя надёжно посчитать scans по числу FROM, CTE или упоминаний имени таблицы в тексте.

Например, CTE может быть встроен в основной запрос, материализован или иначе перестроен. Scalar subquery может получить дополнительные операторы, которые проверяют контракт «не более одной строки». Условие из FILTER может оказаться вычисляемой projection, а не отдельным узлом FILTER.

Поэтому правильный порядок такой:

text
прочитать SQL
-> предсказать крупные ветви
-> открыть план
-> объяснить фактическое дерево

План не заменяет понимание SQL, а проверяет предположение о его выполнении.

Cardinality — сколько строк выходит из оператора

Cardinality в плане — количество строк на определённой границе дерева. Важно всегда уточнять, о какой величине идёт речь.

Поле Смысл Не означает
estimated_rows Сколько строк оптимизатор ожидал до выполнения точный факт о данных
actual_rows Сколько строк оператор фактически отдал следующему узлу сколько строк было физически просмотрено
rows_scanned Сколько строк прочитал scan-оператор число строк итогового результата

Пусть scan прочитал семь строк, а filter оставил четыре:

text
scan rows_scanned = 7
scan actual_rows  = 7
filter actual_rows = 4

Агрегат затем может отдать одну строку:

text
aggregate actual_rows = 1

Все три числа правильны, но отвечают на разные вопросы.

Оценка — не обещание

До выполнения оптимизатор не знает фактический результат каждого условия. Он использует доступную статистику и правила оценки.

Если EXPLAIN ожидает одну строку после filter, а EXPLAIN ANALYZE показывает четыре, это не автоматически ошибка запроса и не автоматически плохой план. Это наблюдение:

text
estimated_rows = 1
actual_rows    = 4

Для маленького примера расхождение нужно уметь назвать. Исследование причин больших ошибок оценки, статистики таблиц и порядка сложных joins относится к углублённой работе с производительностью.

EXPLAIN и EXPLAIN ANALYZE отвечают на разные вопросы

Команда Выполняет исходный запрос Что показывает Когда нужна
EXPLAIN нет выбранный план и оценки безопасно рассмотреть предполагаемую форму работы
EXPLAIN ANALYZE да план, фактические строки и метрики выполнения сопоставить ожидания с реальным запуском

В DuckDB используем структурированный формат:

sql
EXPLAIN (FORMAT JSON)
SELECT ...;

и:

sql
EXPLAIN (ANALYZE, FORMAT JSON)
SELECT ...;

Слово ANALYZE принципиально: исходный запрос действительно выполняется. Поэтому артефакт урока принимает только уже проверенные statements. Он не является SQL-песочницей и не пытается определить безопасность запроса регулярным выражением.

В учебной практике мы анализируем только SELECT. Не запускайте EXPLAIN ANALYZE над изменяющим данные statement, если не готовы к его реальному эффекту.

План не доказывает корректность результата

План может показать:

  • повторное чтение;
  • число входных ветвей;
  • фактический рост строк вокруг join;
  • раннее или позднее сокращение данных;
  • тяжёлую сортировку или агрегацию.

Но он не знает, что одна строка должна означать один заказ или один когортный период. Если неверный join размножил выручку, оператор честно покажет выросшее число строк, но не назовёт его бизнес-ошибкой.

Поэтому сравнение начинается с result gate:

text
одинаковые колонки
+ одинаковый порядок колонок
+ одинаковые dtypes
+ одинаковые строки и их порядок
+ одинаковые значения
-> только затем сравниваем планы

Быстрый запрос с другим результатом — не оптимизация.

Время оператора — наблюдение, а не готовый benchmark

EXPLAIN ANALYZE сообщает timing. Это полезный сигнал, но один запуск маленькой таблицы не отвечает на вопрос «какой вариант быстрее в работе».

На результат влияют:

  • прогрев процесса и библиотек;
  • cache;
  • размер и распределение данных;
  • число потоков;
  • файловый формат и устройство хранения;
  • конкурирующая нагрузка;
  • повторное выполнение запроса самим диагностическим кодом.

Кроме того, времена отдельных операторов нельзя бездумно складывать: часть метрик может быть накопительной, а работа параллельных операторов способна перекрываться по wall time.

В этом уроке timing сохраняется в таблице операторов, но артефакт не выбирает победителя по времени. Воспроизводимые повторы, warm-up, cache policy, медианы и интерпретация разброса изучаются в 12/01 «Корректный benchmarking».

Под «стоимостью» сейчас понимаем наблюдаемую форму работы:

text
сколько входных ветвей
сколько scan-операторов
сколько строк прочитано
сколько строк вышло из ключевых операторов

Это необходимый минимум до полноценного измерения производительности.

Соберите это

Сначала построим уменьшенную модель плана вручную. DuckDB появится после того, как мы сможем предсказать крупные ветви и контрольный результат.

Шаг 1. Зафиксируйте входной grain

Используем знакомый типизированный результат 04/10 и 04/11:

cohort_month activity_month period_index active_users
2026-01-01 2026-01-01 0 4
2026-01-01 2026-02-01 1 3
2026-01-01 2026-03-01 2 2
2026-01-01 2026-04-01 3 0
2026-02-01 2026-02-01 0 3
2026-02-01 2026-03-01 1 2
2026-02-01 2026-04-01 2 1

Всего семь строк. Январской когорте принадлежат четыре строки.

Шаг 2. Рассчитайте результат без плана

Для cohort_month = 2026-01-01:

text
cohort_period_rows      = 4
active_user_period_sum  = 4 + 3 + 2 + 0 = 9
result grain            = одна строка на выбранную когорту

Эти значения становятся oracle. Если второй запрос вернёт 3 и 9, 4 и 8 или поменяет dtype суммы, сравнивать его план с исходным нельзя.

Шаг 3. Нарисуйте ветви первого запроса

Не пытаемся предсказать все технические projections. Достаточно крупных этапов:

text
ветвь A                                ветвь B
cohort_activity                        cohort_activity
-> выбрать январь                      -> выбрать январь
-> count(*) = 4                        -> sum(active_users) = 9
          \                            /
           -> соединить два скаляра
           -> одна строка (4, 9)

Ожидание до запуска:

text
scan branches = 2
rows scanned  = 7 + 7 = 14
filter output = 4 в каждой ветви
result rows   = 1

Это гипотеза о физическом плане. DuckDB может добавить операторы проверки scalar subquery, но две независимые ветви должны остаться наблюдаемыми, если оптимизатор их не объединит.

Шаг 4. Нарисуйте ветвь второго запроса

text
cohort_activity
-> вычислить условие cohort_month = 2026-01-01
-> count FILTER и sum FILTER
-> одна строка (4, 9)

Ожидание:

text
scan branches = 1
rows scanned  = 7
aggregate output = 1
result rows   = 1

Обратите внимание: условие написано внутри двух FILTER, но это не требует двух чтений. Одна строка входа может передать вычисленный признак обоим агрегатам.

Шаг 5. Сформулируйте контракт сравнения

text
обязательно:
  exact result equality = true
  result columns = [cohort_period_rows, active_user_period_sum]
  result dtypes = [int64, int64]
  result values = [(4, 9)]

плановое ожидание:
  baseline scan operators = 2
  candidate scan operators = 1
  baseline rows scanned = 14
  candidate rows scanned = 7

не утверждаем:
  candidate обязательно быстрее на tiny

Теперь можно переходить к DuckDB.

Используйте это

1. Сохраните явную connection

Повторяем границу 04/11:

python
connection = duckdb.connect()
try:
    report = compare_dataframe_queries(
        connection,
        relation_name="cohort_activity",
        frame=cohort_activity,
        baseline_sql=baseline_sql,
        candidate_sql=candidate_sql,
        parameters={"cohort_month": "2026-01-01"},
    )
finally:
    connection.close()

Функция временно регистрирует cohort_activity и снимает регистрацию в finally. Connection остаётся открытой до завершения внешнего блока: вложенная функция не закрывает чужой ресурс.

2. Получите план без выполнения

Внутри inspect_reviewed_query выполняется:

python
row = connection.execute(
    "EXPLAIN (FORMAT JSON) " + sql,
    parameters,
).fetchone()

planned = json.loads(row[1])

JSON содержит вложенные объекты с полями name, children и extra_info. Для scan в extra_info находится Estimated Cardinality.

Упрощённо:

json
{
  "name": "PANDAS_SCAN",
  "children": [],
  "extra_info": {
    "Estimated Cardinality": "7"
  }
}

Это структурированный API плана. Мы не считаем слово TABLE_SCAN в ASCII-рамке и не извлекаем время регулярным выражением.

3. Получите фактический профиль

python
row = connection.execute(
    "EXPLAIN (ANALYZE, FORMAT JSON) " + sql,
    parameters,
).fetchone()

analyzed = json.loads(row[1])

Для каждого оператора доступны, среди прочего:

text
operator_name
operator_cardinality
operator_rows_scanned
operator_timing
children

Помните: на этом шаге sql выполняется.

4. Превратите дерево в таблицу evidence

Артефакт рекурсивно обходит оба дерева, присваивает узлам путь и соединяет плановые и фактические поля:

path operator estimated_rows actual_rows rows_scanned timing_seconds
0 PROJECTION 1 1 0 наблюдение
0.0 UNGROUPED_AGGREGATE — 1 0 наблюдение
0.0.0 PROJECTION 7 7 0 наблюдение
0.0.0.0 PROJECTION 7 7 0 наблюдение
0.0.0.0.0 PANDAS_SCAN 7 7 7 наблюдение

Таблица хранится корнем вперёд, но читаем её от самого глубокого пути:

text
0.0.0.0.0 -> scan прочитал и отдал 7 строк
0.0.0.0   -> вычислены выражения
0.0.0     -> подготовлены входы агрегатов
0.0       -> агрегат отдал 1 строку
0         -> результат приведён к объявленным типам

Точное число PROJECTION не является учебным инвариантом. Значимы одна входная ветвь, один scan семи строк и одна итоговая строка.

5. Сравните два плана только после result gate

compare_reviewed_queries сначала выполняет оба statements и использует точное assert_frame_equal:

text

dtypes
row order
values

При различии функция останавливается:

text

Только после этого формируется сравнение:

json
{
  "scope": {
    "engine": "duckdb",
    "engine_version": "зафиксированная версия окружения",

    "input_rows": 7

Каждый statement фактически выполняется дважды: один раз для результата и второй раз внутри EXPLAIN ANALYZE. Это осознанная цена учебного аудита и ещё одна причина не считать полученный timing benchmark-результатом.

6. Перенесите способ чтения на join

Пусть есть две маленькие relation:

text
cohorts(cohort_id unique, cohort_size)
segments(cohort_id unique, segment)

Запрос:

sql
SELECT c.cohort_id, c.cohort_size, s.segment
FROM cohorts AS c
INNER JOIN segments AS s USING (cohort_id)
ORDER BY c.cohort_id;

Крупная форма плана:

text
scan cohorts ----\
                  -> HASH_JOIN -> ORDER_BY -> result
scan segments ---/

Читаем:

  1. найти два scan-листа;
  2. проверить actual rows каждого входа;
  3. найти join-узел;
  4. проверить actual rows после join;
  5. сопоставить число строк с заявленной cardinality one-to-one.

Если справа появится дубликат cohort_id, join может отдать три строки вместо двух. План сделает рост наблюдаемым, но смысл нарушения по-прежнему определяется контрактом ключа из 04/05.

Названия HASH_JOIN, build side и probe side относятся к физической реализации. Для этого урока достаточно увидеть две входные ветви, тип join и изменение числа строк.

Сломайте это

1. Сравните разные результаты

Добавьте к сумме единицу:

sql
CAST(sum(active_users) FILTER (...) AS BIGINT) + 1
    AS active_user_period_sum

Если сначала смотреть только на scan count, такой кандидат покажется «лучше». Result gate должен остановить сравнение до обсуждения плана.

2. Посчитайте scans по SQL-тексту

Число FROM, CTE или упоминаний relation не является физическим планом. Оптимизатор может перестроить запрос. Сначала сформулируйте ожидание, затем проверьте дерево.

3. Примите estimate за факт

В зафиксированном примере filter может иметь:

text
estimated_rows = 1
actual_rows = 4

Фраза «после фильтра точно одна строка» неверна. Оценка существовала до выполнения.

4. Перепутайте output rows и rows scanned

Агрегат возвращает одну строку, но это не означает, что запрос прочитал одну строку. Ищите scan-узел и его rows_scanned.

5. Назовите победителя по одному timing

На семи строках различия сопоставимы с накладными расходами. Даже если candidate timing меньше, формулировка остаётся ограниченной:

В этом запуске candidate использовал одну scan-ветвь вместо двух. Ускорение на рабочем объёме не измерялось.

6. Запустите EXPLAIN ANALYZE как безопасный preview

ANALYZE выполняет исходный statement. Артефакт не проверяет первое слово SQL и не обещает read-only. Передавайте только проверенные SELECT-assets.

7. Объявите любой CROSS_PRODUCT ошибкой

В baseline он объединяет два скалярных результата 1 × 1 и отдаёт одну строку. Это ожидаемая форма. Опасность определяется cardinality входов и бизнес-смыслом, а не одним названием оператора.

8. Оптимизируйте количество технических projections

Число PROJECTION может меняться с версией DuckDB и преобразованием типов. Не ставьте цель «уменьшить каждый узел». Сначала найдите наблюдаемую дорогую или подозрительную работу: повторное чтение, рост строк, позднее сокращение или сортировку.

Поставьте результат

Главный артефакт — outputs/duckdb_plan_audit.py.

Он предоставляет три уровня повторного использования:

  • inspect_reviewed_query — получить результат, JSON-планы и таблицу операторов одного проверенного statement;
  • compare_reviewed_queries — сначала проверить точную эквивалентность, затем сравнить два плана внутри уже подготовленной connection;
  • compare_dataframe_queries — временно зарегистрировать один типизированный DataFrame, выполнить сравнение и гарантированно снять регистрацию.

SQL-assets:

  • outputs/repeated_scan.sql — baseline с двумя ветвями;
  • outputs/single_scan.sql — эквивалентный кандидат с одной ветвью.

Минимальный вызов:

python

    relation_name="cohort_activity",

    baseline_sql=repeated_scan_sql,
    candidate_sql=single_scan_sql,
    parameters={"cohort_month": "2026-01-01"},
)

Артефакт пригоден для review двух проверенных аналитических запросов, когда нужно зафиксировать:

text
результаты эквивалентны
-> планы получены в одном контексте
-> scan-ветви и строки наблюдаемы

CLI сознательно не добавляется. Новый инструмент используется внутри Python-проверки, ноутбука или следующего интеграционного pipeline; командная оболочка не делает чтение дерева понятнее.

Что сознательно не входит в урок

  • Benchmark harness. Warm-up, повторы, cache policy, медиана и разброс изучаются в 12/01.
  • CPU и memory profiling. Это отдельный результат 12/02.
  • Parquet pushdown, row groups и файловый layout. Они появляются в 12/04, где есть подходящая задача и рабочий объём.
  • Статистика таблиц, join order и настройка оптимизатора. Для первого чтения плана достаточно заметить оценки и фактические строки.
  • Полный каталог операторов. Названия движка меняются; важнее роли scan, filter, aggregate, join и sort.
  • Автоматическая SQL-безопасность. Артефакт принимает только проверенные statements и не изображает sandbox.
  • CLI. Результат урока — способ чтения и сравнения планов, а не внешний интерфейс.

Quiz · 7 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

С какой части дерева удобнее начинать содержательное чтение плана аналитического запроса?

Scan-листья показывают входы. Двигаясь от них к корню, можно восстановить, где строки фильтруются, соединяются, агрегируются и превращаются в результат.

02

Какое различие между EXPLAIN и EXPLAIN ANALYZE принципиально для безопасного использования?

ANALYZE означает реальное выполнение statement. Поэтому его нельзя считать безопасным preview произвольного SQL; в уроке он получает только проверенные SELECT-assets.

03

Scan прочитал семь строк, filter оставил четыре, а aggregate вернул одну строку. Как правильно описать эти величины?

Rows scanned относится к чтению источника, а actual rows — к выходу конкретного оператора. Одна итоговая строка не стирает работу, выполненную ниже по дереву.

04

EXPLAIN оценил одну строку после filter, а EXPLAIN ANALYZE показал четыре. Какой вывод корректен?

Estimated cardinality формируется до выполнения и не является обещанием. Расхождение важно заметить, но само по себе оно не доказывает ни ошибку результата, ни необходимость конкретной оптимизации.

05

Candidate вернул тот же результат, использовал один scan вместо двух и оказался быстрее в одном tiny-запуске. Что можно утверждать?

План подтверждает одну scan-ветвь вместо двух. Один timing на семи строках остаётся наблюдением; воспроизводимый benchmark требует контролируемого входа, warm-up, повторов и cache policy.

06

После JOIN фактическое число строк выросло с двух до трёх. Что план позволяет заключить без дополнительных данных?

План делает изменение cardinality наблюдаемым, но не знает бизнес-контракта. Причину и допустимость роста проверяют по ключам, cardinality и grain из 04/05.

07

Что нужно сохранить вместе с выводом план-аудита, чтобы коллега мог понять его границы?

План зависит от запроса, входа и версии движка. Воспроизводимый handoff сохраняет этот scope, точную проверку результата и evidence обоих вариантов, а не только удобный итог.

class DuckDBPlanAuditTest(unittest.TestCase):
    @classmethod
    def setUpClass(cls) -> None:
        cls.frame = build_cohort_activity()
        connection = duckdb.connect()
        try:
            cls.report = PLANS.compare_dataframe_queries(
                connection,
                relation_name="cohort_activity",
                frame=cls.frame,
                baseline_sql=BASELINE_SQL,
                candidate_sql=CANDIDATE_SQL,
                parameters={"cohort_month": "2026-01-01"},
            )
        finally:
            connection.close()

    def test_equivalent_queries_return_exact_same_result(self) -> None:
        self.assertTrue(self.report["results_equal"])
        self.assertEqual(
            self.report["result"].to_dict(orient="records"),
            [{"cohort_period_rows": 4, "active_user_period_sum": 9}],
        )
        self.assertEqual(
            {column: str(dtype) for column, dtype in self.report["result"].dtypes.items()},
            {"cohort_period_rows": "int64", "active_user_period_sum": "int64"},
        )

    def test_baseline_has_two_scan_branches(self) -> None:
        self.assertEqual(self.report["baseline"]["summary"]["scan_operators"], 2)
        self.assertIn(
            "CROSS_PRODUCT",
            self.report["baseline"]["operators"]["operator"].tolist(),
        )

    def test_candidate_has_one_scan_branch(self) -> None:
        self.assertEqual(self.report["candidate"]["summary"]["scan_operators"], 1)
        self.assertEqual(self.report["comparison"]["scan_operators_removed"], 1)

    def test_rows_scanned_are_reported_separately_from_output_rows(self) -> None:
        self.assertEqual(self.report["baseline"]["summary"]["rows_scanned"], 14)
        self.assertEqual(self.report["candidate"]["summary"]["rows_scanned"], 7)
        candidate_scan = self.report["candidate"]["operators"].loc[
            self.report["candidate"]["operators"]["operator"].str.contains("SCAN", regex=False)

from __future__ import annotations

import json
from collections.abc import Mapping, Sequence
from typing import Any

import duckdb
import pandas as pd
from pandas.testing import assert_frame_equal

QueryParameters = Sequence[Any] | Mapping[str, Any]

OPERATOR_COLUMNS = [
    "path",
    "operator",
    "estimated_rows",
    "actual_rows",
    "rows_scanned",
    "timing_seconds",
]


class QueryPlanAuditError(ValueError):
    """Raised when reviewed queries cannot be compared under one contract."""


def _bound_parameters(parameters: QueryParameters) -> list[Any] | dict[str, Any]:
    return dict(parameters) if isinstance(parameters, Mapping) else list(parameters)


def _json_payload(row: tuple[Any, ...] | None, *, label: str) -> Any:
    if row is None or len(row) < 2:
        raise QueryPlanAuditError(f"{label} returned no JSON plan")
    try:
        return json.loads(row[1])
    except (TypeError, json.JSONDecodeError) as error:
        raise QueryPlanAuditError(f"{label} returned invalid JSON") from error


def _estimated_rows(extra_info: Mapping[str, Any]) -> int | None:
    raw_value = extra_info.get("Estimated Cardinality")
    if raw_value is None:
        return None
    normalized = str(raw_value).strip().lstrip("~").replace(",", "")
    try:
        return int(float(normalized))
    except ValueError:
        return None


def _flatten_explain_node(
    node: Mapping[str, Any],
    *,
    path: str,
) -> list[dict[str, Any]]:
    extra_info = node.get("extra_info")
    if not isinstance(extra_info, Mapping):
        extra_info = {}

    rows = [
        {
            "path": path,
            "operator": str(node.get("name", "UNKNOWN")).strip(),
            "estimated_rows": _estimated_rows(extra_info),
        }
    ]
    children = node.get("children", [])
    if not isinstance(children, list):
        raise QueryPlanAuditError("EXPLAIN node has invalid children")
    for index, child in enumerate(children):
        if not isinstance(child, Mapping):
            raise QueryPlanAuditError("EXPLAIN child is not an object")
        rows.extend(_flatten_explain_node(child, path=f"{path}.{index}"))
    return rows


def _flatten_analyze_node(
    node: Mapping[str, Any],
    *,
    path: str,
) -> list[dict[str, Any]]:
    rows = [
        {
            "path": path,
            "operator": str(node.get("operator_name", "UNKNOWN")).strip(),
            "actual_rows": int(node.get("operator_cardinality", 0)),
            "rows_scanned": int(node.get("operator_rows_scanned", 0)),
            "timing_seconds": float(node.get("operator_timing", 0.0)),
        }
    ]
    children = node.get("children", [])
    if not isinstance(children, list):
        raise QueryPlanAuditError("EXPLAIN ANALYZE node has invalid children")
    for index, child in enumerate(children):
        if not isinstance(child, Mapping):
            raise QueryPlanAuditError("EXPLAIN ANALYZE child is not an object")
        rows.extend(_flatten_analyze_node(child, path=f"{path}.{index}"))
    return rows


def _analyzed_plan_root(payload: Mapping[str, Any]) -> Mapping[str, Any]:
    children = payload.get("children", [])
    if not isinstance(children, list) or len(children) != 1:
        raise QueryPlanAuditError("EXPLAIN ANALYZE has no single wrapper node")
    wrapper = children[0]
    if not isinstance(wrapper, Mapping):
        raise QueryPlanAuditError("EXPLAIN ANALYZE wrapper is invalid")
    plan_children = wrapper.get("children", [])
    if not isinstance(plan_children, list) or len(plan_children) != 1:
        raise QueryPlanAuditError("EXPLAIN ANALYZE has no single physical plan root")
    root = plan_children[0]
    if not isinstance(root, Mapping):
        raise QueryPlanAuditError("EXPLAIN ANALYZE physical plan root is invalid")
    return root


def inspect_reviewed_query(
    connection: duckdb.DuckDBPyConnection,
    *,
    sql: str,
    parameters: QueryParameters = (),
) -> dict[str, Any]:
    """Execute one reviewed query and return its result and structured plan evidence.

    ``EXPLAIN (ANALYZE, FORMAT JSON)`` executes ``sql``. This function is not a SQL
    sandbox and must only receive statements that the caller has already reviewed.
    The caller owns ``connection`` and remains responsible for closing it.
    """

    if not sql.strip():
        raise QueryPlanAuditError("sql must not be empty")

    normalized_parameters = _bound_parameters(parameters)
    result = connection.execute(sql, _bound_parameters(parameters)).fetchdf()
    explain_payload = _json_payload(
        connection.execute(
            "EXPLAIN (FORMAT JSON) " + sql,
            _bound_parameters(parameters),
        ).fetchone(),
        label="EXPLAIN",
    )
    analyze_payload = _json_payload(
        connection.execute(
            "EXPLAIN (ANALYZE, FORMAT JSON) " + sql,
            _bound_parameters(parameters),
        ).fetchone(),
        label="EXPLAIN ANALYZE",
    )

    if not isinstance(explain_payload, list) or len(explain_payload) != 1:
        raise QueryPlanAuditError("EXPLAIN has no single physical plan root")
    explain_root = explain_payload[0]
    if not isinstance(explain_root, Mapping):
        raise QueryPlanAuditError("EXPLAIN physical plan root is invalid")
    if not isinstance(analyze_payload, Mapping):
        raise QueryPlanAuditError("EXPLAIN ANALYZE payload is not an object")

    estimated = pd.DataFrame(_flatten_explain_node(explain_root, path="0"))
    actual = pd.DataFrame(_flatten_analyze_node(_analyzed_plan_root(analyze_payload), path="0"))
    operators = estimated.merge(
        actual,
        on=["path", "operator"],
        how="outer",
        validate="one_to_one",
        indicator=True,
    )
    if not operators["_merge"].eq("both").all():
        mismatch = operators.loc[
            ~operators["_merge"].eq("both"),
            ["path", "operator", "_merge"],
        ].to_dict(orient="records")
        raise QueryPlanAuditError(f"EXPLAIN and EXPLAIN ANALYZE plan shapes differ: {mismatch}")
    operators = operators.drop(columns="_merge")[OPERATOR_COLUMNS]
    operators["estimated_rows"] = operators["estimated_rows"].astype("Int64")
    operators["actual_rows"] = operators["actual_rows"].astype("int64")
    operators["rows_scanned"] = operators["rows_scanned"].astype("int64")

    scan_mask = operators["operator"].str.contains("SCAN", regex=False)
    return {
        "sql": sql.strip(),
        "parameters": normalized_parameters,
        "result": result,
        "operators": operators,
        "summary": {
            "operator_count": int(len(operators)),
            "scan_operators": int(scan_mask.sum()),
            "rows_scanned": int(operators.loc[scan_mask, "rows_scanned"].sum()),
        },
        "explain_json": explain_payload,
        "analyze_json": analyze_payload,
    }


def compare_reviewed_queries(
    connection: duckdb.DuckDBPyConnection,
    *,
    baseline_sql: str,
    candidate_sql: str,
    parameters: QueryParameters = (),
) -> dict[str, Any]:
    """Require exact result equivalence before comparing two physical plans."""

    baseline = inspect_reviewed_query(
        connection,
        sql=baseline_sql,
        parameters=parameters,
    )
    candidate = inspect_reviewed_query(
        connection,
        sql=candidate_sql,
        parameters=parameters,
    )
    try:
        assert_frame_equal(
            baseline["result"],
            candidate["result"],
            check_exact=True,
            check_dtype=True,
            check_like=False,
        )
    except AssertionError as error:
        raise QueryPlanAuditError(
            "candidate result differs from baseline; plans are not comparable"
        ) from error

    removed_scans = baseline["summary"]["scan_operators"] - candidate["summary"]["scan_operators"]
    return {
        "scope": {
            "engine": "duckdb",
            "engine_version": duckdb.__version__,
            "claim_boundary": (
                "The report diagnoses this reviewed query pair on this input and "
                "engine version. Operator timings are observations, not a benchmark "
                "or a speedup guarantee for another workload."
            ),
        },
        "results_equal": True,
        "result": baseline["result"],
        "baseline": baseline,
        "candidate": candidate,
        "comparison": {
            "safe_to_compare_work": True,
            "scan_operators_removed": int(removed_scans),
            "timing_is_observation_not_verdict": True,
            "conclusion": (
                "candidate preserves the exact result and changes the observed plan "
                f"by {removed_scans} scan operator(s); no timing claim is made"
            ),
        },
    }


def compare_dataframe_queries(
    connection: duckdb.DuckDBPyConnection,
    *,
    relation_name: str,
    frame: pd.DataFrame,
    baseline_sql: str,
    candidate_sql: str,
    parameters: QueryParameters = (),
) -> dict[str, Any]:
    """Register one typed DataFrame temporarily and compare two reviewed queries."""

    if not relation_name or not relation_name.isidentifier():
        raise QueryPlanAuditError("relation_name must be a non-empty Python-style identifier")
    if not isinstance(frame, pd.DataFrame):
        raise QueryPlanAuditError("frame must be a pandas DataFrame")

    connection.register(relation_name, frame)
    try:
        report = compare_reviewed_queries(
            connection,
            baseline_sql=baseline_sql,
            candidate_sql=candidate_sql,
            parameters=parameters,
        )
        report["scope"].update(
            {
                "relation_name": relation_name,
                "input_rows": int(len(frame)),
                "input_columns": frame.columns.tolist(),
                "input_dtypes": {column: str(dtype) for column, dtype in frame.dtypes.items()},
            }
        )
        return report
    finally:
        connection.unregister(relation_name)
