Что нужно доказать до сравнения работы двух реализаций одного аналитического расчёта?

Performance-сравнение имеет смысл только после semantic gate: варианты должны отвечать на один вопрос и совпадать по проверяемому результату.

Функция получила открытую DuckDB connection аргументом. Кто обычно должен её закрыть?

Переданная connection является заимствованным ресурсом: функция использует её, а закрывает владелец, создавший соединение.

Проблема

Нужно посчитать две метрики для события order_paid:

  1. число физических строк события;
  2. число уникальных активных пользователей.

Первый запрос выглядит прямолинейно: отдельный scalar subquery для каждой метрики.

sql
SELECT
    (
        SELECT count(*)
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        WHERE event_name = ?
    ) AS event_rows,
    (
        SELECT count(DISTINCT user_id)
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        WHERE event_name = ?
    ) AS active_users;

На tiny-файле он возвращает правдоподобный результат:

event_rows active_users
6 3

Шесть строк включают технический дубль E0005; это осознанная семантика метрики event_rows. Второй показатель считает три разных user_id. В этом уроке мы не меняем политику дублей — иначе одновременно изменились бы и запрос, и бизнес-вопрос.

Проблема не видна в результате: каждый subquery независимо обращается к одному CSV. На маленьком файле разница во времени теряется в шуме запуска, а на большом повторное чтение может стать заметной работой. По длине SQL нельзя надёжно определить, что действительно выполнит движок: оптимизатор имеет право перестроить выражения.

Нужны два доказательства:

text
semantic evidence: оба варианта возвращают один и тот же результат
plan evidence:      кандидат действительно устраняет повторное чтение

Только после них имеет смысл задавать отдельный вопрос о времени.

Концепция

Результат, SQL и план — разные уровни

Один и тот же результат можно получить разными SQL-текстами. Один SQL-текст, в свою очередь, не является буквальной инструкцией «сделай операции в написанном порядке»: DuckDB анализирует выражение и выбирает физический план.

text
бизнес-вопрос
    ↓
проверяемый результат: одна строка с event_rows и active_users
    ↓
SQL: декларативное описание результата
    ↓
physical plan: дерево операторов, которое выбрал DuckDB
    ↓
execution: конкретный запуск этого плана на конкретных данных

Поэтому у каждого уровня свой вопрос:

Уровень Контрольный вопрос
Результат Ответили ли оба варианта на один аналитический вопрос?
План Какие источники и операторы реально выбрал движок?
Выполнение Сколько строк прошло через операторы и что наблюдалось по времени?

Быстрый запрос с другим результатом не является оптимизацией. Красивый план без контрольного результата тоже не доказывает корректность.

Физический план — дерево потока строк

В обычном выводе DuckDB EXPLAIN показывает physical plan — дерево физических операторов. Для первого чтения полезно идти снизу вверх:

text
нижний узел      откуда появляются строки
      ↓
следующий узел   что происходит с потоком
      ↓
...
      ↓
верхний узел     какой результат возвращается

В этом уроке достаточно четырёх семейств операторов:

Оператор Человеческий вопрос
READ_CSV / TABLE_SCAN Какой источник читается и какие столбцы нужны?
FILTER или условие в PROJECTION Какие строки или признаки проходят дальше?
PROJECTION Какие выражения и столбцы формируются?
UNGROUPED_AGGREGATE Как поток строк превращается в одну итоговую строку?

Название зависит от версии DuckDB и режима вывода. Например, статический план может показывать READ_CSV, а профиль выполнения — TABLE_SCAN с полем Function: READ_CSV. Поэтому строка TABLE_SCAN сама по себе не является универсальным API-контрактом. Артефакт сохраняет полный текст и считает узкий, заранее объявленный маркер Function: READ_CSV только для этого учебного эксперимента.

Сначала нарисуйте ожидаемую работу

Для двух scalar subquery ожидаем две независимые ветви:

text
READ_CSV #1 -> filter order_paid -> count rows -----------\
                                                           -> одна строка результата
READ_CSV #2 -> filter order_paid -> count distinct users -/

Кандидат объединяет метрики в одном агрегате:

sql
SELECT
    count(*) FILTER (WHERE event_name = ?) AS event_rows,
    count(DISTINCT user_id) FILTER (WHERE event_name = ?) AS active_users
FROM read_csv(?, header = true, all_varchar = true, nullstr = '');

Ожидаемая работа теперь такая:

text
READ_CSV -> два булевых условия -> один aggregate -> одна строка результата

Это пока гипотеза. Даже очевидную схему нужно сверить с EXPLAIN, потому что движок может встроить фильтр в scan, объединить выражения, переиспользовать подвыражение или, наоборот, создать дополнительную ветвь.

EXPLAIN: план и оценки без выполнения

sql
EXPLAIN
SELECT ...;

Обычный EXPLAIN не выполняет целевой запрос. Он показывает выбранный план и оценочную cardinality — сколько строк, по мнению оптимизатора, будет выдавать оператор.

В DuckDB оценка отмечается тильдой:

text
~31 rows

Это не обещание и не скрытый точный count(*). Оценка строится до выполнения по статистике и эвристикам. Она нужна оптимизатору, чтобы сравнивать варианты плана.

Для tiny CSV урока scan фактически читает 16 строк, но EXPLAIN может показать ~31 rows. Это полезный контраст:

text
~31 rows  = estimate before execution
 16 rows  = observed cardinality in this execution

Расхождение не означает автоматически неверный результат. Оно становится сигналом для диагностики, особенно если ошибка оценки многократно раздувается перед JOIN или агрегацией.

EXPLAIN ANALYZE: запрос действительно выполняется

sql
EXPLAIN ANALYZE
SELECT ...;

EXPLAIN ANALYZE запускает целевой запрос и добавляет:

  • фактические числа строк операторов;
  • наблюдаемые времена операторов;
  • общий Total Time;
  • сведения о реально прочитанных файлах.

Это важная граница безопасности. Для нашего доверенного SELECT выполнение только читает данные. Для INSERT, UPDATE, DELETE, COPY или внешней функции EXPLAIN ANALYZE может произвести реальные эффекты. Слово EXPLAIN перед запросом не превращает произвольный SQL в безопасный preview.

Cardinality относится к выходу узла

Cardinality оператора — число строк, которое этот узел выдаёт родителю, а не универсальное «сколько данных было дорого обработано».

Например:

text
scan читает 16 строк
aggregate выдаёт 1 строку

Одна строка на выходе aggregate не означает, что оператору была доступна только одна входная строка. При чтении плана задавайте два вопроса:

  1. сколько строк пришло снизу;
  2. сколько строк узел передал вверх.

Для JOIN особенно важно сопоставить размеры обеих сторон и выходную cardinality: резкий рост может быть ожидаемым many-to-many результатом или признаком fanout из 04/05.

«Стоимость» не равна одному runtime

Название урока использует стоимость в рабочем смысле: объём наблюдаемой работы, который помогает объяснить поведение запроса. В DuckDB-плане этого эксперимента мы смотрим на:

  • число чтений источника;
  • поток строк между операторами;
  • ширину проекции, видимую по выбранным столбцам;
  • фактические времена как диагностические наблюдения.

Нельзя делать вывод:

text
0.003 s < 0.019 s -> кандидат всегда быстрее в 6.3 раза

Один запуск смешивает собственно выполнение с прогревом, файловым кэшем, компиляцией, нагрузкой машины и малым объёмом данных. Кроме того, времена операторов могут быть накопительными, а при параллельной работе перекрываться; их не следует безусловно складывать.

Допустимый вывод по этому уроку уже:

На DuckDB указанной версии и данном входе варианты вернули одинаковые две метрики. В плане кандидата один узел чтения READ_CSV вместо двух. Это подтверждает устранение повторного чтения в данном workload; устойчивый коэффициент ускорения не измерялся.

Если решение действительно зависит от скорости, после план-аудита нужен отдельный benchmark-протокол из 02/09: representative data, фиксированный scope, warm-up, повторы, распределение времени и сведения об окружении.

Соберите это

Шаг 1. Зафиксируйте semantic contract

До планов запишите результат обеих метрик на tiny:

text
input: ../data/tiny/events.csv
event_name: order_paid
result grain: одна строка на весь выбранный файл
event_rows: 6
active_users: 3

event_rows и active_users проверяются отдельно. Одного совпавшего общего числа недостаточно: компенсирующие ошибки могли бы скрыть изменение population.

Шаг 2. Нарисуйте план карточками

Не копируйте вывод DuckDB. Сначала предскажите минимальное дерево для каждого SQL:

Вариант Чтения источника Фильтры Итоговая cardinality
two_scans 2 по одному в каждой ветви 1 строка
one_scan 1 два условия одного aggregate 1 строка

Теперь у EXPLAIN есть проверяемый вопрос: совпал ли выбранный движком plan shape с ожиданием?

Шаг 3. Получите статический план

Python API из 04/11 позволяет передать параметры и к EXPLAIN:

python
plan_row = connection.execute(
    "EXPLAIN " + trusted_sql,
    parameters,
).fetchone()

plan_text = plan_row[1]

trusted_sql остаётся заранее проверенным asset. Параметры передают путь и значение события, но не делают произвольный SQL безопасным.

Для каждого плана сохраните:

  • полный текст;
  • число объявленных узлов чтения источника;
  • все встреченные оценки ~N rows.

Шаг 4. Выполните EXPLAIN ANALYZE

python
analyzed_row = connection.execute(
    "EXPLAIN ANALYZE " + trusted_sql,
    parameters,
).fetchone()

Теперь сохраните:

  • полный analyzed plan;
  • фактические row markers без ~;
  • Total Time как наблюдение;
  • число фактических чтений источника.

Не сравнивайте времена до semantic gate.

Шаг 5. Сначала сравните результаты

Оба SQL выполняются отдельно и возвращают именованные поля:

python
{
    "event_rows": 6,
    "active_users": 3,
}

Логика решения:

text
results differ
-> stop: candidate is not an optimization of the same calculation

results equal and source reads decrease
-> supported plan-shape improvement on this input

results equal but source reads do not decrease
-> inspect other operators; no improvement proved yet

Шаг 6. Не закрывайте чужую connection

Публичная функция артефакта принимает DuckDBPyConnection:

python
report = build_plan_report(connection, events_path)

Она использует, но не закрывает соединение. CLI создаёт собственную connection и закрывает её в finally. Это тот же ownership contract, который был введён в 04/11.

Шаг 7. Запустите компактную демонстрацию

bash
uv run --locked python code/main.py

Вы увидите:

  • совпавшие результаты;
  • отдельные списки estimate и actual row markers;
  • два чтения против одного;
  • safe_to_compare_work: true;
  • явный запрет превращать одно timing-наблюдение в обещание скорости.

Как читать JSON-отчёт

text
scope
├── engine и engine_version
├── events_path и event_name
└── claim_boundary

variants
├── two_scans
│   ├── result
│   ├── explain
│   └── explain_analyze
└── one_scan
    ├── result
    ├── explain
    └── explain_analyze

comparison
├── results_equal
├── safe_to_compare_work
├── source_reads_removed
├── timing_claim_allowed
└── conclusion

Полный plan_text важнее извлечённых счётчиков. Счётчик — удобный тест конкретного failure mode, а текст сохраняет evidence для человека и позволяет увидеть изменение операторов после обновления DuckDB.

Сломайте это

1. Упростите план ценой другой population

Ошибочный кандидат оставляет фильтр только для event_rows:

sql
SELECT
    count(*) FILTER (WHERE event_name = ?) AS event_rows,
    count(DISTINCT user_id) AS active_users
FROM read_csv(?, header = true, all_varchar = true, nullstr = '');

План содержит одно чтение, но результат равен (6, 8), а не (6, 3). safe_to_compare_work обязан стать false. Это наиболее опасная оптимизация: быстрый и правдоподобный ответ на другой вопрос.

2. Перепутайте estimate и actual

Скопируйте ~31 rows из EXPLAIN в отчёт как «файл содержит 31 строку». Проверка фактического плана покажет 16. Тильда — часть смысла, а не оформление.

3. Запустите EXPLAIN ANALYZE на неизвестном SQL

EXPLAIN ANALYZE выполняет запрос. Не используйте его как валидатор «read-only» для непроверенного текста и не разрешайте произвольный SQL через CLI артефакта.

4. Объявите коэффициент ускорения по tiny

Даже если один запуск показывает заметную разницу, тесты не утверждают порядок времени. На маленьком файле запуск, файловый кэш и шум могут быть сопоставимы с полезной работой.

5. Судите о плане по числу CTE или длине SQL

CTE может быть встроен, материализован или переиспользован в зависимости от запроса и версии движка. Число слов WITH не равно числу scan. Проверяйте физический план.

6. Сделайте текстовый парсер универсальным обещанием

Формат pretty-printed plan может измениться между версиями. Артефакт:

  • сохраняет версию DuckDB;
  • хранит полный текст;
  • извлекает только узкие сигналы этого эксперимента;
  • не обещает совместимость счётчиков с любой СУБД.

7. Закройте переданную connection

Если build_plan_report закроет соединение, вызывающий код потеряет свой каталог и последующие запросы. Behavioral test выполняет SELECT 42 после аудита и подтверждает сохранение ownership.

Проверьте это

Запустите:

bash
uv run --locked python -m unittest discover -s tests

Behavioral suite проверяет:

  • точные две метрики и их эквивалентность;
  • два чтения против одного в EXPLAIN и EXPLAIN ANALYZE;
  • наличие оценок только в статическом evidence;
  • наличие фактических строк и Total Time после выполнения;
  • несовпадение estimate и actual на tiny CSV;
  • присутствие READ_CSV, PROJECTION и UNGROUPED_AGGREGATE;
  • блокировку кандидата с неверной population;
  • нулевой сценарий для отсутствующего события;
  • запрет обещания speedup по одному timing;
  • версию движка и scope входа;
  • сохранение caller-owned connection;
  • ошибки отсутствующего файла, пустого event_name и неподтверждённого SQL-кандидата;
  • JSON stdout, запись самостоятельного отчёта и ошибку CLI.

Тесты сознательно не содержат assertion вида:

python
candidate_time < baseline_time

Упражнения

  1. На tiny вручную подпишите каждый оператор плана кандидата вопросами «что получает?», «что выдаёт?» и «сколько строк проходит?». Сверьте ~N rows с actual rows.
  2. Запустите тот же аудит на sample. Сравните только plan shape и row flow, не объявляя коэффициент ускорения по одному запуску.
  3. Измените кандидата так, чтобы active_users считались по всем событиям. Объясните, почему один scan не проходит semantic gate.
  4. Возьмите проверенный JOIN из 04/05 и найдите в плане два входа и выходную cardinality. Сопоставьте её с ранее объявленным grain, не меняя SQL ради «красивого» оператора.
  5. После обновления DuckDB сравните сохранённые plan text. Отделите изменение оформления от реального изменения дерева и не подгоняйте парсер без просмотра evidence.

  • EN · DuckDB: Profiling — прочитайте разделы EXPLAIN, EXPLAIN ANALYZE и Metrics. Они показывают, как перейти от учебного текстового плана к более подробному профилированию, когда узких сигналов отчёта недостаточно.
  • RU · PostgreSQL: использование EXPLAIN — сосредоточьтесь на объяснении rows, узлах-потомках и разделе про EXPLAIN ANALYZE. Синтаксис и числа PostgreSQL не переносите в DuckDB; переносите способ чтения потока снизу вверх.
  • EN · DuckDB: Performance Guide — используйте страницу как карту следующих диагностик: environment, import, schema, joins, file formats и workload tuning. Не применяйте все советы одновременно до локализации проблемы планом.
  • EN · DuckDB: Benchmarks — прочитайте A Note on Benchmarks и disclaimer. Материал углубляет причину, по которой один tiny-run и неполный workload нельзя превращать в общий performance-claim.
  • RU · YDB: структура планов запросов — разберите определения scan, filter, aggregate, join и связи между стадиями. Это полезный перенос модели дерева на распределённый движок, но названия операторов YDB не являются DuckDB API.
  • RU · YDB: оптимизация запросов — прочитайте введение и раздел об оценке стоимости. Обратите внимание на главное ограничение оптимизатора: альтернативный план должен оставаться эквивалентным по результату.
  • EN · DuckDB Blog: Optimizers — The Low-Key MVP — прочитайте введение и пример с filter pushdown. Статья разработчика DuckDB показывает, почему текстовый порядок SQL не равен физическому порядку работы и почему ручное переписывание нужно подтверждать планом.
  • EN · PostgreSQL: Using EXPLAIN — для углубления прочитайте про estimated cost, rows, width и проверку оценок через ANALYZE. Этот источник помогает отделить абстрактную стоимость планировщика от фактического elapsed time.

Quiz · 7 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

Какое различие между EXPLAIN и EXPLAIN ANALYZE существенно перед запуском неизвестного запроса?

EXPLAIN показывает выбранный физический план и оценки. EXPLAIN ANALYZE исполняет запрос и добавляет фактические cardinality и timing.

02

С какого места новичку полезнее начинать чтение дерева физического плана?

Нижние узлы читают данные, а родительские узлы преобразуют поток и передают его выше. Такой обход связывает дерево с фактической работой.

03

В EXPLAIN у scan указано ~31 rows, а в EXPLAIN ANALYZE — 16 rows. Как это интерпретировать?

Тильда отмечает оценку оптимизатора. Фактическое выполнение даёт наблюдаемое число строк; расхождение является диагностическим сигналом, а не автоматической ошибкой результата.

04

Кандидат читает CSV один раз вместо двух и возвращает тот же контрольный результат. Какой вывод допустим?

План подтверждает конкретное уменьшение работы на данном запросе и входе. Коэффициент ускорения и перенос на другие данные требуют отдельного воспроизводимого измерения.

05

Кандидат имеет более простой план, но считает distinct пользователей по всем событиям вместо только order_paid. Что делать?

Быстрый другой ответ не является оптимизацией. Сначала восстанавливают одинаковую population и результат, затем сравнивают работу.

06

Почему сумма времён отдельных операторов EXPLAIN ANALYZE может не совпасть с общим wall-clock временем?

Профилирование описывает работу операторов, а не простое разбиение общего времени на непересекающиеся части. При параллельном выполнении времена могут перекрываться.

07

Что должно войти в корректный handoff по результатам план-аудита?

Получатель должен воспроизвести контекст и отделить наблюдение от переноса. Поэтому отчёт сохраняет scope, semantic gate, plan evidence и границу утверждения.

from __future__ import annotations

import argparse
import json
import re
from collections.abc import Mapping, Sequence
from pathlib import Path
from typing import Any, TypedDict

import duckdb

TOTAL_TIME_PATTERN = re.compile(r"Total Time:\s*([0-9.]+)s")
ESTIMATED_ROWS_PATTERN = re.compile(r"~([0-9][0-9,]*) rows?")
ACTUAL_ROWS_PATTERN = re.compile(r"(?<!~)([0-9][0-9,]*) rows?")
SOURCE_READ_MARKER = "Function: READ_CSV"

BASELINE_SQL = """
SELECT
    (
        SELECT count(*)
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        WHERE event_name = ?
    ) AS event_rows,
    (
        SELECT count(DISTINCT user_id)
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        WHERE event_name = ?
    ) AS active_users
"""

CONSOLIDATED_SQL = """
SELECT
    count(*) FILTER (WHERE event_name = ?) AS event_rows,
    count(DISTINCT user_id) FILTER (WHERE event_name = ?) AS active_users
FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
"""

WRONG_POPULATION_SQL = """
SELECT
    count(*) FILTER (WHERE event_name = ?) AS event_rows,
    count(DISTINCT user_id) AS active_users
FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
"""


class PlanAuditError(ValueError):
    """Raised when a plan comparison cannot satisfy its input contract."""


class QueryVariant(TypedDict):
    label: str
    sql: str
    parameters: Sequence[Any]


def _validated_events_path(events_path: Path) -> Path:
    path = Path(events_path).expanduser()
    if not path.is_file():
        raise PlanAuditError(f"events file does not exist: {path}")
    return path.resolve()


def _validated_event_name(event_name: str) -> str:
    if not isinstance(event_name, str) or not event_name.strip():
        raise PlanAuditError("event_name must be a non-empty string")
    return event_name


def _plan_text(
    connection: duckdb.DuckDBPyConnection,
    sql: str,
    parameters: Sequence[Any],
    *,
    analyze: bool,
) -> str:
    prefix = "EXPLAIN ANALYZE " if analyze else "EXPLAIN "
    rows = connection.execute(prefix + sql, list(parameters)).fetchall()
    if len(rows) != 1 or len(rows[0]) < 2 or not isinstance(rows[0][1], str):
        kind = "EXPLAIN ANALYZE" if analyze else "EXPLAIN"
        raise PlanAuditError(f"{kind} returned an unexpected result")
    return rows[0][1]


def _row_markers(pattern: re.Pattern[str], plan_text: str) -> list[int]:
    return [int(value.replace(",", "")) for value in pattern.findall(plan_text)]


def _plan_evidence(plan_text: str, *, analyzed: bool) -> dict[str, Any]:
    total_time_match = TOTAL_TIME_PATTERN.search(plan_text)
    return {
        "source_read_nodes": plan_text.count(SOURCE_READ_MARKER),
        "estimated_row_markers": (
            [] if analyzed else _row_markers(ESTIMATED_ROWS_PATTERN, plan_text)
        ),
        "actual_row_markers": (_row_markers(ACTUAL_ROWS_PATTERN, plan_text) if analyzed else []),
        "total_time_seconds": (float(total_time_match.group(1)) if total_time_match else None),
        "plan_text": plan_text,
    }


def _result(connection: duckdb.DuckDBPyConnection, variant: QueryVariant) -> dict[str, int]:
    row = connection.execute(
        variant["sql"],
        list(variant["parameters"]),
    ).fetchone()
    if row is None or len(row) != 2:
        raise PlanAuditError(f"{variant['label']} must return event_rows and active_users")
    return {
        "event_rows": int(row[0]),
        "active_users": int(row[1]),
    }


def inspect_variant(
    connection: duckdb.DuckDBPyConnection,
    variant: QueryVariant,
) -> dict[str, Any]:
    """Run one trusted query variant and preserve static and actual plan evidence."""
    explain_text = _plan_text(
        connection,
        variant["sql"],
        variant["parameters"],
        analyze=False,
    )
    analyzed_text = _plan_text(
        connection,
        variant["sql"],
        variant["parameters"],
        analyze=True,
    )
    return {
        "label": variant["label"],
        "sql": variant["sql"].strip(),
        "parameters": list(variant["parameters"]),
        "result": _result(connection, variant),
        "explain": _plan_evidence(explain_text, analyzed=False),
        "explain_analyze": _plan_evidence(analyzed_text, analyzed=True),
    }


def audit_variants(
    connection: duckdb.DuckDBPyConnection,
    baseline: QueryVariant,
    candidate: QueryVariant,
) -> dict[str, Any]:
    """Compare trusted query variants without taking ownership of the connection."""
    baseline_evidence = inspect_variant(connection, baseline)
    candidate_evidence = inspect_variant(connection, candidate)
    results_equal = baseline_evidence["result"] == candidate_evidence["result"]
    baseline_reads = baseline_evidence["explain"]["source_read_nodes"]
    candidate_reads = candidate_evidence["explain"]["source_read_nodes"]
    reads_removed = baseline_reads - candidate_reads

    if not results_equal:
        conclusion = (
            "blocked: candidate changes the analytical result, so plan and timing "
            "differences are not optimization evidence"
        )
    elif reads_removed > 0:
        conclusion = (
            "supported on this input: candidate preserves the result and removes "
            f"{reads_removed} repeated source read(s); timing remains an observation"
        )
    else:
        conclusion = (
            "inconclusive: results match, but this audit found no reduction in source "
            "reads; inspect other operators and use a separate benchmark if speed matters"
        )

    return {
        "variants": [baseline_evidence, candidate_evidence],
        "comparison": {
            "results_equal": results_equal,
            "safe_to_compare_work": results_equal,
            "baseline_source_read_nodes": baseline_reads,
            "candidate_source_read_nodes": candidate_reads,
            "source_reads_removed": reads_removed,
            "candidate_has_single_source_read": candidate_reads == 1,
            "timing_claim_allowed": False,
            "conclusion": conclusion,
        },
    }


def event_query_variants(
    events_path: Path,
    event_name: str,
    *,
    candidate_sql: str = CONSOLIDATED_SQL,
    candidate_label: str = "one_scan",
) -> tuple[QueryVariant, QueryVariant]:
    path = _validated_events_path(events_path)
    name = _validated_event_name(event_name)
    if candidate_sql == CONSOLIDATED_SQL:
        candidate_parameters = [name, name, str(path)]
    elif candidate_sql == WRONG_POPULATION_SQL:
        candidate_parameters = [name, str(path)]
    else:
        raise PlanAuditError(
            "candidate_sql must be a trusted built-in query; "
            "use audit_variants for an explicitly constructed trusted pair"
        )
    baseline: QueryVariant = {
        "label": "two_scans",
        "sql": BASELINE_SQL,
        "parameters": [str(path), name, str(path), name],
    }
    candidate: QueryVariant = {
        "label": candidate_label,
        "sql": candidate_sql,
        "parameters": candidate_parameters,
    }
    return baseline, candidate


def build_plan_report(
    connection: duckdb.DuckDBPyConnection,
    events_path: Path,
    event_name: str = "order_paid",
    *,
    candidate_sql: str = CONSOLIDATED_SQL,
    candidate_label: str = "one_scan",
) -> dict[str, Any]:
    """Build a bounded DuckDB plan audit for the lesson's event query."""
    path = _validated_events_path(events_path)
    baseline, candidate = event_query_variants(
        path,
        event_name,
        candidate_sql=candidate_sql,
        candidate_label=candidate_label,
    )
    audit = audit_variants(connection, baseline, candidate)
    return {
        "scope": {
            "engine": "duckdb",
            "engine_version": duckdb.__version__,
            "events_path": str(path),
            "event_name": _validated_event_name(event_name),
            "claim_boundary": (
                "The report diagnoses this query pair on this input. It does not "
                "guarantee a speedup for another dataset, engine version, or workload."
            ),
        },
        **audit,
    }


def _write_report(report: Mapping[str, Any], output_path: Path | None) -> None:
    payload = json.dumps(report, ensure_ascii=False, indent=2) + "\n"
    if output_path is None:
        print(payload, end="")
        return
    output_path.parent.mkdir(parents=True, exist_ok=True)
    output_path.write_text(payload, encoding="utf-8")
    print(output_path)


def main() -> None:
    parser = argparse.ArgumentParser(
        description=(
            "Audit equivalent DuckDB queries by result, EXPLAIN shape, and EXPLAIN ANALYZE evidence"
        )
    )
    parser.add_argument("--events", type=Path, required=True)
    parser.add_argument("--event-name", default="order_paid")
    parser.add_argument("--output", type=Path)
    args = parser.parse_args()

    connection = duckdb.connect()
    try:
        report = build_plan_report(connection, args.events, args.event_name)
        _write_report(report, args.output)
    except (duckdb.Error, OSError, PlanAuditError) as error:
        parser.error(str(error))
    finally:
        connection.close()


if __name__ == "__main__":
    main()
