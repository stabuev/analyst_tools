Связь с предыдущими уроками

В 04/10 вы построили SQL-модель месячной когортной активности. Её выход уже имеет определённый контракт:

text
grain       -> одна строка на (cohort_month, period_index)
календарь   -> cohort_month и activity_month
метрики     -> cohort_size, active_users, activity_rate
контекст    -> business_timezone, last_complete_activity_month
порядок     -> cohort_month, затем period_index

Из фазы 03 вы уже знаете, что DataFrame — не просто набор значений. Для следующей операции важны названия и порядок столбцов, dtype каждого столбца и смысл одной строки. Из фазы 04 вы знаете, что SQL-файл может быть самостоятельным проверяемым артефактом.

Новое в этом уроке — не ещё один способ рассчитать когорты. Мы строим явный интерфейс между уже знакомыми частями:

text
типизированный pandas DataFrame
-> relation внутри конкретной DuckDB connection
-> доверенный SQL + отдельно переданные значения
-> компактный результат DuckDB
-> проверенный pandas DataFrame

DuckDBPyConnection, parameter binding, register, unregister и fetchdf раньше встречались в техническом коде запуска уроков, но не были предметом обучения. Поэтому здесь они объясняются, а не считаются известными.

Проблема

Представьте продолжение задачи из 04/10. Когортная таблица уже рассчитана. Для графика нужна одна когорта — январь 2026 года — и только наблюдаемые периоды от нулевого до второго.

В ноутбуке легко написать так:

python
selected_month = "2026-01-01"
max_period = 2

result = duckdb.sql(f"""
    SELECT *
    FROM cohort_activity
    WHERE cohort_month = '{selected_month}'
      AND period_index <= {max_period}
""").df()

Этот фрагмент может вернуть правильные три строки. Но его интерфейс скрыт:

  • duckdb.sql() использует connection по умолчанию;
  • cohort_activity находится по имени Python-переменной из окружающего namespace;
  • значения встроены внутрь SQL через форматирование строки;
  • не видно, кто владеет соединением и когда оно закрывается;
  • downstream-код узнает о переименовании столбца или смене dtype только в месте падения;
  • .df() материализует весь результат, хотя размер результата ничем не ограничен.

Пока ячейки запускаются в одном порядке, скрытое состояние кажется удобством. После переноса кода в функцию или тест ситуация меняется: нужной локальной переменной может не оказаться, default connection может содержать другие временные объекты, а два запуска могут влиять друг на друга.

Нам нужен не универсальный запускатель произвольного SQL. Нужен небольшой явный интерфейс конкретного аналитического шага.

Концепция

У Python, SQL и pandas разные обязанности

Разделим задачу до написания кода:

Часть За что отвечает Чего она не должна скрывать
Python открывает connection, читает SQL-asset, передаёт вход и параметры, проверяет результат SQL-логику и происхождение connection
SQL фильтрует, агрегирует и задаёт grain результата Python namespace и формат доставки
DuckDB connection хранит контекст выполнения запроса неявное глобальное состояние
pandas продолжает анализ компактного типизированного результата тяжёлое чтение и сокращение сырых данных

Эта граница не означает, что один инструмент «главнее». Она делает зависимости наблюдаемыми и проверяемыми.

Connection — это контекст выполнения

duckdb.connect() возвращает объект DuckDBPyConnection. Даже для базы в памяти это не пустая формальность. С connection связаны:

  • каталог доступных таблиц, views и временных объектов;
  • зарегистрированные Python-объекты;
  • настройки текущего сеанса;
  • выполняемые запросы и их результаты;
  • жизненный цикл ресурса.

Две независимо созданные безымянные in-memory connection имеют разное состояние:

python
first = duckdb.connect()
second = duckdb.connect()

first.execute("CREATE TEMP TABLE example AS SELECT 42 AS value")

first.execute("SELECT * FROM example").fetchall()   # [(42,)]
second.execute("SELECT * FROM example")             # Catalog Error

Поэтому фраза «таблица существует в DuckDB» неполна. Нужно уточнить: в какой базе и через какую connection код к ней обращается.

Правило владения

Используем простое правило:

Кто создал connection, тот определяет её полный lifecycle и закрывает её.

Если внешняя функция передала connection в query_dataframe, вложенная функция может выполнить запрос, но не должна закрывать чужой ресурс:

python
connection = duckdb.connect()
try:
    first_result = query_dataframe(connection, ...)
    second_result = query_dataframe(connection, ...)
finally:
    connection.close()

Так вызывающий код может выполнить несколько связанных действий в одном контексте. Функция query_dataframe из артефакта урока вообще не умеет создавать connection: параметр connection обязателен. Это намеренное ограничение интерфейса.

SQL-структура и значения — разные сущности

В запросе меняются два значения:

  • выбранный cohort_month;
  • последний нужный period_index.

Структура запроса не меняется:

sql
WHERE cohort_month = $cohort_month::DATE
  AND period_index <= $max_period::BIGINT

Python передаёт значения отдельно:

python
parameters = {
    "cohort_month": "2026-01-01",
    "max_period": 2,
}

connection.execute(sql, parameters)

DuckDB связывает $cohort_month со строкой, а $max_period — с числом. Кавычки, экранирование и преобразование значения больше не собираются вручную через f-string.

Позиционные параметры ? решают ту же задачу:

python
connection.execute(
    "SELECT ?::DATE AS cohort_month, ?::BIGINT AS max_period",
    ["2026-01-01", 2],
)

Для двух бизнес-параметров именованная форма нагляднее: значения сложнее случайно переставить местами.

Параметр — только значение

Parameter binding не является шаблонизатором SQL. Плейсхолдер нельзя использовать вместо:

  • имени таблицы;
  • имени столбца;
  • оператора сравнения;
  • ключевого слова ASC или DESC;
  • произвольного условия WHERE;
  • целого SQL-фрагмента.

Например:

python
connection.execute(
    "SELECT ? AS chosen FROM cohort_activity LIMIT 1",
    ["active_users"],
).fetchone()

вернёт строку "active_users", а не значение столбца active_users. DuckDB честно воспринял параметр как строковое значение.

Если структура действительно должна меняться, безопасный выбор выглядит иначе:

python
allowed_sort_columns = {
    "period": "period_index",
    "rate": "activity_rate",
}
sort_expression = allowed_sort_columns[user_choice]

В SQL попадает только заранее заданный разработчиком фрагмент. Произвольная строка пользователя не становится структурой запроса.

Параметры не делают произвольный SQL доверенным

В артефакте функция называется execute_trusted_query: она выполняет SQL, который уже находится в репозитории и прошёл review.

Параметризация защищает границу значений:

text
переданная строка -> значение SQL

Но она ничего не доказывает о самом тексте запроса:

text
SQL-файл -> структура и поведение программы

Нельзя надёжно объявить произвольный запрос read-only, проверив только его первое слово регулярным выражением. Комментарии, несколько statements, вызываемые функции и поведение всего запроса не сводятся к префиксу SELECT или WITH.

Поэтому контракт урока честный:

  • SQL — доверенный артефакт из проекта;
  • параметры — недоверенные или меняющиеся значения;
  • функция не изображает SQL-песочницу.

Если рабочая задача требует открыть существующий файл DuckDB строго без записи, это отдельное свойство соединения read_only=True. Оно относится к файловой базе и не заменяет review SQL-логики.

pandas → DuckDB: явная relation

DuckDB умеет находить DataFrame по имени локальной Python-переменной. Механизм называется replacement scan: если SQL ссылается на несуществующую таблицу, DuckDB может найти объект с таким именем в Python-окружении.

Это удобно для одноразового исследования:

python
cohort_activity = ...
duckdb.sql("SELECT * FROM cohort_activity").df()

Но зависимость спрятана в имени и области видимости переменной. В функции или тесте лучше сделать её частью алгоритма:

python
connection.register("cohort_activity", cohort_activity)

После регистрации SQL видит relation с именем cohort_activity. Это временный интерфейс к Python-объекту в данной connection, а не создание постоянной таблицы в файловой базе.

Регистрация тоже является состоянием. Если её оставить, следующий запрос может случайно использовать старый DataFrame. Поэтому шаг должен иметь симметричное завершение:

python
connection.register("cohort_activity", cohort_activity)
try:
    result = connection.execute(sql, parameters).fetchdf()
finally:
    connection.unregister("cohort_activity")

finally выполняется и при успешном результате, и при ошибке запроса или проверки.

DuckDB → pandas: материализация результата

После execute результат ещё принадлежит DuckDB. Вызов:

python
frame = connection.execute(sql, parameters).fetchdf()

создаёт pandas DataFrame со всеми строками результата. Это удобная граница, если SQL уже:

  • выбрал нужную популяцию;
  • сократил объём;
  • установил целевой grain;
  • выбрал только нужные столбцы;
  • задал детерминированный порядок, когда он важен.

Плохая граница:

text
миллионы сырых событий -> fetchdf -> фильтрация и агрегация в pandas

Разумная граница:

text
миллионы сырых событий
-> фильтрация и агрегация в DuckDB
-> сотни строк нужного grain
-> fetchdf
-> визуализация или небольшой downstream-анализ в pandas

DuckDB имеет batch- и Arrow-интерфейсы для результатов, которые нельзя материализовать целиком. В этом уроке мы не изучаем их API: сначала нужно научиться осознанно выбирать саму границу. Наш когортный срез заведомо компактен.

SQL-типы и pandas-dtypes — два контракта

В SQL запрос объявляет типы:

sql
period_index::BIGINT
activity_rate::DOUBLE

После fetchdf() они представлены pandas-dtypes:

text
BIGINT -> int64
DOUBLE -> float64
DATE   -> datetime64[us]  # в зафиксированном окружении этого проекта

Названия систем типов различаются. Поэтому недостаточно проверить только имена столбцов. Если period_index неожиданно стал строкой или nullable-столбец изменил представление, downstream-код может:

  • сортировать числа лексикографически;
  • неверно сравнивать даты;
  • потерять поддержку пропусков;
  • упасть далеко от места передачи данных.

Контракт артефакта проверяет:

text
точный список столбцов
+ точный порядок
+ pandas-dtype каждого столбца

Grain нельзя доказать одним dtype-тестом. Для нашей задачи его отдельно проверяет behavioral test на уникальность (cohort_month, period_index).

Соберите это

Сначала выполним весь механизм явно. Лишь затем спрячем повторяемую часть в функцию.

Шаг 1. Зафиксируйте вход и ожидаемый результат

Возьмём маленький типизированный DataFrame, который воспроизводит контракт результата 04/10:

cohort_month activity_month period_index cohort_size active_users activity_rate
2026-01-01 2026-01-01 0 4 4 1.00
2026-01-01 2026-02-01 1 4 3 0.75
2026-01-01 2026-03-01 2 4 2 0.50
2026-01-01 2026-04-01 3 4 0 0.00
2026-02-01 2026-02-01 0 3 3 1.00
2026-02-01 2026-03-01 1 3 2 0.6667
2026-02-01 2026-04-01 2 3 1 0.3333

Запрос для cohort_month = 2026-01-01 и max_period = 2 должен вернуть первые три строки январской когорты.

До запуска зафиксируйте инварианты:

text
rows                  = 3
period_index          = [0, 1, 2]
active_users          = [4, 3, 2]
activity_rate         = [1.0, 0.75, 0.5]
unique grain          = (cohort_month, period_index)
order                 = period_index ascending

Так проверка не зависит от того, «похоже ли» содержимое DataFrame на правильное.

Шаг 2. Отделите SQL от значений

Файл outputs/cohort_activity_slice.sql содержит устойчивую структуру:

sql
SELECT
    cohort_month,
    activity_month,
    period_index::BIGINT AS period_index,
    cohort_size::BIGINT AS cohort_size,
    active_users::BIGINT AS active_users,
    activity_rate::DOUBLE AS activity_rate
FROM cohort_activity
WHERE cohort_month = $cohort_month::DATE
  AND period_index <= $max_period::BIGINT
ORDER BY period_index;

Изменяемые значения в файл не встраиваются:

python
parameters = {
    "cohort_month": "2026-01-01",
    "max_period": 2,
}

Обратите внимание на две границы:

  • имя relation cohort_activity — часть проверенного SQL;
  • выбранный месяц и горизонт — значения, переданные через DB API.

Шаг 3. Откройте явную connection

python
connection = duckdb.connect()
try:
    # Все действия этого учебного запуска происходят здесь.
    ...
finally:
    connection.close()

Не переносите duckdb.connect() внутрь функции запроса. Иначе функция одновременно начнёт решать две задачи: управлять ресурсом и вычислять результат. Кроме того, зарегистрированная в одной connection relation будет недоступна в случайно созданной второй.

Шаг 4. Зарегистрируйте вход, выполните запрос и снимите регистрацию

python
connection.register("cohort_activity", cohort_activity)
try:
    result = connection.execute(sql, parameters).fetchdf()
finally:
    connection.unregister("cohort_activity")

Здесь видны обе стороны обмена:

text
register -> pandas передаёт relation в DuckDB
fetchdf  -> DuckDB материализует результат в pandas

Если execute или fetchdf завершатся ошибкой, unregister всё равно выполнится. Connection остаётся открытой, потому что её создал внешний код.

Шаг 5. Проверьте результат на границе

Сначала проверим столбцы:

python
expected_columns = [
    "cohort_month",
    "activity_month",
    "period_index",
    "cohort_size",
    "active_users",
    "activity_rate",
]

if result.columns.tolist() != expected_columns:
    raise ValueError("result column contract changed")

Затем dtypes:

python
expected_dtypes = {
    "cohort_month": "datetime64[us]",
    "activity_month": "datetime64[us]",
    "period_index": "int64",
    "cohort_size": "int64",
    "active_users": "int64",
    "activity_rate": "float64",
}

actual_dtypes = {
    column: str(result[column].dtype)
    for column in expected_columns
}

if actual_dtypes != expected_dtypes:
    raise ValueError("result dtype contract changed")

Такая проверка не исправляет данные молча. Она останавливает передачу результата в следующий этап и показывает, где именно изменился интерфейс.

Используйте это

Артефакт outputs/duckdb_dataframe_query.py собирает повторяемый механизм в две функции:

  • execute_trusted_query выполняет доверенный SQL с параметрами и проверяет результат;
  • query_dataframe дополнительно проверяет входной DataFrame, регистрирует его как relation и гарантированно снимает регистрацию.

Сигнатура намеренно подробная:

python
result = query_dataframe(
    connection,
    sql=sql,
    relation_name="cohort_activity",
    frame=cohort_activity,
    parameters={
        "cohort_month": "2026-01-01",
        "max_period": 2,
    },
    expected_input_columns=input_columns,
    expected_input_dtypes=input_dtypes,
    expected_output_columns=output_columns,
    expected_output_dtypes=output_dtypes,
)

По вызову можно восстановить весь интерфейс:

text
какая connection
какой доверенный SQL
под каким именем доступен вход
какой DataFrame передаётся
какие значения меняются
какую схему ожидаем до и после запроса

Функция выполняет операции в таком порядке:

text
1. проверить входные columns и dtypes
2. register(relation_name, frame)
3. execute(sql, parameters)
4. fetchdf()
5. проверить выходные columns и dtypes
6. unregister(relation_name) в finally
7. вернуть новый DataFrame

Она не:

  • открывает или закрывает connection;
  • ищет DataFrame в глобальном namespace;
  • читает сырой CSV;
  • меняет исходный DataFrame;
  • принимает произвольные SQL-фрагменты как параметры;
  • объявляет непроверенный SQL безопасным;
  • добавляет CLI, JSON-конфигурацию или формат доставки.

Запустите законченный пример:

bash
uv run --locked python code/main.py

В выводе должны быть три строки январской когорты, period_index от 0 до 2 и явный словарь pandas-dtypes.

Сломайте это

1. Верните скрытую default connection

Замените явный вызов на:

python
duckdb.sql("SELECT * FROM cohort_activity").df()

Теперь поведение зависит от connection по умолчанию и от того, сможет ли replacement scan найти Python-переменную в текущем scope. Функция больше не сообщает свои зависимости через аргументы.

2. Попробуйте параметризовать имя столбца

python
connection.execute(
    "SELECT ? AS chosen FROM cohort_activity LIMIT 1",
    ["active_users"],
).fetchone()

Правдоподобная ошибка — ожидать значение 4. Фактический результат — строка "active_users". Параметр остался значением и не стал идентификатором.

3. Закройте чужую connection

Добавьте connection.close() внутрь query_dataframe. Первый запрос может пройти, а следующий вызов внешнего кода упадёт на уже закрытом ресурсе. Ошибка возникнет не там, где было нарушено владение.

4. Оставьте регистрацию после запроса

Удалите unregister. Следующий тест или расчёт сможет случайно прочитать прежний cohort_activity. Результат будет зависеть от истории работы процесса.

Особенно важно, чтобы очистка происходила и при исключении. Поэтому она находится в finally, а не после успешного return.

5. Подмените parameter binding f-string

python
sql = f"""
    SELECT *
    FROM cohort_activity
    WHERE cohort_month = '{selected_month}'
"""

Теперь строка значения и структура SQL снова склеены. Помимо риска изменения смысла запроса, появляются ручные правила кавычек, типов и экранирования.

6. Добавьте regex-проверку «read-only»

Проверка вида:

python
re.match(r"^\s*(SELECT|WITH|EXPLAIN)", sql)

не анализирует поведение всего SQL. Она создаёт сильное обещание безопасности на основе слабого признака. Граница должна быть сформулирована честно: функция исполняет только доверенные SQL-assets проекта.

7. Измените dtype на входе

python
broken = cohort_activity.copy()
broken["period_index"] = broken["period_index"].astype("string")

Значения "0", "1" и "2" визуально похожи на числа. Но типизированный контракт должен остановить расчёт до регистрации relation. Иначе неявные преобразования могут скрыть проблему до более сложного запроса.

8. Передайте через fetchdf сырые события

Замените компактный когортный срез на SELECT * из большой таблицы событий. Код может быть логически корректным, но граница выбрана плохо: pandas получает объём, который SQL мог сократить заранее.

fetchdf() не является стриминговым обещанием. Если результат нельзя безопасно материализовать целиком, нужно изменить запрос или выбрать batch-интерфейс в отдельной рабочей задаче.

Поставьте результат

Главный артефакт — outputs/duckdb_dataframe_query.py.

Он пригоден, когда аналитическому Python-коду нужно:

  1. передать уже типизированный DataFrame в DuckDB;
  2. выполнить над ним доверенный SQL-asset с меняющимися значениями;
  3. получить компактный DataFrame с явной схемой;
  4. не оставить после себя скрытую relation и не закрыть чужую connection.

SQL-пример outputs/cohort_activity_slice.sql показывает ожидаемую форму доверенного asset: комментарий с входным и выходным контрактом, фиксированная структура, параметры-значения и детерминированный порядок.

CLI здесь сознательно не добавляется. Новый результат урока — корректная программная граница DuckDB ↔ pandas, а не интерфейс командной строки. Если у расчёта появится реальный внешний потребитель, формат запуска следует проектировать вместе с доставкой, обработкой ошибок и наблюдаемостью, а не добавлять argparse ради единообразия.

Quiz · 6 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

Функция получила уже открытую DuckDB connection. Кто должен закрыть её после нескольких последовательных запросов?

Владение определяется созданием ресурса. Вложенная функция использует переданное соединение, но не решает, когда завершена вся работа вызывающего кода.

02

Нужно выбирать один из разрешённых столбцов для сортировки. Почему нельзя передать его имя через обычный SQL-параметр?

Плейсхолдер отделяет данные от синтаксиса. Структурный выбор делают через заранее проверенный SQL или allowlist допустимых фрагментов, а не через value binding.

03

Зачем явно вызывать connection.register("cohort_activity", frame), если DuckDB иногда сам находит локальный DataFrame?

Явная регистрация заменяет зависимость от Python namespace понятным шагом интерфейса. Она создаёт доступную запросу relation в конкретном соединении, но не постоянную таблицу.

04

Запрос возвращает несколько миллионов сырых строк, а следующий шаг использует только месячные итоги. Где должна проходить граница с pandas?

fetchdf создаёт pandas DataFrame со всем результатом. Тяжёлое сокращение объёма лучше выполнить в DuckDB и передать через границу уже нужный аналитический grain.

05

Почему проверка первого слова SQL регулярным выражением не превращает runner в безопасную read-only песочницу?

SQL-файл должен быть доверенным и проверенным артефактом. Value binding не анализирует и не ограничивает структуру переданного SQL.

06

DataFrame зарегистрирован в одной безымянной in-memory connection, но запрос через вторую connection не видит relation. Как это объяснить?

Регистрация относится к контексту конкретного соединения. Два независимо созданных безымянных in-memory соединения не разделяют этот временный каталог.

def load_module(name: str, path: Path):
    spec = importlib.util.spec_from_file_location(name, path)
    if spec is None or spec.loader is None:
        raise RuntimeError(f"cannot load {path}")
    module = importlib.util.module_from_spec(spec)
    sys.modules[name] = module
    spec.loader.exec_module(module)
    return module


QUERY = load_module("duckdb_dataframe_query", ARTIFACT)
EXAMPLE_MODULE = load_module("duckdb_python_example", EXAMPLE)

INPUT_COLUMNS = EXAMPLE_MODULE.INPUT_COLUMNS
INPUT_DTYPES = EXAMPLE_MODULE.INPUT_DTYPES
OUTPUT_COLUMNS = EXAMPLE_MODULE.OUTPUT_COLUMNS
OUTPUT_DTYPES = EXAMPLE_MODULE.OUTPUT_DTYPES


def run_slice(
    connection: duckdb.DuckDBPyConnection,
    frame: pd.DataFrame,
    *,
    cohort_month: str = "2026-01-01",
    max_period: int = 2,
) -> pd.DataFrame:
    return QUERY.query_dataframe(
        connection,
        sql=SQL.read_text(encoding="utf-8"),
        relation_name="cohort_activity",
        frame=frame,
        parameters={"cohort_month": cohort_month, "max_period": max_period},
        expected_input_columns=INPUT_COLUMNS,
        expected_input_dtypes=INPUT_DTYPES,
        expected_output_columns=OUTPUT_COLUMNS,
        expected_output_dtypes=OUTPUT_DTYPES,
    )


class DuckDBDataFrameQueryTest(unittest.TestCase):

        self.connection = duckdb.connect()
        self.frame = EXAMPLE_MODULE.build_cohort_activity()

        self.connection.close()

    def test_reference_slice_has_expected_values_order_and_grain(self) -> None:
        result = run_slice(self.connection, self.frame)

        self.assertEqual(result["period_index"].tolist(), [0, 1, 2])
        self.assertEqual(result["active_users"].tolist(), [4, 3, 2])
        self.assertEqual(result["activity_rate"].tolist(), [1.0, 0.75, 0.5])
        self.assertFalse(result.duplicated(["cohort_month", "period_index"]).any())

        january = run_slice(self.connection, self.frame, cohort_month="2026-01-01")
        february = run_slice(self.connection, self.frame, cohort_month="2026-02-01")

        self.assertEqual(january["cohort_size"].unique().tolist(), [4])
        self.assertEqual(february["cohort_size"].unique().tolist(), [3])

        short = run_slice(self.connection, self.frame, max_period=1)
        long = run_slice(self.connection, self.frame, max_period=3)

        self.assertEqual(short["period_index"].tolist(), [0, 1])
        self.assertEqual(long["period_index"].tolist(), [0, 1, 2, 3])

    def test_bound_text_remains_a_value(self) -> None:
        payload = "x'; DROP TABLE cohort_activity; --"
        result = QUERY.execute_trusted_query(

            "SELECT ?::VARCHAR AS value",
            [payload],
            expected_columns=["value"],
            expected_dtypes={"value": "str"},
        )

        self.assertEqual(result.loc[0, "value"], payload)

        try:

                expected_columns=["chosen"],
                expected_dtypes={"chosen": "str"},

        self.assertEqual(result.loc[0, "chosen"], "active_users")

    cohort_month,
    activity_month,
    period_index::BIGINT AS period_index,
    cohort_size::BIGINT AS cohort_size,
    active_users::BIGINT AS active_users,
    activity_rate::DOUBLE AS activity_rate
FROM cohort_activity
WHERE cohort_month = $cohort_month::DATE
  AND period_index <= $max_period::BIGINT
ORDER BY period_index;

from __future__ import annotations

from collections.abc import Mapping, Sequence
from typing import Any

import duckdb
import pandas as pd

QueryParameters = Sequence[Any] | Mapping[str, Any]


class QueryContractError(ValueError):
    """Raised when a DataFrame does not satisfy a declared query contract."""


def _normalized_contract(
    expected_columns: Sequence[str],
    expected_dtypes: Mapping[str, str],
) -> tuple[list[str], dict[str, str]]:
    columns = list(expected_columns)
    dtypes = dict(expected_dtypes)

    if not columns:
        raise QueryContractError("expected_columns must not be empty")
    if len(columns) != len(set(columns)):
        raise QueryContractError("expected_columns must not contain duplicates")

    missing_dtypes = [column for column in columns if column not in dtypes]
    extra_dtypes = [column for column in dtypes if column not in columns]
    if missing_dtypes or extra_dtypes:
        raise QueryContractError(
            "dtype contract must describe exactly expected_columns; "
            f"missing={missing_dtypes}, extra={extra_dtypes}"
        )

    return columns, dtypes


def validate_dataframe_contract(
    frame: object,
    *,
    expected_columns: Sequence[str],
    expected_dtypes: Mapping[str, str],
    role: str,
) -> None:
    """Validate exact column order and pandas dtypes at an engine boundary."""

    columns, dtypes = _normalized_contract(expected_columns, expected_dtypes)
    if not isinstance(frame, pd.DataFrame):
        raise QueryContractError(f"{role} must be a pandas DataFrame")

    actual_columns = frame.columns.tolist()
    if actual_columns != columns:
        raise QueryContractError(
            f"{role} columns {actual_columns} differ from expected {columns}"
        )

    actual_dtypes = {column: str(frame[column].dtype) for column in columns}
    wrong_dtypes = {
        column: {"expected": dtypes[column], "actual": actual_dtypes[column]}
        for column in columns
        if actual_dtypes[column] != dtypes[column]
    }
    if wrong_dtypes:
        raise QueryContractError(f"{role} dtype contract violation: {wrong_dtypes}")


def execute_trusted_query(
    connection: duckdb.DuckDBPyConnection,
    sql: str,
    parameters: QueryParameters = (),
    *,
    expected_columns: Sequence[str],
    expected_dtypes: Mapping[str, str],
) -> pd.DataFrame:
    """Execute reviewed SQL with bound values and validate its pandas result."""

    columns, dtypes = _normalized_contract(expected_columns, expected_dtypes)
    bound_parameters: list[Any] | dict[str, Any] = (
        dict(parameters) if isinstance(parameters, Mapping) else list(parameters)
    )

    frame = connection.execute(sql, bound_parameters).fetchdf()
    validate_dataframe_contract(
        frame,
        expected_columns=columns,
        expected_dtypes=dtypes,
        role="query result",
    )
    return frame


def query_dataframe(
    connection: duckdb.DuckDBPyConnection,
    *,
    sql: str,
    relation_name: str,
    frame: pd.DataFrame,
    parameters: QueryParameters = (),
    expected_input_columns: Sequence[str],
    expected_input_dtypes: Mapping[str, str],
    expected_output_columns: Sequence[str],
    expected_output_dtypes: Mapping[str, str],
) -> pd.DataFrame:
    """Expose one typed DataFrame to reviewed SQL and return a checked DataFrame."""

    validate_dataframe_contract(
        frame,
        expected_columns=expected_input_columns,
        expected_dtypes=expected_input_dtypes,
        role=f"input relation {relation_name!r}",
    )

    connection.register(relation_name, frame)
    try:
        return execute_trusted_query(
            connection,
            sql,
            parameters,
            expected_columns=expected_output_columns,
            expected_dtypes=expected_output_dtypes,
        )
    finally:
        connection.unregister(relation_name)
