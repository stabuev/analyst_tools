CTE, подзапросы и композиция

Длинный SQL-запрос становится надежнее не тогда, когда его просто разбили на части, а тогда, когда у каждой части понятны назначение, набор строк и grain.

Тип: Build

Треки: Core

Пререквизиты: 04/05

Время: ~75 минут

Результат: собирает знакомые SQL-преобразования в цепочку нерекурсивных CTE, объявляет grain и population каждого этапа и выбирает форму подзапроса по ожидаемой форме результата.

Цели обучения

После урока вы сможете:

  • собрать несколько уже знакомых преобразований в один читаемый SQL-запрос;
  • объяснить, от каких предыдущих этапов зависит каждый CTE;
  • до выполнения запроса назвать population, grain и ключ промежуточного результата;
  • точечно выполнить промежуточный CTE и проверить его контракт;
  • выбрать подзапрос в FROM, scalar subquery или EXISTS по форме нужного ответа;
  • объяснить, почему CTE сам по себе не проверяет данные и не является временной таблицей;
  • безопасно искать отсутствующие соответствия через NOT EXISTS, не попадая в ловушку NOT IN и NULL.

Что уже известно

Этот урок продолжает запросы из 04/05, а не начинает новую предметную задачу. Мы считаем, что вы уже умеете:

Опора Где появилась Что понадобится сейчас
SELECT, WHERE, CASE, NULL 04/02–04/03 выбирать строки и сохранять явные состояния качества
GROUP BY, count, sum, FILTER 04/04 менять grain осознанной агрегацией
ключи, fanout и unmatched-строки 04/05 безопасно соединять отношения разного grain
предварительная агрегация order_items 04/05 получить одну строку на заказ до JOIN
суммы в разных валютах 04/04–04/05 не складывать RUB, USD, EUR и KZT в одно число

Коротко напомним два термина.

  • Population — какие именно объекты входят в результат. Например, все заказы или только оплаченные заказы.
  • Grain — что означает одна строка. Например, один заказ или одна валюта.

В 04/05 безопасная витрина строилась двумя отдельными запросами:

  1. order_items агрегировались до одной строки на order_id;
  2. orders соединялись с этим результатом и users.

Так было проще впервые увидеть правила безопасного JOIN. Теперь преобразований стало достаточно много, чтобы связать их в один запрос и при этом не потерять возможность проверить каждый этап.

Проблема

Представьте запрос, который одновременно:

  1. считает стоимость строк товаров;
  2. собирает безопасную витрину заказов;
  3. оставляет оплаченные заказы;
  4. считает итоги по валютам.

Все отдельные операции уже знакомы. Новая сложность — композиция, то есть сборка нескольких преобразований в одну связную конструкцию.

Если записать весь расчет одним вложенным выражением без имен и контрактов, ошибка может дать правдоподобный результат:

  • JOIN незаметно размножит заказы;
  • WHERE status = 'paid' окажется не на том уровне;
  • заказ без товаров исчезнет;
  • неполная сумма строк товаров будет принята за полную;
  • валюты будут сложены в одну бессмысленную сумму;
  • найти первый сломанный шаг будет трудно.

Само число в финале не сообщает, где возникла проблема. Нужна цепочка, которую можно прочитать, предсказать и проверить по частям.

Наша целевая цепочка:

text
order_items
    |
    v
item_totals          одна строка на заказ с товарами
    |
    v
safe_order_mart      одна строка на каждый заказ
    |
    v
paid_order_mart      одна строка на оплаченный заказ
    |
    v
currency_summary     одна строка на валюту

Это не последовательность команд, которые изменяют таблицы. Это граф зависимостей внутри одного SQL-выражения: каждый следующий результат определяется через предыдущие.

Концепция

1. CTE — именованное отношение внутри запроса

CTE расшифровывается как common table expression. В обычном нерекурсивном варианте это запрос, которому дали имя в секции WITH:

sql
WITH paid_orders AS (
    SELECT
        order_id,
        currency,
        amount
    FROM orders
    WHERE status = 'paid'
)
SELECT
    order_id,
    currency,
    amount
FROM paid_orders;

Внутри внешнего SELECT имя paid_orders ведет себя как имя отношения: его можно поставить в FROM, соединить с другим отношением или агрегировать.

Область действия имени ограничена одним SQL-выражением. После завершения запроса CTE не становится постоянной таблицей и сам по себе не остается в базе для следующего запроса.

2. Несколько CTE образуют граф зависимостей

CTE перечисляются через запятую. Поздний этап может обратиться к раннему:

sql
WITH
paid_orders AS (
    SELECT
        order_id,
        currency,
        amount
    FROM orders
    WHERE status = 'paid'
),
currency_summary AS (
    SELECT
        currency,
        count(*) AS paid_order_rows,
        sum(amount) AS known_paid_amount
    FROM paid_orders
    GROUP BY currency
)
SELECT
    currency,
    paid_order_rows,
    known_paid_amount
FROM currency_summary
ORDER BY currency;

Зависимость здесь направлена от paid_orders к currency_summary. Чтобы читать такой запрос, не нужно мысленно выполнять каждую строку SQL. Сначала ответьте:

  1. какое отношение производит этап;
  2. от каких отношений он зависит;
  3. что означает его строка;
  4. какие строки должны войти;
  5. какой ключ обязан быть уникальным.

3. Карточка контракта этапа

Имя делает шаг видимым, но не делает его правильным. Для каждого содержательного CTE полезно заранее заполнить короткую карточку:

Поле Контрольный вопрос
Назначение Зачем этот этап существует?
Источники От каких отношений он зависит?
Population Какие объекты входят и какие исключены?
Grain Что означает одна строка?
Ключ Какие колонки должны быть уникальны?
Единицы В чем измерены суммы и другие величины?
Проверка Какая ошибка наиболее опасна на этом шаге?

Для нашей цепочки контракт выглядит так:

CTE Population Grain и ключ Ожидаемо на учебных данных Главная проверка
item_totals заказы, у которых есть хотя бы одна строка товара одна строка на order_id 12 строк нет fanout; неполная сумма помечена
safe_order_mart все заказы одна строка на order_id 12 строк ни один заказ не потерян
paid_order_mart только status = 'paid' одна строка на order_id 9 строк population действительно сужена
currency_summary валюты оплаченных заказов одна строка на currency 4 строки суммы не смешивают валюты

Число строк — лишь одна проверка. Двенадцать строк могут содержать один заказ дважды и не содержать другой. Поэтому count нужно проверять вместе с ключом и смыслом population.

4. Чего CTE не гарантирует

CTE — способ выразить структуру запроса. Он не гарантирует, что:

  • ключ уникален;
  • строки не потерялись;
  • единицы измерения совместимы;
  • сумма полна при наличии NULL;
  • результат физически сохранен как отдельная таблица;
  • запрос автоматически станет быстрее.

Оптимизатор базы решает, как исполнять выражение. В этом уроке нас интересует не физический план, а логический контракт промежуточных отношений. Оптимизация, управление материализацией, рекурсивные CTE и разбор плана выполнения не нужны для текущего результата.

5. Подзапрос — запрос внутри другого запроса

CTE — не единственный способ составлять запросы из частей. Подзапрос помещается внутрь другого SQL-выражения. Выбор формы зависит не от длины кода, а от формы ответа, который нужен внешнему запросу.

Подзапрос в FROM: нужно отношение

Подзапрос в FROM возвращает строки и колонки. Его также называют производной таблицей (derived table):

sql
SELECT
    paid_orders.currency,
    count(*) AS paid_order_rows
FROM (
    SELECT
        order_id,
        currency
    FROM orders
    WHERE status = 'paid'
) AS paid_orders
GROUP BY paid_orders.currency;

Форма результата внутреннего запроса — таблица. Внешний запрос агрегирует ее. Такая форма удобна для короткого результата, который используется один раз. Когда этап важен для рассуждения, имеет собственный контракт или используется несколько раз, имя CTE обычно делает структуру понятнее.

Scalar subquery: нужна одна ячейка

Скалярный подзапрос (scalar subquery) используется там, где выражение ожидает одно значение:

sql
SELECT
    (SELECT count(*) FROM orders) AS source_order_rows,
    (SELECT count(*) FROM orders WHERE status = 'paid') AS source_paid_order_rows;

Его точный контракт:

  • одна колонка;
  • не более одной строки;
  • одна строка дает одно значение;
  • отсутствие строк дает NULL;
  • несколько строк вместо одной — ошибка.

Например, выражение ниже ошибочно, потому что заказов несколько:

sql
SELECT
    (SELECT order_id FROM orders) AS one_order_id;

Не следует маскировать проблему случайным LIMIT 1. Сначала нужно понять, почему по смыслу ожидалось одно значение и какое правило действительно выбирает единственную строку.

EXISTS: нужен ответ «есть ли хотя бы одна строка»

EXISTS превращает результат подзапроса в логическое значение:

sql
SELECT EXISTS (
    SELECT 1
    FROM orders
    WHERE status = 'paid'
) AS has_paid_orders;

TRUE означает, что подзапрос нашел хотя бы одну строку. Значение после SELECT внутри EXISTS не используется; запись SELECT 1 подчеркивает, что нам важен сам факт существования.

Подзапрос может ссылаться на строку внешнего запроса. Тогда он называется коррелированным:

sql
SELECT
    o.order_id,
    o.user_id
FROM orders AS o
WHERE o.user_id IS NOT NULL
  AND NOT EXISTS (
      SELECT 1
      FROM users AS u
      WHERE u.user_id = o.user_id
  );

Для каждой строки orders условие спрашивает: «существует ли пользователь с тем же user_id?» NOT EXISTS оставляет заказ, если такого пользователя нет.

На учебных данных это выявляет заказ O1010 со ссылкой на отсутствующего пользователя U999. Отдельная проверка o.user_id IS NOT NULL отличает два разных состояния:

  • идентификатор не заполнен;
  • идентификатор заполнен, но объекта с таким ключом нет.

EXISTS полезен, когда нужны строки левой стороны, а от правой стороны требуется только факт совпадения. Он не добавляет колонки правой таблицы и не размножает левую строку множеством совпадений.

6. Почему NOT IN опасен при NULL

На первый взгляд поиск отсутствующих ключей можно записать так:

sql
SELECT
    order_id,
    user_id
FROM orders
WHERE user_id NOT IN (
    SELECT user_id
    FROM users
);

Но если подзапрос вернет хотя бы один NULL, результат может неожиданно не содержать ни одной строки. Причина — трехзначная логика из 04/03.

Проверка x NOT IN (a, b, NULL) по смыслу требует доказать, что x не равен каждому элементу. Сравнение x <> NULL дает не TRUE, а UNKNOWN. Строка проходит через WHERE только при TRUE, поэтому UNKNOWN отбрасывается.

Для поиска отсутствия соответствия обычно яснее и безопаснее выразить намерение через NOT EXISTS и явное условие сопоставления.

7. Как выбрать форму

Сначала сформулируйте форму нужного ответа:

Что нужно внешнему запросу Подходящая форма Пример
именованный проверяемый этап CTE безопасная витрина заказов
отношение, используемое один раз подзапрос в FROM короткая фильтрация перед агрегацией
одно значение scalar subquery число исходных заказов
факт существования совпадения EXISTS есть ли оплаченные заказы
факт отсутствия совпадения NOT EXISTS заказы с несуществующим пользователем

Нет правила «CTE всегда лучше подзапроса» или наоборот. Важна точность контракта. Если вы ожидаете таблицу, не притворяйтесь, что это одно значение. Если нужен только факт совпадения, не создавайте JOIN, колонки которого не используете.

Соберите это

Сначала соберем цепочку без нового синтаксиса. Для каждого шага запишем вход, изменение и выход.

Шаг 1. item_totals

Вход: строки товаров, несколько строк могут относиться к одному заказу.

Изменение: группировка по order_id.

Выход: одна строка на заказ, у которого есть товары.

Кроме суммы, сохраняем:

  • сколько строк товаров было;
  • для скольких строк можно было вычислить quantity * unit_price;
  • полна ли итоговая сумма.

Последний признак важен: sum пропускает NULL. Число может выглядеть правдоподобно, даже если часть слагаемых неизвестна.

Шаг 2. safe_order_mart

Вход: все заказы, агрегированные товары, пользователи.

Изменение: два LEFT JOIN.

Выход: одна строка на каждый заказ.

LEFT JOIN нужен, чтобы отсутствие товара или пользователя осталось видимым состоянием, а не удалило заказ. Состояния из 04/05 сохраняются:

  • item_match_state;
  • user_match_state;
  • amount_reconciliation_state.

Шаг 3. paid_order_mart

Вход: безопасная витрина всех заказов.

Изменение: фильтр status = 'paid'.

Выход: одна строка на оплаченный заказ.

Это первый этап, который намеренно сужает population с 12 до 9 строк. Grain при этом не меняется: строка по-прежнему означает один заказ.

Шаг 4. currency_summary

Вход: оплаченные заказы.

Изменение: группировка по currency.

Выход: одна строка на валюту.

Grain меняется осознанно. Вместе с известной суммой сохраняются показатели качества:

  • сколько оплаченных заказов содержит известный amount;
  • сколько amount отсутствует;
  • сколько заказов осталось без товаров;
  • сколько ссылается на отсутствующего пользователя;
  • сколько сумм расходится с товарами;
  • сколько товарных итогов неполны.

Мы не создаем одну сумму по всем валютам. Числа в RUB, USD, EUR и KZT имеют разные единицы и без правила конвертации несопоставимы.

Используйте это

Готовая цепочка находится в outputs/checked_order_pipeline.sql.

sql
WITH
item_totals AS (
    SELECT
        order_id,
        count(*) AS item_rows,
        count(quantity * unit_price) AS known_item_amount_rows,
        sum(quantity * unit_price) AS item_total,
        count(*) = count(quantity * unit_price) AS item_amount_complete
    FROM order_items
    GROUP BY order_id
),
safe_order_mart AS (
    SELECT
        o.order_id,
        o.user_id,
        o.status,
        o.currency,
        o.amount,
        i.item_rows,
        i.known_item_amount_rows,
        i.item_total,
        i.item_amount_complete,
        CASE
            WHEN i.order_id IS NULL THEN 'no_items'
            ELSE 'matched'
        END AS item_match_state,
        CASE
            WHEN o.user_id IS NULL THEN 'missing_reference'
            WHEN u.user_id IS NULL THEN 'orphan_reference'
            ELSE 'matched'
        END AS user_match_state,
        CASE
            WHEN i.order_id IS NULL AND o.amount IS NULL THEN 'both_missing'
            WHEN i.order_id IS NULL THEN 'item_total_missing'
            WHEN NOT i.item_amount_complete THEN 'item_total_incomplete'
            WHEN o.amount IS NULL THEN 'order_amount_missing'
            WHEN o.amount = i.item_total THEN 'matches'
            ELSE 'differs'
        END AS amount_reconciliation_state
    FROM orders AS o
    LEFT JOIN item_totals AS i
        ON o.order_id = i.order_id
    LEFT JOIN users AS u
        ON o.user_id = u.user_id
),
paid_order_mart AS (
    SELECT
        order_id,
        user_id,
        currency,
        amount,
        item_rows,
        known_item_amount_rows,
        item_total,
        item_amount_complete,
        item_match_state,
        user_match_state,
        amount_reconciliation_state
    FROM safe_order_mart
    WHERE status = 'paid'
),
currency_summary AS (
    SELECT
        currency,
        count(*) AS paid_order_rows,
        count(amount) AS paid_known_amount_rows,
        count(*) - count(amount) AS paid_missing_amount_rows,
        sum(amount) AS known_paid_amount,
        count(*) FILTER (
            WHERE item_match_state = 'no_items'
        ) AS orders_without_items,
        count(*) FILTER (
            WHERE user_match_state = 'orphan_reference'
        ) AS orphan_user_orders,
        count(*) FILTER (
            WHERE amount_reconciliation_state = 'differs'
        ) AS amount_mismatch_orders,
        count(*) FILTER (
            WHERE amount_reconciliation_state = 'item_total_incomplete'
        ) AS incomplete_item_total_orders
    FROM paid_order_mart
    GROUP BY currency
)
SELECT
    currency,
    paid_order_rows,
    paid_known_amount_rows,
    paid_missing_amount_rows,
    known_paid_amount,
    orders_without_items,
    orphan_user_orders,
    amount_mismatch_orders,
    incomplete_item_total_orders
FROM currency_summary
ORDER BY currency;

Обратите внимание на три решения.

  1. Этапы названы по смыслу результата, а не cte1, cte2, data.
  2. Колонки перечислены явно. Контракт следующего этапа не меняется случайно при добавлении колонки в предыдущий.
  3. Комментарии в артефакте фиксируют population и grain рядом с определением этапа.

Для подзапросов есть небольшой сопутствующий артефакт outputs/subquery_audit.sql:

sql
SELECT
    (SELECT count(*) FROM orders) AS source_order_rows,
    (SELECT count(*) FROM orders WHERE status = 'paid') AS source_paid_order_rows,
    EXISTS (
        SELECT 1
        FROM orders AS o
        WHERE o.user_id IS NOT NULL
          AND NOT EXISTS (
              SELECT 1
              FROM users AS u
              WHERE u.user_id = o.user_id
          )
    ) AS has_orphan_user_reference;

Он возвращает одну строку аудита:

source_order_rows source_paid_order_rows has_orphan_user_reference
12 9 TRUE

Здесь два scalar subquery дают по одному числу, а EXISTS дает один логический ответ. Это уместно для компактной сводки. Сам pipeline остается отношением из нескольких строк, поэтому его не нужно упаковывать в scalar subquery.

Сломайте это

Ошибка 1. CTE получил имя, но не контракт

sql
WITH data1 AS (...),
data2 AS (...)
SELECT ...

Такая запись разбила текст, но не помогла рассуждать. По именам нельзя восстановить population, grain и изменение. Исправление — именовать результат, а не порядковый номер: item_totals, paid_order_mart, currency_summary.

Ошибка 2. Фильтр перенесли до проверки сохранности заказов

Если оплаченные заказы отфильтрованы до safe_order_mart, уже нельзя проверить, что соединение сохранило все исходные заказы. Иногда ранний фильтр корректен, но тогда population этапа должна быть объявлена как «оплаченные заказы», а не «все заказы».

В нашей цепочке разделение намеренное:

  • safe_order_mart проверяет безопасность соединения на всех 12 заказах;
  • paid_order_mart отдельно сужает population до 9 оплаченных.

Ошибка 3. У заказа исчезли все товары

Тогда item_totals больше не содержит этот order_id. Это не причина удалять заказ. LEFT JOIN сохраняет его в safe_order_mart, а item_match_state = 'no_items' делает проблему наблюдаемой.

Если удалить товар заказа O1012, ожидаем:

  • в item_totals 11 строк;
  • в safe_order_mart по-прежнему 12 строк;
  • у O1012 состояние no_items;
  • в строке EUR итогового отчета orders_without_items = 1.

Ошибка 4. Одна товарная сумма стала неполной

Если у одной позиции неизвестен unit_price, обычный sum(quantity * unit_price) пропустит ее. Получившееся число нельзя сравнивать с orders.amount как полный итог.

Пара:

sql
count(*) AS item_rows,
count(quantity * unit_price) AS known_item_amount_rows

позволяет заметить потерю. При различии counts флаг item_amount_complete становится FALSE, а состояние — item_total_incomplete.

Ошибка 5. Scalar subquery вернул несколько строк

sql
SELECT
    (SELECT order_id FROM orders) AS order_id;

Внутренний запрос не соответствует форме «одно значение». Правильное исправление зависит от намерения:

  • если нужны все заказы — использовать отношение в FROM;
  • если нужно число заказов — агрегировать через count(*);
  • если нужен факт наличия — использовать EXISTS;
  • если действительно нужен один конкретный заказ — сформулировать детерминированное правило его выбора.

Ошибка 6. NOT IN встретил NULL

Добавьте NULL в набор идентификаторов правой стороны. NOT IN может вернуть пустой результат даже при наличии U999, а коррелированный NOT EXISTS продолжит находить отсутствующее соответствие. Это не особенность CTE, а следствие логики сравнений с NULL.

Ошибка 7. В финале появилась общая денежная сумма

Строки currency_summary имеют одну строку на валюту. Складывать их sum(known_paid_amount) без пересчета в общую валюту нельзя. Такой результат будет арифметически вычислимым, но аналитически бессмысленным.

Что сознательно не входит в урок

  • Рекурсивные CTE. Они решают другие задачи: обход иерархий и повторяющиеся вычисления. Для композиции аналитического pipeline не нужны.
  • Настройки materialization. Сначала нужен корректный логический запрос; физическое исполнение изучают при реальной задаче производительности.
  • EXPLAIN и планы запросов. Это отдельный инструмент диагностики производительности, а не способ доказать корректность grain.
  • Загрузка CSV и Python API DuckDB. Отношения уже подготовлены предыдущими уроками.
  • CLI. Артефакт урока — SQL-запрос, и оболочка командной строки не делает его понятнее или полезнее.
  • Полный каталог подзапросов. В основном маршруте достаточно трех форм: relation, одно значение и существование строки.

Ключевые термины

Термин Человеческое объяснение Важная граница
CTE именованный результат запроса внутри WITH не постоянная и не временная таблица
Нерекурсивный CTE этап, который не обращается к самому себе рекурсивные графы здесь не изучаются
Композиция сборка результата из зависимых реляционных преобразований порядок текста не заменяет контракт
Population какие объекты входят в отношение фильтр меняет population
Grain что означает одна строка агрегация меняет grain
Derived table подзапрос в FROM, возвращающий отношение обычно получает псевдоним
Scalar subquery подзапрос в позиции одного значения одна колонка и не более одной строки
Correlated subquery подзапрос, ссылающийся на текущую внешнюю строку полезен для проверки совпадения
EXISTS проверка, нашлась ли хотя бы одна строка не возвращает колонки найденной строки
NOT EXISTS проверка отсутствия совпадения обычно безопаснее NOT IN при возможном NULL

Quiz · 5 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

Что сам по себе гарантирует нерекурсивный CTE?

CTE помогает описать и переиспользовать именованное отношение внутри одного выражения, но не создает таблицу и не проверяет контракт данных.

02

Промежуточный набор paid_orders нужен один раз как источник в FROM. Какая форма точно соответствует ожидаемому результату?

Подзапрос в FROM возвращает отношение: строки и столбцы, к которым внешний запрос обращается как к таблице.

03

Что произойдет, если scalar subquery вместо одной строки вернет несколько?

Скалярный подзапрос должен дать одну колонку и не более одной строки; несколько строк нарушают его контракт.

04

Нужно найти заказы, для которых нет пользователя, не размножая строки orders. Что выбрать?

NOT EXISTS отвечает только на вопрос о существовании совпадения и сохраняет одну внешнюю строку на заказ.

05

Почему NOT IN может неожиданно не вернуть ни одной строки, если подзапрос содержит NULL?

Из-за трехзначной логики наличие NULL в правом наборе может сделать проверку принадлежности неизвестной; для поиска отсутствия обычно безопаснее NOT EXISTS.

        LESSON.prepare_relations(self.connection)

    def stage(self, name: str, key: str) -> tuple[list[str], list[tuple]]:
        columns, _, rows = LESSON.execute_stage(
            self.connection,
            name,
            order_by=key,
        )
        return columns, rows

        return LESSON.execute_pipeline(self.connection)

    def test_pipeline_has_four_named_stages_in_dependency_order(self) -> None:
        query = PIPELINE_PATH.read_text(encoding="utf-8")
        positions = [
            query.index(f"{stage} AS")
            for stage in (
                "item_totals",
                "safe_order_mart",
                "paid_order_mart",
                "currency_summary",
            )
        ]
        self.assertEqual(positions, sorted(positions))

    def test_every_stage_preserves_its_declared_grain(self) -> None:
        expectations = {
            "item_totals": ("order_id", 12),
            "safe_order_mart": ("order_id", 12),
            "paid_order_mart": ("order_id", 9),
            "currency_summary": ("currency", 4),
        }
        for stage, (key, expected_rows) in expectations.items():
            columns, rows = self.stage(stage, key)
            values = [row[columns.index(key)] for row in rows]
            self.assertEqual(len(rows), expected_rows, stage)
            self.assertEqual(len(set(values)), expected_rows, stage)

def _schema(connection: duckdb.DuckDBPyConnection, relation: str) -> dict[str, str]:
    return {row[0]: str(row[1]) for row in connection.execute(f"DESCRIBE {relation}").fetchall()}


def _require_columns(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    required: dict[str, str],
) -> None:
    actual = _schema(connection, relation)
    for column, expected_type in required.items():
        if column not in actual:
            raise ValueError(f"{relation} is missing required column {column}")
        if actual[column] != expected_type:
            raise ValueError(f"{relation}.{column} must be {expected_type}, got {actual[column]}")


def _validate_grain(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    key: tuple[str, ...],
) -> None:
    key_sql = ", ".join(key)
    missing_condition = " OR ".join(f"{column} IS NULL OR trim({column}) = ''" for column in key)
    missing = connection.execute(
        f"SELECT count(*) FROM {relation} WHERE {missing_condition}"
    ).fetchone()[0]
    if missing:
        raise ValueError(f"{relation} grain {key} contains NULL or blank values")

    duplicate = connection.execute(
        f"""
        SELECT {key_sql}
        FROM {relation}
        GROUP BY {key_sql}
        HAVING count(*) > 1
        LIMIT 1
        """
    ).fetchone()
    if duplicate is not None:
        raise ValueError(f"{relation} grain violation for {key}: {duplicate}")


def validate_input(connection: duckdb.DuckDBPyConnection) -> None:
    _require_columns(
        connection,
        "orders",
        {
            "order_id": "VARCHAR",
            "user_id": "VARCHAR",
            "status": "VARCHAR",
            "currency": "VARCHAR",
            "amount": "DECIMAL(18,2)",
        },
    )
    _require_columns(connection, "users", {"user_id": "VARCHAR"})
    _require_columns(
        connection,
        "order_items",
        {
            "order_id": "VARCHAR",
            "product_id": "VARCHAR",
            "quantity": "INTEGER",
            "unit_price": "DECIMAL(18,2)",
        },
    )
    _validate_grain(connection, "orders", ("order_id",))
    _validate_grain(connection, "users", ("user_id",))
    _validate_grain(connection, "order_items", ("order_id", "product_id"))


def read_pipeline(query_path: Path = PIPELINE_PATH) -> str:
    query = query_path.read_text(encoding="utf-8")
    if query.count(FINAL_MARKER) != 1:
        raise ValueError(f"pipeline must contain exactly one {FINAL_MARKER!r} marker")
    return query


def _with_clause(query: str) -> str:
    return query.split(FINAL_MARKER, maxsplit=1)[0].rstrip()


def execute_stage(
    connection: duckdb.DuckDBPyConnection,
    stage: str,
    *,
    order_by: str,
    query: str | None = None,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    allowed_stages = {
        "item_totals",
        "safe_order_mart",
        "paid_order_mart",
        "currency_summary",
    }
    if stage not in allowed_stages:
        raise ValueError(f"unknown pipeline stage: {stage}")
    pipeline = query or read_pipeline()
    relation = connection.execute(
        f"{_with_clause(pipeline)}\nSELECT * FROM {stage} ORDER BY {order_by}"
    )
    columns = [column[0] for column in relation.description]
    types = [str(column[1]) for column in relation.description]
    return columns, types, relation.fetchall()


def execute_pipeline(
    connection: duckdb.DuckDBPyConnection,
    query: str | None = None,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    relation = connection.execute(query or read_pipeline())
    columns = [column[0] for column in relation.description]
    types = [str(column[1]) for column in relation.description]
    return columns, types, relation.fetchall()


def validate_pipeline(
    connection: duckdb.DuckDBPyConnection,
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
) -> None:
    if columns != EXPECTED_FINAL_COLUMNS:
        raise ValueError(f"pipeline columns must be {EXPECTED_FINAL_COLUMNS}, got {columns}")
    if types != EXPECTED_FINAL_TYPES:
        raise ValueError(f"pipeline types must be {EXPECTED_FINAL_TYPES}, got {types}")

    stage_contracts = {
        "item_totals": ("order_id", 12, 12),
        "safe_order_mart": ("order_id", 12, 12),
        "paid_order_mart": ("order_id", 9, 9),
        "currency_summary": ("currency", 4, 4),
    }
    for stage, (key, expected_rows, expected_keys) in stage_contracts.items():
        stage_columns, _, stage_rows = execute_stage(
            connection,
            stage,
            order_by=key,
        )
        key_position = stage_columns.index(key)
        keys = [row[key_position] for row in stage_rows]
        if len(stage_rows) != expected_rows or len(set(keys)) != expected_keys:
            raise ValueError(
                f"{stage} must have {expected_rows} rows and {expected_keys} unique {key}"
            )

    currencies = [row[0] for row in rows]
    if currencies != sorted(currencies) or len(currencies) != len(set(currencies)):
        raise ValueError("final result must have one ordered row per currency")


def execute_subquery_audit(
    connection: duckdb.DuckDBPyConnection,
    query_path: Path = SUBQUERY_AUDIT_PATH,
) -> dict[str, Any]:
    relation = connection.execute(query_path.read_text(encoding="utf-8"))
    columns = [column[0] for column in relation.description]
    row = relation.fetchone()
    return dict(zip(columns, row, strict=True))


def _json_value(value: Any) -> Any:
    if isinstance(value, Decimal):
        return str(value)
    return value


def run_example() -> dict[str, Any]:
    with duckdb.connect() as connection:
        prepare_relations(connection)
        validate_input(connection)
        columns, types, rows = execute_pipeline(connection)
        validate_pipeline(connection, columns, types, rows)
        stage_counts = {}
        for stage, key in (
            ("item_totals", "order_id"),
            ("safe_order_mart", "order_id"),
            ("paid_order_mart", "order_id"),
            ("currency_summary", "currency"),
        ):
            _, _, stage_rows = execute_stage(
                connection,
                stage,
                order_by=key,
            )
            stage_counts[stage] = len(stage_rows)
        return {
            "stage_rows": stage_counts,
            "subquery_audit": execute_subquery_audit(connection),
            "currency_summary": [
                {column: _json_value(value) for column, value in zip(columns, row, strict=True)}
                for row in rows
            ],
        }


def main() -> None:
    print(json.dumps(run_example(), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

WITH
item_totals AS (
    -- population: заказы, у которых есть хотя бы одна строка товара
    -- grain: одна строка на order_id
    SELECT
        order_id,
        count(*) AS item_rows,
        count(quantity * unit_price) AS known_item_amount_rows,
        sum(quantity * unit_price) AS item_total,
        count(*) = count(quantity * unit_price) AS item_amount_complete
    FROM order_items
    GROUP BY order_id
),
safe_order_mart AS (
    -- population: все заказы
    -- grain: одна строка на order_id
    SELECT
        o.order_id,
        o.user_id,
        o.status,
        o.currency,
        o.amount,
        i.item_rows,
        i.known_item_amount_rows,
        i.item_total,
        i.item_amount_complete,
        CASE
            WHEN i.order_id IS NULL THEN 'no_items'
            ELSE 'matched'
        END AS item_match_state,
        CASE
            WHEN o.user_id IS NULL THEN 'missing_reference'
            WHEN u.user_id IS NULL THEN 'orphan_reference'
            ELSE 'matched'
        END AS user_match_state,
        CASE
            WHEN i.order_id IS NULL AND o.amount IS NULL THEN 'both_missing'
            WHEN i.order_id IS NULL THEN 'item_total_missing'
            WHEN NOT i.item_amount_complete THEN 'item_total_incomplete'
            WHEN o.amount IS NULL THEN 'order_amount_missing'
            WHEN o.amount = i.item_total THEN 'matches'
            ELSE 'differs'
        END AS amount_reconciliation_state
    FROM orders AS o
    LEFT JOIN item_totals AS i
        ON o.order_id = i.order_id
    LEFT JOIN users AS u
        ON o.user_id = u.user_id
),
paid_order_mart AS (
    -- population: только оплаченные заказы
    -- grain: одна строка на order_id
    SELECT
        order_id,
        user_id,
        currency,
        amount,
        item_rows,
        known_item_amount_rows,
        item_total,
        item_amount_complete,
        item_match_state,
        user_match_state,
        amount_reconciliation_state
    FROM safe_order_mart
    WHERE status = 'paid'
),
currency_summary AS (
    -- population: валюты, встречающиеся среди оплаченных заказов
    -- grain: одна строка на currency
    SELECT
        currency,
        count(*) AS paid_order_rows,
        count(amount) AS paid_known_amount_rows,
        count(*) - count(amount) AS paid_missing_amount_rows,
        sum(amount) AS known_paid_amount,
        count(*) FILTER (
            WHERE item_match_state = 'no_items'
        ) AS orders_without_items,
        count(*) FILTER (
            WHERE user_match_state = 'orphan_reference'
        ) AS orphan_user_orders,
        count(*) FILTER (
            WHERE amount_reconciliation_state = 'differs'
        ) AS amount_mismatch_orders,
        count(*) FILTER (
            WHERE amount_reconciliation_state = 'item_total_incomplete'
        ) AS incomplete_item_total_orders
    FROM paid_order_mart
    GROUP BY currency
)
-- FINAL RESULT
SELECT
    currency,
    paid_order_rows,
    paid_known_amount_rows,
    paid_missing_amount_rows,
    known_paid_amount,
    orders_without_items,
    orphan_user_orders,
    amount_mismatch_orders,
    incomplete_item_total_orders
FROM currency_summary
ORDER BY currency;
