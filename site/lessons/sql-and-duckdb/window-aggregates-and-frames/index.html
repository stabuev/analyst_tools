Проверка перед уроком

Ответьте до чтения: результат поможет заметить исходные предположения.

01

Что задают PARTITION BY currency и ORDER BY ordered_at, order_id внутри уже знакомого оконного контракта?

PARTITION BY выбирает независимые разделы расчёта, а оконный ORDER BY задаёт положение строк внутри них. Они не меняют grain сами по себе и не гарантируют порядок финальной выдачи.

02

В группе находятся три заказа с amount 100, NULL и 50. Что вернут COUNT(*) и COUNT(amount)?

COUNT(*) считает все три строки, а COUNT(amount) — только два известных значения. То же различие сохраняется внутри оконной рамки.

Оконные агрегаты и рамки: накопительные и скользящие расчёты

Раздел отвечает, какие строки относятся к одной задаче; порядок — где находится текущая строка; рамка — какие строки относительно неё прямо сейчас входят в агрегат.

Тип: Build Треки: Core Пререквизиты: 04/07 Время: ~120 минут Результат: сохраняет grain заказов, строит общий, накопительный и скользящий агрегаты с явной рамкой, контролирует включение текущей строки и NULL-знаменатель и объясняет различие ROWS, RANGE и рамки по умолчанию.

Цели обучения

После урока вы сможете:

  • превратить знакомые SUM, AVG и COUNT в оконные агрегаты, не сворачивая строки;
  • отдельно сформулировать partition, order и frame для рабочего вопроса;
  • отличить итог всей partition от накопительного итога до текущей строки;
  • построить скользящий расчёт по последним N строкам через ROWS;
  • явно решить, входит ли текущая строка в её собственный baseline;
  • объяснить, почему рамка на начале или конце partition может содержать меньше N строк;
  • публиковать размер frame и число известных значений рядом со средним;
  • предсказать скачок неявной RANGE-рамки на строках-peers;
  • выбрать между позиционной семантикой ROWS и диапазоном значений RANGE;
  • проверить, что оконный расчёт сохранил grain, типы, единицы измерения и порядок.

На что опирается урок

Это не второй независимый обзор оконных функций. Урок продолжает конкретные механизмы, которые уже были построены:

Что уже известно Где пройдено Как используется сейчас
grain описывает смысл одной строки 03/01, 04/01 до и после окна остаётся одна строка на оплаченный order_id
NULL не равен нулю или пустой строке 04/03 неизвестная сумма не подменяется нулём внутри rolling average
COUNT(*) и COUNT(amount) имеют разные знаменатели 04/04 различаем размер frame и число известных сумм
SUM и AVG пропускают NULL-аргументы 04/04 рядом с агрегатом публикуем число известных значений
суммы разных валют нельзя складывать вместе 04/04, 04/05 денежные окна разделяются по currency
CTE — именованный этап со своим population и grain 04/06 сначала выбираем оплаченные заказы, затем добавляем оконные столбцы
окно сохраняет строки, а PARTITION BY задаёт независимые разделы 04/07 агрегаты добавляются к заказам без GROUP BY
оконный ORDER BY задаёт положение, но не порядок выдачи 04/07 расчёт и опубликованная сортировка проверяются отдельно
peers равны по всем ключам оконного порядка 04/07 объясняем, почему RANGE может включить несколько строк одновременно
tie-breaker делает позиционную последовательность однозначной 04/07 ROWS использует порядок ordered_at, order_id

ordered_at снова приходит в артефакт уже типизированным как TIMESTAMPTZ. Мы используем его только как сравнимый ключ порядка. Разбор строк, выбор бизнес-timezone и календарные дни начнутся в следующем уроке. Поэтому здесь нет временных рамок вроде RANGE BETWEEN INTERVAL 7 DAYS PRECEDING ...: сначала нужно понять frame без второй одновременно новой темы.

Проблема

Таблица orders имеет grain:

text
одна строка = один order_id

Для каждой оплаченной покупки нужно сохранить сам заказ и добавить:

  1. общую известную сумму оплаченных заказов в той же валюте;
  2. накопительную известную сумму к моменту текущего заказа;
  3. среднюю известную сумму текущего и двух предыдущих заказов в валюте;
  4. среднюю сумму трёх предыдущих заказов, не включая текущий;
  5. количество строк и известных сумм в каждом скользящем расчёте.

Здесь независимый поток задаёт PARTITION BY currency. Поэтому «предыдущие заказы» — это предыдущие оплаченные заказы всего магазина в той же валюте, независимо от покупателя. user_id остаётся в результате для идентификации заказа, но не входит в partition. Такой расчёт описывает недавний уровень заказов магазина, а не личную историю пользователя.

Для вопроса о предыдущих покупках конкретного человека понадобился бы другой контракт, например PARTITION BY user_id, currency, и достаточная история каждого пользователя. Менять partition незаметно нельзя: вместе с ним меняется смысл метрики.

Эти вопросы похожи, но используют разные множества строк:

text
вся currency partition
начало partition ... текущая строка
две предыдущие строки ... текущая строка
три предыдущие строки ... одна предыдущая строка

Почему GROUP BY недостаточно

Так можно получить итог по валюте:

sql
SELECT
    currency,
    sum(amount) AS total_known_amount
FROM orders
WHERE status = 'paid'
GROUP BY currency;

Но grain изменится:

text
до:    одна строка на order_id
после: одна строка на currency

У результата больше нет order_id, времени и текущей суммы. Такой итог полезен как отдельная витрина, но не позволяет показать, каким был накопительный результат на каждой строке.

Оконный агрегат использует знакомую функцию, но добавляет OVER:

sql
sum(amount) OVER (
    PARTITION BY currency
) AS currency_total_known_amount

Теперь итог валюты повторяется рядом с каждой строкой этой валюты. Заказы не сворачиваются.

Почему одного partition и order уже недостаточно

Из предыдущего урока знакомо окно:

sql
PARTITION BY currency
ORDER BY ordered_at, order_id

Оно отвечает:

  • какие строки не смешиваются между собой;
  • какая строка первая, вторая и следующая.

Но оно ещё не отвечает, что должен увидеть AVG:

  • всю валютную partition;
  • всё от начала до текущего заказа;
  • только последние три заказа;
  • только три заказа перед текущим;
  • текущую строку и одну следующую;
  • строки в определённом диапазоне значений времени или другого ключа.

Эту третью часть контракта задаёт window frame — рамка окна.

Правдоподобные ошибки

Ошибки frame опасны тем, что SQL выполняется и возвращает аккуратные числа:

  • накопительная сумма без явной рамки скачком включает все строки с одинаковым ключом;
  • «последние три заказа» на первой строке фактически содержат одну строку, но публикуются как полноценное трёхстрочное окно;
  • AVG(amount) по трём строкам получает знаменатель два из-за одного NULL, а название говорит «среднее трёх заказов»;
  • baseline «предыдущие три заказа» включает текущий заказ и становится зависимым от значения, с которым его сравнивают;
  • без PARTITION BY currency складываются рубли, доллары, евро и тенге;
  • last_value(order_id) считается последней строкой пользователя, хотя функция видит только frame до текущей строки;
  • ROWS и RANGE используются как взаимозаменяемые варианты синтаксиса, хотя отвечают на разные вопросы.

Поэтому в этом уроке рамка является частью бизнес-контракта, а не необязательной настройкой функции.

Концепция

1. Обычный агрегат и оконный агрегат используют одну функцию по-разному

Сравните две формы:

sql
-- Новый grain: одна строка на currency
SELECT
    currency,
    sum(amount)
FROM paid_orders
GROUP BY currency;
sql
-- Исходный grain: одна строка на order_id
SELECT
    order_id,
    currency,
    amount,
    sum(amount) OVER (
        PARTITION BY currency
    ) AS currency_total_known_amount
FROM paid_orders;

Во втором запросе SUM не стал другой арифметической функцией. Изменился контекст:

text
GROUP BY:
несколько строк -> одна строка результата

SUM(...) OVER (...):
для каждой текущей строки определить контекст
-> посчитать агрегат по этому контексту
-> записать значение к текущей строке

Поэтому оконные SUM, AVG, COUNT, MIN и MAX сохраняют строки, если другие части запроса не меняют их. Но они не исправляют grain входа: если предыдущий JOIN уже размножил заказ по товарным позициям, окно честно агрегирует размноженные строки.

2. У оконного агрегата три независимых вопроса

Полный контракт удобно читать сверху вниз:

sql
avg(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
Часть Вопрос Ответ примера
PARTITION BY какие строки относятся к независимым задачам? заказы одной валюты
ORDER BY где находится текущая строка? хронология с tie-breaker order_id
ROWS BETWEEN ... какие позиции около текущей участвуют? текущая и две предыдущие

Короткая модель:

text
partition = весь отдельный коридор
order     = координата строки в коридоре
frame     = подвижный участок коридора для текущего расчёта

Partition обычно одна для многих строк. Frame пересчитывается для каждой текущей строки.

3. Frame движется вместе с текущей строкой

Пусть внутри одной currency строки уже упорядочены:

text
A -> B -> C -> D -> E

Для:

sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

рамки будут:

text
current=A: [A]
current=B: [A, B]
current=C: [A, B, C]
current=D: [B, C, D]
current=E: [C, D, E]

Это не один общий набор из трёх строк. Для каждой текущей строки окно сдвигается.

На границе partition рамка обрезается. SQL не создаёт две вымышленные строки перед A. Поэтому первые строки имеют неполную историю:

Текущая строка Запрошенный размер Реальный размер
A 3 1
B 3 2
C 3 3

Если полнота истории важна для сравнения, её нужно проверить явно:

sql
count(*) OVER recent_3_rows AS recent_3_order_rows

4. Границы frame читаются относительно текущей строки

Основные обозначения:

Граница Обычный смысл
UNBOUNDED PRECEDING самое начало partition
3 PRECEDING позиция или значение на расстоянии три назад
1 PRECEDING непосредственно предыдущая позиция или диапазон
CURRENT ROW текущая позиция; для RANGE также её peers
1 FOLLOWING следующая позиция или диапазон
UNBOUNDED FOLLOWING самый конец partition

Frame задаётся началом и концом:

sql
ROWS BETWEEN <начало> AND <конец>

Начало не может находиться после конца. Например, конструкция от 1 FOLLOWING до CURRENT ROW противоречива.

5. Четыре полезных контракта не являются синонимами

Итог всей partition

sql
sum(amount) OVER (
    PARTITION BY currency
)

При отсутствии оконного ORDER BY default frame охватывает всю partition. Все строки одной валюты получают один и тот же итог.

Накопительный итог

sql
sum(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)

Каждая строка видит всё от начала валютной последовательности до себя.

Текущая и две предыдущие строки

sql
avg(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)

Текущий amount входит в своё скользящее среднее.

Только три предыдущие строки

sql
avg(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
)

Текущая строка исключена. В нашем контракте такой frame сравнивает покупку с недавним потоком заказов магазина в той же валюте. Иначе baseline уже содержит проверяемое значение. Это не baseline личного поведения покупателя: для него нужна partition по user_id.

6. ROWS считает позиции

ROWS выбирает физические позиции в логическом оконном порядке:

sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

означает:

text
не более двух предыдущих строк + текущая строка

Это не означает:

  • два предыдущих дня;
  • значения ключа в пределах двух единиц;
  • две предыдущие группы peers;
  • обязательно три строки на границе partition.

Позиционная рамка требует однозначного порядка. Поэтому основной артефакт использует:

sql
ORDER BY ordered_at, order_id

ordered_at задаёт бизнес-хронологию, а уникальный order_id разрешает одинаковые timestamps. Без tie-breaker непонятно, какая из равных строк является «предыдущей позицией».

7. RANGE выбирает диапазон значений порядка

Для маленького числового примера:

sql
ORDER BY sort_key
RANGE BETWEEN 1 PRECEDING AND CURRENT ROW

строка с sort_key = 4 видит строки, у которых:

text
sort_key находится от 3 до 4

Если в данных нет ключа 3, предыдущая физическая строка с ключом 2 не входит.

При тех же данных:

sql
ROWS BETWEEN 1 PRECEDING AND CURRENT ROW

возьмёт текущую строку с ключом 4 и физически предыдущую строку с ключом 2.

Следовательно:

text
ROWS  -> расстояние в позициях
RANGE -> расстояние в значениях ORDER BY

Для RANGE с числовым или временным смещением DuckDB требует ровно одно выражение порядка, поддерживающее вычитание. Несколько выражений допустимы, когда используются только границы UNBOUNDED PRECEDING, UNBOUNDED FOLLOWING и CURRENT ROW. Поэтому в эксперименте RANGE со смещением использует только sort_key; row_id нельзя добавить как косметический tie-breaker — он изменил бы смысл peers и не соответствовал бы контракту диапазона.

8. CURRENT ROW ведёт себя по-разному для ROWS и RANGE

Пусть есть:

row_id sort_key amount
A 1 10
B 1 20
C 2 5

A и B — peers по единственному ключу sort_key.

Для ROWS ... CURRENT ROW текущая строка означает одну конкретную позицию. Если порядок дополнен row_id, накопительная сумма может быть:

text
A -> 10
B -> 30
C -> 35

Для RANGE ... CURRENT ROW текущая граница включает всех peers:

text
A -> 30
B -> 30
C -> 35

Оба результата корректны, но отвечают на разные вопросы:

  • ROWS: итог после каждой отдельной, однозначно упорядоченной записи;
  • RANGE: итог на уровне значения ключа, общий для равных ключей.

9. Default frame зависит от наличия ORDER BY

Это правило нельзя оставлять скрытым.

Без оконного ORDER BY

sql
sum(amount) OVER (
    PARTITION BY currency
)

Default frame — вся partition.

С оконным ORDER BY

sql
sum(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at
)

В DuckDB default frame соответствует:

sql
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

Текущая граница включает peers. Поэтому две покупки с одинаковым ordered_at могут войти в накопительный итог одновременно.

Если в ORDER BY добавить уникальный order_id, peers исчезнут и на текущих данных default RANGE может дать те же числа, что явный ROWS. Но это совпадение результата не делает контракты одинаковыми. Удаление tie-breaker или изменение бизнес-вопроса снова проявит разницу.

Правило артефакта:

text
если порядок влияет на агрегат, frame записывается явно

Так ревьюер видит не только число, но и намерение автора.

10. Размер frame и знаменатель агрегата — разные величины

Пусть frame содержит:

text
1200, NULL, 1500

Тогда:

text
COUNT(*)      = 3
COUNT(amount) = 2
SUM(amount)   = 2700
AVG(amount)   = 1350

Среднее не равно:

text
2700 / 3 = 900

Потому что AVG(amount) пропускает неизвестный аргумент и использует:

text
SUM известных amount / COUNT известных amount

Если опубликовать только AVG, читатель не знает:

  • frame действительно содержал две строки;
  • frame содержал три строки, но одна сумма неизвестна;
  • frame был обрезан границей partition;
  • все суммы в frame неизвестны.

Поэтому артефакт выпускает рядом:

sql
count(*)     OVER recent_3_rows AS recent_3_order_rows,
count(amount) OVER recent_3_rows AS recent_3_known_amounts,
avg(amount)  OVER recent_3_rows AS recent_3_known_amount_avg

COALESCE(amount, 0) здесь не является техническим исправлением. Нулевая покупка и неизвестная сумма имеют разный смысл.

Тип результата AVG нужно проверить отдельно

Входной amount имеет точный фиксированный тип DECIMAL(18, 2). В DuckDB:

text
SUM(amount) -> DECIMAL(38, 2)
AVG(amount) -> DOUBLE

Среднее содержит деление, а деление фиксированных десятичных чисел не всегда даёт конечную десятичную дробь. Поэтому DuckDB возвращает приближённый floating-point результат DOUBLE. Это не повод превращать исходный amount в DOUBLE: точный тип по-прежнему нужен для хранения сумм и сложения денег.

Артефакт сохраняет вычислительное среднее без скрытого округления. Поэтому значение 1625 / 3 равно примерно 541.67, а не точно 541.67. Если результат поставляется как денежное число с двумя знаками, правило публикации нужно согласовать отдельно и записать явно, например:

sql
cast(
    round(avg(amount) OVER currency_recent_3_rows, 2)
    AS DECIMAL(18, 2)
) AS recent_3_known_amount_avg_rounded

Так ревьюер видит границу между расчётом среднего и его представлением в отчёте.

11. Накопительная сумма на NULL не доказывает нулевой вклад

Если текущий amount неизвестен, SUM(amount) пропустит его. Накопительный итог может остаться равным предыдущему:

text
до строки с NULL:    1200
на строке с NULL:    1200

Это не означает, что заказ добавил ноль. Значит только:

text
сумма известных значений пока не изменилась

Поэтому рядом с running sum сохраняются:

sql
count(*) OVER currency_running_rows AS currency_running_order_rows,
count(amount) OVER currency_running_rows AS currency_running_known_amounts

Разница этих счётчиков показывает, сколько строк не вошло в денежный итог из-за неизвестного значения.

12. Именованное окно может включать frame

В предыдущем уроке одно имя связывало partition и order. Здесь имя фиксирует полный контракт:

sql
WINDOW currency_recent_3_rows AS (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)

Затем несколько агрегатов используют ровно один набор строк:

sql
count(*)      OVER currency_recent_3_rows,
count(amount) OVER currency_recent_3_rows,
avg(amount)   OVER currency_recent_3_rows

Это важно: если среднее и его знаменатель случайно используют разные frames, проверка перестаёт описывать сам расчёт.

В артефакте четыре имени:

Имя Смысл
currency_partition вся валюта без порядка
currency_running_rows от начала валюты до текущего заказа
currency_recent_3_rows текущий и два предыдущих заказа
currency_prior_3_rows три заказа перед текущим, без текущего

Необязательное углубление: last_value возвращает последнюю строку frame

На однозначном порядке:

sql
last_value(order_id) OVER (
    ORDER BY sort_key, row_id
)

default frame заканчивается на текущей строке. Поэтому для A, B, C, D функция может вернуть:

text
A, B, C, D

Чтобы увидеть последнюю строку всей partition, frame должен доходить до конца:

sql
last_value(order_id) OVER (
    ORDER BY sort_key, row_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
)

Теперь каждая строка видит D.

Это не обязательный новый инструмент и не результат, который нужно запоминать после урока. Пример можно разобрать после основной практики как дополнительное доказательство: функции first_value, last_value и оконные агрегаты зависят не только от partition и order, но и от frame.

13. Входной контракт остаётся обязательным

Основной SQL ожидает:

Поле Контракт
order_id заполненный уникальный ключ
status каноническое значение cancelled, paid, pending или refunded
user_id заполнен для оплаченного заказа
ordered_at заполненный TIMESTAMPTZ для оплаченного заказа
currency заполнена для оплаченного заказа
amount DECIMAL(18, 2), может быть неизвестна

Почему:

  • дубликат order_id создаст лишнюю позицию в ROWS;
  • пустое время не имеет честного места в хронологии;
  • пустая валюта смешает несопоставимые суммы в диагностической NULL-partition;
  • неканонический status незаметно изменит population;
  • строковый amount не является готовой денежной мерой;
  • исходный DOUBLE вместо DECIMAL может изменить точность денежных сумм;
  • выходной AVG(DECIMAL) отдельно требует осознанной политики округления.

Артефакт не загружает и не чистит данные. Эти обязанности остаются у внешнего слоя.

Что сознательно остаётся за границей

В обязательный результат не входят:

  • GROUPS frames — расстояние в группах peers;
  • EXCLUDE CURRENT ROW, EXCLUDE GROUP и другие варианты исключения;
  • DISTINCT и FILTER внутри оконных агрегатов;
  • nth_value, percentile- и distribution-функции;
  • временные RANGE с INTERVAL;
  • centered rolling windows;
  • sessionization;
  • оптимизация и стоимость оконного оператора;
  • rolling features для прогнозирования и защита от temporal leakage.

После текущего урока эти темы можно понять, но они не нужны для минимальной уверенной работы аналитика с накопительными и скользящими SQL-расчётами. Календарные интервалы появятся после времени в SQL, а leakage-free rolling features — в фазе временных рядов.

Соберите это

Сначала рассчитаем два маленьких результата вручную. Первый показывает движение frame, второй связывает механизм с заказами.

Шаг 1. Постройте frame experiment

Даны четыре строки:

row_id sort_key amount
A 1 10
B 1 20
C 2 5
D 4 40

У данных есть две особенности:

  • A и B — peers по sort_key;
  • между ключами 2 и 4 есть разрыв.

Они нужны не для сложности, а чтобы ROWS и RANGE перестали случайно давать один ответ.

Шаг 2. Накопите сумму по позициям

Для однозначного порядка:

text
sort_key, row_id

и frame:

sql
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

получаем:

current Строки frame Сумма
A A 10
B A, B 30
C A, B, C 35
D A, B, C, D 75

Шаг 3. Накопите сумму по диапазону

Для:

sql
ORDER BY sort_key
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

получаем:

current Значения sort_key Строки frame Сумма
A до 1 включительно A, B 30
B до 1 включительно A, B 30
C до 2 включительно A, B, C 35
D до 4 включительно A, B, C, D 75

Первая строка сразу получает 30, потому что CURRENT ROW для RANGE включает peer B.

Шаг 4. Сравните расстояние 1

Теперь два контракта:

sql
ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
sql
RANGE BETWEEN 1 PRECEDING AND CURRENT ROW

Ручной oracle:

row_id ROWS сумма RANGE сумма Почему различаются
A 10 30 RANGE включает peer B
B 30 30 обе строки с ключом 1 входят
C 25 35 ROWS берёт B и C, RANGE — все ключи 1 и 2
D 45 40 ROWS берёт C и D, в диапазоне ключей 3..4 есть только D

Если эта таблица понятна до запуска SQL, различие механизмов уже не сводится к запоминанию синтаксиса.

Шаг 5. Постройте oracle для заказов EUR

В оплаченной EUR-partition:

order_id ordered_at amount
O1006 2026-02-20 25
O1009 2026-03-07 900
O1012 2026-04-05 700

Общая известная сумма:

text
25 + 900 + 700 = 1625

Ручной результат:

order_id total running recent rows recent avg prior rows prior avg
O1006 1625 25 1 25 0 NULL
O1009 1625 925 2 462.5 1 25
O1012 1625 1625 3 ≈ 541.67 2 462.5

Проверьте смысл:

  • total одинаков на всех строках partition;
  • running растёт вместе с текущей позицией;
  • recent включает текущую строку;
  • prior заканчивается на предыдущей строке;
  • первые frames меньше трёх строк;
  • отсутствие предыдущих строк даёт COUNT(*) = 0 и AVG = NULL.

Шаг 6. Зафиксируйте четыре оконных контракта

Используйте это

Этап 1. Зафиксировать population

Этап 2. Получить итог всей partition

sql
currency_partition AS (
    PARTITION BY currency

Этап 3. Получить накопительный итог

sql

sql

count(amount) OVER currency_recent_3_rows AS recent_3_known_amounts,

    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

Название говорит именно «последние три заказа», а не «последние три дня».

Этап 5. Получить prior-3 без текущей строки

sql

count(amount) OVER currency_prior_3_rows AS prior_3_known_amounts,

    ORDER BY ordered_at, order_id

)

Это baseline для сравнения текущей покупки с предыдущими заказами магазина в той же валюте. Он не описывает историю конкретного пользователя. На первой строке partition frame пуст, поэтому оба счётчика равны 0, а среднее — NULL.

Этап 6. Опубликовать детерминированный результат

sql
ORDER BY currency, ordered_at, order_id

Финальный порядок не меняет frames. Он только позволяет читателю увидеть валютные последовательности в том же удобном порядке.

Сломайте это

Ошибка 1. Заменить окно на GROUP BY

Итог по валюте станет корректным, но order_id исчезнет. Это другая витрина с другим grain.

Проверка:

text
число оплаченных строк до окна = число строк после окна
order_id остаётся уникальным

Ошибка 2. Положиться на default frame

Хрупкая форма:

sql
sum(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at
)

На уникальных timestamps она может выглядеть как обычный running sum. После добавления двух peer-строк один timestamp получит общий скачок.

Исправление: сначала решить, нужен ROWS или RANGE, затем записать frame явно.

Ошибка 3. Убрать partition по валюте

sql
sum(amount) OVER (
    ORDER BY ordered_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)

Такой запрос складывает числа с разными единицами. Результат не становится осмысленным только потому, что тип всех сумм — DECIMAL.

Исправление текущей задачи:

sql
PARTITION BY currency

Ошибка 4. Использовать ROWS без полного порядка

sql
ORDER BY ordered_at
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

При двух заказах в один момент неизвестно, какая строка является предыдущей позицией. Разные планы могут менять rolling average.

Исправление:

sql
ORDER BY ordered_at, order_id

Это детерминированная договорённость, но не доказательство истинной очередности одновременных событий.

Ошибка 5. Считать ROWS 7 PRECEDING семью днями

ROWS считает строки. Если в один день было 100 заказов, семь позиций могут покрыть несколько минут. Если заказов не было неделю, соседние строки могут быть разделены десятью днями.

Для календарного вопроса нужна временная модель и RANGE с интервалом либо предварительно построенный полный календарный ряд. Это будет осмысленно после урока о датах.

Ошибка 6. Считать начальную рамку полной

На первой строке:

sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

содержит одну строку, а не три.

Исправление: публиковать COUNT(*) OVER same_frame и вводить политику полноты там, где она влияет на сравнение.

Ошибка 7. Назвать AVG(amount) средним всех строк frame

При одном NULL:

text
frame rows   = 3
known values = 2
AVG denominator = 2

Исправление: выпускать COUNT(*), COUNT(amount) и AVG(amount) из одного именованного окна.

Ошибка 8. Подменить неизвестную сумму нулём

sql
avg(coalesce(amount, 0)) OVER (...)

Так среднее отвечает на новую задачу, где отсутствие измерения объявлено реальным нулём. Это допустимо только при отдельном бизнес-правиле, а не как автоматическая очистка.

Ошибка 9. Включить текущую строку в prior baseline

Если текущий заказ сравнивается с:

sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW

его собственная сумма уже влияет на baseline.

Для трёх предыдущих заказов:

sql
ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING

Эта граница особенно важна позже для аномалий, прогнозов и признаков моделей.

Необязательный пример. Принять last_value за конец partition

Default frame с ORDER BY обычно заканчивается на текущей строке или её peers. last_value возвращает конец именно этого frame.

Проверка: сравнить default-вариант с явным:

sql
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING

Ошибка 10. Запустить окно после fanout

Если заказ размножен по позициям, ROWS 2 PRECEDING считает позиции товара, а не три заказа.

Перед окном:

  • назовите grain;
  • проверьте уникальность order_id;
  • при необходимости сначала агрегируйте позиции до заказа;
  • затем применяйте оконный расчёт.

Ошибка 11. Спрятать пустое время через NULLS LAST

Заказ без ordered_at не имеет честной позиции в хронологии. NULLS LAST технически разместит его, но не объяснит, когда он произошёл и какие rows должны попасть в frame.

Текущий входной контракт отклоняет оплаченный заказ без времени.

Quiz · 6 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

Что вычисляет SUM(amount) OVER (PARTITION BY currency), если в OVER нет ORDER BY?

Без оконного ORDER BY рамка по умолчанию охватывает всю partition. Оконный агрегат повторяет её итог на каждой строке и не сворачивает grain.

02

Первая строка раздела использует ROWS BETWEEN 2 PRECEDING AND CURRENT ROW. Сколько строк реально попадёт в рамку?

Рамка не создаёт отсутствующие строки. На начале partition она обрезается, поэтому в расчёте участвует только текущая строка.

03

Две строки имеют одинаковый единственный ключ оконного ORDER BY. Почему накопительная сумма с default frame может сразу включить обе?

При наличии ORDER BY default frame в DuckDB ведёт себя как RANGE от начала partition до CURRENT ROW, а CURRENT ROW включает peers с тем же ключом порядка.

04

Как посчитать среднее только по трём заказам перед текущим, не включая текущий заказ?

Начальная граница берёт до трёх предшествующих строк, а конечная 1 PRECEDING останавливает рамку до текущей строки.

05

В рамке три строки, но amount известен только у двух. Как честно опубликовать AVG(amount)?

AVG(amount) использует только известные значения. Пара COUNT(*) и COUNT(amount) показывает одновременно размер рамки и фактический знаменатель среднего.

06

Для строк (A, 1, 10), (B, 1, 20), (C, 2, 5), (D, 4, 40) вычисляется сумма для D. Что вернут ROWS BETWEEN 1 PRECEDING AND CURRENT ROW и RANGE BETWEEN 1 PRECEDING AND CURRENT ROW?

ROWS измеряет расстояние в позициях и берёт C плюс D. RANGE измеряет расстояние в значениях sort_key: для текущего ключа 4 диапазон равен 3..4, а строки с ключом 3 нет.

def prepare_orders(
    connection: duckdb.DuckDBPyConnection,
    orders_path: Path = DATA_PATH,
) -> None:
    """Prepare a typed fixture; file loading is infrastructure, not the SQL artifact."""
    connection.execute(
        """
        CREATE OR REPLACE TABLE orders AS
        SELECT
            CAST(order_id AS VARCHAR) AS order_id,
            CAST(user_id AS VARCHAR) AS user_id,
            CAST(ordered_at AS TIMESTAMPTZ) AS ordered_at,
            CAST(status AS VARCHAR) AS status,
            CAST(currency AS VARCHAR) AS currency,
            CAST(amount AS DECIMAL(18, 2)) AS amount
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        """,
        [str(orders_path)],
    )


def _schema(connection: duckdb.DuckDBPyConnection, relation: str) -> dict[str, str]:
    return {row[0]: str(row[1]) for row in connection.execute(f"DESCRIBE {relation}").fetchall()}


def _require_populated_text(
    connection: duckdb.DuckDBPyConnection,
    column: str,
    *,
    where: str = "TRUE",
) -> None:
    missing = connection.execute(
        f"""
        SELECT count(*)
        FROM orders
        WHERE ({where})
          AND ({column} IS NULL OR trim({column}) = '')
        """
    ).fetchone()[0]
    if missing:
        raise ValueError(f"orders.{column} contains {missing} NULL or blank values where {where}")


def validate_input(connection: duckdb.DuckDBPyConnection) -> None:
    expected_schema = {
        "order_id": "VARCHAR",
        "user_id": "VARCHAR",
        "ordered_at": "TIMESTAMP WITH TIME ZONE",
        "status": "VARCHAR",
        "currency": "VARCHAR",
        "amount": "DECIMAL(18,2)",
    }
    actual_schema = _schema(connection, "orders")
    for column, expected_type in expected_schema.items():
        actual_type = actual_schema.get(column)
        if actual_type is None:
            raise ValueError(f"orders is missing required column {column}")
        if actual_type != expected_type:
            raise ValueError(f"orders.{column} must be {expected_type}, got {actual_type}")

    _require_populated_text(connection, "order_id")
    _require_populated_text(connection, "status")

    placeholders = ", ".join("?" for _ in CANONICAL_ORDER_STATUSES)
    unknown_statuses = [
        row[0]
        for row in connection.execute(
            f"""
            SELECT DISTINCT status
            FROM orders
            WHERE status NOT IN ({placeholders})
            ORDER BY status
            """,
            list(CANONICAL_ORDER_STATUSES),
        ).fetchall()
    ]
    if unknown_statuses:
        raise ValueError(
            "orders.status must use canonical values "
            f"{CANONICAL_ORDER_STATUSES}, got {unknown_statuses}"
        )

    duplicate = connection.execute(
        """
        SELECT order_id
        FROM orders
        GROUP BY order_id
        HAVING count(*) > 1
        LIMIT 1
        """
    ).fetchone()
    if duplicate is not None:
        raise ValueError(f"orders grain violation for order_id: {duplicate[0]}")

    _require_populated_text(connection, "user_id", where="status = 'paid'")
    _require_populated_text(connection, "currency", where="status = 'paid'")
    missing_ordered_at = connection.execute(
        """
        SELECT count(*)
        FROM orders
        WHERE status = 'paid' AND ordered_at IS NULL
        """
    ).fetchone()[0]
    if missing_ordered_at:
        raise ValueError("paid orders require ordered_at before an ordered frame can be built")


def execute_sql(
    connection: duckdb.DuckDBPyConnection,
    query_path: Path,

    relation = connection.execute(query_path.read_text(encoding="utf-8"))
    columns = [description[0] for description in relation.description]
    types = [str(description[1]) for description in relation.description]
    return columns, types, relation.fetchall()

def validate_frames(
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
) -> None:
    if columns != EXPECTED_FRAME_COLUMNS:
        raise ValueError(f"frame columns must be {EXPECTED_FRAME_COLUMNS}, got {columns}")
    if types != EXPECTED_FRAME_TYPES:
        raise ValueError(f"frame types must be {EXPECTED_FRAME_TYPES}, got {types}")

    order_id_at = columns.index("order_id")
    if len(rows) != 9 or len({row[order_id_at] for row in rows}) != len(rows):
        raise ValueError("window aggregates must preserve nine unique paid order_id rows")

    total_at = columns.index("currency_total_known_amount")
    currency_at = columns.index("currency")
    totals_by_currency: dict[str, set[Decimal | None]] = {}
    for row in rows:
        totals_by_currency.setdefault(row[currency_at], set()).add(row[total_at])
    if any(len(totals) != 1 for totals in totals_by_currency.values()):
        raise ValueError("partition total must be constant inside each currency")

    for row in rows:
        recent_rows = row[columns.index("recent_3_order_rows")]
        recent_known = row[columns.index("recent_3_known_amounts")]
        recent_avg = row[columns.index("recent_3_known_amount_avg")]
        prior_rows = row[columns.index("prior_3_order_rows")]
        prior_known = row[columns.index("prior_3_known_amounts")]
        prior_avg = row[columns.index("prior_3_known_amount_avg")]

        if not 1 <= recent_rows <= 3 or not 0 <= recent_known <= recent_rows:
            raise ValueError("recent frame row and known-value counts are inconsistent")
        if not 0 <= prior_rows <= 3 or not 0 <= prior_known <= prior_rows:
            raise ValueError("prior frame row and known-value counts are inconsistent")
        if (recent_avg is None) != (recent_known == 0):
            raise ValueError("recent average must expose an empty known-value denominator")
        if (prior_avg is None) != (prior_known == 0):
            raise ValueError("prior average must expose an empty known-value denominator")


def _json_value(value: Any) -> Any:
    if isinstance(value, Decimal):
        return str(value)
    if isinstance(value, datetime):
        return value.isoformat()
    return value


def _records(
    columns: list[str],
    rows: list[tuple[Any, ...]],
) -> list[dict[str, Any]]:
    return [
        {column: _json_value(value) for column, value in zip(columns, row, strict=True)}
        for row in rows
    ]

    connection = duckdb.connect()
    try:
        prepare_orders(connection)
        validate_input(connection)
        frame_columns, frame_types, frame_rows = execute_frames(connection)
        validate_frames(frame_columns, frame_types, frame_rows)
        experiment_columns, _, experiment_rows = execute_experiment(connection)
    finally:
        connection.close()

    return {
        "grain": ["order_id"],
        "rows": _records(frame_columns, frame_rows),
        "frame_experiment": _records(experiment_columns, experiment_rows),
        "checks": {
            "paid_order_rows": len(frame_rows),
            "order_id_unique": True,
            "ordered_aggregates_use_explicit_frames": True,
        },
    }


def main() -> None:
    print(json.dumps(run_example(), ensure_ascii=False, indent=2))

    main()

-- A deliberately small oracle for frame semantics.
-- sort_key has peers (A and B) and a gap before D.
--
-- default_running_sum demonstrates the implicit RANGE-like frame.
-- rows_running_sum counts deterministic row positions.
-- range_running_sum includes all peers at the current sort_key.
-- rows_distance_1_sum selects one preceding row position.
-- range_distance_1_sum selects values whose sort_key is within one unit.
-- default_last_value stops at the current frame; partition_last_value sees the full
-- partition because its frame ends at UNBOUNDED FOLLOWING.

WITH frame_events(row_id, sort_key, amount) AS (
    VALUES
        ('A', 1, 10),
        ('B', 1, 20),
        ('C', 2, 5),
        ('D', 4, 40)
)
SELECT
    row_id,
    sort_key,
    amount,
    sum(amount) OVER (
        ORDER BY sort_key
    ) AS default_running_sum,
    sum(amount) OVER (
        ORDER BY sort_key, row_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS rows_running_sum,
    sum(amount) OVER (
        ORDER BY sort_key
        RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS range_running_sum,
    sum(amount) OVER (
        ORDER BY sort_key, row_id
        ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
    ) AS rows_distance_1_sum,
    sum(amount) OVER (
        ORDER BY sort_key
        RANGE BETWEEN 1 PRECEDING AND CURRENT ROW
    ) AS range_distance_1_sum,
    last_value(row_id) OVER (
        ORDER BY sort_key, row_id
    ) AS default_last_value,
    last_value(row_id) OVER (
        ORDER BY sort_key, row_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS partition_last_value
FROM frame_events
ORDER BY sort_key, row_id;

-- Input contract:
-- orders has grain one row per unique non-NULL order_id;
-- status is one of cancelled, paid, pending or refunded for every order;
-- paid orders have non-NULL user_id, ordered_at TIMESTAMPTZ and currency;
-- amount is DECIMAL(18, 2) and may be NULL.
--
-- Output contract:
-- one row per paid order_id;
-- monetary aggregates never mix currencies;
-- every ordered aggregate has an explicit ROWS frame;
-- row and known-value counts make partial frames and NULL denominators visible;
-- AVG(DECIMAL) is delivered as unrounded DOUBLE; presentation rounding is a separate
-- explicit policy.

WITH paid_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount
    FROM orders
    WHERE status = 'paid'
),
framed_orders AS (
    SELECT
        order_id,
        user_id,
        ordered_at,
        currency,
        amount,
        sum(amount) OVER currency_partition AS currency_total_known_amount,
        sum(amount) OVER currency_running_rows AS currency_running_known_amount,
        count(*) OVER currency_running_rows AS currency_running_order_rows,
        count(amount) OVER currency_running_rows AS currency_running_known_amounts,
        count(*) OVER currency_recent_3_rows AS recent_3_order_rows,
        count(amount) OVER currency_recent_3_rows AS recent_3_known_amounts,
        avg(amount) OVER currency_recent_3_rows AS recent_3_known_amount_avg,
        count(*) OVER currency_prior_3_rows AS prior_3_order_rows,
        count(amount) OVER currency_prior_3_rows AS prior_3_known_amounts,
        avg(amount) OVER currency_prior_3_rows AS prior_3_known_amount_avg
    FROM paid_orders
    WINDOW
        currency_partition AS (
            PARTITION BY currency
        ),
        currency_running_rows AS (
            PARTITION BY currency
            ORDER BY ordered_at, order_id
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ),
        currency_recent_3_rows AS (
            PARTITION BY currency
            ORDER BY ordered_at, order_id
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ),
        currency_prior_3_rows AS (
            PARTITION BY currency
            ORDER BY ordered_at, order_id
            ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
        )
)
SELECT
    order_id,
    user_id,
    ordered_at,
    currency,
    amount,
    currency_total_known_amount,
    currency_running_known_amount,
    currency_running_order_rows,
    currency_running_known_amounts,
    recent_3_order_rows,
    recent_3_known_amounts,
    recent_3_known_amount_avg,
    prior_3_order_rows,
    prior_3_known_amounts,
    prior_3_known_amount_avg
FROM framed_orders
ORDER BY currency, ordered_at, order_id;
