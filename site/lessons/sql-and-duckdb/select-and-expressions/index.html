Проверка перед уроком

Ответьте до чтения: результат поможет заметить исходные предположения.

01

Таблица orders имеет grain «одна строка на заказ». Что произойдет с grain, если без фильтра выбрать только order_id, user_id и amount?

Проекция столбцов сама по себе не меняет смысл строки. Пока строки не агрегируются и не размножаются, grain остается одной строкой на заказ.

02

Что нужно объявить до построения новой проверяемой таблицы из orders?

Контракт результата описывает смысл строки, схему и наблюдаемый порядок, если его использует человек или downstream-проверка.

SELECT и выражения

Сначала предскажите таблицу результата, затем запишите SELECT и проверьте, что строки, столбцы, типы и порядок совпали с предсказанием.

Тип: Build Треки: Core Пререквизиты: 04/01 Время: ~90 минут Результат: по бизнес-правилу строит SELECT с явной проекцией, вычисляемыми и условными полями, фильтром и детерминированным порядком, затем сверяет grain, схему, типы и значения с ручной таблицей.

Проблема

Заказчику нужен небольшой список оплаченных заказов в рублях. Для каждой строки нужно показать:

  • идентификатор заказа и пользователя;
  • исходную сумму;
  • сумму после добавления сервисного сбора 5%;
  • категорию large, если исходная сумма не меньше 1300 рублей, иначе regular.

В результате сначала должны идти более дорогие заказы. Если суммы совпали, порядок должен однозначно определяться по order_id.

Запрос на первый взгляд прост:

sql
SELECT *
FROM orders
WHERE status = 'paid';

Но он не является ответом на поставленную задачу:

  • в результат попали все валюты;
  • состав столбцов зависит от текущей схемы источника;
  • вычисляемых полей нет;
  • правило large не записано;
  • порядок строк не обещан;
  • по тексту запроса нельзя восстановить полный контракт результата.

Правдоподобные числа ещё не делают результат проверяемым. До выполнения запроса нужно уметь ответить:

text
что означает одна строка результата;
какие исходные строки должны остаться;
какие столбцы и типы получит новая таблица;
как вычисляется каждый новый столбец;
какой порядок считается правильным.

Что уже известно

Урок не начинает работу с таблицами заново. Меняется язык, но не способ рассуждения.

Уже освоено Где Перенос в SQL
grain и ключ результата 04/01 объявляем одну строку на order_id до запроса
выбор столбцов и булева маска 03/03 SELECT задаёт столбцы, WHERE оставляет строки
производные столбцы 03/04 выражение с AS создаёт вычисляемый столбец
явные типы и строгая граница преобразования 03/02 проверяем типы входа и результата, не надеемся на случайный cast

проверяемый handoff 03/12 SQL и контракт результата передаются вместе

Короткая карта переноса:

text
frame[["order_id", "amount"]] -> SELECT order_id, amount
frame.loc[mask]               -> WHERE <predicate>
frame.assign(total=...)       -> <expression> AS total
frame.sort_values(...)        -> ORDER BY ...

Это не утверждение, что Pandas и SQL устроены одинаково. Карта нужна только как мост: знакомое аналитическое действие получает новый синтаксис и новые границы.

Концепция

1. Результат запроса — новая таблица

SELECT не «показывает часть файла». Он формирует новую relation с собственным контрактом.

Для нашей задачи контракт выглядит так:

text
популяция  -> оплаченные RUB-заказы из orders
grain      -> один заказ
ключ       -> order_id
столбцы    -> order_id, user_id, currency, amount,
              amount_with_fee, amount_band
типы       -> VARCHAR, VARCHAR, VARCHAR, DECIMAL(18,2),
              DECIMAL(18,2), VARCHAR
порядок    -> amount DESC, затем order_id ASC

Фильтрация уменьшает популяцию, но не обязана менять grain:

text
до фильтра  -> одна строка на заказ
после фильтра -> одна строка на оплаченный RUB-заказ

Если один order_id неожиданно повторяется, SELECT не исправляет модель данных. Нарушение ключа останется нарушением и в результате.

2. Текстовый и логический порядок — не одно и то же

Запрос обычно записывают так:

sql
SELECT ...
FROM ...
WHERE ...
ORDER BY ...

Для предсказания результата полезно читать его в другом порядке:

text
1. FROM     -> откуда берутся строки
2. WHERE    -> какие строки остаются
3. SELECT   -> какие столбцы и выражения строятся
4. ORDER BY -> как упорядочивается готовый результат
5. LIMIT    -> сколько первых строк упорядоченного результата оставить

Это логический порядок. Движок может физически оптимизировать выполнение, но наблюдаемый смысл запроса должен соответствовать этой модели.

Практическое следствие: alias, созданный в SELECT, логически ещё не существует на шаге WHERE. В переносимом SQL не следует строить фильтр на предположении, что новый alias уже доступен. Именованные стадии для таких случаев появятся в 04/06 вместе с CTE.

3. SELECT задаёт проекцию

Проекция — выбор столбцов и выражений, которые войдут в результат.

sql
SELECT
    order_id,
    user_id,
    amount
FROM orders;

Порядок элементов в select list становится порядком столбцов результата:

text
order_id -> user_id -> amount

SELECT * означает «возьми все столбцы, которые источник имеет сейчас». Это удобно при разовом просмотре, но слабо как контракт:

  • производитель добавил internal_note — потребитель внезапно получил новый столбец;
  • изменился порядок исходных столбцов — изменилась схема выгрузки;
  • тяжёлый или чувствительный столбец ушёл downstream без явного решения;
  • по запросу нельзя понять, какие поля действительно нужны.

Для поставляемого результата используем явный select list.

4. Выражение вычисляет значение для строки

Выражение может состоять из:

  • ссылки на столбец: amount;
  • литерала: 1.05, 'large';
  • оператора: *, +, >=;
  • функции: round(...);
  • других выражений.

Например:

sql
round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2)

Для каждой выбранной строки это означает:

text
взять amount
-> умножить на точный десятичный коэффициент 1.05
-> округлить результат до двух знаков

Вычисление не меняет число строк. Оно добавляет новое значение к прежнему grain.

5. Alias является частью интерфейса

Без имени вычисляемый столбец получает техническую подпись, зависящую от текста выражения. Потребителю неудобно и ненадёжно обращаться к такому полю.

sql
round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2) AS amount_with_fee

AS amount_with_fee — alias, или стабильное имя результата выражения.

Хороший alias:

  • описывает смысл, а не реализацию;
  • не меняется без причины;
  • согласован с контрактом и downstream-кодом;
  • не скрывает единицы измерения или валюту.

Переименование amount_with_fee в total может не изменить числа, но всё равно сломать контракт потребителя.

6. Тип выражения тоже входит в контракт

Денежная сумма в учебном контракте имеет тип DECIMAL(18,2). Он хранит точное десятичное значение с двумя знаками после запятой.

В запросе коэффициент записан явно:

sql
CAST(1.05 AS DECIMAL(4, 2))

Это делает намерение видимым: мы считаем денежное выражение в десятичной арифметике, а не превращаем сумму в приблизительный floating-point результат.

При этом сам amount не нужно заново разбирать из строки в каждом аналитическом запросе. Урок принимает типизированную relation orders. Если источник всё ещё хранит непроверенный текст, преобразование и отказ на неразбираемом значении должны происходить на входной границе, а не случайно внутри каждого отчёта.

После выполнения проверяем не только значения:

text
amount          -> DECIMAL(18,2)
amount_with_fee -> DECIMAL(18,2)
amount_band     -> VARCHAR

7. CASE создаёт условное поле

Для бизнес-категории используем searched CASE:

sql
CASE
    WHEN amount >= CAST(1300 AS DECIMAL(18, 2)) THEN 'large'
    ELSE 'regular'
END AS amount_band

Читаем обычным языком:

text
если amount не меньше 1300.00 -> large
иначе                         -> regular

Граница включена в верхнюю категорию:

amount amount_band
1299.99 regular
1300.00 large
1500.00 large

Условия WHEN проверяются сверху вниз, и используется первая подходящая ветка. ELSE фиксирует поведение для всех остальных допустимых значений.

В этом уроке есть входное предположение: у выбранного оплаченного RUB-заказа сумма известна. Tiny-набор ему соответствует, а runner проверяет его отдельно. Что SQL делает с отсутствующим значением внутри сравнения и почему простой ELSE может дать опасную классификацию, подробно разберём в 04/03.

8. WHERE оставляет только строки с подходящим условием

Predicate, или предикат, — выражение, которое используется как условие.

sql
WHERE status = 'paid'
  AND currency = 'RUB'

Обе части должны выполняться одновременно:

text
status является paid
И
currency является RUB

WHERE меняет набор строк, но не создаёт столбцы результата.

Скобки сохраняют бизнес-смысл

Предположим, нужны оплаченные заказы в RUB или EUR:

text
status = paid AND (currency = RUB OR currency = EUR)

Правильная запись:

sql
WHERE status = 'paid'
  AND (currency = 'RUB' OR currency = 'EUR')

Без скобок:

sql
WHERE status = 'paid'
  AND currency = 'RUB'
   OR currency = 'EUR'

условие читается как:

text
(paid AND RUB) OR EUR

и пропустит любой EUR-заказ, включая отменённый. Синтаксис останется корректным, а аналитический ответ — нет.

9. ORDER BY создаёт наблюдаемый порядок

Relation не обещает «естественного» порядка строк. Порядок CSV, текущий план выполнения или результат вчерашнего запуска не являются контрактом.

sql
ORDER BY amount DESC, order_id ASC

Читаем:

  1. сначала большая сумма;
  2. при равной сумме — меньший order_id.

Второй столбец является tie-breaker. Без него два заказа с одинаковой суммой могут меняться местами между запусками.

LIMIT выбирает первые строки только после логической сортировки:

sql
ORDER BY amount DESC, order_id ASC
LIMIT 10

LIMIT 10 без ORDER BY обещает не «десять крупнейших» и не «первые по времени», а только не более десяти строк неопределённого состава.

Соберите это

Сначала решим задачу вручную. Код пока не нужен.

Возьмём четыре строки, достаточные для проверки фильтра:

order_id user_id status currency amount
O1001 U001 paid RUB 1200.00
O1002 U002 refunded RUB 800.00
O1003 U003 paid USD 75.00
O1005 U001 paid RUB 1500.00

Шаг 1. Зафиксируйте контракт результата

text
grain   -> одна строка на оплаченный RUB-заказ
key     -> order_id
columns -> order_id, user_id, currency, amount,
           amount_with_fee, amount_band
order   -> amount DESC, order_id ASC

Шаг 2. Примените фильтр

Проверяем две части отдельно:

order_id status = paid currency = RUB Остаётся
O1001 да да да
O1002 нет да нет
O1003 да нет нет
O1005 да да да

После фильтра остаются O1001 и O1005.

Шаг 3. Вычислите новые поля

Для O1001:

text
amount_with_fee = 1200.00 * 1.05 = 1260.00
amount_band     = regular, потому что 1200.00 < 1300.00

Для O1005:

text
amount_with_fee = 1500.00 * 1.05 = 1575.00
amount_band     = large, потому что 1500.00 >= 1300.00

Шаг 4. Постройте проекцию

Оставляем только шесть полей контракта:

order_id user_id currency amount amount_with_fee amount_band
O1001 U001 RUB 1200.00 1260.00 regular
O1005 U001 RUB 1500.00 1575.00 large

Шаг 5. Примените порядок

Сортируем amount DESC. Итоговая ручная таблица:

order_id user_id currency amount amount_with_fee amount_band
O1005 U001 RUB 1500.00 1575.00 large
O1001 U001 RUB 1200.00 1260.00 regular

Теперь у нас есть полный oracle: ожидаем не просто две строки, а конкретные строки, столбцы, типы, значения и порядок.

Используйте это

SQL-артефакт решает ту же задачу:

sql
SELECT
    order_id,
    user_id,
    currency,
    amount,
    round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2) AS amount_with_fee,
    CASE
        WHEN amount >= CAST(1300 AS DECIMAL(18, 2)) THEN 'large'
        ELSE 'regular'
    END AS amount_band
FROM orders
WHERE status = 'paid'
  AND currency = 'RUB'
ORDER BY amount DESC, order_id ASC;

Разберите его по логическим стадиям:

Стадия Фрагмент Что меняется
источник FROM orders появляется популяция исходных заказов
фильтр status = 'paid' AND currency = 'RUB' остаются две строки tiny-набора
проекция шесть выражений после SELECT фиксируются столбцы результата
вычисление round(amount * ..., 2) появляется точная сумма со сбором
классификация CASE ... END появляется категория заказа
порядок amount DESC, order_id ASC строки получают воспроизводимую последовательность

Запустите reference runner:

bash
uv run --locked python code/main.py

Runner выполняет только инфраструктурную работу:

  1. создаёт типизированную relation orders из учебного CSV;
  2. запускает outputs/paid_rub_orders.sql;
  3. читает outputs/select_result_contract.json;
  4. сравнивает столбцы, типы, grain и порядок;
  5. сопоставляет SQL-результат с ручной таблицей.

Python DB API, параметры и управление connection не являются материалом этого урока. Здесь достаточно запустить runner и изучать SQL-артефакт. Программную границу DuckDB разберём в 04/10.

Успешный запуск заканчивается:

json
{
  "matches_manual": true
}

Не ограничивайтесь этим флагом. Откройте полный JSON и вручную подтвердите:

  • сначала идёт O1005, затем O1001;
  • суммы равны 1575.00 и 1260.00;
  • категории равны large и regular;
  • шесть столбцов совпадают с контрактом;
  • денежные поля остались DECIMAL(18,2).

Сломайте это

Поломка 1. Замените проекцию на SELECT *

Добавьте в источник технический столбец:

sql
ALTER TABLE orders ADD COLUMN internal_note VARCHAR;

При SELECT * он попадёт в результат без решения автора запроса. Явный select list сохранит прежние шесть столбцов.

Поломка 2. Уберите скобки из смешанного AND / OR

Сравните:

sql
WHERE status = 'paid'
  AND (currency = 'RUB' OR currency = 'EUR')

и:

sql
WHERE status = 'paid'
  AND currency = 'RUB'
   OR currency = 'EUR'

Во втором случае найдите cancelled или refunded EUR-строку, которая неожиданно прошла фильтр.

Поломка 3. Попробуйте «исправить» ключ через DISTINCT

Скопируйте строку O1001 в источник и добавьте:

sql
SELECT DISTINCT ...

Точный дубль может исчезнуть из текущей проекции, но причина не устранена:

  • источник всё ещё нарушает grain;
  • изменение одного непроецируемого столбца снова проявит две строки;
  • автор не решил, какая версия заказа правильная;
  • DISTINCT скрыл evidence дефекта.

Сначала проверяют ключ и происхождение дубля. DISTINCT применяют только когда уникализация является объявленной операцией результата.

Поломка 4. Уберите tie-breaker

Добавьте заказ O1000 с суммой 1500.00. При:

sql
ORDER BY amount DESC

относительный порядок O1000 и O1005 не закреплён. Полный контракт:

sql
ORDER BY amount DESC, order_id ASC

Поломка 5. Измените alias или тип

Переименуйте amount_with_fee в total либо приведите его к DOUBLE. Число может выглядеть тем же, но контракт схемы должен остановить поставку.

Поломка 6. Добавьте выбранную строку без amount

Создайте оплаченный RUB-заказ с отсутствующей суммой. Входной контракт должен остановить расчёт до классификации. Не превращайте такую сумму в ноль и не отправляйте её автоматически в regular. Механизм NULL и трёхзначную логику разберём в следующем уроке.

Проверьте это

Проверка охватывает вход и результат.

Входные инварианты

  • relation называется orders;
  • одна строка означает один заказ;
  • order_id не повторяется;
  • необходимые столбцы существуют и типизированы;
  • у выбранного оплаченного RUB-заказа известна сумма.

Инварианты результата

  • grain остаётся одной строкой на order_id;
  • столбцы и их порядок точно совпадают с контрактом;
  • amount и amount_with_fee имеют тип DECIMAL(18,2);
  • ручные и SQL-значения совпадают;
  • граница 1300.00 относится к large;
  • при равной сумме order_id задаёт tie-breaker;
  • новый исходный столбец не протекает в проекцию;
  • дубликат ключа не маскируется как корректный результат.

  6. Microsoft Learn: выражение CASE — прочитайте «Поисковое выражение CASE», «Типы возвращаемых данных» и пример B: русское объяснение закрепляет правило «первое истинное условие побеждает» и показывает, почему ветви должны образовывать осмысленный выходной тип. Агрегаты и глубокую вложенность пока пропустите.
  7. DuckDB: ORDER BY Clause — разберите вводную часть и примеры с несколькими выражениями, ASC и DESC: добавление полного tie-breaker превращает просто отсортированный результат в воспроизводимый. ORDER BY ALL, collations и модификаторы порядка NULL пока не нужны.
  8. DuckDB: Numeric Types — прочитайте только Fixed-Point Decimals и итоговое сравнение DECIMAL с FLOAT: там точно определены precision и scale и объяснено, почему денежные суммы требуют десятичного типа. Продвинутые стадии пока просто пропустите и восстановите только цепочку текущего урока: FROM → WHERE → SELECT → ORDER BY → LIMIT.

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

В каком порядке полезно логически предсказывать результат простого запроса?

Сначала определяется источник строк, затем фильтр, после него проекция и вычисления, а готовый результат упорядочивается.

02

Почему SELECT * является слабым контрактом поставляемого результата?

Звездочка связывает выходную схему со всей текущей схемой источника. Явный select list сохраняет только осознанно выбранные поля.

03

Какую категорию должен вернуть CASE с условием amount >= 1300 для amount = 1300.00?

Оператор >= включает точку 1300.00 в ветку large. Граничные значения нужно фиксировать в ручном примере и тесте.

04

Как записать правило «оплаченный заказ и валюта RUB или EUR» без пропуска отмененных EUR-заказов?

Скобки объединяют допустимые валюты в одну часть условия. Без них ветка EUR может пройти независимо от статуса.

05

Как получить воспроизводимые десять крупнейших заказов, если суммы могут совпадать?

Сортировка по сумме задает основной приоритет, а уникальный order_id однозначно разрешает равенство перед LIMIT.

06

Что доказывает исчезновение точного дубля после SELECT DISTINCT?

DISTINCT уникализирует полную проекцию, но не объясняет происхождение дубля и не выбирает правильную версию сущности.

import json
from decimal import Decimal
from pathlib import Path
from typing import Any

import duckdb

ROOT = Path(__file__).resolve().parents[1]
QUERY_PATH = ROOT / "outputs" / "paid_rub_orders.sql"
CONTRACT_PATH = ROOT / "outputs" / "select_result_contract.json"
DATA_PATH = ROOT.parent / "data" / "tiny" / "orders.csv"


MANUAL_EXPECTED = [
    {
        "order_id": "O1005",
        "user_id": "U001",
        "currency": "RUB",
        "amount": "1500.00",
        "amount_with_fee": "1575.00",
        "amount_band": "large",
    },
    {
        "order_id": "O1001",
        "user_id": "U001",
        "currency": "RUB",
        "amount": "1200.00",
        "amount_with_fee": "1260.00",
        "amount_band": "regular",

def load_contract(path: Path = CONTRACT_PATH) -> dict[str, Any]:
    return json.loads(path.read_text(encoding="utf-8"))


def prepare_orders(
    connection: duckdb.DuckDBPyConnection,
    orders_path: Path = DATA_PATH,
) -> None:
    """Prepare the typed lesson fixture; ingestion itself is not the lesson outcome."""
    connection.execute("DROP TABLE IF EXISTS orders")
    connection.execute(
        """
        CREATE TABLE orders AS
        SELECT
            CAST(order_id AS VARCHAR) AS order_id,
            CAST(user_id AS VARCHAR) AS user_id,
            CAST(ordered_at AS VARCHAR) AS ordered_at,
            CAST(status AS VARCHAR) AS status,
            CAST(currency AS VARCHAR) AS currency,
            CAST(amount AS DECIMAL(18, 2)) AS amount
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        """,
        [str(orders_path)],
    )


def execute_select(
    connection: duckdb.DuckDBPyConnection,
    query_path: Path = QUERY_PATH,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    relation = connection.execute(query_path.read_text(encoding="utf-8"))
    columns = [item[0] for item in relation.description]
    types = [str(item[1]) for item in relation.description]
    return columns, types, relation.fetchall()


def validate_input(
    connection: duckdb.DuckDBPyConnection,
    contract: dict[str, Any],
) -> None:
    rows = connection.execute(
        "SELECT order_id, status, currency, amount FROM orders"
    ).fetchall()
    order_ids = [row[0] for row in rows]
    if len(order_ids) != len(set(order_ids)):
        raise ValueError("input grain violation for ['order_id']")

    rule = contract["business_rule"]
    target_missing = [
        row[0]
        for row in rows
        if row[1] == rule["status"]
        and row[2] == rule["currency"]
        and row[3] is None
    ]
    if rule["selected_amount_required"] and target_missing:
        raise ValueError(
            "selected paid RUB orders require amount; "
            f"missing for {target_missing}"
        )


def validate_result(
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
    contract: dict[str, Any],
) -> None:
    expected_columns = [item["name"] for item in contract["output"]["columns"]]
    expected_types = [item["type"] for item in contract["output"]["columns"]]
    if columns != expected_columns:
        raise ValueError(
            f"output columns do not match contract: expected {expected_columns}, got {columns}"
        )
    if types != expected_types:
        raise ValueError(
            f"output types do not match contract: expected {expected_types}, got {types}"
        )

    grain_columns = contract["output"]["grain"]
    grain_positions = [columns.index(column) for column in grain_columns]
    grain_values = [tuple(row[position] for position in grain_positions) for row in rows]
    if len(grain_values) != len(set(grain_values)):
        raise ValueError(f"output grain violation for {grain_columns}")

    amount_position = columns.index("amount")
    order_id_position = columns.index("order_id")
    expected_order = sorted(
        rows,
        key=lambda row: (-row[amount_position], row[order_id_position]),
    )
    if rows != expected_order:
        raise ValueError("output order does not match amount DESC, order_id ASC")


def _json_value(value: Any) -> Any:
    if isinstance(value, Decimal):
        return format(value, "f")
    return value


def rows_as_dicts(
    columns: list[str],
    rows: list[tuple[Any, ...]],
) -> list[dict[str, Any]]:
    return [
        {
            column: _json_value(value)
            for column, value in zip(columns, row, strict=True)
        }
        for row in rows
    ]


def run_example(orders_path: Path = DATA_PATH) -> dict[str, Any]:
    connection = duckdb.connect()
    try:
        prepare_orders(connection, orders_path)
        contract = load_contract()
        validate_input(connection, contract)
        columns, types, rows = execute_select(connection)
    finally:
        connection.close()

    validate_result(columns, types, rows, contract)
    actual = rows_as_dicts(columns, rows)
    return {
        "manual_expected": MANUAL_EXPECTED,
        "sql_result": actual,
        "contract": contract["output"],
        "matches_manual": actual == MANUAL_EXPECTED,
    }


def main() -> None:
    print(json.dumps(run_example(), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

-- Input relation:
--   orders(order_id, user_id, ordered_at, status, currency, amount)
-- Input grain:
--   one row per order, keyed by order_id
--
-- Output grain:
--   one paid RUB order
-- Output order:
--   amount DESC, then order_id ASC as a deterministic tie-breaker

SELECT
    order_id,
    user_id,
    currency,
    amount,
    round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2) AS amount_with_fee,
    CASE
        WHEN amount >= CAST(1300 AS DECIMAL(18, 2)) THEN 'large'
        ELSE 'regular'
    END AS amount_band
FROM orders
WHERE status = 'paid'
  AND currency = 'RUB'
ORDER BY amount DESC, order_id ASC;
