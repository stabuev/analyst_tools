Проверка перед уроком

Ответьте до чтения: результат поможет заметить исходные предположения.

01

Что нужно сделать до date_trunc, если моменты регистрации и активности должны попасть в месяцы одной business timezone?

Календарный месяц строят после отображения однозначного момента в явно выбранной business timezone. Настройка сессии не должна неявно задавать бизнес-календарь.

02

Полная таблица периодов соединяется с подсчитанной активностью. Как применить LEFT JOIN, чтобы сохранить период, для которого справа нет строки?

LEFT JOIN сохраняет все строки заранее построенной наблюдаемой сетки. Только после этого NULL числителя можно интерпретировать как отсутствие активности и заменить нулём.

03

События имеют grain одну строку на доставку event_id, а вопрос задан о пользователях, активных за месяц. Какой промежуточный grain нужен перед подсчётом?

Пара user_id, activity_month оставляет пользователю не более одного вклада в месячный числитель независимо от числа его настоящих событий.

Когорты на SQL

Чтобы сравнивать группы пользователей по возрасту, сначала зафиксируйте правило входа, правило активности, календарь и последний полностью наблюдаемый период.

Тип: Case Треки: Core Пререквизиты: 04/09 Время: ~105 минут Результат: строит месячную когортную матрицу активности с явными правилами входа, активности, календаря, горизонта наблюдения и фиксированным знаменателем.

Цели обучения

  • объяснять обычным языком, что такое когорта, месяц активности и возраст когорты;
  • записывать до SQL единицу наблюдения, правила входа и активности;
  • строить cohort_month и activity_month из типизированных моментов в одной business timezone;
  • различать технический повтор доставки события и несколько настоящих событий одного пользователя за месяц;
  • переводить календарный месяц активности в относительный period_index;
  • строить полную треугольную сетку только до явно заданного последнего завершённого месяца;
  • считать одного активного пользователя один раз за период и делить числитель на неизменный размер исходной когорты;
  • проверять grain, знаменатель, календарную ось и наблюдаемые нулевые ячейки.

Проблема

Команда хочет сравнить пользователей, зарегистрировавшихся в декабре, январе и феврале. Обычная таблица активности по календарным месяцам неудобна:

text
декабрьские пользователи в феврале прожили уже два месяца;
январские — один;
февральские только вошли в продукт.

Если поставить эти числа рядом как будто они относятся к одному этапу жизни, сравнение будет нечестным. Поэтому календарный месяц нужно перевести в возраст группы:

text
месяц входа -> period 0
следующий календарный месяц -> period 1
ещё через месяц -> period 2

Но одного номера периода недостаточно. Правдоподобно неверный результат получается, если:

  • сегодня считать активностью вход в приложение, а завтра — только оплату;
  • делить активных на число активных того же месяца;
  • считать события, хотя вопрос задан о пользователях;
  • принять отсутствие строки за нулевую активность, даже если месяц ещё не завершился;
  • строить месяц регистрации в UTC, а месяц активности в Москве.

Когортная таблица начинается не с GROUP BY, а с точного ответа на пять вопросов.

Вопрос Контракт этого урока
Кого считаем? уникальных пользователей user_id
Как пользователь входит в когорту? по моменту регистрации registered_at
Что считаем активностью? хотя бы одно событие app_open, order_paid или trial_started за месяц
В каком календаре строим месяцы? Europe/Moscow
До какого месяца данные полностью наблюдаемы? включительно до апреля 2026 года

В другой компании ответы будут другими. Важна не конкретная тройка событий, а привычка фиксировать правило до расчёта.

Концепция

1. Когорта — группа с общим правилом входа

Группа «пользователи тарифа premium» сама по себе не является временной когортой: пользователь может менять тариф. В этом уроке когорта определяется событием, которое случается один раз:

text
cohort_month = бизнес-месяц регистрации пользователя

Для пользователя U001 регистрация произошла в декабре 2025 года, значит:

text
user_id = U001
cohort_month = 2025-12-01

Первое число месяца — не точный момент регистрации. Это типизированная метка календарного периода.

2. Правило входа и правило активности — разные договорённости

Регистрация отвечает на вопрос «когда пользователь вошёл в группу». Активность отвечает на другой вопрос: «проявил ли он нужное поведение в данном месяце».

В reference-задаче любое событие из явного списка считается активностью. Несколько подходящих событий пользователя за один месяц всё равно дают один ответ:

text
пользователь был активен в месяце: да / нет

Регистрация хранится в таблице users, а не в списке событий активности. Поэтому period_index = 0 может иметь нулевую активность. Это не техническая ошибка: пользователь вошёл в когорту, но не совершил ни одного подходящего события в месяц регистрации.

В продуктовой задаче команда могла бы считать входом первый заказ, а активностью — повторный заказ. Тогда контракт и интерпретация результата изменились бы.

3. Календарный месяц превращается в возраст когорты

После 04/09 оба момента сначала переводятся в один бизнес-календарь:

sql
date_trunc(
    'month',
    timezone('Europe/Moscow', occurred_at)
)::DATE

Затем номер периода считается как число пересечённых границ месяца:

sql
date_diff('month', cohort_month, activity_month)

Примеры:

cohort_month activity_month period_index
2025-12-01 2025-12-01 0
2025-12-01 2026-01-01 1
2025-12-01 2026-04-01 4
2026-02-01 2026-04-01 2

Это календарное расстояние, а не число прошедших 30-дневных интервалов.

4. Дедупликация происходит на двух разных уровнях

В данных строка E0005 доставлена дважды. Обе копии описывают одно и то же реальное событие:

text
одинаковый event_id
-> одинаковые user_id, occurred_at и event_name
-> одна техническая доставка после дедупликации

Если две строки с одним event_id расходятся по пользователю, времени или типу события, нельзя молча выбрать одну. Это конфликт источника, который входная проверка должна остановить.

Но после технической дедупликации у U001 остаются два настоящих январских события: E0001 и E0002. Для пользовательской месячной активности они превращаются в одну строку:

text
grain = user_id, activity_month

Таким образом:

text
техническая дедупликация
    одна строка на реальное event_id

смысловая дедупликация
    один активный user_id на календарный месяц

Повтор E0005 сам по себе не завысит итоговую долю, если запрос позже корректно схлопывает данные до user_id, activity_month. Но очищать технические повторы всё равно нужно: они ломают grain событий и завышают метрики, считающие события, деньги или частоту действий.

5. Знаменатель фиксируется в момент входа

Для каждой когорты один раз считаем:

text
cohort_size = число пользователей, вошедших в cohort_month

Затем для каждого периода:

text
active_users =
    число участников этой когорты с подходящей активностью в activity_month

activity_rate =
    active_users / cohort_size

Знаменатель не уменьшается, когда часть пользователей перестаёт появляться. Иначе метрика отвечала бы на бессмысленный вопрос «какая доля активных была активна».

6. Ноль и неизвестное будущее нельзя смешивать

Предположим, апрель полностью закончился, а у февральской когорты в апреле не было ни одного события. Ячейка:

text
cohort_month = 2026-02-01
period_index = 2
active_users = 0

должна существовать: это наблюдаемый ноль.

Май ещё не закончился. Нулевую майскую ячейку строить нельзя: данных пока недостаточно. Поэтому горизонт задаётся явно:

text
last_complete_activity_month = 2026-04-01

Нельзя заменять его max(activity_month). Если в полностью наблюдаемом апреле не было ни одного события, максимум остановился бы на марте и скрыл реальный ноль.

7. Матрица имеет треугольную форму

При общем горизонте в апреле более старые когорты имеют больше наблюдаемых периодов:

text
декабрьская когорта: periods 0, 1, 2, 3, 4
январская когорта:   periods 0, 1, 2, 3
февральская когорта: periods 0, 1, 2

Это 5 + 4 + 3 = 12 строк. Будущие периоды молодых когорт отсутствуют, а наблюдаемые периоды без активности присутствуют с нулём.

8. Что именно мы называем результатом

Артефакт строит месячную когортную матрицу активности. Во многих командах похожую таблицу называют retention matrix. Однако профессиональное определение retention требует ещё точнее зафиксировать событие возврата и правило окна: активность ровно в периоде, активность начиная с периода, повторная покупка и другие варианты отвечают на разные вопросы.

Здесь важно освоить SQL-механику матрицы: cohort, relative period, фиксированный знаменатель, полный наблюдаемый grid. В фазе 08 курс отдельно разберёт методологию когортного анализа и определения retention.

Соберите это

Шаг 1. Назначьте пользователям месяц входа

После перевода registered_at в московский календарь получаем:

Когорта Участники cohort_size
2025-12-01 U001, U002 2
2026-01-01 U003, U004, U005 3
2026-02-01 U006, U007, U008 3

Grain этого промежуточного результата:

text
cohort_members: одна строка на user_id
cohort_sizes: одна строка на cohort_month

Шаг 2. Схлопните активность до пользователя и месяца

Сначала удалите точную повторную доставку E0005. Затем для каждого подходящего события постройте activity_month и оставьте уникальные пары:

text
user_id, activity_month

Например, два январских события U001 дают одну строку активности, а февральское событие того же пользователя — другую:

user_id activity_month
U001 2026-01-01
U001 2026-02-01

Шаг 3. Посчитайте одну когорту вручную

У декабрьской когорты два участника. До завершённого апреля её строки выглядят так:

period_index activity_month Активные Расчёт
0 2025-12-01 — 0 / 2 = 0.0
1 2026-01-01 U001, U002 2 / 2 = 1.0
2 2026-02-01 U001 1 / 2 = 0.5
3 2026-03-01 U002 1 / 2 = 0.5
4 2026-04-01 U001 1 / 2 = 0.5

Перед SQL предскажите две вещи:

  1. cohort_size должен оставаться равным 2 во всех пяти строках.
  2. Даже пустой period 0 должен существовать как строка.

Шаг 4. Нарисуйте полную сетку

Для каждой когорты нужны целые числа от нуля до её последнего наблюдаемого возраста. DuckDB возвращает их через табличную функцию:

sql
range(0, upper_bound)

Верхняя граница не включается. Поэтому для периодов 0..4 значение upper_bound должно быть равно 5.

Число строк зависит от конкретной когорты, поэтому range обращается к её cohort_month:

sql
CROSS JOIN LATERAL range(
    0,
    date_diff(
        'month',
        cohort_month,
        last_complete_activity_month
    ) + 1
) AS periods(period_index)

LATERAL здесь означает: выполнить правую табличную функцию отдельно для текущей строки слева. Декабрь получит пять периодов, январь — четыре, февраль — три.

Шаг 5. Присоедините фактическую активность

Сначала посчитайте активных на grain:

text
cohort_month, activity_month

Затем присоедините их к полной сетке через LEFT JOIN. Только после этого:

sql
coalesce(active_users, 0)

становится корректным. Ноль означает отсутствие активности внутри уже построенного наблюдаемого периода, а не попытку угадать ещё не наступившее будущее.

Используйте это

Артефакт outputs/monthly_cohort_activity.sql ожидает две уже типизированные relation:

text
users(
    user_id VARCHAR,
    registered_at TIMESTAMPTZ
)

events(
    event_id VARCHAR,
    user_id VARCHAR,
    occurred_at TIMESTAMPTZ,
    event_name VARCHAR
)

Загрузка CSV и преобразование строк во временные типы находятся в reference runner, а не в SQL-модели. Это продолжает контракт 04/09: когортный запрос получает однозначные моменты и занимается своей задачей, а не повторяет парсинг источника.

Цепочка CTE отражает последовательность рассуждения:

  1. settings объявляет business timezone и последний завершённый месяц;
  2. qualifying_event_names фиксирует бизнес-правило активности;
  3. cohort_members назначает пользователю месяц входа;
  4. cohort_sizes замораживает знаменатели;
  5. deduplicated_events убирает точные повторные доставки;
  6. qualifying_activity строит месяцы только для разрешённых событий;
  7. user_month_activity оставляет одну строку на пользователя и месяц;
  8. cohort_period_grid создаёт все наблюдаемые ячейки;
  9. active_users считает числители;
  10. финальный LEFT JOIN сохраняет нули и рассчитывает activity_rate.

Запустите reference-пример из корня репозитория:

bash
uv run --locked python phases/04-sql-and-duckdb/10-cohorts/code/main.py

Python здесь только подготавливает типизированные учебные таблицы, выполняет SQL и показывает результат. Пользовательского CLI у артефакта нет. Параметризацию SQL через Python вы построите в следующем уроке.

Сломайте это

1. Считайте строки событий вместо пользователей

count(*) непосредственно над events ответит на вопрос о числе строк. Активный пользователь с пятью событиями станет важнее пользователя с одним событием.

Как заметить: active_users может превысить cohort_size.

2. Смешайте два уровня дедупликации

DISTINCT event_id не заменяет уникальность user_id, activity_month: у одного пользователя могут быть несколько настоящих событий. И наоборот, схлопывание до пользователя не делает конфликтующие доставки одного event_id качественными данными.

Как заметить: отдельно проверить конфликтующие event_id, затем grain user_id, activity_month.

3. Возьмите активных как знаменатель

Деление active_users / active_users даст убедительные 100% даже для почти исчезнувшей когорты.

Как заметить: cohort_size должен вычисляться только из участников когорты и быть постоянным по всем её периодам.

4. Получите горизонт из последнего события

В полностью завершённом месяце может не быть активности. max(activity_month) удалит такой месяц вместе с важным нулём.

Как заметить: удалить все апрельские события; апрельские строки должны остаться, но получить active_users = 0.

5. Используйте INNER JOIN с активностью

Ячейки с нулём исчезнут, среднее по оставшимся строкам станет завышенным.

Как заметить: в reference-примере должно быть ровно 12 строк, включая три нулевых period 0.

6. Смешайте календари

Момент около полуночи или границы месяца попадёт в разные периоды в UTC и Москве.

Как заметить: смена timezone сессии не должна менять cohort_month и activity_month.

7. Не объявите набор событий активности

Технические логи, heartbeat или служебный retry начнут выглядеть как возвращение пользователя.

Как заметить: событие с именем вне allow-list не должно менять матрицу.

8. Молча потеряйте плохие связи

Обычный JOIN удалит событие неизвестного пользователя. Событие до регистрации создаст отрицательный возраст или попадёт в неожиданный период.

Как заметить: входная проверка отдельно останавливает orphan-события, конфликты event_id и активность до регистрации.

Проверьте это

Для reference-данных ожидаются:

  • размеры когорт 2, 3, 3;
  • 16 доставленных строк и 15 уникальных event_id;
  • 12 строк треугольной матрицы;
  • декабрьский period_index = 1: 2 / 2 = 1.0;
  • декабрьский period_index = 2: 1 / 2 = 0.5;

  • февральский period_index = 2: 1 / 3 = 0.3333.

  1. GA4: когортное исследование — на русском — прочитайте разделы о критериях включения и возврата, уровне детализации и типах расчёта. Они показывают, почему «когорта» задаётся двумя отдельными правилами и почему standard, rolling и cumulative ячейки нельзя называть одной метрикой.
  2. DuckDB: Date Functions — на английском — разберите контракты date_trunc, date_diff и date_sub. Особенно важно различие между числом пересечённых календарных границ и длиной прошедшего интервала: в уроке period_index использует именно первое.
  3. DuckDB: Range Functions — на английском — прочитайте подразделы range, generate_series и Date Ranges. Сравните исключаемую верхнюю границу range с включаемой границей generate_series и объясните + 1 в построении cohort grid.
  4. DuckDB: FROM and JOIN Clauses — на английском — сосредоточьтесь на разделе Lateral Joins и модели «правая часть выполняется для каждой строки слева». Это точный механизм, через который разные когорты получают разное число наблюдаемых периодов.
  5. DuckDB: SELECT и DISTINCT — на английском — сопоставьте DISTINCT и DISTINCT ON. Страница помогает увидеть, что удаление одинаковых строк и выбор одной строки по ключу — разные операции, а конфликтующие версии одного event_id требуют отдельной проверки, а не произвольного DISTINCT.
  6. DuckDB: Timestamp Issues — на английском — прочитайте Timestamp with Time Zone Promotion Casts и Half-Open Intervals. Примеры показывают, как timezone сессии незаметно меняет календарный отбор и почему business timezone должна оставаться частью контракта витрины.
  7. Postgres Pro: функции даты и времени — на русском — откройте подразделы date_trunc и AT TIME ZONE. Это перенос модели урока на PostgreSQL и дополнительная проверка порядка действий: сначала однозначный момент и выбранная зона, затем календарный период.
  8. Postgres Pro: функции, возвращающие множества — на русском — изучите таблицы и примеры generate_series для чисел и времени. Это PostgreSQL-вариант того же паттерна полного календарного каркаса, который в DuckDB построен через range.
  9. dbt-utils: SQL generators — на английском — найдите описания date_spine и deduplicate, а затем тест unique_combination_of_columns. Они показывают, как вынести календарную сетку, политику выбора дубля и проверку grain в переиспользуемые production-макросы, когда ручной SQL уже понятен.
  10. Amplitude: Retention Analysis FAQ — на английском — прочитайте ответы о расчёте точек, неполных последних периодах и изменяющемся знаменателе агрегированного графика. Сопоставьте их с фиксированным знаменателем строки нашей матрицы: источник хорошо показывает, почему без точного определения окна слово retention неоднозначно.

Quiz · 8 вопроса

Проверьте себя

Ответьте после практики. Объяснение появится сразу после выбора.

01

Какой знаменатель нужен для activity_rate во всех периодах одной когорты?

Когортная доля сравнивает активных с одним и тем же исходным составом. Уменьшение знаменателя вместе с оттоком искусственно завышает результат.

02

Почему после дедупликации event_id всё равно нужен DISTINCT по user_id и activity_month?

Техническая дедупликация восстанавливает grain событий, а смысловая дедупликация user-month отвечает на вопрос о числе активных пользователей.

03

В последнем завершённом месяце не было ни одного подходящего события. Что должно произойти с когортной матрицей?

Явный observation cutoff сообщает, что месяц наблюдался полностью. Отсутствие активности внутри этого горизонта является нулём, а не отсутствием строки.

04

Что означает period_index = 2 для месячной когорты?

Индекс задаёт относительный календарный возраст когорты. Он не считает события и не предполагает фиксированную длительность месяца.

05

Почему period 0 может иметь activity_rate = 0, хотя пользователи уже вошли в когорту?

Событие входа и событие активности могут различаться. В этом уроке регистрация формирует когорту, а активность определяется отдельным allow-list событий.

06

Почему полная матрица до общего апреля имеет треугольную, а не прямоугольную форму?

При одном календарном горизонте декабрьская когорта наблюдается дольше февральской. Наблюдаемые нули сохраняются, но ещё не наступившие периоды не создаются.

07

Событие с неизвестным user_id исчезает при JOIN с участниками когорт. Почему это нельзя считать нормальной фильтрацией?

Молчаливое исчезновение orphan-ключа делает результат правдоподобным, но скрывает неполноту связей. Политика качества должна быть явной.

08

Почему результат урока точнее называть месячной когортной матрицей активности, а не универсальным retention?

Матрица реализует конкретный контракт активности ровно в месяце. Другие определения возврата отвечают на другие вопросы и подробно рассматриваются в продуктовой фазе.

            CAST(user_id AS VARCHAR) AS user_id,
            CAST(occurred_at AS TIMESTAMPTZ) AS occurred_at,
            CAST(event_name AS VARCHAR) AS event_name
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        """,
        [str(events_path)],
    )


def _schema(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
) -> dict[str, str]:
    return {row[0]: str(row[1]) for row in connection.execute(f"DESCRIBE {relation}").fetchall()}


def _require_schema(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    expected: dict[str, str],
) -> None:
    actual = _schema(connection, relation)
    for column, expected_type in expected.items():
        actual_type = actual.get(column)
        if actual_type is None:
            raise ValueError(f"{relation} is missing required column {column}")
        if actual_type != expected_type:
            raise ValueError(f"{relation}.{column} must be {expected_type}, got {actual_type}")


def _require_populated(
    connection: duckdb.DuckDBPyConnection,
    relation: str,
    columns: tuple[str, ...],
) -> None:
    for column in columns:
        missing = connection.execute(
            f"""
            SELECT count(*)
            FROM {relation}
            WHERE {column} IS NULL
               OR (
                    typeof({column}) = 'VARCHAR'
                    AND trim(CAST({column} AS VARCHAR)) = ''
               )
            """
        ).fetchone()[0]
        if missing:
            raise ValueError(f"{relation}.{column} contains {missing} NULL or blank values")


def validate_inputs(connection: duckdb.DuckDBPyConnection) -> None:
    _require_schema(
        connection,
        "users",
        {
            "user_id": "VARCHAR",
            "registered_at": "TIMESTAMP WITH TIME ZONE",
        },
    )
    _require_schema(
        connection,
        "events",
        {
            "event_id": "VARCHAR",
            "user_id": "VARCHAR",
            "occurred_at": "TIMESTAMP WITH TIME ZONE",
            "event_name": "VARCHAR",
        },
    )
    _require_populated(connection, "users", ("user_id", "registered_at"))
    _require_populated(
        connection,
        "events",
        ("event_id", "user_id", "occurred_at", "event_name"),
    )

    duplicate_user = connection.execute(
        """
        SELECT user_id
        FROM users
        GROUP BY user_id
        HAVING count(*) > 1
        LIMIT 1
        """
    ).fetchone()
    if duplicate_user is not None:
        raise ValueError(f"users grain violation for user_id: {duplicate_user[0]}")

    conflicting_event = connection.execute(
        """
        SELECT event_id
        FROM events
        GROUP BY event_id
        HAVING count(DISTINCT user_id) > 1
            OR count(DISTINCT occurred_at) > 1
            OR count(DISTINCT event_name) > 1
        LIMIT 1
        """
    ).fetchone()
    if conflicting_event is not None:
        raise ValueError(
            f"events contains conflicting deliveries for event_id: {conflicting_event[0]}"
        )

    orphan_event = connection.execute(
        """
        SELECT events.event_id
        FROM events
        LEFT JOIN users USING (user_id)
        WHERE users.user_id IS NULL
        LIMIT 1
        """
    ).fetchone()
    if orphan_event is not None:
        raise ValueError(f"events contains an unknown user: {orphan_event[0]}")

    event_before_registration = connection.execute(
        """
        SELECT events.event_id
        FROM events
        JOIN users USING (user_id)
        WHERE events.occurred_at < users.registered_at
        LIMIT 1
        """
    ).fetchone()
    if event_before_registration is not None:
        raise ValueError(
            f"events contains activity before registration: {event_before_registration[0]}"
        )


def execute_model(
    connection: duckdb.DuckDBPyConnection,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    relation = connection.execute(MODEL_SQL_PATH.read_text(encoding="utf-8"))
    columns = [description[0] for description in relation.description]
    types = [str(description[1]) for description in relation.description]
    return columns, types, relation.fetchall()


def validate_model(
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
) -> None:
    if columns != EXPECTED_COLUMNS:
        raise ValueError(f"cohort model columns must be {EXPECTED_COLUMNS}, got {columns}")
    if types != EXPECTED_TYPES:
        raise ValueError(f"cohort model types must be {EXPECTED_TYPES}, got {types}")

    cohort_at = columns.index("cohort_month")
    activity_at = columns.index("activity_month")
    period_at = columns.index("period_index")
    size_at = columns.index("cohort_size")
    active_at = columns.index("active_users")
    rate_at = columns.index("activity_rate")
    timezone_at = columns.index("business_timezone")
    cutoff_at = columns.index("last_complete_activity_month")

    if not rows:
        raise ValueError("cohort model must contain at least one observed period")

    grain = [(row[cohort_at], row[period_at]) for row in rows]
    if len(grain) != len(set(grain)):
        raise ValueError("cohort model grain must be unique")

    sizes_by_cohort: dict[Any, set[Any]] = {}
    periods_by_cohort: dict[date, set[int]] = {}
    cutoffs = {row[cutoff_at] for row in rows}
    timezones = {row[timezone_at] for row in rows}
    if len(cutoffs) != 1 or len(timezones) != 1:
        raise ValueError("settings must stay constant across the cohort model")
    cutoff = next(iter(cutoffs))

    for row in rows:
        sizes_by_cohort.setdefault(row[cohort_at], set()).add(row[size_at])
        periods_by_cohort.setdefault(row[cohort_at], set()).add(row[period_at])
        if row[size_at] <= 0:
            raise ValueError("cohort_size must be positive")
        if row[active_at] < 0 or row[active_at] > row[size_at]:
            raise ValueError("active_users must be between zero and cohort_size")
        if row[rate_at] < 0 or row[rate_at] > 1:
            raise ValueError("activity_rate must be between zero and one")
        if row[rate_at] != round(row[active_at] / row[size_at], 4):
            raise ValueError("activity_rate must use active_users / cohort_size")
        cohort_month: date = row[cohort_at]
        month_number = cohort_month.month - 1 + row[period_at]
        expected_month = date(
            cohort_month.year + month_number // 12,
            month_number % 12 + 1,
            1,
        )
        if row[activity_at] != expected_month:
            raise ValueError("activity_month must equal cohort_month shifted by period_index")
        if row[activity_at] > row[cutoff_at]:
            raise ValueError("activity_month must not exceed the observation cutoff")

    if any(len(sizes) != 1 for sizes in sizes_by_cohort.values()):
        raise ValueError("cohort_size must stay fixed within a cohort")
    for cohort_month, actual_periods in periods_by_cohort.items():
        last_period = (cutoff.year - cohort_month.year) * 12 + cutoff.month - cohort_month.month
        expected_periods = set(range(last_period + 1))
        if actual_periods != expected_periods:
            raise ValueError(
                "cohort periods must form a complete grid through the observation cutoff"
            )


def main() -> None:
    connection = duckdb.connect()
    try:
        connection.execute("SET TimeZone = 'UTC'")
        prepare_inputs(connection)
        validate_inputs(connection)
        columns, types, rows = execute_model(connection)
        validate_model(columns, types, rows)
    finally:
        connection.close()

    manual_december = {
        "cohort_size": 2,
        "period_0": {"active_users": 0, "activity_rate": 0.0},
        "period_1": {"active_users": 2, "activity_rate": 1.0},
        "period_2": {"active_users": 1, "activity_rate": 0.5},
    }
    report = {
        "manual_december": manual_december,
        "model": {
            "columns": columns,
            "types": types,
            "rows": [dict(zip(columns, row, strict=True)) for row in rows],
        },
    }
    print(json.dumps(report, ensure_ascii=False, indent=2, default=str))


if __name__ == "__main__":
    main()

-- Input contract:
-- users has grain one row per unique non-NULL user_id and contains
-- registered_at TIMESTAMPTZ;
-- events contains non-NULL event_id, user_id, occurred_at TIMESTAMPTZ and
-- event_name; repeated deliveries of one event_id must be exact copies;
-- every events.user_id must exist in users and an event cannot precede the
-- user's registration moment.
--
-- Output contract:
-- grain is one row per cohort_month and period_index;
-- cohort and activity months use the same explicit business timezone;
-- only the named activity events count;
-- one user contributes at most once to one activity month;
-- cohort_size is fixed for every period of one cohort;
-- the grid ends at last_complete_activity_month, so a missing activity row
-- inside the grid is an observed zero rather than an unobserved future period.

WITH settings AS (
    SELECT
        'Europe/Moscow'::VARCHAR AS business_timezone,
        DATE '2026-04-01' AS last_complete_activity_month
),
qualifying_event_names(event_name) AS (
    VALUES
        ('app_open'),
        ('order_paid'),
        ('trial_started')
),
cohort_members AS (
    SELECT
        users.user_id,
        CAST(
            date_trunc(
                'month',
                timezone(settings.business_timezone, users.registered_at)
            )
            AS DATE
        ) AS cohort_month
    FROM users
    CROSS JOIN settings
),
cohort_sizes AS (
    SELECT
        cohort_month,
        count(*) AS cohort_size
    FROM cohort_members
    CROSS JOIN settings
    WHERE cohort_month <= settings.last_complete_activity_month
    GROUP BY cohort_month
),
deduplicated_events AS (
    SELECT DISTINCT
        event_id,
        user_id,
        occurred_at,
        event_name
    FROM events
),
qualifying_activity AS (
    SELECT
        deduplicated_events.user_id,
        CAST(
            date_trunc(
                'month',
                timezone(settings.business_timezone, deduplicated_events.occurred_at)
            )
            AS DATE
        ) AS activity_month
    FROM deduplicated_events
    JOIN qualifying_event_names USING (event_name)
    CROSS JOIN settings
),
user_month_activity AS (
    SELECT DISTINCT
        cohort_members.user_id,
        cohort_members.cohort_month,
        qualifying_activity.activity_month
    FROM cohort_members
    JOIN qualifying_activity USING (user_id)
    CROSS JOIN settings
    WHERE qualifying_activity.activity_month >= cohort_members.cohort_month
      AND qualifying_activity.activity_month
            <= settings.last_complete_activity_month
),
cohort_period_grid AS (
    SELECT
        cohort_sizes.cohort_month,
        CAST(
            cohort_sizes.cohort_month
                + periods.period_index * INTERVAL '1 month'
            AS DATE
        ) AS activity_month,
        periods.period_index,
        cohort_sizes.cohort_size
    FROM cohort_sizes
    CROSS JOIN settings
    CROSS JOIN LATERAL range(
        0,
        date_diff(
            'month',
            cohort_sizes.cohort_month,
            settings.last_complete_activity_month
        ) + 1
    ) AS periods(period_index)
),
active_users AS (
    SELECT
        cohort_month,
        activity_month,
        count(*) AS active_users
    FROM user_month_activity
    GROUP BY cohort_month, activity_month
)
SELECT
    cohort_period_grid.cohort_month,
    cohort_period_grid.activity_month,
    cohort_period_grid.period_index,
    cohort_period_grid.cohort_size,
    coalesce(active_users.active_users, 0) AS active_users,
    round(
        coalesce(active_users.active_users, 0)::DOUBLE
            / cohort_period_grid.cohort_size,
        4
    ) AS activity_rate,
    settings.business_timezone,
    settings.last_complete_activity_month
FROM cohort_period_grid
LEFT JOIN active_users
  ON cohort_period_grid.cohort_month = active_users.cohort_month
 AND cohort_period_grid.activity_month = active_users.activity_month
CROSS JOIN settings
ORDER BY cohort_period_grid.cohort_month, cohort_period_grid.period_index;
