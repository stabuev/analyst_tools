В pandas сравнение отсутствующей суммы с порогом дало pd.NA. Какой принцип из предыдущих уроков нужно перенести в SQL?

Nullable-маска не принимает бизнес-решение за аналитика: судьбу неизвестного условия нужно определить явно.

NULL и трёхзначная логика

Если факта нет, SQL не обязан отвечать «да» или «нет»: условие может остаться неизвестным, а политику такого результата выбирает аналитик.

Тип: Learn Треки: Core Пререквизиты: 04/02 Время: ~90 минут Результат: для сравнений и составных условий предсказывает TRUE, FALSE и UNKNOWN, объясняет поведение WHERE и CASE и задаёт явную политику NULL без подмены неизвестного нулём.

Цели обучения

После урока вы сможете:

  • отличить NULL в данных от логического результата UNKNOWN;
  • предсказать TRUE, FALSE и UNKNOWN для сравнения, NOT, AND и OR;
  • объяснить, почему WHERE сохраняет только TRUE, а отрицание фильтра не возвращает строки с неизвестным условием;
  • искать пропуски через IS NULL и IS NOT NULL, а не через = NULL;
  • не отправлять NULL в правдоподобную, но неверную ветку CASE;
  • выбрать и назвать политику: исключить неизвестное, сохранить для проверки или осознанно заменить результат через COALESCE;
  • проверить построчный SQL-аудит по ручной таблице и машинно-читаемому контракту.

На что опирается урок

Новый синтаксис здесь небольшой. Основная работа — перенести уже знакомую идею неопределённости в SQL.

Уже освоено Где Что переносим
пропуск отличается от нуля и ошибки разбора 03/02 NULL amount не означает сумму 0
сравнение nullable-значения может дать pd.NA 03/02–03/04 SQL-сравнение с NULL может дать UNKNOWN
судьба неизвестной маски требует явной политики 03/03–03/04 движок не должен молча решать бизнес-вопрос
выражения, CASE, WHERE, AND, OR 04/02 смотрим, как они ведут себя при неполных данных
grain и явная проекция 04/01–04/02 аудит сохраняет одну строку на order_id

Полезный мост:

text
pandas: неизвестное значение -> pd.NA в nullable-маске
SQL:    NULL в сравнении      -> UNKNOWN в логическом выражении

Механизмы похожи по смыслу, но синтаксис и точное поведение библиотек различаются. Поэтому в SQL мы заново проверим каждое правило на маленьких строках.

Проблема

В 04/02 мы построили условную категорию:

sql
CASE
    WHEN amount >= CAST(1300 AS DECIMAL(18, 2)) THEN 'large'
    ELSE 'regular'
END AS amount_band

Для выбранных оплаченных RUB-заказов входной контракт временно требовал известную сумму. Теперь это упрощение снимается. Представьте, что в выбранную популяцию попал заказ:

order_id status currency amount
O1999 paid RUB NULL

Можно ли утверждать, что его сумма не меньше 1300? Нет. Можно ли утверждать, что она меньше 1300? Тоже нет: самого факта пока не хватает.

Но прежний CASE ведёт себя так:

text
amount >= 1300 -> UNKNOWN
WHEN выбирается только при TRUE
UNKNOWN не выбирает WHEN
срабатывает ELSE -> 'regular'

Запрос исполняется и выдаёт правдоподобную категорию. Именно поэтому ошибка опасна: неизвестная сумма превращается не в явный сигнал, а в обычный заказ.

Та же проблема возникает при фильтрации. На двенадцати строках orders условие:

sql
amount > CAST(100 AS DECIMAL(18, 2))

подтверждается для шести заказов:

text
O1001, O1002, O1005, O1007, O1009, O1012

Его отрицание подтверждается только для четырёх:

text
O1003, O1006, O1010, O1011

Заказы O1004 и O1008 с отсутствующей суммой не попадают ни в один список. Отрицание не вернуло их, потому что «неизвестно, больше ли сумма порога» и «известно, что сумма не больше порога» — разные утверждения.

Концепция

NULL — маркер отсутствующего факта, а не обычное значение

В конкретном столбце NULL может означать:

  • факт пока не получен;
  • факт неприменим для этой строки;
  • источник разрешает отсутствие значения;
  • значение было потеряно раньше и требует расследования.

Точную предметную причину задаёт контракт данных. Сам SQL знает только одно: обычного значения в ячейке нет.

Сравните:

Запись в amount Что она утверждает
0.00 сумма известна и равна нулю
75.00 сумма известна и равна 75
NULL известной суммы нет
'' пустая строка; для типизированного DECIMAL это обычно не сумма, а проблема границы чтения

Поэтому автоматическая замена NULL на 0 не «чинит формат». Она добавляет новый бизнес-факт: «отсутствующая сумма считается нулевой».

UNKNOWN — третий результат условия

Обычная логика предлагает два ответа:

text
TRUE  -> условие подтверждено
FALSE -> условие опровергнуто

При неполных данных нужен третий:

text
UNKNOWN -> известных фактов недостаточно, чтобы выбрать TRUE или FALSE

Например:

Выражение Результат Объяснение
120 > 100 TRUE известное значение проходит порог
80 > 100 FALSE известное значение не проходит порог
NULL > 100 UNKNOWN сравнивать нечего
NULL = NULL UNKNOWN нельзя доказать равенство двух отсутствующих фактов
NULL <> 0 UNKNOWN нельзя доказать отличие неизвестного значения от нуля

UNKNOWN — логический результат. В DuckDB булев результат с таким смыслом отображается как NULL.

Фраза «любая операция с NULL даёт UNKNOWN» была бы слишком грубой. Специальная проверка отсутствия устроена иначе:

sql
amount IS NULL
amount IS NOT NULL

Она отвечает именно на вопрос о наличии значения и возвращает обычные TRUE или FALSE:

amount amount IS NULL amount IS NOT NULL
75.00 FALSE TRUE
0.00 FALSE TRUE
NULL TRUE FALSE

Именно поэтому искать пропуск через amount = NULL нельзя.

NOT не превращает неизвестность в знание

A NOT A
TRUE FALSE
FALSE TRUE
UNKNOWN UNKNOWN

Если мы не знаем, больше ли сумма 100, отрицание не добавляет сумму в источник:

text
amount > 100       -> UNKNOWN
NOT (amount > 100) -> UNKNOWN

Это объясняет, почему прямой и отрицательный фильтры могут вместе покрыть не все строки.

AND: FALSE уже достаточно

Полная таблица:

A B A AND B
TRUE TRUE TRUE
TRUE FALSE FALSE
TRUE UNKNOWN UNKNOWN
FALSE TRUE FALSE
FALSE FALSE FALSE
FALSE UNKNOWN FALSE
UNKNOWN TRUE UNKNOWN
UNKNOWN FALSE FALSE
UNKNOWN UNKNOWN UNKNOWN

Запоминать девять строк необязательно. Достаточно рассуждения:

  1. Если хотя бы одна часть точно FALSE, всё выражение AND уже FALSE.
  2. Если обе части точно TRUE, результат TRUE.
  3. В остальных случаях решение зависит от неизвестной части, поэтому результат UNKNOWN.

Пример:

sql
status = 'paid' AND amount > 100
  • для cancelled и NULL amount первая часть уже FALSE, поэтому всё условие FALSE;
  • для paid и NULL amount первая часть TRUE, а вторая UNKNOWN, поэтому всё условие UNKNOWN.

OR: TRUE уже достаточно

Полная таблица:

A B A OR B
TRUE TRUE TRUE
TRUE FALSE TRUE
TRUE UNKNOWN TRUE
FALSE TRUE TRUE
FALSE FALSE FALSE
FALSE UNKNOWN UNKNOWN
UNKNOWN TRUE TRUE
UNKNOWN FALSE UNKNOWN
UNKNOWN UNKNOWN UNKNOWN

Здесь правило зеркальное:

  1. Если хотя бы одна часть точно TRUE, всё выражение OR уже TRUE.
  2. Если обе части точно FALSE, результат FALSE.
  3. В остальных случаях результат зависит от неизвестной части.

Например, политика:

sql
amount > 100 OR amount IS NULL

явно сохраняет подтверждённо крупные заказы и заказы с неизвестной суммой для отдельной проверки.

WHERE сохраняет только TRUE

WHERE получает результат предиката — логического выражения, используемого как условие. Дальше правило простое:

Результат предиката Строка проходит WHERE
TRUE да
FALSE нет
UNKNOWN нет

FALSE и UNKNOWN одинаково не проходят фильтр, но не становятся одним и тем же логическим результатом. Это различие нужно сохранить до момента, когда аналитик выберет политику.

Безопасная последовательность:

text
1. Вычислить условие для всех строк.
2. Сделать UNKNOWN наблюдаемым.
3. Назвать предметную политику.
4. Только после этого фильтровать.

CASE WHEN тоже выбирает только TRUE

Searched CASE проверяет ветви сверху вниз. Ветка выбирается только тогда, когда её условие равно TRUE. FALSE и UNKNOWN передают управление следующему WHEN или ELSE.

Опасный вариант:

sql
CASE
    WHEN amount > 100 THEN 'above_threshold'
    ELSE 'at_or_below_threshold'
END

Для NULL amount первая ветка получает UNKNOWN, поэтому срабатывает ELSE. Результат утверждает, что сумма не выше порога, хотя этого никто не доказал.

Явная политика:

sql
CASE
    WHEN amount IS NULL THEN 'missing'
    WHEN amount > 100 THEN 'above_threshold'
    ELSE 'at_or_below_threshold'
END

Порядок читается как решение:

  1. сначала отделяем строки без факта;
  2. затем применяем порог к известным значениям;
  3. последняя ветка остаётся только для известных значений на границе или ниже неё.

COALESCE принимает решение, а не восстанавливает факт

COALESCE возвращает первый аргумент, который не равен NULL:

sql
coalesce(amount, 0)

Эта запись превращает неизвестную сумму в известный ноль. Она допустима только тогда, когда предметная область действительно считает эти состояния эквивалентными.

Можно разрешить неизвестность на уровне условия:

sql
coalesce(amount > 100, FALSE)

Теперь строка с неизвестной суммой не проходит критерий. Это может быть корректной политикой для автоматической отправки только подтверждённых заказов, но она всё равно должна быть названа:

text
UNKNOWN считается не прошедшим этот конкретный критерий.

В другой задаче неизвестные суммы нужно не исключить, а направить в очередь проверки. Тогда потребуется OR amount IS NULL или отдельная категория missing.

IS DISTINCT FROM — сравнение с явной политикой NULL

Обычные = и <> сохраняют UNKNOWN. Иногда нужно получить обычный двухзначный ответ, считая NULL сравнимым состоянием:

sql
amount IS DISTINCT FROM 0
Выражение Результат
0 IS DISTINCT FROM 0 FALSE
75 IS DISTINCT FROM 0 TRUE
NULL IS DISTINCT FROM 0 TRUE
NULL IS DISTINCT FROM NULL FALSE

Это полезный точный инструмент, но его смысл отличается от amount <> 0: новая запись явно утверждает, как сравнивать пропуски.

Соберите это

Сначала не пишите SQL. Постройте прозрачный результат для пяти сумм и порога 100.

Шаг 1. Объявите вход и правило

text
grain: одна строка на order_id
amount: DECIMAL(18, 2), NULL разрешён
threshold: 100.00
comparison: amount > threshold

Строгий знак > важен: значение ровно 100.00 относится к ветке at_or_below_threshold.

Шаг 2. Предскажите условие и его отрицание

order_id amount amount > 100 NOT (amount > 100)
A 120.00 TRUE FALSE
B 100.00 FALSE TRUE
C 80.00 FALSE TRUE
D 0.00 FALSE TRUE
E NULL UNKNOWN UNKNOWN

Строка E показывает ключевую идею: отрицательный фильтр не является «всем остальным».

Шаг 3. Отделите факт пропуска от порогового решения

Добавьте проверку и итоговое состояние:

order_id amount IS NULL amount_state
A FALSE above_threshold
B FALSE at_or_below_threshold
C FALSE at_or_below_threshold
D FALSE at_or_below_threshold
E TRUE missing

Проверьте четыре инварианта:

text
1. Число выходных строк равно числу входных строк.
2. Каждая строка получила ровно одно amount_state.
3. Для известной суммы условия amount > 100 и NOT(amount > 100) противоположны.
4. Для неизвестной суммы оба условия остаются UNKNOWN, а amount_state равен missing.

Шаг 4. Разделите настоящий tiny-набор по order_id

Не считайте строки агрегатной функцией — она появится в 04/04. Выпишите идентификаторы:

text
above_threshold:
O1001, O1002, O1005, O1007, O1009, O1012

at_or_below_threshold:
O1003, O1006, O1010, O1011

missing:
O1004, O1008

Объединение трёх непересекающихся списков должно восстановить все двенадцать order_id. Это ручной oracle для SQL.

Используйте это

Рабочий артефакт сохраняет все строки и делает каждый промежуточный результат наблюдаемым:

sql
SELECT
    order_id,
    amount,
    amount > CAST(100 AS DECIMAL(18, 2)) AS amount_above_threshold,
    NOT (amount > CAST(100 AS DECIMAL(18, 2))) AS amount_not_above_threshold,
    amount IS NULL AS amount_is_missing,
    CASE
        WHEN amount IS NULL THEN 'missing'
        WHEN amount > CAST(100 AS DECIMAL(18, 2)) THEN 'above_threshold'
        ELSE 'at_or_below_threshold'
    END AS amount_state
FROM orders
ORDER BY order_id ASC;

Обратите внимание на отсутствие WHERE: сейчас задача не выбрать финальную популяцию, а проверить, что произойдёт с каждой исходной строкой.

Столбец Что проверяет
amount_above_threshold исходный результат условия
amount_not_above_threshold что отрицание не возвращает UNKNOWN
amount_is_missing двухзначную проверку наличия значения
amount_state явную бизнес-классификацию без скрытого ELSE для пропуска

Из папки урока запустите reference runner:

bash
uv run --locked python code/main.py

Python здесь только:

  • создаёт типизированную relation orders;
  • выполняет SQL-файл;
  • сравнивает результат с ручной таблицей и контрактом.

Выбирайте WHERE после объявления политики

Если задача звучит «передать только подтверждённо крупные заказы», допустим фильтр:

sql
WHERE amount > CAST(100 AS DECIMAL(18, 2))

Но handoff должен явно говорить, что строки с неизвестной суммой не включены.

Если задача звучит «передать крупные заказы и все строки, которым не хватает суммы»:

sql
WHERE amount > CAST(100 AS DECIMAL(18, 2))
   OR amount IS NULL

Если неизвестные строки должны идти в отдельную ветку процесса, удобнее сначала создать amount_state, а затем фильтровать уже названные состояния в следующей стадии. Именованные SQL-стадии появятся в 04/06.

Сломайте это

Поломка 1. Искать пропуск через равенство

sql
WHERE amount = NULL

Для каждой строки сравнение получает UNKNOWN, поэтому WHERE не возвращает ничего. Правильно:

sql
WHERE amount IS NULL

Поломка 2. Считать отрицание дополнением

sql
WHERE amount > 100

и:

sql
WHERE NOT (amount > 100)

не покрывают строки с NULL amount. Если нужна полная проверка, отдельно найдите amount IS NULL и сверьте объединение трёх наборов с исходным grain.

Поломка 3. Спрятать пропуск в ELSE

sql
CASE
    WHEN amount > 100 THEN 'above_threshold'
    ELSE 'at_or_below_threshold'
END

Запрос работает, но NULL получает правдоподобную неверную категорию. Добавьте отдельную ветку WHEN amount IS NULL THEN 'missing'.

Поломка 4. Выдать техническую замену за факт

sql
coalesce(amount, 0)

После такой замены уже нельзя отличить настоящий нулевой заказ от заказа без суммы. Если нулевая замена действительно является правилом, сохраните рядом исходный признак amount IS NULL и опишите решение в контракте.

Поломка 5. Не заметить NULL внутри NOT IN

IN можно прочитать как цепочку сравнений через OR. Поэтому:

sql
'USD' NOT IN ('RUB', NULL)

логически похоже на:

text
NOT ('USD' = 'RUB' OR 'USD' = NULL)
NOT (FALSE OR UNKNOWN)
NOT UNKNOWN
UNKNOWN

В WHERE строка исчезнет. Если список допустимых значений пришёл из данных, сначала проверьте его на NULL и объявите политику. Вариант через NOT EXISTS появится после изучения подзапросов в 04/06.

Проверьте это

Behavioral tests проверяют не Python-оболочку, а наблюдаемую SQL-семантику:

  • все девять сочетаний для AND;
  • все девять сочетаний для OR;
  • NOT UNKNOWN;
  • различие NULL = NULL и NULL IS NULL;
  • правило WHERE: проходит только TRUE;
  • неполное покрытие прямого и отрицательного фильтров;
  • сохранение двенадцати строк в аудите;
  • отдельную категорию missing;
  • строгую границу amount > 100;
  • сохранение DECIMAL(18, 2);
  • grain order_id, явную проекцию и порядок;
  • осознанное разрешение UNKNOWN через COALESCE.

Ответьте после практики. Объяснение появится сразу после выбора.

01

Каков результат выражения amount > 100, если amount равен NULL?

Обычное сравнение с отсутствующим значением не даёт достаточно фактов для TRUE или FALSE и возвращает UNKNOWN.

02

Что вернёт NOT (amount > 100) для строки с NULL amount?

NOT меняет TRUE на FALSE и FALSE на TRUE, но не создаёт отсутствующий факт: NOT UNKNOWN остаётся UNKNOWN.

03

Почему CASE WHEN amount >= 1300 THEN 'large' ELSE 'regular' опасен для NULL amount?

Ветка WHEN выбирается только при TRUE. Для UNKNOWN управление переходит к следующей ветке или ELSE, поэтому пропуск нужно обработать отдельно.

04

Нужно оставить подтверждённо крупные заказы и не потерять заказы с неизвестной суммой. Какой фильтр выражает эту политику?

Первая ветка сохраняет подтверждённо крупные суммы, а IS NULL явно сохраняет строки, которым нужна отдельная проверка.

05

Когда допустимо написать coalesce(amount > 100, FALSE)?

COALESCE превращает UNKNOWN в выбранное решение. Это допустимо только как названная политика конкретной задачи, а не как автоматическая очистка.

def load_contract(path: Path = CONTRACT_PATH) -> dict[str, Any]:
    return json.loads(path.read_text(encoding="utf-8"))


def prepare_orders(
    connection: duckdb.DuckDBPyConnection,
    orders_path: Path = DATA_PATH,
) -> None:
    """Prepare the typed fixture; CSV ingestion and Python DB API are not lesson outcomes."""
    connection.execute("DROP TABLE IF EXISTS orders")
    connection.execute(
        """
        CREATE TABLE orders AS
        SELECT
            CAST(order_id AS VARCHAR) AS order_id,
            CAST(user_id AS VARCHAR) AS user_id,
            CAST(ordered_at AS VARCHAR) AS ordered_at,
            CAST(status AS VARCHAR) AS status,
            CAST(currency AS VARCHAR) AS currency,
            CAST(amount AS DECIMAL(18, 2)) AS amount
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        """,
        [str(orders_path)],
    )


def validate_input(
    connection: duckdb.DuckDBPyConnection,
    contract: dict[str, Any],
) -> None:
    grain = contract["input"]["grain"]
    rows = connection.execute("SELECT order_id FROM orders").fetchall()
    order_ids = [row[0] for row in rows]
    if any(order_id is None for order_id in order_ids):
        raise ValueError(f"input grain {grain} contains NULL")
    if len(order_ids) != len(set(order_ids)):
        raise ValueError(f"input grain violation for {grain}")


def execute_audit(
    connection: duckdb.DuckDBPyConnection,
    query_path: Path = QUERY_PATH,
) -> tuple[list[str], list[str], list[tuple[Any, ...]]]:
    relation = connection.execute(query_path.read_text(encoding="utf-8"))
    columns = [item[0] for item in relation.description]
    types = [str(item[1]) for item in relation.description]
    return columns, types, relation.fetchall()


def validate_result(
    columns: list[str],
    types: list[str],
    rows: list[tuple[Any, ...]],
    contract: dict[str, Any],
) -> None:
    expected_columns = [item["name"] for item in contract["output"]["columns"]]
    expected_types = [item["type"] for item in contract["output"]["columns"]]
    if columns != expected_columns:
        raise ValueError(
            f"output columns do not match contract: expected {expected_columns}, got {columns}"
        )
    if types != expected_types:
        raise ValueError(
            f"output types do not match contract: expected {expected_types}, got {types}"
        )

    grain = contract["output"]["grain"]
    grain_positions = [columns.index(column) for column in grain]
    grain_values = [tuple(row[position] for position in grain_positions) for row in rows]
    if len(grain_values) != len(set(grain_values)):
        raise ValueError(f"output grain violation for {grain}")

    order_id_position = columns.index("order_id")
    if rows != sorted(rows, key=lambda row: row[order_id_position]):
        raise ValueError("output order does not match order_id ASC")

    threshold = Decimal(contract["policy"]["threshold"])
    states = contract["policy"]["states"]
    positions = {column: columns.index(column) for column in columns}
    for row in rows:
        amount = row[positions["amount"]]
        above = row[positions["amount_above_threshold"]]
        not_above = row[positions["amount_not_above_threshold"]]
        is_missing = row[positions["amount_is_missing"]]
        state = row[positions["amount_state"]]

        if amount is None:
            if (above, not_above, is_missing, state) != (
                None,
                None,
                True,
                states["missing"],
            ):
                raise ValueError("missing amount lost UNKNOWN or explicit missing state")
            continue

        expected_above = amount > threshold
        expected_state = states["above"] if expected_above else states["not_above"]
        if (above, not_above, is_missing, state) != (
            expected_above,
            not expected_above,
            False,
            expected_state,
        ):
            raise ValueError("known amount does not match threshold policy")

def rows_as_dicts(
    columns: list[str],
    rows: list[tuple[Any, ...]],
) -> list[dict[str, Any]]:
    return [
        {
            column: _json_value(value)
            for column, value in zip(columns, row, strict=True)
        }
        for row in rows
    ]


def state_order_ids(rows: list[dict[str, Any]]) -> dict[str, list[str]]:
    states = sorted({str(row["amount_state"]) for row in rows})
    return {
        state: [
            str(row["order_id"])
            for row in rows
            if row["amount_state"] == state
        ]
        for state in states
    }


def run_example(orders_path: Path = DATA_PATH) -> dict[str, Any]:
    connection = duckdb.connect()
    try:
        prepare_orders(connection, orders_path)
        contract = load_contract()
        validate_input(connection, contract)
        columns, types, rows = execute_audit(connection)
    finally:
        connection.close()

    validate_result(columns, types, rows, contract)
    actual = rows_as_dicts(columns, rows)
    return {
        "manual_expected": MANUAL_EXPECTED,
        "sql_result": actual,
        "state_order_ids": state_order_ids(actual),
        "contract": contract["output"],
        "matches_manual": actual == MANUAL_EXPECTED,
    }


def main() -> None:
    print(json.dumps(run_example(), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

-- Expects a typed relation:
-- orders(order_id VARCHAR, amount DECIMAL(18, 2), ...)
--
-- The audit keeps every input row so that UNKNOWN remains observable before
-- a WHERE clause can remove it.

SELECT
    order_id,
    amount,
    amount > CAST(100 AS DECIMAL(18, 2)) AS amount_above_threshold,
    NOT (amount > CAST(100 AS DECIMAL(18, 2))) AS amount_not_above_threshold,
    amount IS NULL AS amount_is_missing,
    CASE
        WHEN amount IS NULL THEN 'missing'
        WHEN amount > CAST(100 AS DECIMAL(18, 2)) THEN 'above_threshold'
        ELSE 'at_or_below_threshold'
    END AS amount_state
FROM orders
ORDER BY order_id ASC;
