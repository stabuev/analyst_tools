# Путеводитель по фазе 03: pandas

Фаза учит не набору методов pandas, а одному рабочему процессу: превратить несколько
грязных таблиц в витрину, смысл и полноту которой можно проверить. Этот путеводитель
показывает связи между уроками и отделяет **порядок изучения** от **порядка выполнения**
готового пайплайна.

## Сквозная задача

Нужно собрать таблицу с grain «одна строка на заказ», добавить сумму товарных позиций и
данные пользователя, подготовить признаки для отчёта и передать результат вместе с
контрактом. Учебные источники лежат в `phases/03-pandas/data/tiny/`:

- `users.csv`: одна строка на пользователя;
- `orders.csv`: одна строка на заказ;
- `order_items.csv`: одна строка на товарную позицию заказа.

В данных намеренно есть пробелы и разный регистр в строках, разные timezone offsets,
пропуски, заказ неизвестного пользователя и категории, которые нужно привести к общему
словарю. Эти дефекты нельзя исправлять одной неявной «очисткой».

Создайте отдельную рабочую папку:

```bash
mkdir -p work/phase-03
```

Reference-функции находятся в `outputs/` соответствующих уроков. Не копируйте весь код
целиком. Сначала сформулируйте контракт шага, напишите собственную маленькую функцию и
только затем сравните её поведение с артефактом.

## Два порядка, которые нельзя путать

### Порядок изучения

Уроки выстроены по росту сложности:

| Урок | Новый учебный переход |
|---|---|
| `03/01` | Структура `DataFrame`/`Series`, маркированные оси, grain и ключ |
| `03/02` | Dtype, допустимый пропуск и неразбираемое значение |
| `03/03` | Выбор строк, nullable-маска и явная политика `NA` |
| `03/04` | Построчное преобразование с сохранением grain |
| `03/05` | Агрегация и переход к новой единице анализа |
| `03/06` | Сопоставление разных таблиц по ключу через `merge` |
| `03/07` | Сборка одинаковых партий строк через `concat` и явный порядок |
| `03/08` | Изменение wide/long-формы без скрытой агрегации |
| `03/09` | Время, длительности и локальный календарь |
| `03/10` | Нормализация текста и стабильный категориальный словарь |
| `03/11` | Композиция уже понятных функций в читаемый pipeline |
| `03/12` | Экспорт проверенной витрины и машинного манифеста |

`merge` и `concat` стоят рядом намеренно. Первый отвечает: «какая строка другой таблицы
соответствует этой сущности по ключу?». Второй отвечает: «как добавить новые наблюдения
того же типа?». Reshape появляется после них, потому что решает уже третий вопрос — как
расположить те же факты по осям.

### Порядок исполнения

В итоговом рабочем процессе функция из более позднего урока может выполняться раньше
функции из более раннего. Например, сначала нужно нормализовать `"paid"`, `" paid "` и
`"PAID"` по правилам `03/10`, а уже затем применять точный фильтр из `03/03`.

Общий контур выглядит так:

```text
каждая сырая партия
-> осмотреть структуру и grain
-> разобрать dtype, пропуски и ошибки
-> нормализовать предметные строки
-> объединить одинаковые партии через concat

order_items
-> построить line_total
-> агрегировать до order_id

orders + order_rollup + users
-> merge по объявленным ключам
-> нормализовать время и вывести календарные признаки
-> применить категориальные словари
-> выбрать строки или подготовить reshape для конкретного отчёта
-> собрать проверенные функции через pipe
-> проверить и экспортировать
```

Это не противоречие. Учебная последовательность вводит по одному механизму, а рабочая
последовательность следует зависимостям данных.

## 1. Осмотрите таблицу до вычислений

Начните с `orders.csv`, не меняя данные:

```python
from pathlib import Path

import pandas as pd

DATA = Path("phases/03-pandas/data/tiny")
orders_raw = pd.read_csv(DATA / "orders.csv")

print(orders_raw.shape)
print(orders_raw.columns.tolist())
print(orders_raw.dtypes)
print(orders_raw.head())
```

До следующего шага ответьте письменно:

1. Что означает одна строка?
2. Какой полный бизнес-ключ должен быть уникален?
3. Может ли `RangeIndex(0, 1, ...)` заменить этот ключ?
4. Какие повторы допустимы в `order_items`, но недопустимы в `orders`?
5. Какие проверки нужны кроме уникальности ключа?

Проверяйте missing, blank и дубликаты ключа отдельно. Успешный `is_unique` на
техническом индексе ничего не говорит о `order_id`.

## 2. Сделайте dtype-контракт явным

`read_csv` выводит dtype по текущему файлу. Смысл и допустимость пропуска задаёт
аналитик. Для `orders` минимальный контракт включает:

| Поле | Смысл | Целевой dtype на этой стадии | Пропуск |
|---|---|---|---|
| `order_id` | идентификатор заказа | `string` | запрещён |
| `user_id` | идентификатор пользователя | `string` | запрещён |
| `status` | исходный статус | `string` | политика объявляется явно |
| `currency` | код валюты | `string` | политика объявляется явно |
| `amount` | сумма заказа | `Float64` | разрешён учебным контрактом |
| `ordered_at` | исходное представление времени | `string` | разрешён до временного аудита |

Не перезаписывайте сырой столбец до проверки. Для числа сначала различите пустое значение
и непустую строку, которую parser не понимает:

```python
amount_raw = orders_raw["amount"].astype("string")
amount_missing = amount_raw.isna() | amount_raw.str.strip().eq("").fillna(False)
amount_parsed = pd.to_numeric(
    amount_raw.mask(amount_missing, pd.NA),
    errors="coerce",
)
amount_invalid = (~amount_missing) & amount_parsed.isna()

if amount_invalid.any():
    raise ValueError(amount_raw.loc[amount_invalid].to_dict())

orders_typed = orders_raw.assign(
    order_id=orders_raw["order_id"].astype("string"),
    user_id=orders_raw["user_id"].astype("string"),
    status=orders_raw["status"].astype("string"),
    currency=orders_raw["currency"].astype("string"),
    amount=amount_parsed.astype("Float64"),
    ordered_at=orders_raw["ordered_at"].astype("string"),
)
```

Точный временной parsing будет выполнен по контракту `03/09`, а не как побочный эффект
чтения CSV. `Float64` здесь остаётся учебным аналитическим типом; требования к точному
денежному хранению нужно объявлять отдельно.

## 3. Нормализуйте предметный текст до точного сравнения

В `orders.csv` есть `"paid"`, `" paid "` и `"PAID"`. Точный фильтр до нормализации
выберет только часть оплаченных заказов и даст правдоподобно заниженную метрику.

Используйте три отдельных решения из `03/10`:

```text
техническая нормализация -> Unicode, внешние пробелы, регистр, blank -> missing
aliases                  -> только явно подтверждённые предметные синонимы
словарь                  -> allowed, unknown и missing не смешиваются
```

Например, после `normalize_text`:

```python
status = normalize_text(
    orders_typed["status"],
    case="lower",
)
currency = normalize_text(
    orders_typed["currency"],
    case="upper",
)

orders_clean = orders_typed.assign(status=status, currency=currency)
```

Нормализатор не должен молча превращать любое неизвестное значение в `other`. Сначала
сохраните evidence и только затем примените выбранную политику категорий.

## 4. Соберите одинаковые партии строк

В tiny-наборе `orders.csv` один, но в рабочей практике это часто несколько дневных или
месячных файлов. Для упражнения разделите `orders_clean` на две части и представьте их
как независимые уже проверенные партии:

```python
order_batches = {
    "part-01": orders_clean.iloc[:4].copy(),
    "part-02": orders_clean.iloc[4:].copy(),
}
```

До `concat` подтвердите:

- одна строка каждой партии означает заказ;
- полный ключ — `order_id`;
- состав столбцов и dtype совпадают;
- имена партий отражают происхождение;
- ожидаемое число строк равно сумме строк партий.

Затем используйте контракт `03/07`:

```python
orders_all, concat_audit = concat_batches(
    order_batches,
    key=["order_id"],
)
```

`concat` добавляет наблюдения; он не сопоставляет заказ с пользователем. Если один
`order_id` оказался в двух партиях, не включайте `source_batch` в ключ автоматически и
не вызывайте слепой `drop_duplicates`: сначала выясните границы партий или правило
версий.

## 5. Выбирайте строки только после подготовки полей

Теперь точный фильтр из `03/03` работает с каноническими значениями:

```python
is_paid = orders_all["status"].eq("paid")
has_positive_amount = orders_all["amount"].gt(0)
paid_mask = is_paid & has_positive_amount
```

Сначала сохраните распределение `True`, `False` и `NA`, затем выберите политику для
unknown. Не превращайте `NA` в `False` в момент построения условия: это смешивает
неизвестность данных и предметный отказ.

Маска связана со строками индексом. Проверяйте уникальность индекса и точное совпадение
меток и порядка перед применением. Для изменения используйте одно присваивание через
`loc` на копии, а не chained assignment.

## 6. Разведите построчное преобразование и агрегацию

Для `order_items` сначала выполните тот же цикл структуры, dtype и строковой
нормализации. Затем постройте `line_total` операциями над `Series`:

```text
quantity * unit_price -> line_total
```

Этот шаг из `03/04` сохраняет grain товарной позиции, количество строк, индекс и
составной ключ `(order_id, product_id)`.

Только после него `03/05` меняет единицу анализа:

```text
вход  -> одна строка на товарную позицию
выход -> одна строка на заказ
```

На выходе `aggregate_order_items` должны остаться:

```text
order_id
line_count
known_amount_lines
missing_amount_lines
known_amount_total
order_amount
```

Проверьте три независимых инварианта:

```python
assert order_rollup["order_id"].is_unique
assert order_rollup["line_count"].sum() == len(items_clean)
assert (
    order_rollup["missing_amount_lines"].sum()
    == items_clean["line_total"].isna().sum()
)
```

Не заменяйте неизвестную позицию нулём. Сумма известных частей и строгая полная сумма
отвечают на разные вопросы.

## 7. Смоделируйте merge до вызова pandas

Перед каждым соединением заполните контракт:

| Левая таблица | Правая таблица | Ключ | Cardinality | `how` | Target grain |
|---|---|---|---|---|---|
| `orders_all` | `order_rollup` | `order_id` | one-to-one | left | заказ |
| результат | `users_clean` | `user_id` | many-to-one | left | заказ |

Затем используйте `merge_with_contract` или специализированный
`attach_order_rollup`. Проверьте отдельно:

- число строк и уникальность `order_id` результата;
- сохранение исходных значений заказов;
- уникальные `left_only` и `right_only` ключи;
- отсутствие размножения order-level метрик;
- явную политику заказа с неизвестным пользователем `U999`.

`indicator` конкретного left join не показывает правые orphan-ключи. Их множество нужно
сравнивать отдельно, как в `03/06`.

## 8. Нормализуйте время до календарных выводов

Строки `ordered_at` имеют разные явные offsets, а одна строка пропущена. Контракт
`03/09` сначала переводит допустимые timestamps в UTC, затем считает `Timedelta` между
согласованными моментами и только после этого выводит локальный день в выбранной
бизнес-timezone.

Проверьте:

- timestamp содержит явный offset, если он заявлен как момент времени;
- naive-время не принимается за UTC молча;
- отрицательная длительность не скрывается `abs`;
- `Timedelta` сохраняется до границы отчёта;
- `.dt.seconds` не подменяет полную длительность больше суток;
- локальный день вычисляется после `tz_convert`, а не из исходной строки.

Временной признак добавляет столбец и не должен менять order-level grain.

## 9. Используйте reshape как ветку, а не обязательную очистку

`melt` и `pivot` не обязаны находиться в основном пути сборки order mart. Они нужны,
когда конкретный график, отчёт или интерфейс требует wide- или long-форму.

Перед `melt` назовите:

```text
полный идентификатор wide-строки
уровни одной переменной в value_vars
ожидаемые строки = wide rows * number of value_vars
```

Перед `pivot` докажите уникальность полного ключа будущей ячейки. Если ключ повторяется,
не прячьте конфликт за `pivot_table` со случайным агрегатом. Сначала решите, является ли
повтор ошибкой данных или несколькими ожидаемыми наблюдениями.

## 10. Компонуйте функции только после локальной проверки

В `03/11` уже понятные стадии можно связать через `pipe` или обычную композицию. Это не
требование поместить весь проект в одно длинное выражение.

Хорошая структура рабочего каталога может быть такой:

```text
work/phase-03/
├── pipeline.py       # порядок стадий и входные параметры
├── checks.py         # проверки границ между стадиями
└── artifacts/        # локальные отчёты и итоговая витрина
```

Названия стадий должны выражать контракты:

```text
load raw
-> validate types
-> normalize text
-> concat batches
-> derive line values
-> aggregate items
-> merge entities
-> normalize time
-> apply category dictionaries
-> verify mart
-> export
```

Если промежуточный результат нужен для диагностики, теста или handoff, дайте ему имя.
Читаемость не измеряется минимальным числом переменных.

## 11. Финальная проверка и поставка

Перед `03/12` подтвердите:

- одна строка результата означает один заказ;
- `order_id` non-missing, non-blank и уникален;
- число строк согласовано с сохраняемой популяцией заказов;
- если одна сущность поступала несколькими партиями, каждая партия отражена в
  concat-аудите; для единственной партии этот шаг не нужен;
- dtype и схема соответствуют объявленному контракту;
- `paid` определяется по нормализованному статусу, а не по сырой строке;
- order-level суммы не размножились после joins;
- unmatched users сохранены с явным статусом и политикой;
- timestamps нормализованы в UTC, а календарный день имеет бизнес-timezone;
- unknown категории не смешаны с missing без evidence;
- экспорт содержит schema version, grain, проверки и checksums входов.

Только после этого формируйте файл витрины и машинный манифест. Успешная запись CSV или
Parquet подтверждает сериализацию, но не корректность аналитического результата.

## Карта ошибок для самостоятельной проверки

Намеренно воспроизведите хотя бы по одной ошибке каждого типа:

| Ошибка | Какой урок должен её поймать |
|---|---|
| Дубликат `order_id` в orders | `03/01` |
| Непустой неразбираемый `amount` | `03/02` |
| `NA` в составной маске | `03/03` |
| Несогласованный индекс Series при арифметике | `03/04` |
| Неполная сумма заказа | `03/05` |
| Many-to-many по слишком грубому ключу | `03/06` |
| Один заказ в двух партиях или schema drift | `03/07` |
| Повтор ключа pivot-ячейки | `03/08` |
| Naive timestamp или неверный локальный день | `03/09` |
| Unknown категория, потерянная при прямом `astype(category)` | `03/10` |
| Проверка, спрятанная внутри нечитаемой цепочки | `03/11` |
| Экспорт без grain и проверяемого манифеста | `03/12` |

После самостоятельного pipeline сравните решения с уроками `03/01`–`03/12`, запустите
только относящиеся к вашим изменениям тесты, затем пройдите перемешанную самопроверку:

```bash
uv run --locked python scripts/run_quiz.py --phase 3 --stage post --limit 8
```

Фаза освоена, если вы можете объяснить каждую границу таблицы, получить проверенный mart
на tiny-данных и диагностировать поломку по evidence, а не только добиться выполнения
кода без исключений.
