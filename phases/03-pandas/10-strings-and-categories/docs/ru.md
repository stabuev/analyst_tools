После урока вы сможете:

- отличать известную категорию, неизвестное непустое значение, агрегат `other` и пропуск;
- сохранять evidence до потенциально необратимого объединения значений.

## На что опирается урок

В `03/02` вы уже объявляли dtype и nullable-политику столбца. Там были введены nullable
`string`, `pd.NA`, `isna()` и важное различие между пустым значением и непустым
невалидным токеном. В `03/03` вы строили маски `isin` и не разрешали `NA` неявно.
В `03/04` применяли операции над `Series`, сохраняли индекс и избегали построчного
`apply` там, где есть табличная операция.

Уроки `03/05` и `03/06` показали цену несогласованных измерений:

- `groupby` создаёт отдельную группу для каждой фактической метки;
- `merge` сопоставляет точные ключи, а не «похожие по смыслу» строки;
- библиотека не знает, что `Addon` и `add-on` обозначают одно и то же.

В `03/09` вы отделяли исходную строку времени от разобранного `Timestamp` и проверяли

```text
сырой токен
→ прозрачное преобразование
→ отдельная проверка потерянных или неизвестных значений
→ только затем рабочий dtype
```

Это последний типовой этап очистки перед `03/11`. В следующем уроке числовые, временные
и строковые преобразования будут собраны в один проверяемый pipeline.

## Проблема

В таблице товарных позиций одна бизнес-категория записана четырьмя способами:

| `order_id` | Исходное `category` | Как читает человек | Как сравнивает pandas |
|---|---|---|---|
| `O1001` | `" add-on "` | add-on | отдельная строка с пробелами |
| `O1001` | `"Addon"` | add-on | отдельная строка без дефиса |
| `O1003` | `"ADD-ON"` | add-on | отдельная строка в другом регистре |
| `O1007` | `"add-on"` | add-on | ещё одна точная метка |

Прямой расчёт выглядит корректно:

```python
items.groupby("category", dropna=False)["quantity"].sum()
```

Но он ответит на технический вопрос «сколько строк имеет каждое точное представление»,
а не на бизнес-вопрос «сколько товаров каждой категории продано». Одна категория
распадётся на несколько групп, и итог будет правдоподобным: все строки учтены, сумма
сходится, исключения нет.

Та же проблема проявится в других операциях:

- `merge` не присоединит справочник для `" add-on "`, если его ключ — `"add_on"`;
- фильтр `eq("add_on")` пропустит только одно точное написание;
- `value_counts` покажет раздробленный словарь;
- сортировка расположит текст лексикографически, а не в бизнес-порядке;
- новая категория из свежей выгрузки может незаметно стать пропуском при неосторожном
  приведении к закрытому `category`.

Задача поэтому шире, чем «привести строки к нижнему регистру». Нужно объявить:

1. какие технические различия не меняют смысл;
2. какие разные токены являются известными синонимами;
3. какие канонические значения допустимы;
4. что делать с новым непустым значением;
5. как сохранить свидетельства о преобразовании.

## Концепция

### Четыре состояния нельзя смешивать

После очистки строковый признак может находиться в одном из четырёх состояний:

| Состояние | Пример | Что известно | Типичное решение |
|---|---|---|---|
| Известная категория | `premium` | значение входит в объявленный словарь | принять |
| Известный синоним | `Premium Plan` → `premium` | отображение утверждено явно | сохранить отображение в аудите |
| Unknown | `enterprise` | значение есть, но его смысл не разрешён контрактом | остановить или явно отправить в `other` |
| Missing | `pd.NA` или пустая строка по принятому правилу | значения нет | сохранить пропуск или применить отдельную nullable-политику |

Unknown и missing отвечают на разные вопросы.

- `pd.NA`: факт отсутствует.
- `enterprise`: факт присутствует, но текущий словарь его не знает.

Если оба состояния превратить в один пропуск, аналитик не отличит неполные данные от
изменения продуктового справочника. Если оба превратить в `other`, отсутствие факта
станет реальной бизнес-категорией.

### `string` задаёт текстовое хранение, но не смысл

Начинайте со строковой `Series`:

```python
raw = items["category"].astype("string")
```

Явный nullable `string` нужен по трём причинам:

- столбец больше не является общим контейнером `object`;
- пропуски доступны через `isna()`;
- строковые операции вызываются через единый accessor `.str`.

`.str` применяет операцию к каждому непропущенному значению `Series` и сохраняет её
индекс. Это важно для последующего присваивания обратно в `DataFrame`: результат
остаётся связан с исходными строками метками, а не только длиной.

```python
trimmed = raw.str.strip()

assert trimmed.index.equals(raw.index)
assert trimmed.isna().equals(raw.isna())
```

Однако dtype `string` не сообщает, что `basic` разрешён, `enterprise` неизвестен, а
`Premium` является вариантом `premium`. Эти решения относятся к отдельному предметному
контракту.

### Нормализация не угадывает бизнес-смысл

Техническая нормализация удаляет различия, которые договорились считать
несущественными:

- совместимое Unicode-представление;
- внешние пробелы;
- регистр;
- несколько согласованных разделителей;
- пустой результат после очистки.

Для категориальных кодов этого урока используем правило:

```text
NFKC
→ strip
→ casefold
→ пробелы, дефисы и подчёркивания заменить одним _
→ убрать крайние _
→ пустой результат считать missing
```

Примеры:

| Исходное значение | После технической нормализации |
|---|---|
| `" Premium "` | `premium` |
| `"ADD-ON"` | `add_on` |
| `"add on"` | `add_on` |
| `"Ａdd‑On"` | `add_on` |
| `"   "` | `pd.NA` |

`NFKC` приводит совместимые Unicode-формы к общему представлению. Например,
полноширинная латинская `Ａ` становится обычной `A`. `casefold` предназначен для
регистронезависимого сравнения и работает шире, чем `lower`.

Это правило не является универсальной очисткой любого текста. Его разумно применять к
машинным кодам, тегам, статусам и другим контролируемым значениям. Для имён людей,
адресов, комментариев и юридических названий такая нормализация может удалить значимое
различие. Там нужно хранить исходный текст и проектировать отдельный предметный контракт.

### Порядок этапов является частью контракта

Безопасный pipeline:

```text
1. техническая нормализация
2. проверка структуры строки
3. явная карта синонимов
4. проверка канонического словаря
5. политика unknown
6. создание category
```

Почему именно так:

- проверять `" ADD-ON "` по каноническому словарю слишком рано: технические различия
  создадут ложный unknown;
- применять aliases до нормализации неудобно: словарю придётся перечислять каждый
  регистр, пробел и вариант дефиса;
- приводить к `category` до проверки опасно: потерянное значение уже будет трудно
  отличить от исходного пропуска.

Карта aliases содержит только утверждённые предметные соответствия:

```python
aliases = {
    "addon": "add_on",
}
```

Техническое правило не должно самостоятельно решать, что `pro`, `premium` и `paid` —
один тариф. Такое объединение требует знания домена и отдельного изменения контракта.

### Минимальный строковый набор: нормализовать, проверить, извлечь

У `.str` много методов. Для основного маршрута сейчас нужны три вида действий.

#### 1. Нормализация

```python
normalized = (
    raw
    .str.normalize("NFKC")
    .str.strip()
    .str.casefold()
    .str.replace(r"[\s_\-‐‑‒–—]+", "_", regex=True)
    .str.strip("_")
)
```

Регулярное выражение здесь выполняет узкую работу:

- квадратные скобки обозначают один символ из перечисленного класса;
- `\s` означает пробельный символ;
- `+` означает один или несколько подряд;
- вся последовательность заменяется одним подчёркиванием.

Полный язык регулярных выражений для этого урока не нужен.

#### 2. Проверка всей строки

Для формата из двух заглавных латинских букв:

```python
country = users["country"].astype("string").str.strip().str.upper()
matches_format = country.str.fullmatch(r"[A-Z]{2}")
```

`fullmatch` проверяет всю строку. `contains` отвечает на другой вопрос — встречается ли
совпадение где-либо внутри:

| Значение | `contains("[A-Z]{2}")` | `fullmatch("[A-Z]{2}")` |
|---|---:|---:|
| `RU` | `True` | `True` |
| `RU-extra` | `True` | `False` |

Regex проверяет только форму. `ZZ` соответствует двум буквам, но не становится от этого
реальным кодом страны. Семантическая допустимость всё равно проверяется словарём.

#### 3. Извлечение структурированных частей

Если в одном текстовом поле записан составной токен, используйте именованные группы:

```python
labels = pd.Series(
    ["plan:premium", "plan:basic", pd.NA],
    dtype="string",
)

parts = labels.str.extract(
    r"^(?P<kind>[a-z_]+):(?P<value>[a-z_]+)$"
)
```

Результат — `DataFrame` с колонками `kind` и `value`. Строка, не совпавшая с шаблоном,
даст пропуски в извлечённых частях. Поэтому после `extract` нужно отдельно сравнить
непустой источник с неразобранным результатом — так же, как вы делали для чисел и дат.

`split`, `extractall` и сложные регулярные выражения изучаются по мере появления
реальной задачи. Каталог методов не заменяет модель проверки.

### Category — словарь, codes и признак порядка

Категориальная `Series` хранит:

1. массив допустимых значений `categories`;
2. целочисленный code для каждой строки;
3. флаг `ordered`.

Пример:

```python
plan_dtype = pd.CategoricalDtype(
    categories=["trial", "basic", "premium"],
    ordered=True,
)
```

| Значение | Внутренний code |
|---|---:|
| `trial` | `0` |
| `basic` | `1` |
| `premium` | `2` |
| missing | `-1` |

Codes являются внутренним представлением, а не бизнес-идентификаторами. Если изменить
порядок словаря, code изменится. В отчёт и обменный файл нужно передавать значения и
контракт, а не полагаться на число `0` или `1`.

Пропуск не входит в `categories`. Он хранится в значениях отдельно и получает code `-1`.
Именно поэтому неизвестное значение нельзя молча превращать в отсутствующее.

### `astype("category")` выводит словарь из текущих данных

Короткая запись:

```python
batch["plan"].astype("category")
```

создаёт словарь из значений конкретной порции. Это удобно для исследования, но слабо как
контракт production-pipeline:

```text
batch A → ["basic", "premium"]
batch B → ["basic", "enterprise", "premium"]
```

Одинаковый код создаёт разные dtype. Сравнение, конкатенация, сортировка и downstream-
проверки становятся зависимыми от того, какие значения случайно встретились сегодня.

Явный `CategoricalDtype` фиксирует один словарь для всех порций:

```python
plan_dtype = pd.CategoricalDtype(
    categories=["trial", "basic", "premium", "other"],
    ordered=True,
)
```

Неиспользованная сегодня категория остаётся частью контракта. Например,
`value_counts()` для categorical может показать её с нулевой частотой. Это полезно:
отсутствие наблюдений не стирает допустимый уровень шкалы.

### Category не является валидатором неизвестных значений

Рассмотрим:

```python
source = pd.Series(
    ["basic", "enterprise", pd.NA],
    dtype="string",
)

source.astype(
    pd.CategoricalDtype(["basic", "premium"])
)
```

В используемой версии pandas неизвестное `enterprise` при таком создании становится
missing и получает code `-1`; pandas также предупреждает, что это поведение меняется в
будущей версии. Исходный пропуск и новый тариф оказываются технически одинаковыми.

Если же categorical уже создан, присваивание значения вне словаря завершится ошибкой:

```python
plans.iloc[0] = "enterprise"
```

Это два разных сценария, но вывод один: сначала самостоятельно сравните непустые
канонические значения со словарём, затем вызывайте dtype-преобразование.

```python
unknown = normalized.notna() & ~normalized.isin(allowed)
```

### Политика `other` должна быть стабильной и наблюдаемой

Есть две основные политики unknown.

#### `error`

Остановить преобразование и показать значения с частотами:

```text
unknown categories: 'enterprise': 12, 'legacy': 3
```

Это правильный default для ключей справочников, критичных статусов и небольших
контролируемых словарей.

#### `other`

Явно объединить все неизвестные значения:

```text
enterprise ┐
legacy     ├→ other
partner    ┘
```

Эта политика допустима, если downstream-решению не требуется различать новые значения.
Но она необратима: после объединения по рабочему столбцу нельзя восстановить, какие
токены составляли `other`.

Поэтому хороший контракт:

- всегда включает `other` в итоговый dtype, даже если текущая порция не содержит unknown;
- сохраняет частоты исходных unknown до объединения;
- не отправляет в `other` настоящие пропуски;
- позволяет установить порог или alert на рост доли `other` в рабочем pipeline.

Если `other` добавляется только при встрече нового значения, schema меняется от порции к
порции. Это не стабильный контракт.

### Ordered означает предметный порядок

Без `ordered=True` категории являются именованными уровнями без отношения «меньше —
больше». При `ordered=True` сортировка и сравнения используют порядок `categories`:

```python
plan_dtype = pd.CategoricalDtype(
    ["trial", "basic", "premium", "other"],
    ordered=True,
)
```

Это уместно, только если бизнес действительно объявил порядок отчёта или шкалы.

- `low < medium < high` — естественный порядок.
- `trial < basic < premium` — допустимый порядок отчёта, если он утверждён владельцем.
- `service < subscription < add_on` — обычно просто произвольная последовательность,
  поэтому такая категория должна оставаться unordered.

Алфавитная сортировка строк не доказывает предметный порядок.

### Когда category уместен

Хорошие кандидаты:

- статус заказа из небольшого справочника;
- тариф из управляемого словаря;
- страна или канал привлечения при явном контракте;
- уровень шкалы с утверждённым порядком;
- повторяющийся признак, который downstream-инструмент должен воспринимать как
  categorical.

Плохие кандидаты:

- свободный комментарий;
- `order_id` или `user_id`;
- URL, email и другие почти уникальные строки;
- быстро растущий словарь без владельца;
- число, превращённое в текст только ради уменьшения числа уникальных значений.

Экономия памяти возможна, когда значения многократно повторяются. Category хранит codes
и отдельный словарь. Если число уникальных значений приближается к числу строк, словарь
может занять столько же или больше памяти, чем строковый столбец. Универсального порога
кардинальности нет — измеряйте `memory_usage(deep=True)` на своих данных. Главное
назначение в этом уроке — явная семантика и стабильное поведение, а не обещание
оптимизации.

### Граница урока

В основном маршруте достаточно:

- nullable `string`;
- нормализации контролируемых токенов;
- `fullmatch` и одного примера `extract`;
- aliases;
- unknown/missing policy;
- явного `CategoricalDtype`;
- ordered/unordered;
- evidence до `other`.

Здесь не нужны fuzzy matching, транслитерация, стемминг, токенизация естественного языка,
сложные regex-парсеры, locale-зависимое сопоставление имён и энциклопедия операций
`.cat`. Эти темы требуют отдельных задач и более сильных допущений.

## Соберите это

Сначала сделаем скрытые решения видимыми без pandas.

### Шаг 1. Объявите техническое правило для одного токена

```python
import re
import unicodedata


SEPARATORS = re.compile(r"[\s_\-‐‑‒–—]+")


def canonical_token(value: str | None) -> str | None:
    if value is None:
        return None

    normalized = unicodedata.normalize("NFKC", value)
    normalized = normalized.strip().casefold()
    normalized = SEPARATORS.sub("_", normalized).strip("_")

    return normalized or None
```

До запуска предскажите результат:

```python
raw_values = [
    " add-on ",
    "Addon",
    "ＡDD‑ON",
    "subscription",
    "   ",
    None,
    "enterprise",
]
```

Ожидаем:

```python
[
    "add_on",
    "addon",
    "add_on",
    "subscription",
    None,
    None,
    "enterprise",
]
```

`Addon` пока не стал `add_on`. Техническая нормализация не должна угадывать, что
отсутствующий разделитель не меняет бизнес-смысл.

### Шаг 2. Примените явные aliases

```python
aliases = {
    "addon": "add_on",
}

canonical_values = [
    aliases.get(value, value)
    if value is not None
    else None
    for value in map(canonical_token, raw_values)
]
```

Теперь первые три непустых варианта дают один `add_on`, а решение `addon → add_on`
видно в коде и может быть согласовано с владельцем данных.

### Шаг 3. Разделите known, unknown и missing

```python
allowed = {
    "add_on",
    "subscription",
    "service",
}

states = []
for value in canonical_values:
    if value is None:
        states.append("missing")
    elif value in allowed:
        states.append("known")
    else:
        states.append("unknown")
```

Контрольная таблица:

| Исходное значение | Канон | Состояние |
|---|---|---|
| `" add-on "` | `add_on` | known |
| `"Addon"` | `add_on` | known |
| `"ＡDD‑ON"` | `add_on` | known |
| `"subscription"` | `subscription` | known |
| `"   "` | missing | missing |
| `None` | missing | missing |
| `"enterprise"` | `enterprise` | unknown |

Эта таблица и есть прозрачный baseline. Она показывает, что библиотечный dtype позже
скроет за одним вызовом:

- нормализацию представления;
- утверждённые семантические отображения;
- классификацию значения;
- решение о потере информации.

### Шаг 4. Выберите политику до преобразования

Для `error` итог не строится, пока есть `enterprise`. Ошибка должна содержать само
значение и частоту.

Для `other` замените только unknown:

```python
prepared = [
    "other" if state == "unknown" else value
    for value, state in zip(canonical_values, states, strict=True)
]
```

Missing останется `None`. Отдельно сохраните:

```python
unknown_counts = {
    "enterprise": 1,
}
```

Только теперь можно безопасно создавать categorical dtype.

## Используйте это

### Векторная нормализация сохраняет ось

```python
raw = items["category"].astype("string")

normalized = (
    raw
    .str.normalize("NFKC")
    .str.strip()
    .str.casefold()
    .str.replace(r"[\s_\-‐‑‒–—]+", "_", regex=True)
    .str.strip("_")
)

normalized = normalized.mask(
    normalized.eq("").fillna(False),
    pd.NA,
)
normalized = normalized.replace(
    {"addon": "add_on"}
)

assert normalized.index.equals(items.index)
assert normalized.name == items["category"].name
```

`replace` здесь применяется после технической нормализации и выполняет только явную
карту aliases.

### Проверка unknown выполняется до dtype

```python
categories = [
    "add_on",
    "subscription",
    "service",
]

unknown = normalized.notna() & ~normalized.isin(categories)
unknown_counts = normalized.loc[unknown].value_counts()

if not unknown_counts.empty:
    raise ValueError(
        f"unknown categories: {unknown_counts.to_dict()}"
    )
```

Если политика разрешает `other`:

```python
final_categories = [
    "add_on",
    "subscription",
    "service",
    "other",
]

prepared = normalized.mask(unknown, "other")
```

Обратите внимание: `other` присутствует в `final_categories` всегда, а не только при
unknown в текущей порции.

### Явный dtype создаётся последним

```python
category_dtype = pd.CategoricalDtype(
    categories=final_categories,
    ordered=False,
)

items_clean = items.assign(
    category=prepared.astype(category_dtype)
)
```

Теперь словарь можно проверить независимо от фактических наблюдений:

```python
assert items_clean["category"].cat.categories.tolist() == [
    "add_on",
    "subscription",
    "service",
    "other",
]
```

contracted = categorize_text(

{

        "add_on": 4,

Именно audit делает политику `other` наблюдаемой. Рабочая `Series` удобна для расчёта,

### Ordered dtype объявляется только по предметному правилу

Итоговый словарь стабилен:

## Что сознательно остаётся за границей урока

- fuzzy matching и расстояния между строками;
- исправление опечаток без владельца справочника;
- транслитерация и locale-зависимые правила имён;
- очистка естественного языка, токенизация и NLP;
- полный синтаксис регулярных выражений;
- полный каталог `Series.cat`;
- объединение несовместимых categorical dtype между множеством источников;
- оптимизация памяти без измерения на реальных данных.

Если задача требует автоматически решить, что две разные строки обозначают одну
сущность, это уже entity resolution. Простая нормализация не даёт достаточных оснований
для такого вывода.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Canonical value | Самый частый вариант | Единственное договорённое представление значения после явных правил |
| Technical normalization | Исправление бизнес-смысла | Удаление согласованных различий представления без угадывания семантики |
| Alias | Любая похожая строка | Утверждённое отображение известного варианта в канон |
| Unicode normalization | Перевод текста на один язык | Приведение совместимых кодовых представлений к выбранной нормальной форме |
| `casefold` | Красивое форматирование регистра | Нормализация для регистронезависимого сопоставления |
| `fullmatch` | Поиск фрагмента | Проверка совпадения всей строки с шаблоном |
| Category vocabulary | Уникальные строки текущего файла | Явный стабильный набор допустимых значений |
| Category code | Постоянный бизнес-ID | Внутренняя позиция значения в текущем словаре |
| Ordered category | Category, которую можно сортировать | Категория с объявленным предметным порядком уровней |
| Unknown | То же, что missing | Непустое каноническое значение вне объявленного словаря |
| Missing | Строка `"unknown"` | Отсутствие значения по явной nullable-политике |
| `other` | Безопасное исправление любого unknown | Необратимое объединение неизвестных значений, требующее evidence |
| Unused category | Ошибка словаря | Допустимый уровень, не встретившийся в текущей порции |
