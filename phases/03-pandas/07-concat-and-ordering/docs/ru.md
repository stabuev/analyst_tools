# Concat, партии данных и порядок строк

> `merge` сопоставляет строки по ключу, а `concat` складывает одинаковые по смыслу
> партии строк. Успешный вызов ещё не доказывает, что партии совместимы.

**Тип:** Build

**Треки:** Core

**Пререквизиты:** 03/06

**Время:** ~45 минут

**Результат:** выбирает `concat` вместо `merge` для одинаковых по grain партий строк,
проверяет схему, dtype, происхождение и пересечения бизнес-ключей и задаёт
воспроизводимый порядок результата.

## Цели обучения

После урока вы сможете:

- отличить добавление строк через `concat` от сопоставления строк через `merge`;
- до объединения объявить общий grain, полный бизнес-ключ, схему и dtype партий;
- предсказать число строк и выполнить вертикальный `pd.concat` с новым техническим
  индексом;
- обнаружить дрейф схемы, dtype и пересечение бизнес-ключей;
- сохранить происхождение каждой строки в обычном столбце;
- задать полный воспроизводимый порядок с бизнес-ключом как tie-breaker;
- проверить строки, grain, схему, dtype, происхождение и индекс результата.

## Где мы находимся в маршруте

В `02/05` мы уже складывали однотипные наблюдения через `np.concatenate`. Там
совместимость означала согласованные размеры массивов, а одна перестановка сохраняла
связь между элементами нескольких массивов. pandas переносит тот же механизм на таблицы:

| NumPy из `02/05` | pandas в этом уроке |
|---|---|
| Добавить элементы вдоль существующей оси | Добавить строки одного grain |
| Согласовать остальные размеры | Согласовать набор столбцов и dtype |
| Применить одну перестановку ко всем массивам | Сортировать целые строки DataFrame |
| Позиции не имеют названий | Столбцы, индекс и пропуски имеют явный контракт |

В `03/06` мы разобрали другой вид объединения — таблицы с разными ролями:

```text
orders             -> одна строка на заказ
order_rollup       -> одна строка на заказ, другие столбцы
merge по order_id  -> сопоставить строки и добавить столбцы
```

Теперь возникает соседняя, но другая рабочая задача. Заказы приходят несколькими
файлами:

```text
orders_part_01     -> одна строка на заказ, столбцы order_id/status/amount
orders_part_02     -> одна строка на заказ, те же столбцы
concat по строкам  -> добавить наблюдения в одну таблицу
```

Именно поэтому `concat` расположен сразу после joins. Студент уже умеет объявлять grain,
бизнес-ключ и dtype, а теперь учится выбирать между двумя способами объединения:

| Вопрос | `merge` из 03/06 | `concat` в этом уроке |
|---|---|---|
| Что соединяем | Таблицы с разными ролями и столбцами | Партии строк одного типа |
| Как определяется соответствие | По бизнес-ключу | Соответствие строк не ищется |
| Что обычно растёт | Число столбцов; строки зависят от cardinality | Число строк |
| Главный риск | Размножение через неверную cardinality | Несовместимые партии или пересечение ключей |
| Базовая сверка | Прогноз по частотам ключа | Сумма строк всех партий |

Следующий урок `03/08` изменит форму уже одной собранной таблицы через `melt` и `pivot`.
Сначала нужно научиться получать эту таблицу без скрытого дрейфа и случайного порядка.

## Проблема

Сервис выгружает заказы двумя частями. В первой партии:

| `order_id` | `status` | `amount` |
|---|---|---:|
| `O1001` | `paid` | 1200.0 |
| `O1002` | `paid` | 800.0 |

Во второй:

| `order_id` | `status` | `amount` |
|---|---|---:|
| `O1003` | `refunded` | 5500.0 |
| `O1004` | `paid` | пропуск |

У обеих таблиц один контракт:

```text
grain              -> одна строка на заказ
бизнес-ключ        -> order_id
столбцы            -> order_id, status, amount
dtype              -> string, string, Float64
пропуск в amount   -> допустим и остаётся неизвестностью
```

Нужно получить четыре строки, а не искать пары заказов между файлами. `merge` здесь
задаёт неверный вопрос: он попытался бы сопоставить `O1001` из одной таблицы с `O1001`
из другой и расположить поля рядом. Нам нужно просто добавить вторую порцию наблюдений.

Кажется, что достаточно одной строки:

```python
orders = pd.concat([part_01, part_02])
```

Но pandas не знает предметного контракта. Он может технически собрать результат, даже
если:

- во второй партии исчез обязательный столбец;
- появился неожиданный новый столбец;
- `amount` прочитан как строка;
- один `order_id` попал в обе партии;
- старые технические индексы повторяются;
- порядок входных файлов изменился между запусками;
- происхождение проблемной строки потерялось.

Исключения может не быть. Поэтому задача урока — не запомнить `pd.concat`, а превратить
«сложить файлы» в проверяемую операцию над партиями одного типа.

## Концепция

### Сначала выберите операцию по смыслу

До API сформулируйте, что должно измениться:

```text
добавить признаки существующим сущностям -> merge по ключу
добавить наблюдения того же типа       -> concat по строкам
переставить уже имеющиеся факты        -> reshape в 03/08
```

Количество одинаковых столбцов не является достаточным признаком. Две таблицы могут
иметь одинаковые названия и всё равно описывать разные сущности или разные grain.

### Вертикальный concat добавляет строки

У `DataFrame` две оси:

- `axis=0`, или ось индекса, идёт вниз по строкам;
- `axis=1`, или ось столбцов, идёт вправо.

Для партий наблюдений нужен `axis=0`:

```python
combined = pd.concat(
    [part_01, part_02],
    axis=0,
    ignore_index=True,
    sort=False,
)
```

Это можно прочитать так:

```text
возьми строки первой таблицы
затем строки второй таблицы
согласуй их по названиям столбцов
создай новый технический индекс 0..n-1
```

Здесь `sort=False` относится не к порядку строк. При `axis=0` он запрещает pandas
сортировать метки другой оси — названия столбцов — во время их согласования. Порядок
строк задаётся отдельно через `sort_values`.

`concat` не проверяет `order_id` и не ищет пары. Строка `O1001` из двух партий даст две
строки результата. Если целевой grain обещает одну строку на заказ, пересечение нужно
обнаружить отдельной проверкой.

### Совместимость начинается с grain, затем проверяется технически

**Партия данных** — отдельная поставка одного логического набора. Она не создаёт новый
тип сущности и не меняет grain. Для безопасного объединения партии должны разделять один
контракт:

1. **Одинаковый grain.** Одна строка означает сущность одного типа.
2. **Один полный бизнес-ключ.** Одни и те же столбцы проверяют уникальность строки.
3. **Одинаковая схема.** Набор столбцов и их смысл совпадают.
4. **Одинаковые dtype.** Значения уже приведены по контракту `03/02`.
5. **Согласованная семантика пропусков.** `NA` означает одну и ту же неизвестность.

Совпадение названий проверяет только часть контракта: `amount` может означать сумму
заказа в одной партии и сумму позиции в другой. Если повтор ключа является версией, это
нужно выразить новым grain и полным ключом, например `order_id + effective_at`, а не
скрывать через `(source_batch, order_id)` или `drop_duplicates(keep="last")`.

### Что pandas сделает при дрейфе столбцов

По умолчанию `concat` согласует столбцы по их меткам и использует объединение столбцов.
Новый `channel` появится с `NA` в старых партиях. `join="inner"`, наоборот, молча
оставит только общие столбцы. Оба технически успешных результата способны спрятать
изменение поставки, поэтому точную схему нужно сравнивать до concat.

Порядок столбцов не несёт того же смысла, что их названия. Артефакт разрешает разный
физический порядок, но переставляет столбцы каждой партии по схеме первой и отражает это
в аудите.

### Dtype нужно согласовать до объединения

Если `amount` имеет `Float64` в первой партии и `string` во второй, pandas может выбрать
общий, более слабый dtype. Правильная последовательность знакома по `03/02`:

```text
сырая партия
-> отдельно разобрать и проверить значения
-> привести к объявленному dtype
-> только затем объединять
```

Артефакт не исправляет типы на лету: иначе источник дрейфа исчезнет из evidence.

Для расширенных типов одного имени бывает недостаточно, поэтому артефакт сравнивает сами
dtype-объекты. Категориальные словари подробно появятся в `03/10`.

### Базовая сверка — сумма строк партий

Если операция лишь добавляет наблюдения, ожидаемое число строк известно заранее:

```text
result_rows = rows(part_01) + rows(part_02) + ... + rows(part_n)
```

Для партий на 40, 35 и 25 строк ожидается 100 строк. Результат на 99 или 101 строку
нарушает контракт независимо от того, выглядит ли таблица правдоподобно.

Эта сверка не заменяет проверку бизнес-ключа:

- 100 строк могут содержать два представления одного заказа и не содержать другого;
- уникальный `order_id` не доказывает, что все ожидаемые партии загружены;
- обе проверки отвечают на разные вопросы.

### Происхождение лучше хранить обычным столбцом

Чтобы по ошибочной строке найти исходную поставку, добавьте происхождение до concat:

```python
part = frame.copy()
part["source_batch"] = batch_name
```

Так provenance остаётся доступным фильтрации, группировке и экспорту. Параметр `keys`
создал бы `MultiIndex`, но в основном маршруте происхождение остаётся обычным столбцом,
а индекс — технической осью.

### `ignore_index=True` решает только вопрос технического индекса

Каждая партия часто получает собственный `RangeIndex` `0..n-1`. Без
`ignore_index=True` метки повторятся: `0, 1, 0, 1`.

Если индекс не содержит бизнес-смысла, создайте новый:

```python
pd.concat(parts, ignore_index=True)
```

Это не удаляет повторные `order_id`: как и в `03/01`, индекс и бизнес-ключ — разные
контракты.

### Порядок поступления не равен бизнес-порядку

Вертикальный concat сохраняет последовательность переданных объектов и строк внутри
них. Но список файлов может измениться из-за обхода каталога, параллельной загрузки или
новой партии. Значит, «строка была первой» не является устойчивым бизнес-фактом.

Если порядок нужен для сравнения, экспорта или воспроизводимого теста, задайте его явно:

```python
combined.sort_values(
    by=["status", "order_id"],
    na_position="last",
    ignore_index=True,
)
```

`status` группирует строки, а уникальный `order_id` становится **tie-breaker** —
дополнительным правилом для равных значений. Без него порядок нескольких `paid`-заказов
может зависеть от входной последовательности партий.

Как и в `02/05`, стабильная сортировка сохраняет исходный порядок равных элементов, но
не делает неполный ключ сортировки полным. Если исходный порядок партий случаен, его
стабильное сохранение тоже не даёт воспроизводимости. Поэтому последним правилом должен
быть уникальный бизнес-ключ.

### Почему `concat(axis=1)` не заменяет merge

`pd.concat([orders, users], axis=1)` располагает столбцы рядом, выравнивая строки по
меткам индекса. Одинаковый `RangeIndex` не доказывает совпадение `user_id`. Для
сопоставления сущностей используйте `merge` из `03/06`; `axis=1` уместен только при
заранее проверенной общей индексной оси и здесь отдельно не изучается.

### Граница урока

Обязательный минимум — вертикальный concat одинаковых по grain партий, проверка схемы,
dtype, строк и ключа, provenance, новый индекс и полный порядок. `MultiIndex`,
горизонтальное выравнивание, `merge_ordered`, `merge_asof`, потоковая обработка и выбор
версии сущности требуют других задач и остаются за границей урока.

## Соберите это

Сначала воспроизведите механизм без pandas. Есть две партии как списки словарей:

```python
part_01 = [
    {"order_id": "O1001", "status": "paid", "amount": 1200.0},
    {"order_id": "O1002", "status": "paid", "amount": 800.0},
]
part_02 = [
    {"order_id": "O1003", "status": "refunded", "amount": 5500.0},
    {"order_id": "O1004", "status": "paid", "amount": None},
]
```

### Шаг 1. Объявите общий контракт

До объединения запишите:

```text
grain         -> одна строка на заказ
key           -> order_id
schema        -> order_id, status, amount
expected rows -> 2 + 2 = 4
```

### Шаг 2. Добавьте происхождение и строки

```python
manual = []
for batch_name, rows in [("part-01", part_01), ("part-02", part_02)]:
    for row in rows:
        manual.append({**row, "source_batch": batch_name})
```

Здесь виден механизм, который скроет `concat`:

1. строки не сопоставляются между собой;
2. каждая строка переносится один раз;
3. схема должна быть общей;
4. происхождение добавляется до потери границы партий.

### Шаг 3. Проверьте ключ и порядок

```python
keys = [row["order_id"] for row in manual]
assert len(manual) == len(part_01) + len(part_02)
assert None not in keys
assert len(keys) == len(set(keys))

manual = sorted(manual, key=lambda row: row["order_id"])
```

Теперь намеренно добавьте `O1002` во вторую партию. Сумма строк всё ещё сойдётся, но
уникальность ключа нарушится. Это показывает, почему одна сверка не заменяет другую.

## Используйте это

### Минимальный вызов pandas

Для уже типизированных таблиц:

```python
import pandas as pd

part_01_df = pd.DataFrame(part_01).astype(
    {"order_id": "string", "status": "string", "amount": "Float64"}
)
part_02_df = pd.DataFrame(part_02).astype(
    {"order_id": "string", "status": "string", "amount": "Float64"}
)

combined = pd.concat(
    [part_01_df, part_02_df],
    axis=0,
    ignore_index=True,
    sort=False,
)
```

Этот вызов выполняет саму операцию, но не проверяет предметный контракт. Поэтому рабочий
артефакт принимает именованные партии и ключ:

```python
from outputs.batch_concat import concat_batches

orders, audit = concat_batches(
    {
        "part-01": part_01_df,
        "part-02": part_02_df,
    },
    key=["order_id"],
)
```

Функция выполняет последовательность:

```text
проверить mapping и имена партий
-> проверить DataFrame и уникальные названия столбцов
-> сравнить точную схему и dtype
-> проверить non-missing/non-blank бизнес-ключ
-> добавить source_batch на копиях
-> pd.concat(axis=0, ignore_index=True)
-> сверить сумму строк
-> отклонить пересечение полного ключа
-> отсортировать по ключу
-> вернуть DataFrame и audit
```

### Явный ведущий порядок

Если для отчёта сначала нужен порядок загрузки, передайте существующий типизированный
столбец:

```python
orders, audit = concat_batches(
    batches,
    key=["order_id"],
    sort_by=["loaded_sequence"],
)
```

Артефакт добавит отсутствующие столбцы полного ключа в конец сортировки:

```text
effective sort -> loaded_sequence, order_id
```

Так равные `loaded_sequence` получают однозначный tie-breaker. Функция сортирует только
по возрастанию: редкие варианты направления лучше задавать отдельной прозрачной стадией,
чем раздувать первый контракт concat.

### Что находится в аудите

```python
{
    "batch_rows": {"part-01": 2, "part-02": 2},
    "result_rows": 4,
    "schema": ["order_id", "status", "amount"],
    "dtypes": {"order_id": "string", "status": "string", "amount": "Float64"},
    "key": ["order_id"],
    "effective_sort_columns": ["order_id"],
    "row_reconciliation_passed": True,
    "grain_valid": True,
}
```

Полный отчёт дополнительно сохраняет полученный порядок партий, имя provenance-столбца,
нормализацию порядка столбцов и политику индекса. Эти поля полезны при расследовании,
но не меняют основной критерий успешности.

Это не сертификат качества всех данных. Аудит подтверждает только заявленные инварианты
операции: совместимость партий, полноту переноса строк, уникальность объявленного ключа и
воспроизводимый порядок.

## Сломайте это

### 1. Выбрать неверную операцию или ось

`merge` начнёт искать пары по ключу, а `concat(axis=1)` выровняет строки по техническому
индексу. Ни одна операция не означает «добавить новые заказы». Сначала сформулируйте,
добавляются наблюдения или признаки, и только затем выбирайте API.

### 2. Смешать разные grain, схемы или dtype

Заказы и товарные позиции могут иметь похожие столбцы, но разный смысл строки. Новый
`channel`, исчезнувший `amount` или строковый dtype суммы тоже являются изменениями
контракта. `join="outer"` способен скрыть их через `NA`, а `join="inner"` — через потерю
столбца. Оба варианта требуют явного решения до concat.

### 3. Узаконить пересечение ключей техническим приёмом

Разные индексы и названия партий не превращают два `O1001` в разные заказы. Добавление
`source_batch` в бизнес-ключ или безусловный `drop_duplicates(keep="last")` лишь прячет
конфликт. Для версий нужен новый объявленный grain и предметное правило выбора.

### 4. Проверить только число строк

Сумма строк может сойтись, даже если один заказ представлен дважды, а другой отсутствует.
Поэтому row reconciliation и уникальность полного ключа проверяются независимо.

### 5. Потерять происхождение

После concat видно неверное значение, но уже неизвестно, какую партию исправлять.
`source_batch` нужно добавить до объединения; технический индекс происхождение не
заменяет.

### 6. Положиться на случайный или неполный порядок

Порядок файлов может измениться между запусками, а `sort_values("status")` не определяет
порядок внутри одинаковых статусов. Добавьте полный бизнес-ключ как последний
tie-breaker и только после этого сбрасывайте индекс.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Concat | Ещё один способ join по ключу | Объединение pandas-объектов вдоль выбранной оси без поиска пар по бизнес-ключу |
| Партия данных | Отдельный тип сущности | Часть одного логического набора, полученная отдельной поставкой |
| `axis=0` | Сортировка строк | Ось добавления строк при вертикальном concat |
| Schema drift | Любой другой порядок столбцов | Незаявленное изменение состава, смысла или контракта полей |
| Row reconciliation | Проверка уникальности ключа | Сверка числа строк результата с суммой строк партий |
| Provenance | Технический индекс строки | Явное происхождение наблюдения, например имя исходной партии |
| `ignore_index=True` | Удаление бизнес-дубликатов | Создание новой технической оси на результате |
| Tie-breaker | Случайный второй столбец | Дополнительное правило, однозначно упорядочивающее равные значения основного ключа сортировки |

- [pandas.concat API](https://pandas.pydata.org/docs/reference/api/pandas.concat.html) — используйте как точный справочник по `axis`, `join`, `ignore_index`, `keys`, `verify_integrity` и `sort`; отдельно проверьте, что `verify_integrity` относится к меткам оси concat, а не к бизнес-ключу в обычных столбцах.
- [pandas.DataFrame.duplicated](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.duplicated.html) — изучите `subset` и `keep=False`: так можно показать все строки с повторным полным ключом и сохранить evidence, не превращая поиск конфликта в безусловный `drop_duplicates`.
- [pandas.DataFrame.sort_values](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.sort_values.html) — сосредоточьтесь на нескольких столбцах в `by`, `na_position`, `ignore_index` и ограничении `kind`; сопоставьте их с правилом урока «бизнес-порядок плюс уникальный tie-breaker».
- [Postgres Pro: сочетание запросов `UNION`, `INTERSECT`, `EXCEPT`](https://postgrespro.ru/docs/postgrespro/current/queries-union) — русскоязычный перенос идеи в SQL: прочитайте про `UNION ALL`, совместимость числа и типов столбцов и отсутствие гарантированного порядка; сравните добавление строк с `concat(axis=0)` и не путайте его с удаляющим дубликаты `UNION`.
- [Postgres Pro: сортировка строк `ORDER BY`](https://postgrespro.ru/docs/postgrespro/current/queries-order) — прочитайте первые абзацы и правило нескольких выражений сортировки: без явного `ORDER BY` порядок не определён, а последующие выражения упорядочивают строки с равными предыдущими значениями — это SQL-аналог tie-breaker.
- [Postgres Pro: разрешение типов для `UNION`](https://postgrespro.ru/docs/postgrespro/current/typeconv-union-case) — разберите алгоритм согласования типов по каждому столбцу; материал показывает, почему технически найденный общий тип ещё не доказывает совпадение исходных контрактов.
- [NumPy: `numpy.concatenate`](https://numpy.org/doc/stable/reference/generated/numpy.concatenate.html) — вернитесь к условиям одинаковой формы вне выбранной оси и параметрам `axis`, `dtype`, `casting`; это точный мост от позиционных массивов `02/05` к маркированным таблицам pandas.
