# Pagination, timeouts и retries

> Многостраничная загрузка завершена только тогда, когда клиент дошёл до договорного
> конца, проверил общий grain и опубликовал весь снимок целиком.

**Тип:** Build  
**Треки:** Core  
**Пререквизиты:** 05/04  
**Время:** ~90 минут  
**Результат:** проходит все страницы одного JSON API по доверенной цепочке `next`,
ограничивает retries общим бюджетом и атомарно публикует результат только после
доказанного завершения и проверки grain.

## Цели обучения

- Отличать страницу ответа от полного набора данных.
- Следовать только договорному `next` до явного `null`, не угадывая число страниц.
- Разделять попытку, timeout, повтор страницы и общий retry budget загрузки.
- Повторять только безопасный `GET` при временной ошибке, учитывая `Retry-After` и jitter.
- Отклонять циклы, чужой origin, нарушение page contract и дубли бизнес-ключа.
- Не выдавать накопленные до ошибки записи за полный снимок и сохранять предыдущую поставку.

## Как этот урок продолжает маршрут

В `05/04` вы получили **один** JSON-ресурс и проверили его транспортный контракт:
точный status, media type, UTF-8, timeout, размер, redirect policy и атомарную запись.
Теперь сервер намеренно возвращает не все заказы сразу, а небольшие страницы:

```text
GET page=1 -> items O2301, O2302 -> next page=2
GET page=2 -> items O2303, O2304 -> next page=3
GET page=3 -> items O2305        -> next null
```

Новый механизм — не ещё один способ разобрать JSON. Клиент должен доказать, что прошёл
всю цепочку, ограничить цену временных сбоев и проверить единый grain уже **между**
страницами. Поэтому артефакт сохраняет гарантии `05/04`: только `200`, JSON в UTF-8,
ограниченный размер страницы, запрет автоматических redirects и явные timeouts.

После урока вы умеете получить полный снимок одного JSON API. В `05/06` источник станет
HTML и изменится способ извлечения полей. Кеш, checksum, manifest и повторное использование
уже загруженного raw-слоя остаются интеграционному уроку `05/11`.

## Проблема

Аналитик запускает ежедневную загрузку заказов. Первая страница вернула 200, вторая после
двух попыток ответила 503, а в каталоге уже появились записи с первой страницы.
Следующий расчёт прочитал файл и сообщил падение выручки. Технически JSON корректен, но
аналитически это правдоподобный неверный ответ: частичная выборка выглядит как полная.

Другой источник после редизайна начинает возвращать:

```json
{
  "items": [{"order_id": "O2304"}],
  "next": "https://api.example.test/orders?page=2"
}
```

со второй страницы снова на вторую. Без памяти о посещённых ссылках цикл не завершится.
Если ограничиться `max_pages`, процесс остановится, но это всё равно не успех: договорный
конец `next: null` не достигнут.

## Концепция

### 1. Страница — не полный набор

В уроке используется контракт страницы:

```json
{
  "items": [
    {"order_id": "O2301"},
    {"order_id": "O2302"}
  ],
  "next": "https://api.example.test/orders?page=2"
}
```

- `items` — записи только текущей страницы;
- `next` — выданный сервером переход к следующей странице;
- `next: null` — единственное договорное доказательство конца в этом API.

Пустой `items` сам по себе не означает конец. Некоторые API способны вернуть пустую
промежуточную страницу и непустой `next`. Отсутствующее поле `next` тоже нельзя молча
прочитать как `null`: контракт мог измениться, а клиент потеряет хвост данных.

У реальных API встречаются page numbers, offset/limit, cursor, page token и HTTP `Link`.
Их синтаксис разный, но инвариант один: клиент следует опубликованному механизмом API
переходу и заканчивает только по документированному признаку.

### 2. Цепочка имеет состояние и инварианты

Минимальное состояние обхода:

| Состояние | Зачем хранить |
|---|---|
| `current_url` | знать, какую страницу запросить сейчас |
| `visited` | не запросить уже посещённый переход повторно |
| `records` | накапливать записи только внутри ещё не опубликованного снимка |
| `seen_ids` | проверять единый grain между всеми страницами |
| `pages` | доказать путь и условие завершения |
| `retries` | сделать временные сбои и цену восстановления наблюдаемыми |

Для учебного набора grain — одна строка на уникальный `order_id`. Дубликат внутри страницы
ловится тем же правилом, что дубликат между первой и третьей страницами. Клиент не выбирает
«последнюю версию» дубликата: без предметного правила это замаскировало бы нестабильную
pagination или ошибку источника.

Переход `next` сначала разрешается относительно текущей страницы, а затем проверяется.
Артефакт разрешает только тот же scheme, host и port, что у начального URL. Он не следует
автоматическому HTTP redirect и не переносит сессию на чужой origin. Это прямое применение
границы безопасности из `05/04`.

### 3. Timeout, attempt и retry — разные величины

Пусть `max_retries_per_page=2`. Тогда одна страница получает не две, а максимум три
попытки:

```text
initial attempt -> retry 1 -> retry 2 -> stop
```

Timeout относится к каждой отдельной попытке. Он не ограничивает суммарное время обхода.
Поэтому нужны независимые пределы:

| Предел | Что ограничивает |
|---|---|
| connect/read timeout | одно сетевое ожидание |
| `max_retries_per_page` | повторы одной страницы |
| `max_total_retries` | сумму повторов всего снимка |
| `max_backoff` | допустимую паузу перед одним повтором |
| `max_pages` | длину ошибочной или неожиданной цепочки |
| `max_page_bytes` | память на одну декодированную JSON-страницу |

Только page-level предел выглядит конечным, но при 100 страницах и трёх повторах может
создать 300 дополнительных запросов. Общий бюджет делает верхнюю границу явной для всей
загрузки.

### 4. Повтор зависит от метода и причины

Урок повторяет только `GET`. По HTTP semantics он безопасен и идемпотентен: повтор
запрашивает то же представление и не должен создавать новую сущность. Это не разрешение
автоматически повторять любой `POST`: если сервер обработал создание, но ответ потерялся,
повтор может создать дубль.

Рабочая allowlist урока:

- transport failure Requests — временный кандидат для повтора `GET`;
- `429`, `500`, `502`, `503`, `504` — временные status по принятой политике;
- `400`, `401`, `403`, `404` — немедленный отказ, потому что ожидание не исправляет
  запрос или доступ;
- `3xx` — отказ, потому что автоматические redirects отключены;
- `206` — отказ: частичный HTTP response не является страницей целиком.

Allowlist — часть контракта конкретного источника, а не универсальная истина. Например,
некоторые API используют `409` как временный сигнал, а другие — как постоянный конфликт.

### 5. Backoff, Retry-After и jitter решают разные задачи

Если сервер не дал подсказку, базовая пауза растёт экспоненциально:

```python
ceiling = min(backoff_factor * 2 ** (retry_number - 1), max_backoff)
```

Одинаковый график у тысячи клиентов создаёт новую волну нагрузки. Поэтому артефакт
случайно выбирает задержку в верхней части интервала:

```text
[ceiling * (1 - jitter_ratio), ceiling]
```

`Retry-After` имеет иной смысл: сервер сообщает, сколько следует ждать. Значение бывает
целым числом секунд или HTTP-date. Если оно превышает локальный `max_backoff`, клиент не
обрезает его и не повторяет раньше разрешённого времени. Он завершает загрузку ошибкой
retry budget. Это честнее, чем нарушить ограничение сервера.

Невалидный `Retry-After` не превращается в бесконечное ожидание: клиент фиксирует обычный
локальный backoff. Пауза инъецируется через `sleep_fn`, а jitter — через `random_fn`,
поэтому behavioral tests не ждут реальное время и остаются детерминированными.

### 6. «Дошли до конца» не всегда означает стабильный снимок источника

Если в offset-pagination между запросами добавилась новая запись в начало списка,
какая-то запись может повториться или сдвинуться на другую страницу. Уникальность
`order_id` поймает повтор, но не всегда обнаружит пропуск.

Клиент может честно доказать:

- прошёл наблюдавшуюся цепочку до `next: null`;
- не повторял URL;
- не увидел дубликатов ключа;
- каждая страница выполнила transport и page contract.

Он не может сам доказать неизменность удалённой коллекции. Для сильной гарантии API должен
дать snapshot token, стабильный cursor, watermark или документированную сортировку.
Артефакт не делает production-claim о согласованном снимке без такого server contract.

### 7. Частичные records — диагностика, а не поставка

Во время обхода записи находятся только в памяти. Если третья страница не прошла,
исключение сообщает `completed_pages` и `buffered_records`, но не возвращает records как
успешный результат и не изменяет output.

Только после `next: null` и проверки всех ключей строится один self-contained JSON:

```text
fetch all pages
-> validate traversal and grain
-> write .snapshot.<unique>.part
-> flush + fsync
-> os.replace
-> orders_snapshot.json
```

В одном файле находятся records, page journal, retry journal, policy, checks и summary.
Поэтому потребитель не может случайно совместить новый `orders.jsonl` со старым report.
Checksum и versioned manifest появятся в `05/11`.

## Соберите это

### Шаг 1. Пройдите три сохранённые страницы вручную

`code/main.py` сначала обходит словарь из трёх fixture-страниц без Requests. Перед
запуском предскажите:

- последовательность URL;
- число записей после каждой страницы;
- значение, которое доказывает завершение;
- что произойдёт при повторе `order_id`.

```bash
uv run --locked python code/main.py
```

Прозрачный цикл делает только центральный механизм:

```python
while url is not None:
    if url in visited:
        raise RuntimeError("cycle")
    visited.add(url)
    payload = pages[url]
    require("next" in payload)
    require_unique(payload["items"])
    url = payload["next"]
```

`max_pages` здесь не показан ради краткости, но standalone-артефакт проверяет его до
каждого нового запроса.

### Шаг 2. Отделите попытку страницы от обхода

Одна функция отвечает за HTTP attempt и bounded retries; внешний цикл отвечает за
pagination. Это разделение не даёт случайно сбросить `visited`, общий retry budget или
список ключей при повторе текущей страницы.

Успешная попытка принимает только:

```text
200
application/json или application/*+json
UTF-8
decoded body <= max_page_bytes
JSON object
```

Status и headers проверяются до разбора JSON. Response закрывается после успеха,
отклонения и перед retry.

### Шаг 3. Проверьте страницу до накопления

Сначала проверяются `items`, `order_id` и `next`; только затем записи присоединяются к
буферу. Если внутри страницы второй `order_id` дублирует первый, ни одна запись этой
страницы не считается принятой.

Относительный `next` вроде `?page=2` превращается в абсолютный URL через `urljoin`, но
после этого обязан остаться на исходном origin.

### Шаг 4. Публикуйте один полный объект

`download_snapshot` выполняет две операции строго по порядку:

```python
result = fetch_all(start_url, ...)
publish_snapshot(result, output)
```

При исключении между ними публикация не вызывается. Если по output уже лежит предыдущий
валидный снимок, он остаётся неизменным.

## Используйте это

Самостоятельный CLI предназначен для документированного JSON API с полями `items` и
`next`. Для публичного HTTPS-источника:

```bash
uv run --locked python outputs/paginated_client.py \
  --url 'https://api.example.org/orders?limit=100' \
  --output work/orders_snapshot.json \
  --record-id-field order_id \
  --max-pages 100 \
  --max-retries-per-page 3 \
  --max-total-retries 10
```

URL заключён в кавычки, чтобы shell не интерпретировал `&`. Значения query parameters
редактируются в отчёте. Credentials нельзя помещать в URL.

Если API требует bearer token, передайте **имя** переменной окружения:

```bash
export ORDERS_API_TOKEN='...'
uv run --locked python outputs/paginated_client.py \
  --url 'https://api.example.org/orders?limit=100' \
  --output work/orders_snapshot.json \
  --bearer-token-env ORDERS_API_TOKEN
```

Token читается из environment, добавляется в Session header и не попадает в report.
Ключ `--trust-env` нужен только при осознанном использовании локальных proxy и `.netrc`.

Для loopback-fixture разрешён отдельный флаг `--allow-http`; публичный HTTP он не
разрешает. Успех возвращает exit code `0`. Нарушение ответа, page contract, pagination,
grain или retry budget возвращает `1`; configuration, transport bootstrap и filesystem
failure — `2`. Ни один отказ не сопровождается traceback в обычном CLI-выводе.

## Сломайте это

1. Удалите `next` с последней страницы. Клиент должен отказаться считать отсутствие поля
   окончанием.
2. Верните `206` с синтаксически корректным JSON. Страница всё равно должна быть
   отклонена.
3. Сделайте `next` равным уже посещённому URL. Повторный GET не должен состояться.
4. Направьте `next` на другой host или с HTTPS на HTTP. Переход блокируется до запроса.
5. Повторите `order_id` на двух разных страницах. Полный снимок не публикуется.
6. Верните `429 Retry-After: 2`, затем `200`. В retry journal должна появиться одна пауза
   от сервера.
7. Верните `503 Retry-After: 120` при `max_backoff=30`. Клиент должен остановиться, а не
   повторить через 30 секунд вопреки серверу.
8. Исчерпайте общий retry budget на второй странице. Первая страница остаётся только
   диагностическим буфером.
9. Превысьте `max_page_bytes` после декомпрессии. Предыдущий snapshot должен сохраниться.

Самая опасная поломка — не явный exception, а файл с одной успешной страницей и меткой
«готово». Behavioral tests запрещают такую публикацию.

## Проверьте это

Тесты используют response/session doubles: они проверяют решения клиента без внешней сети
и реального ожидания. Fixture JSON остаются теми же данными, что в `05/03` и `05/04`.

Проверяется:

- три страницы, пять записей и точный порядок ключей;
- transport policy на каждой попытке;
- абсолютный и относительный `next`, same-origin и HTTPS;
- cycle и `max_pages` до лишнего запроса;
- обязательные `items`, `next` и бизнес-ключ;
- дубликат внутри и между страницами;
- точный `200`, media type, UTF-8 и decoded size;
- `Retry-After` в секундах и HTTP-date;
- jittered backoff, per-page и общий retry budget;
- закрытие response и lifecycle Session;
- атомарная замена полного снимка и сохранение предыдущего при провале;
- редактирование URL и отсутствие traceback при CLI configuration error.

```bash
uv run --locked python -m unittest discover -s tests
```

Успешные тесты доказывают поведение артефакта на заданных сценариях. Они не доказывают,
что произвольный внешний API стабилен или предоставляет согласованный snapshot.

## Поставьте результат

`outputs/paginated_client.py` — самостоятельный импортируемый клиент и CLI. Он не зависит
от `code/main.py`, тестовых doubles, внешнего учебного сервера или незакоммиченного файла.

Результат `orders_snapshot.json` содержит:

- все records только завершённого обхода;
- redacted start URL и имя бизнес-ключа;
- фактически применённую timeout/retry policy;
- журнал страниц и переходов;
- журнал повторов с причиной, номером и источником задержки;
- проверки окончания, уникальности grain и same-origin chain;
- итоговые page, record и retry counts.

Чтобы адаптировать артефакт к другому API, измените page contract (`items`, `next`) и
`record_id_field`, но не удаляйте разделение между полным обходом и публикацией.

## Упражнения

1. Сделайте вторую страницу один раз ответившей `503`, а затем успешной. Предскажите
   число attempts и retries и подтвердите его журналом.
2. Адаптируйте чистую функцию разбора страницы к API с `next_page_token`, сохранив все
   остальные инварианты клиента.
3. Добавьте в fixtures вставку новой записи между offset-страницами. Покажите сценарий,
   который ловится дубликатом, и отдельно объясните пропуск, который клиент не может
   обнаружить без server-side snapshot contract.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Pagination | несколько независимых запросов | договорная последовательность страниц с явным переходом и концом |
| Cursor / page token | номер страницы, который можно вычислить | непрозрачное значение сервера для продолжения того же обхода |
| Attempt | то же, что retry | любой запрос страницы; retry — только повтор после неудачной попытки |
| Retry budget | число повторов одной страницы | верхняя граница повторов одной страницы и/или всей операции |
| Exponential backoff | гарантия восстановления | растущая пауза, которая ограничивает нагрузку, но не делает постоянную ошибку временной |
| Jitter | случайная потеря времени | разброс пауз, уменьшающий синхронную волну повторов клиентов |
| Retry-After | timeout запроса | серверная рекомендация, когда допустима следующая попытка |
| Partial result | допустимый fallback полного снимка | диагностический буфер, который нельзя публиковать под контрактом полноты |
| Snapshot consistency | факт достижения `next: null` | гарантия стабильной коллекции, которую должен предоставить server contract |

- [Google AIP-158: Pagination](https://google.aip.dev/158) — прочитайте Guidance и Opacity: `next_page_token` является непрозрачным продолжением, а пустой token — договорным концом, не приглашением вычислить следующий offset.
- [GitHub Docs: Using pagination in the REST API](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) — сравните JSON `next` урока с HTTP `Link rel="next"` и посмотрите, почему клиент следует опубликованной ссылке API.
- [RFC 9110: Safe and idempotent methods](https://www.rfc-editor.org/rfc/rfc9110#section-9.2) — прочитайте §§9.2.1–9.2.2 и §10.2.3: стандарт задаёт границу автоматического повтора и две формы `Retry-After`.
- [Requests: Quickstart — Timeouts, errors and streaming](https://requests.readthedocs.io/en/latest/user/quickstart/#timeouts) — повторите точный смысл timeout и соседние разделы об ошибках и `iter_content`, которые артефакт наследует из `05/04`.
- [Requests: Advanced Usage — Automatic Retries](https://requests.readthedocs.io/en/stable/user/advanced/#example-automatic-retries) — изучите подключение `urllib3.Retry` через `HTTPAdapter`; применяйте его как transport policy, оставляя pagination и grain прикладному коду.
- [urllib3: `Retry`](https://urllib3.readthedocs.io/en/stable/reference/urllib3.util.html#urllib3.util.Retry) — разберите `allowed_methods`, `status_forcelist`, `backoff_max`, jitter и `respect_retry_after_header`, прежде чем заменять учебный механизм библиотечным.
- [Amazon Builders' Library: Timeouts, retries and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) — прочитайте разделы Retries and backoff и Jitter: первичный инженерный разбор показывает, как локально полезный retry усиливает общую перегрузку.
