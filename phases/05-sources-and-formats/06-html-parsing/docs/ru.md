# HTML и Beautiful Soup

> Селектор — это не просто способ достать значение. Это проверяемое предположение о
> структуре страницы, которое должно остановить поставку при нарушении.

**Тип:** Case  
**Треки:** Core  
**Пререквизиты:** 05/05  
**Время:** ~60 минут  
**Результат:** извлекает один проверяемый табличный grain из сохранённого HTML по
версионированному selector contract, обнаруживает drift и публикует результат только
после успешных проверок.

## Цели обучения

После урока вы сможете:

- объяснить разницу между исходными HTML-байтами, parse tree Beautiful Soup и DOM в
  браузере;
- ограничить поиск цепочкой `document → container → record → field`;
- отдельно задать источник значения, его тип и допустимую cardinality селектора;
- обнаружить пропавшее, неоднозначное или невалидное поле до публикации данных;
- сохранить один самостоятельный snapshot с записями, проверками и provenance.

## Проблема

### Почему «нашёл первый узел» недостаточно

В `05/05` мы получили все страницы API и сохранили результат только после доказанного
завершения пагинации. Но источник не всегда предоставляет JSON API. Представим, что
владелец системы разрешил использовать сохранённую HTML-страницу со списком заказов.
Наша задача — превратить карточки в строки:

| order_id | user_id | amount |
|---|---|---:|
| O2601 | U001 | 1200.50 |
| O2602 | U002 | 950.00 |

Наивный скрипт вызывает `select_one()` для каждого поля. После редизайна второй
`data-field="amount"` меняется на `data-field="total"`. Скрипт либо падает далеко от
причины, либо подставляет `None`, а затем всё равно записывает файл. Обе реакции плохи:

- падение не называет нарушенное предположение;
- тихий `None` превращает drift разметки в правдоподобные испорченные данные;
- частичный файл может заменить предыдущий валидный snapshot.

Нужен не «скрейпер, который иногда работает», а маленький проверяемый конвейер:

```text
saved UTF-8 bytes
  → parse tree с фиксированным parser
  → ровно один container
  → набор record nodes
  → ровно один node на обязательное field
  → явные types и grain
  → проверки
  → атомарная публикация
```

Урок работает только с сохранёнными fixtures. HTTP, retries и получение разрешения на
доступ уже не смешиваются с разбором HTML: так сбой транспорта не маскируется под сбой
селектора.

## Концепция

### Три разных представления страницы

### 1. Исходные bytes

Файл `orders.html` — последовательность байтов. До парсинга мы:

1. ограничиваем размер;
2. декодируем bytes как строгий UTF-8;
3. считаем SHA-256 именно исходных bytes.

Это позволяет связать результат с конкретным входом. Хеш уже распарсенного текста был
бы слабее: разные исходные bytes могут превратиться в похожее представление.

### 2. Parse tree Beautiful Soup

`BeautifulSoup(text, "html.parser")` передаёт строку выбранному parser и строит дерево
Python-объектов. Теги становятся `Tag`, текст — строковыми узлами. Невалидный HTML
parser может исправить; разные parsers способны построить разные деревья. Поэтому имя
parser — часть контракта и provenance, а не локальная деталь окружения.

### 3. DOM браузера

Браузер тоже парсит HTML, но затем может выполнить JavaScript, изменить DOM и дорисовать
данные. Beautiful Soup JavaScript не выполняет. Если искомой карточки нет в сохранённом
HTML, но она появляется после выполнения скрипта, текущий инструмент её не увидит.

Это сознательная граница урока. Мы не добавляем browser automation «на всякий случай».
Сначала следует поискать официальный API, export или HTML, который уже содержит данные.
Playwright/Selenium нужны только для отдельной доказанной задачи, а не для исправления
непонятного селектора.

### HTML как дерево

В fixture одна запись выглядит так:

```html
<article data-order-card data-order-id="O2601">
  <span data-field="user">U001</span>
  <span data-field="amount">1200.50</span>
</article>
```

Здесь есть три разных источника значений:

- имя тега: `article`, `span`;
- attribute: `data-order-id="O2601"`;
- text внутри тега: `1200.50`.

CSS selector отвечает только на вопрос «какие узлы подходят». Он не решает, откуда
взять значение и каким типом оно должно стать.

### Почему поиск должен быть scoped

Селектор `[data-field='amount']` по всему документу найдёт суммы из всех карточек. Нам
нужна цепочка областей:

1. `[data-orders]` — единственный контейнер нужного списка;
2. `[data-order-card]` — записи только внутри этого контейнера;
3. `[data-field='amount']` — поле только внутри текущей записи.

Так одинаковое имя поля в боковой панели или шаблоне страницы не попадёт в таблицу.

### Устойчивость селектора условна

Обычно `div > div:nth-child(2)` хрупче, чем семантический `data-*`, потому что первый
описывает визуальное положение, а второй может выражать назначение. Но `data-*` не даёт
гарантии: владелец страницы также может его переименовать. Устойчивость появляется из
сочетания:

- осмысленного selector;
- сохранённого fixture;
- проверки cardinality;
- явного отказа от публикации при drift.

### Selector contract

`../data/html_contract.json` отделяет правила извлечения от кода:

```json
{
  "version": "2.0.0",
  "parser": "html.parser",
  "encoding": "utf-8",
  "container_selector": "[data-orders]",
  "record_selector": "[data-order-card]",
  "record_count": {"mode": "exact", "value": 2},
  "record_id": {"name": "order_id", "attribute": "data-order-id"},
  "fields": {
    "user_id": {
      "selector": "[data-field='user']",
      "source": "text",
      "type": "string",
      "non_blank": true
    },
    "amount": {
      "selector": "[data-field='amount']",
      "source": "text",
      "type": "decimal",
      "non_blank": true
    }
  }
}
```

Контракт отвечает на отдельные вопросы:

| Часть | Вопрос |
|---|---|
| `version` | Какую форму контракта понимает extractor? |
| `parser`, `encoding` | Как именно bytes превращаются в дерево? |
| `container_selector` | Где начинается нужный список? |
| `record_selector` | Какой узел соответствует одной записи? |
| `record_count` | Сколько записей допустимо в этом fixture? |
| `record_id` | Как называется ключ grain и из какого attribute он берётся? |
| `fields.*.selector` | Как найти узел поля внутри записи? |
| `source` | Читать text или named attribute? |
| `type`, `non_blank` | Как проверить найденное значение? |

Неизвестные ключи и неподдерживаемая версия запрещены. Иначе опечатка вроде
`record_selecter` могла бы выглядеть как настройка, хотя код её игнорирует.

### `select()` вместо преждевременного `select_one()`

Для обязательного поля допустима cardinality ровно `1`:

```python
matches = card.select("[data-field='amount']")
if len(matches) != 1:
    # 0 — поле пропало; 2+ — поле стало неоднозначным
    report_failure()
```

`select_one()` сразу оставляет только первое совпадение. Это удобно для исследования,
но скрывает дубликат в проверяемом pipeline.

### `text` и `attribute` — разные контракты

Для `<span data-field="amount">1200.50</span>` значение берётся из text. Для
`<a data-user-id="U001">Анна</a>` аналитическим ключом может быть attribute
`data-user-id`, а видимый текст — подписью. Эти варианты нельзя угадывать по наличию
атрибута: источник значения объявляется явно.

### Типизация после извлечения

`amount` разбирается как `Decimal`, а не `float`. Контракт урока принимает обычную
десятичную запись с точкой и отвергает `NaN`, `Infinity`, экспоненциальную запись и
десятичную запятую. Если источник использует другой формат, это нужно описать отдельным
правилом, а не расширять parser молча.

### Grain и record count

Grain результата — одна строка на `order_id`. Поэтому недостаточно найти карточки:

- `order_id` должен присутствовать и быть непустым;
- `order_id` должен быть уникальным;
- каждое обязательное поле должно быть валидно;
- число records должно удовлетворять выбранной политике.

Для regression fixture используется `exact: 2`: любое добавление или исчезновение
карточки означает, что fixture или ожидаемый результат надо осознанно пересмотреть. Для
регулярной страницы можно выбрать `min: N`, если рост списка нормален, но исчезновение
всех записей всё равно должно быть заметно. Политика числа строк не заменяет проверку
grain и полей.

## Соберите это

### Разберите путь вручную

Запустите короткий прозрачный пример из директории урока:

```bash
uv run --locked python code/main.py
```

Он делает пять видимых шагов:

1. читает сохранённые bytes;
2. строго декодирует UTF-8;
3. требует ровно один container;
4. показывает mapping каждой карточки в словарь;
5. запускает самостоятельный contract-driven artifact и печатает его checks.

Функция `exactly_one()` намеренно мала. Она показывает механизм, который часто теряется
за удобным `select_one()`:

```python
def exactly_one(scope, selector, label):
    matches = scope.select(selector)
    if len(matches) != 1:
        raise ValueError(f"{label}: expected one match, got {len(matches)}")
    return matches[0]
```

В production artifact вместо первого исключения собирается полный audit report: так за
один запуск видны все записи и поля, которые потребуют разбора.

## Используйте это

### Проверьте и опубликуйте snapshot

Из директории урока выполните:

```bash
uv run --locked python outputs/html_extractor.py \
  --input ../data/tiny/orders.html \
  --contract ../data/html_contract.json \
  --output delivery/orders_snapshot.json
```

Успешный запуск возвращает код `0` и атомарно создаёт один JSON-файл. В нём находятся:

- `records` с двумя строками;
- точная копия применённого selector contract;
- file names, SHA-256 и размер исходного HTML;
- SHA-256 файла контракта;
- counts селекторов, checks и errors;
- `summary.valid=true` и `summary.published=true`.

Локальные абсолютные пути в provenance не записываются: snapshot можно передать другому
человеку без утечки структуры домашней директории.

### Почему один snapshot, а не JSONL плюс отдельный report

Если записи и отчёт заменяются двумя независимыми операциями, потребитель может увидеть
новые records со старым report. Один self-contained файл образует единую версию данных и
доказательств. Временный файл создаётся рядом с target, синхронизируется и заменяет
предыдущий snapshot через `os.replace()` только после успешных checks.

## Сломайте это

### Вызовите selector drift

Fixture `orders_changed.html` меняет поле суммы второго заказа:

```html
<strong data-field="total">950.00</strong>
```

Запустите аудит без публикации:

```bash
uv run --locked python outputs/html_extractor.py \
  --input ../data/tiny/orders_changed.html \
  --contract ../data/html_contract.json
```

Ожидаемый код возврата — `1`. В `errors` будут record `2`, `record_id=O2602`, поле
`amount`, исходный selector и `matches=0`.

Флаг `--allow-failures` нужен только для диагностического batch-аудита:

```bash
uv run --locked python outputs/html_extractor.py \
  --input ../data/tiny/orders_changed.html \
  --contract ../data/html_contract.json \
  --output delivery/must-not-exist.json \
  --allow-failures
```

Команда вернёт `0`, чтобы вызывающий процесс мог продолжить сбор отчётов, но файл
`must-not-exist.json` не появится. `allow failures` никогда не означает `allow bad
data`.

Попробуйте ещё четыре поломки:

1. удалите `data-orders` или создайте второй container;
2. продублируйте amount внутри одной карточки;
3. повторите `order_id` у двух карточек;
4. замените `950.00` на `NaN` или `1,20`.

В каждом случае спросите: нарушена структура документа, cardinality, grain или тип?

## Проверьте это

### Докажите поведение

```bash
uv run --locked python -m unittest discover -s tests
```

Behavioral tests проверяют не только happy path, но и:

- отсутствие и неоднозначность container;
- exact/min policy числа records;
- пропавшие, пустые и дублирующиеся IDs;
- ноль и два совпадения обязательного field;
- text и attribute sources;
- пустые строки и недопустимые decimals;
- invalid UTF-8, charset drift и лимит bytes;
- invalid selectors, версии, неизвестные и duplicate JSON keys;
- self-contained provenance;
- запрет публикации invalid result и сохранность предыдущего файла;
- отсутствие временного файла после atomic replace;
- коды CLI и диагностическую семантику `--allow-failures`.

Fixture test не доказывает, что внешний сайт никогда не изменится. Он доказывает более
узкое и полезное утверждение: при известном входе extractor даёт ожидаемый результат, а
при известных нарушениях блокирует поставку.

## Поставьте результат

### Передайте воспроизводимый результат

Именованный артефакт урока — `outputs/html_extractor.py`. Для handoff передайте:

1. сохранённый HTML или способ независимо получить именно его;
2. `html_contract.json`;
3. созданный `orders_snapshot.json`;
4. команду запуска и версию locked-окружения;
5. решение владельца данных о допустимом способе доступа.

Получатель snapshot может без исходного рабочего каталога увидеть records, контракт,
parser, encoding, checks и checksums. Для повторной проверки ему всё ещё нужны исходный
HTML и contract bytes: checksum подтверждает совпадение, но не восстанавливает источник.

## Границы безопасного применения

Техническая возможность прочитать HTML не означает разрешение собирать данные. Перед
работой с внешним сайтом уточните официальный API/export, условия использования,
договорённость с владельцем и применимые ограничения. `robots.txt` стандартизует
правила для crawler-ов, но не является механизмом авторизации и сам по себе не выдаёт
право доступа.

Этот урок не охватывает:

- обход сайта и очереди URL;
- авторизацию, cookies и персональные данные;
- JavaScript rendering и browser automation;
- anti-bot обходы;
- автоматическую «починку» selectors по догадке.

При drift правильная первая реакция — остановить поставку, изучить новый fixture и
согласованно изменить contract, tests и его version.

## Упражнения

1. Измените `user_id` так, чтобы он читался из `data-user-id`, и добавьте fixture test.
2. Переключите `record_count` с `exact` на `min`; объясните, какую поломку теперь не
   обнаружит один только count check.
3. Спроектируйте политику optional field: как отличить допустимое отсутствие от drift и
   как оно должно выглядеть в report? Не меняйте основной контракт, пока правило не
   сформулировано.
4. Разберите намеренно повреждённый HTML с `html.parser` и другим parser. Сравните
   построенные деревья, не объявляя одно из них «истиной» без контракта источника.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение в уроке |
|---|---|---|
| Source HTML | То, что видно в браузере | Сохранённые bytes до выполнения JavaScript |
| Parse tree | Исходный файл без изменений | Дерево, построенное конкретным parser, включая его исправления |
| DOM | Любое HTML-дерево | Объектная модель документа; browser DOM может измениться после scripts |
| CSS selector | Гарантия стабильности | Правило сопоставления узлов, которое надо проверять |
| Cardinality | Число колонок | Допустимое число совпадений selector: здесь ровно одно для field |
| Grain | Число карточек | Что означает одна строка: один уникальный `order_id` |
| Selector drift | Любое изменение дизайна | Изменение дерева, нарушающее договор извлечения |
| Audit | Публикация плохих строк | Сбор records, counts, checks и errors без обязательной поставки |
| Atomic publish | Быстрая запись | Замена целого валидного snapshot одной файловой операцией |
| Fixture | Копия production навсегда | Малый сохранённый вход для воспроизводимой regression-проверки |

- [MDN: использование data-атрибутов](https://developer.mozilla.org/ru/docs/Web/HTML/How_to/Use_data_attributes) — разберите назначение `data-*` и не путайте семантический hook с гарантией неизменности.
- [Beautiful Soup documentation](https://www.crummy.com/software/BeautifulSoup/bs4/doc/) — прочитайте разделы Making the soup, parser differences, navigating и CSS selectors; это основной API-справочник артефакта.
- [Soup Sieve: selectors](https://facelessuser.github.io/soupsieve/selectors/) — сверьте поддерживаемый Beautiful Soup CSS-синтаксис и ограничения конкретного selector engine.
- [WHATWG HTML: parsing](https://html.spec.whatwg.org/multipage/parsing.html) — используйте как первичный источник о том, как HTML превращается в дерево и почему исправление malformed markup не тривиально.
- [WHATWG DOM Standard](https://dom.spec.whatwg.org/) — уточните модель nodes и trees; отделяйте стандарт DOM от Python parse tree и визуального представления страницы.
- [W3C Selectors Level 4](https://www.w3.org/TR/selectors-4/) — обращайтесь к спецификации, когда нужна точная семантика matching, а не только пример библиотечного вызова.
- [RFC 9309: Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309) — прочитайте область действия протокола и его security considerations до проектирования crawler-а.
- [Python: `html.parser`](https://docs.python.org/3/library/html.parser.html) — проверьте поведение выбранного встроенного parser и явно учитывайте, что он не проверяет соответствие документа HTML-стандарту.
