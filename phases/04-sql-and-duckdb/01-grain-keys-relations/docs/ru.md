# Grain, ключи и связи

> До первого SQL-запроса нужно договориться, что означает строка каждой таблицы, как
> она идентифицируется и на какие другие сущности имеет право ссылаться.

**Тип:** Learn
**Треки:** Core
**Пререквизиты:** 03/12
**Время:** ~75 минут
**Результат:** для набора связанных таблиц объявляет grain, выбирает простой или
составной primary key, задаёт направление и обязательность foreign key и отличает
пропуск ссылки от orphan-ключа.

## Цели обучения

После урока вы сможете:

- перенести знакомые grain, бизнес-ключи и cardinality из Pandas в реляционную модель;
- отличить популяцию таблицы, смысл строки и способ идентификации строки;
- выбрать primary key из кандидатных ключей и не потерять части составного ключа;
- прочитать foreign key от дочерней таблицы к уникальному ключу родительской;
- отдельно зафиксировать обязательность ссылки и ожидаемую cardinality;
- отличить отсутствующую необязательную ссылку от непустого orphan-ключа;
- разделить объявленный контракт, состояние текущих данных и ограничение,
  действительно обеспечиваемое базой;
- передать реляционный контракт коллеге до написания аналитических запросов.

## Проблема

Вам передали четыре знакомых CSV:

```text
users.csv
orders.csv
order_items.csv
events.csv
```

Запрос звучит просто: «Посчитайте выручку по пользователям». Но один и тот же
синтаксически корректный запрос может ответить на разные вопросы или вернуть
правдоподобно завышенную сумму.

До вычислений неизвестно:

- означает ли строка `orders` один заказ или одну версию заказа;
- почему `order_id` повторяется в `order_items` и является ли это дефектом;
- обязана ли каждая строка `orders` ссылаться на существующего пользователя;
- идентифицирует ли `event_id` логическое событие или отдельную попытку доставки;
- какие ограничения только написаны в документации, а какие реально проверяет база.

Представьте две строки:

| order_id | product_id | quantity |
|---|---|---:|
| O1001 | P01 | 1 |
| O1001 | P02 | 2 |

Если `order_items` содержит одну строку на товарную позицию, повтор `order_id`
закономерен. Если таблица объявлена как одна строка на заказ, те же данные нарушают
контракт. Сами значения не сообщают, какая интерпретация правильна.

Или другой пример:

```text
orders.user_id = U999
```

В `users` такого значения нет. Это может означать:

- повреждённую ссылку;
- удалённого пользователя, которого политика разрешает сохранить как warning;
- неверно выбранную родительскую таблицу;
- допустимую внешнюю сущность, которую вообще не следовало объявлять foreign key.

Сначала нужно сформулировать модель. SQL сможет проверить только то утверждение,
которое мы сделали явным.

## Что уже известно из Pandas

Урок не начинает модель данных заново. В фазе 03 вы уже:

| Пройденное знание | Где применялось |
|---|---|
| grain — смысл одной строки | `03/01`, `03/05`, `03/12` |
| простой и составной кандидатный ключ | `03/01` |
| пропуск и пустое значение в ключе | `03/01`, `03/02` |
| cardinality и частоты ключей | `03/06` |
| unmatched-строки и политика их сохранения | `03/06`, `03/12` |
| data contract и проверяемый handoff | `03/12` |

Теперь меняется не предметная область, а язык описания:

```text
кандидатный бизнес-ключ  -> candidate key
выбранный основной ключ -> primary key
ссылка одной сущности на другую -> foreign key
непустая ссылка без родителя -> orphan key
```

В Pandas эти правила проверяли функции перед `merge`. В реляционной системе часть
правил может стать ограничениями таблиц, а часть всё равно останется внешним
контрактом и проверяемым запросом.

## Концепция

### 1. Таблица становится отношением только вместе со смыслом

В практическом SQL слова **table** и **relation** часто используют почти как
синонимы. Для первого рабочего проекта достаточно следующей модели:

- таблица хранит строки;
- каждая строка описывает объект, событие или состояние одного объявленного вида;
- столбцы описывают свойства этого вида;
- схема задаёт имена, типы и ограничения;
- ключи позволяют идентифицировать строки и связывать таблицы.

В теории реляционной модели строку называют **tuple**, а столбец — **attribute**.
Эти термины полезны при чтении документации, но сейчас важнее не словарь, а
контракт конкретной таблицы.

Файл с заголовком и строками ещё не сообщает:

- какую популяцию он охватывает;
- что означает одна строка;
- какие повторы допустимы;
- какие ссылки обязательны;
- какое состояние считается нарушением.

### 2. Популяция, grain и ключ отвечают на разные вопросы

Эти понятия связаны, но не взаимозаменяемы.

| Понятие | Вопрос |
|---|---|
| Популяция | Какие объекты или события вообще могут находиться в таблице? |
| Grain | Что означает одна строка? |
| Ключ | Как однозначно назвать строку заявленного grain? |

Для `orders`:

```text
популяция -> заказы, попавшие в выбранный источник и период
grain     -> один заказ
ключ      -> order_id
```

Для `order_items`:

```text
популяция -> товарные позиции заказов
grain     -> одна товарная позиция в одном заказе
ключ      -> order_id + product_id
```

Уникальность текущих значений не создаёт grain. Например, `ordered_at` сегодня может
случайно не повторяться, но время заказа не становится от этого его идентичностью.

### 3. Candidate key сначала предлагается, primary key затем выбирается

**Candidate key**, или кандидатный ключ, — столбец либо комбинация столбцов, которые
по смыслу должны однозначно идентифицировать строку.

У таблицы может быть несколько кандидатных ключей. Например, технический идентификатор
и устойчивый внешний номер могут оба претендовать на эту роль. Нужно оценить:

- соответствует ли ключ grain;
- обязаны ли все его части быть заполнены;
- может ли значение измениться;
- кто гарантирует уникальность;
- одинаково ли ключ понимают производитель и потребитель данных.

**Primary key** — один кандидатный ключ, выбранный основным идентификатором строки
в реляционном контракте.

Важно:

```text
уникален в сегодняшнем файле != является candidate key
candidate key != автоматически выбран primary key
назван primary key != уже обеспечен фактическими данными
```

В SQL primary key обычно объединяет два требования:

1. ключ не может быть `NULL`;
2. полная комбинация ключа не повторяется.

Генерация surrogate keys и выбор между естественным и техническим ключом требуют
отдельного архитектурного решения. В этом уроке мы не проектируем генераторы ключей:
нам достаточно уметь обосновать уже выбранный идентификатор.

### 4. Составной ключ является одной комбинацией

В `order_items` ключ:

```text
(order_id, product_id)
```

Проверяется целиком.

| order_id | product_id | Нарушение? |
|---|---|---|
| O1001 | P01 | нет |
| O1001 | P02 | нет |
| O1002 | P01 | нет |
| O1001 | P01 | да: повторилась полная пара |

Отдельный `order_id` имеет право повторяться: один заказ содержит несколько позиций.
Отдельный `product_id` тоже может повторяться между заказами. Ошибкой становится повтор
полной пары.

Если из составного ключа убрать `product_id`, контракт незаметно сменит grain с
товарной позиции на заказ. Это не упрощение проверки, а изменение модели данных.

### 5. Foreign key читается от child к parent

**Foreign key** хранится в дочерней таблице и ссылается на уникальный ключ
родительской таблицы.

```text
orders.user_id -> users.user_id
```

Читаем обычными словами:

> Значение `orders.user_id` называет пользователя, который должен быть представлен
> уникальной строкой `users`.

Здесь:

| Роль | Таблица и столбец |
|---|---|
| child | `orders.user_id` |
| parent | `users.user_id` |
| foreign key | `orders.user_id` |
| referenced key | `users.user_id` |

Стрелка направлена от места, где хранится ссылка, к месту, где находится
идентифицируемая сущность.

Foreign key должен вести на уникальный ключ родителя. Если `users.user_id`
повторяется, ссылка одного заказа перестаёт однозначно называть пользователя.

### 6. Foreign key не означает one-to-one

Пусть один пользователь сделал три заказа:

```text
orders.user_id = U001, U001, U001
users.user_id  = U001
```

Все три дочерние строки корректно ссылаются на одну родительскую. Со стороны
`orders` это связь `many-to-one`; в обратном чтении `users -> orders` —
`one-to-many`.

Поэтому проверяются отдельно:

```text
foreign key  -> существует ли допустимый parent
cardinality  -> сколько строк может соответствовать одному ключу с каждой стороны
grain        -> что означает строка каждой таблицы и будущего результата
```

Связь `one-to-many` не является дефектом. Она становится опасной, если будущий
аналитический запрос использует метрику стороны `one` так, будто строка не
размножилась. Подробно выполнять такие JOIN будем в `04/05`.

### 7. Missing-ссылка и orphan-ключ — разные состояния

Пусть таблица `support_tickets` может содержать обращение гостя. Тогда
`support_tickets.user_id` может отсутствовать:

```text
user_id = NULL
```

Это **missing foreign key**. Допустимость определяется предметным правилом:
может ли обращение существовать без известного пользователя?

Теперь другой случай:

```text
support_tickets.user_id = U999
```

Значение присутствует, но соответствующего `users.user_id` нет. Это
**orphan key**.

| Состояние | Значение child key | Parent найден | Возможный смысл |
|---|---|---|---|
| корректная ссылка | `U001` | да | известный пользователь |
| missing-ссылка | `NULL` | не проверяется как конкретный ключ | пользователь неизвестен или ссылка необязательна |
| orphan-ключ | `U999` | нет | нарушенная или несогласованная ссылка |

Формальную трёхзначную логику `NULL` разберём в `04/03`. Здесь достаточно не
смешивать отсутствие значения с непустым значением, для которого не найден parent.

### 8. Обязательность ссылки является предметным решением

Нельзя вывести обязательность foreign key только из названия столбца.

Например:

- `order_items.order_id` обязателен: товарная позиция без заказа не имеет смысла
  в нашей модели;
- `support_tickets.user_id` может быть необязательным, если разрешены гости;
- `events.session_id` может быть nullable и вообще не быть foreign key, если
  отдельной таблицы сессий нет.

В `03/12` заказ неизвестного пользователя сохранялся как warning, потому что
политика delivery mart разрешала такую неполноту и делала её наблюдаемой.
Если теперь объявить строгий контракт
`orders.user_id -> users.user_id`, тот же `U999` станет нарушением связи.

Противоречия нет:

```text
наблюдение одно: parent U999 не найден
решение разное: warning или blocker
причина решения: назначение конкретного контракта
```

### 9. Grain событий должен описывать логическое событие

В raw-потоках одна и та же запись может доставляться повторно:

| event_id | delivery |
|---|---|
| E0005 | первая |
| E0005 | повторная |

Если наша аналитическая таблица должна содержать одно **логическое продуктовое
событие**, её grain именно так и формулируется, а `event_id` является кандидатным
primary key. Повторная доставка нарушает ожидаемую уникальность.

Если бы строка означала отдельную попытку доставки, `event_id` одного события имел бы
право повторяться, а ключу понадобился бы идентификатор доставки. Поэтому формулировка
«одна доставленная строка» была бы недостаточной для объявления `event_id` primary key.

Ключ не выбирают отдельно от смысла строки.

### 10. Объявлено, наблюдается и обеспечивается — три разных уровня

Рассмотрим утверждение:

```text
orders.order_id является primary key
```

Оно может находиться на трёх уровнях:

| Уровень | Что известно |
|---|---|
| Объявленный контракт | автор утверждает, что `order_id` обязан идентифицировать заказ |
| Наблюдаемые данные | в текущем CSV нет missing и повторов `order_id` |
| Обеспечиваемое ограничение | база не разрешает записать missing или повторяющийся ключ |

Эти уровни не заменяют друг друга.

- Чистый сегодняшний файл не доказывает, что завтра не появится дубликат.
- Запись в документации не останавливает плохую загрузку.
- Ограничение базы не доказывает, что выбранный ключ правильно выражает бизнес-grain.

CSV хранит текстовые строки и заголовок, но не переносит primary и foreign keys как
исполняемые ограничения. При чтении CSV в DuckDB мы получаем данные, а реляционный
контракт нужно хранить и проверять отдельно.

Позже в фазе мы постепенно сделаем проверки исполняемыми:

| Что проверяем | Где появится механизм |
|---|---|
| проекция и контракт результата | `04/02` |
| поведение `NULL` | `04/03` |
| повторы ключа через группировку | `04/04` |
| orphan-ключи и cardinality JOIN | `04/05` |
| композиция проверок через CTE | `04/06` |
| запуск DuckDB из Python | `04/11` |

Сейчас задача — сформулировать проверяемые утверждения до появления синтаксиса.

## Соберите это

Практика выполняется без SQL. Возьмите маленькие таблицы и заполните реляционный
контракт так, чтобы другой аналитик мог позже написать однозначные проверки.

### Шаг 1. Назовите популяцию и grain

Начните с четырех карточек:

| Таблица | Популяция | Grain |
|---|---|---|
| `users` | пользователи продукта | один пользователь |
| `orders` | заказы выбранного источника | один заказ |
| `order_items` | товарные позиции заказов | одна позиция одного товара в одном заказе |
| `events` | логические продуктовые события | одно логическое событие |

Проверьте каждую формулировку вопросом:

> Если две строки имеют одинаковый предполагаемый ключ, описывают ли они один объект
> дважды или два допустимых объекта?

### Шаг 2. Предложите candidate keys и выберите primary keys

| Таблица | Candidate key | Выбранный primary key | Почему |
|---|---|---|---|
| `users` | `user_id` | `user_id` | называет одного пользователя |
| `orders` | `order_id` | `order_id` | называет один заказ |
| `order_items` | `order_id, product_id` | `order_id, product_id` | называет товар внутри заказа |
| `events` | `event_id` | `event_id` | называет одно логическое событие |

Для каждой таблицы отдельно запишите:

- какие повторы отдельных столбцов допустимы;
- что будет missing-нарушением;
- какой конкретный пример опровергнет уникальность полной комбинации.

### Шаг 3. Нарисуйте направление связей

```text
users.user_id
      ↑
      └── orders.user_id

orders.order_id
      ↑
      └── order_items.order_id
```

Затем прочитайте каждую стрелку предложением:

```text
каждый обязательный orders.user_id должен называть существующего users.user_id
каждый order_items.order_id должен называть существующий orders.order_id
```

Не добавляйте связь только потому, что два столбца имеют похожие названия. Нужен
общий предметный смысл и уникальный parent key.

### Шаг 4. Разберите нарушения вручную

#### Повтор logical event

```text
event_id = E0001, E0002, E0005, E0005
```

Результат:

```text
duplicate groups -> 1
affected rows    -> 2
example          -> E0005
```

Одна группа означает один повторившийся ключ. Две затронутые строки означают все
строки, входящие в эту группу.

#### Orphan user

```text
orders.user_id = {U001, U002, U999}
users.user_id  = {U001, U002}
```

`U999` присутствует в child, но отсутствует среди parent keys:

```text
orphan keys -> 1
orphan rows -> 1
example     -> U999
```

Не удаляйте строку из контрольного примера. Задача аудита — сохранить evidence и
принять явное решение.

### Шаг 5. Разделите наблюдение и политику

Заполните таблицу:

| Наблюдение | Контракт | Решение | Обоснование |
|---|---|---|---|
| `events.event_id=E0005` повторён | одно логическое событие на `event_id` | blocker | событие будет посчитано дважды |
| `orders.user_id=U999` не найден | строгая ссылка на `users` | blocker | обязательный parent отсутствует |
| `support_tickets.user_id=NULL` | ссылка необязательна для гостя | допустимо | конкретный неизвестный ключ не заявлен |

Если политика допускает orphan как warning, так и напишите. Не называйте его
«корректным foreign key»: это наблюдаемое отклонение, которое разрешено конкретным
потребителем.

### Шаг 6. Заполните артефакт

Скопируйте:

```text
outputs/relational-contract-template.md
```

Заполните как минимум:

1. контракты `users`, `orders`, `order_items`, `events`;
2. две связи из схемы выше;
3. три контрольных сценария;
4. policy для duplicate event и orphan user;
5. границу между документацией, фактической проверкой и ограничениями базы.

Не открывайте рубрику как список ответов до первой попытки. Сначала сформулируйте
контракт своими словами.

## Используйте это

Шаблон является рабочим preflight перед SQL-задачей. Его можно приложить к задаче,
положить рядом с моделью или использовать как основу для data contract.

Короткий заполненный фрагмент связи:

```text
child            -> orders
foreign key      -> user_id
parent           -> users
referenced key   -> user_id
meaning          -> заказ принадлежит известному пользователю
optional         -> нет
cardinality      -> many orders to one user
orphan policy    -> blocker для source contract
evidence         -> count + до пяти user_id
```

Такой фрагмент уже отвечает на вопросы, которые нельзя восстановить из будущего
`JOIN`:

- почему выбраны именно эти столбцы;
- где требуется уникальность;
- можно ли сохранить missing;
- что делать с отсутствующим parent;
- какой уровень строк ожидается после объединения.

В `04/02` вы используете тот же способ мышления для результата `SELECT`: сначала
назовёте grain и столбцы новой таблицы, затем напишете выражения.

## Сломайте это

### Ошибка 1. Вывести grain из случайной уникальности

`ordered_at` сегодня уникален, поэтому его объявляют primary key. Завтра два заказа
созданы в одну секунду, и модель ломается. Наблюдение подменило бизнес-утверждение.

### Ошибка 2. Сократить составной ключ

Для `order_items` оставляют только `order_id`. Все многопозиционные заказы становятся
«дубликатами», хотя нарушен не источник, а контракт аудитора.

### Ошибка 3. Развернуть foreign key

Записывают:

```text
users.user_id -> orders.user_id
```

Но ссылка хранится в `orders`. Такое направление ошибочно требует, чтобы каждый
пользователь имел заказ, и смешивает существование parent с наличием child.

### Ошибка 4. Ссылаться на неуникального parent

Если parent key повторяется, одна child-строка соответствует нескольким parent-строкам.
Foreign key больше не называет одну родительскую сущность.

### Ошибка 5. Смешать missing и orphan

`NULL` и `U999` объединяют в «нет пользователя». В первом случае конкретная ссылка
не заявлена, во втором заявлено значение, которому не найдено соответствие.

### Ошибка 6. Считать foreign key гарантией one-to-one

Несколько заказов одного пользователя объявляют нарушением. Но foreign key проверяет
существование parent, а не уникальность child key.

### Ошибка 7. Исправить аудит удалением evidence

Orphan-строки фильтруют, после чего отчёт показывает ноль нарушений. Данные стали
удобнее, но причина и масштаб дефекта исчезли.

## Проверьте это

Проверьте заполненный документ по:

```text
outputs/relational-contract-rubric.md
```

Для учебного tiny-набора сильный контракт должен привести к следующим выводам:

- `users`: grain — один пользователь, primary key `user_id`;
- `orders`: grain — один заказ, primary key `order_id`;
- `order_items`: grain — одна товарная позиция заказа, составной primary key
  `(order_id, product_id)`;
- `events`: grain — одно логическое событие, primary key `event_id`;
- повтор одного `order_id` в `order_items` сам по себе допустим;
- повтор полной пары `(order_id, product_id)` был бы нарушением;
- `orders.user_id -> users.user_id` направлен от child к parent;
- `order_items.order_id -> orders.order_id` направлен от child к parent;
- повторный `E0005` нарушает grain логического события;
- непустой `U999` без parent является orphan, а не missing-ссылкой.

Результат готов не тогда, когда таблица терминов заполнена, а когда новый человек
может получить те же выводы на трёх контрольных сценариях.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Relation | Любой CSV | Табличное представление с объявленной схемой и смыслом строк |
| Population | Все возможные строки | Множество объектов или событий, которое охватывает таблица |
| Grain | Количество строк | Смысл одной строки |
| Candidate key | Любой уникальный столбец текущего файла | Осмысленный претендент на однозначную идентификацию grain |
| Primary key | Любая колонка с `id` | Выбранный непустой уникальный идентификатор строки |
| Composite key | Несколько независимых ключей | Один ключ из полной комбинации столбцов |
| Foreign key | Гарантия `one-to-one` | Child key, ссылающийся на уникальный parent key |
| Parent | Таблица слева в `JOIN` | Таблица с идентифицируемой сущностью |
| Child | Таблица справа в `JOIN` | Таблица, в которой хранится ссылка на parent |
| Missing foreign key | Несуществующий parent | Отсутствие самого значения ссылки |
| Orphan key | Любой `NULL` | Непустой child key, которому не найден parent |
| Cardinality | Количество столбцов | Допустимое число соответствий ключа между названными сторонами |
| Constraint | Проверка, которая однажды прошла | Правило, объявленное и при наличии механизма обеспечиваемое системой |
