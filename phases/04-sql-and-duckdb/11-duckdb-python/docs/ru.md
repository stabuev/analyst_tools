# DuckDB из Python

> Python управляет выполнением, SQL описывает преобразование, а данные пересекают границу
> между DuckDB и pandas только через явный проверяемый контракт.

**Тип:** Build
**Треки:** Core
**Пререквизиты:** 04/10
**Время:** ~90 минут
**Результат:** выполняет доверенный параметризованный SQL через явную DuckDB connection,
регистрирует pandas DataFrame как relation и возвращает результат с проверенными
колонками и dtypes.

```text
-> доверенный SQL + отдельно переданные значения
-> компактный результат DuckDB
-> проверенный pandas DataFrame
```

## Проблема

Представьте продолжение задачи из `04/10`. Когортная таблица уже рассчитана. Для графика
нужна одна когорта — январь 2026 года — и только наблюдаемые периоды от нулевого до
второго.

В ноутбуке легко написать так:

```python
selected_month = "2026-01-01"
max_period = 2

result = duckdb.sql(f"""
    SELECT *
    FROM cohort_activity
    WHERE cohort_month = '{selected_month}'
      AND period_index <= {max_period}
""").df()
```

Этот фрагмент может вернуть правильные три строки. Но его интерфейс скрыт:

- `duckdb.sql()` использует connection по умолчанию;
- `cohort_activity` находится по имени Python-переменной из окружающего namespace;
- значения встроены внутрь SQL через форматирование строки;
- не видно, кто владеет соединением и когда оно закрывается;
- downstream-код узнает о переименовании столбца или смене dtype только в месте падения;
- `.df()` материализует весь результат, хотя размер результата ничем не ограничен.

Пока ячейки запускаются в одном порядке, скрытое состояние кажется удобством. После
переноса кода в функцию или тест ситуация меняется: нужной локальной переменной может не
оказаться, default connection может содержать другие временные объекты, а два запуска
могут влиять друг на друга.

Нам нужен не универсальный запускатель произвольного SQL. Нужен небольшой явный
интерфейс конкретного аналитического шага.

## Концепция

### У Python, SQL и pandas разные обязанности

Разделим задачу до написания кода:

| Часть | За что отвечает | Чего она не должна скрывать |
|---|---|---|
| Python | открывает connection, читает SQL-asset, передаёт вход и параметры, проверяет результат | SQL-логику и происхождение connection |
| SQL | фильтрует, агрегирует и задаёт grain результата | Python namespace и формат доставки |
| DuckDB connection | хранит контекст выполнения запроса | неявное глобальное состояние |
| pandas | продолжает анализ компактного типизированного результата | тяжёлое чтение и сокращение сырых данных |

Эта граница не означает, что один инструмент «главнее». Она делает зависимости
наблюдаемыми и проверяемыми.

### Connection — это контекст выполнения

`duckdb.connect()` возвращает объект `DuckDBPyConnection`. Даже для базы в памяти это не
пустая формальность. С connection связаны:

- каталог доступных таблиц, views и временных объектов;
- зарегистрированные Python-объекты;
- настройки текущего сеанса;
- выполняемые запросы и их результаты;
- жизненный цикл ресурса.

Две независимо созданные безымянные in-memory connection имеют разное состояние:

```python
first = duckdb.connect()
second = duckdb.connect()

first.execute("CREATE TEMP TABLE example AS SELECT 42 AS value")

first.execute("SELECT * FROM example").fetchall()   # [(42,)]
second.execute("SELECT * FROM example")             # Catalog Error
```

Поэтому фраза «таблица существует в DuckDB» неполна. Нужно уточнить: в какой базе и через
какую connection код к ней обращается.

#### Правило владения

Используем простое правило:

> Кто создал connection, тот определяет её полный lifecycle и закрывает её.

Если внешняя функция передала connection в `query_dataframe`, вложенная функция может
выполнить запрос, но не должна закрывать чужой ресурс:

```python
connection = duckdb.connect()
try:
    first_result = query_dataframe(connection, ...)
    second_result = query_dataframe(connection, ...)
finally:
    connection.close()
```

Так вызывающий код может выполнить несколько связанных действий в одном контексте.
Функция `query_dataframe` из артефакта урока вообще не умеет создавать connection:
параметр `connection` обязателен. Это намеренное ограничение интерфейса.

### SQL-структура и значения — разные сущности

В запросе меняются два значения:

- выбранный `cohort_month`;
- последний нужный `period_index`.

Структура запроса не меняется:

```sql
WHERE cohort_month = $cohort_month::DATE
  AND period_index <= $max_period::BIGINT
```

Python передаёт значения отдельно:

```python
parameters = {
    "cohort_month": "2026-01-01",
    "max_period": 2,
}

connection.execute(sql, parameters)
```

DuckDB связывает `$cohort_month` со строкой, а `$max_period` — с числом. Кавычки,
экранирование и преобразование значения больше не собираются вручную через f-string.

Позиционные параметры `?` решают ту же задачу:

```python
connection.execute(
    "SELECT ?::DATE AS cohort_month, ?::BIGINT AS max_period",
    ["2026-01-01", 2],
)
```

Для двух бизнес-параметров именованная форма нагляднее: значения сложнее случайно
переставить местами.

#### Параметр — только значение

Parameter binding не является шаблонизатором SQL. Плейсхолдер нельзя использовать вместо:

- имени таблицы;
- имени столбца;
- оператора сравнения;
- ключевого слова `ASC` или `DESC`;
- произвольного условия `WHERE`;
- целого SQL-фрагмента.

Например:

```python
connection.execute(
    "SELECT ? AS chosen FROM cohort_activity LIMIT 1",
    ["active_users"],
).fetchone()
```

вернёт строку `"active_users"`, а не значение столбца `active_users`. DuckDB честно
воспринял параметр как строковое значение.

Если структура действительно должна меняться, безопасный выбор выглядит иначе:

```python
allowed_sort_columns = {
    "period": "period_index",
    "rate": "activity_rate",
}
sort_expression = allowed_sort_columns[user_choice]
```

В SQL попадает только заранее заданный разработчиком фрагмент. Произвольная строка
пользователя не становится структурой запроса.

### Параметры не делают произвольный SQL доверенным

В артефакте функция называется `execute_trusted_query`: она выполняет SQL, который уже
находится в репозитории и прошёл review.

Параметризация защищает границу значений:

```text
переданная строка -> значение SQL
```

Но она ничего не доказывает о самом тексте запроса:

```text
SQL-файл -> структура и поведение программы
```

Нельзя надёжно объявить произвольный запрос read-only, проверив только его первое слово
регулярным выражением. Комментарии, несколько statements, вызываемые функции и поведение
всего запроса не сводятся к префиксу `SELECT` или `WITH`.

Поэтому контракт урока честный:

- SQL — доверенный артефакт из проекта;
- параметры — недоверенные или меняющиеся значения;
- функция не изображает SQL-песочницу.

Если рабочая задача требует открыть существующий файл DuckDB строго без записи, это
отдельное свойство соединения `read_only=True`. Оно относится к файловой базе и не
заменяет review SQL-логики.

### pandas → DuckDB: явная relation

DuckDB умеет находить DataFrame по имени локальной Python-переменной. Механизм называется
replacement scan: если SQL ссылается на несуществующую таблицу, DuckDB может найти объект
с таким именем в Python-окружении.

Это удобно для одноразового исследования:

```python
cohort_activity = ...
duckdb.sql("SELECT * FROM cohort_activity").df()
```

Но зависимость спрятана в имени и области видимости переменной. В функции или тесте лучше
сделать её частью алгоритма:

```python
connection.register("cohort_activity", cohort_activity)
```

После регистрации SQL видит relation с именем `cohort_activity`. Это временный
интерфейс к Python-объекту в данной connection, а не создание постоянной таблицы в
файловой базе.

Регистрация тоже является состоянием. Если её оставить, следующий запрос может случайно
использовать старый DataFrame. Поэтому шаг должен иметь симметричное завершение:

```python
connection.register("cohort_activity", cohort_activity)
try:
    result = connection.execute(sql, parameters).fetchdf()
finally:
    connection.unregister("cohort_activity")
```

`finally` выполняется и при успешном результате, и при ошибке запроса или проверки.

### DuckDB → pandas: материализация результата

После `execute` результат ещё принадлежит DuckDB. Вызов:

```python
frame = connection.execute(sql, parameters).fetchdf()
```

создаёт pandas DataFrame со всеми строками результата. Это удобная граница, если SQL уже:

- выбрал нужную популяцию;
- сократил объём;
- установил целевой grain;
- выбрал только нужные столбцы;
- задал детерминированный порядок, когда он важен.

Плохая граница:

```text
миллионы сырых событий -> fetchdf -> фильтрация и агрегация в pandas
```

Разумная граница:

```text
миллионы сырых событий
-> фильтрация и агрегация в DuckDB
-> сотни строк нужного grain
-> fetchdf
-> визуализация или небольшой downstream-анализ в pandas
```

DuckDB имеет batch- и Arrow-интерфейсы для результатов, которые нельзя материализовать
целиком. В этом уроке мы не изучаем их API: сначала нужно научиться осознанно выбирать
саму границу. Наш когортный срез заведомо компактен.

### SQL-типы и pandas-dtypes — два контракта

В SQL запрос объявляет типы:

```sql
period_index::BIGINT
activity_rate::DOUBLE
```

После `fetchdf()` они представлены pandas-dtypes:

```text
BIGINT -> int64
DOUBLE -> float64
DATE   -> datetime64[us]  # в зафиксированном окружении этого проекта
```

Названия систем типов различаются. Поэтому недостаточно проверить только имена столбцов.
Если `period_index` неожиданно стал строкой или nullable-столбец изменил представление,
downstream-код может:

- сортировать числа лексикографически;
- неверно сравнивать даты;
- потерять поддержку пропусков;
- упасть далеко от места передачи данных.

Контракт артефакта проверяет:

```text
точный список столбцов
+ точный порядок
+ pandas-dtype каждого столбца
```

Grain нельзя доказать одним dtype-тестом. Для нашей задачи его отдельно проверяет
behavioral test на уникальность `(cohort_month, period_index)`.

## Соберите это

Сначала выполним весь механизм явно. Лишь затем спрячем повторяемую часть в функцию.

### Шаг 1. Зафиксируйте вход и ожидаемый результат

Возьмём маленький типизированный DataFrame, который воспроизводит контракт результата
`04/10`:

| cohort_month | activity_month | period_index | cohort_size | active_users | activity_rate |
|---|---|---:|---:|---:|---:|
| 2026-01-01 | 2026-01-01 | 0 | 4 | 4 | 1.00 |
| 2026-01-01 | 2026-02-01 | 1 | 4 | 3 | 0.75 |
| 2026-01-01 | 2026-03-01 | 2 | 4 | 2 | 0.50 |
| 2026-01-01 | 2026-04-01 | 3 | 4 | 0 | 0.00 |
| 2026-02-01 | 2026-02-01 | 0 | 3 | 3 | 1.00 |
| 2026-02-01 | 2026-03-01 | 1 | 3 | 2 | 0.6667 |
| 2026-02-01 | 2026-04-01 | 2 | 3 | 1 | 0.3333 |

Запрос для `cohort_month = 2026-01-01` и `max_period = 2` должен вернуть первые три
строки январской когорты.

До запуска зафиксируйте инварианты:

```text
rows                  = 3
period_index          = [0, 1, 2]
active_users          = [4, 3, 2]
activity_rate         = [1.0, 0.75, 0.5]
unique grain          = (cohort_month, period_index)
order                 = period_index ascending
```

Так проверка не зависит от того, «похоже ли» содержимое DataFrame на правильное.

### Шаг 2. Отделите SQL от значений

Файл `outputs/cohort_activity_slice.sql` содержит устойчивую структуру:

```sql
SELECT
    cohort_month,
    activity_month,
    period_index::BIGINT AS period_index,
    cohort_size::BIGINT AS cohort_size,
    active_users::BIGINT AS active_users,
    activity_rate::DOUBLE AS activity_rate
FROM cohort_activity
WHERE cohort_month = $cohort_month::DATE
  AND period_index <= $max_period::BIGINT
ORDER BY period_index;
```

Изменяемые значения в файл не встраиваются:

```python
parameters = {
    "cohort_month": "2026-01-01",
    "max_period": 2,
}
```

Обратите внимание на две границы:

- имя relation `cohort_activity` — часть проверенного SQL;
- выбранный месяц и горизонт — значения, переданные через DB API.

### Шаг 3. Откройте явную connection

```python
connection = duckdb.connect()
try:
    # Все действия этого учебного запуска происходят здесь.
    ...
finally:
    connection.close()
```

Не переносите `duckdb.connect()` внутрь функции запроса. Иначе функция одновременно
начнёт решать две задачи: управлять ресурсом и вычислять результат. Кроме того,
зарегистрированная в одной connection relation будет недоступна в случайно созданной
второй.

### Шаг 4. Зарегистрируйте вход, выполните запрос и снимите регистрацию

```python
connection.register("cohort_activity", cohort_activity)
try:
    result = connection.execute(sql, parameters).fetchdf()
finally:
    connection.unregister("cohort_activity")
```

Здесь видны обе стороны обмена:

```text
register -> pandas передаёт relation в DuckDB
fetchdf  -> DuckDB материализует результат в pandas
```

Если `execute` или `fetchdf` завершатся ошибкой, `unregister` всё равно выполнится.
Connection остаётся открытой, потому что её создал внешний код.

### Шаг 5. Проверьте результат на границе

Сначала проверим столбцы:

```python
expected_columns = [
    "cohort_month",
    "activity_month",
    "period_index",
    "cohort_size",
    "active_users",
    "activity_rate",
]

if result.columns.tolist() != expected_columns:
    raise ValueError("result column contract changed")
```

Затем dtypes:

```python
expected_dtypes = {
    "cohort_month": "datetime64[us]",
    "activity_month": "datetime64[us]",
    "period_index": "int64",
    "cohort_size": "int64",
    "active_users": "int64",
    "activity_rate": "float64",
}

actual_dtypes = {
    column: str(result[column].dtype)
    for column in expected_columns
}

if actual_dtypes != expected_dtypes:
    raise ValueError("result dtype contract changed")
```

Такая проверка не исправляет данные молча. Она останавливает передачу результата в
следующий этап и показывает, где именно изменился интерфейс.

## Используйте это

Артефакт `outputs/duckdb_dataframe_query.py` собирает повторяемый механизм в две функции:

- `execute_trusted_query` выполняет доверенный SQL с параметрами и проверяет результат;
- `query_dataframe` дополнительно проверяет входной DataFrame, регистрирует его как
  relation и гарантированно снимает регистрацию.

Сигнатура намеренно подробная:

```python
result = query_dataframe(
    connection,
    sql=sql,
    relation_name="cohort_activity",
    frame=cohort_activity,
    parameters={
        "cohort_month": "2026-01-01",
        "max_period": 2,
    },
    expected_input_columns=input_columns,
    expected_input_dtypes=input_dtypes,
    expected_output_columns=output_columns,
    expected_output_dtypes=output_dtypes,
)
```

По вызову можно восстановить весь интерфейс:

```text
какая connection
какой доверенный SQL
под каким именем доступен вход
какой DataFrame передаётся
какие значения меняются
какую схему ожидаем до и после запроса
```

Функция выполняет операции в таком порядке:

```text
1. проверить входные columns и dtypes
2. register(relation_name, frame)
3. execute(sql, parameters)
4. fetchdf()
5. проверить выходные columns и dtypes
6. unregister(relation_name) в finally
7. вернуть новый DataFrame
```

Она не:

- открывает или закрывает connection;
- ищет DataFrame в глобальном namespace;
- читает сырой CSV;
- меняет исходный DataFrame;
- принимает произвольные SQL-фрагменты как параметры;
- объявляет непроверенный SQL безопасным;
- добавляет CLI, JSON-конфигурацию или формат доставки.

Запустите законченный пример:

```bash
uv run --locked python code/main.py
```

В выводе должны быть три строки январской когорты, `period_index` от 0 до 2 и явный
словарь pandas-dtypes.

## Сломайте это

### 1. Верните скрытую default connection

Замените явный вызов на:

```python
duckdb.sql("SELECT * FROM cohort_activity").df()
```

Теперь поведение зависит от connection по умолчанию и от того, сможет ли replacement scan
найти Python-переменную в текущем scope. Функция больше не сообщает свои зависимости
через аргументы.

### 2. Попробуйте параметризовать имя столбца

```python
connection.execute(
    "SELECT ? AS chosen FROM cohort_activity LIMIT 1",
    ["active_users"],
).fetchone()
```

Правдоподобная ошибка — ожидать значение `4`. Фактический результат — строка
`"active_users"`. Параметр остался значением и не стал идентификатором.

### 3. Закройте чужую connection

Добавьте `connection.close()` внутрь `query_dataframe`. Первый запрос может пройти, а
следующий вызов внешнего кода упадёт на уже закрытом ресурсе. Ошибка возникнет не там,
где было нарушено владение.

### 4. Оставьте регистрацию после запроса

Удалите `unregister`. Следующий тест или расчёт сможет случайно прочитать прежний
`cohort_activity`. Результат будет зависеть от истории работы процесса.

Особенно важно, чтобы очистка происходила и при исключении. Поэтому она находится в
`finally`, а не после успешного `return`.

### 5. Подмените parameter binding f-string

```python
sql = f"""
    SELECT *
    FROM cohort_activity
    WHERE cohort_month = '{selected_month}'
"""
```

Теперь строка значения и структура SQL снова склеены. Помимо риска изменения смысла
запроса, появляются ручные правила кавычек, типов и экранирования.

### 6. Добавьте regex-проверку «read-only»

Проверка вида:

```python
re.match(r"^\s*(SELECT|WITH|EXPLAIN)", sql)
```

не анализирует поведение всего SQL. Она создаёт сильное обещание безопасности на основе
слабого признака. Граница должна быть сформулирована честно: функция исполняет только
доверенные SQL-assets проекта.

### 7. Измените dtype на входе

```python
broken = cohort_activity.copy()
broken["period_index"] = broken["period_index"].astype("string")
```

Значения `"0"`, `"1"` и `"2"` визуально похожи на числа. Но типизированный контракт
должен остановить расчёт до регистрации relation. Иначе неявные преобразования могут
скрыть проблему до более сложного запроса.

### 8. Передайте через fetchdf сырые события

Замените компактный когортный срез на `SELECT *` из большой таблицы событий. Код может
быть логически корректным, но граница выбрана плохо: pandas получает объём, который SQL
мог сократить заранее.

`fetchdf()` не является стриминговым обещанием. Если результат нельзя безопасно
материализовать целиком, нужно изменить запрос или выбрать batch-интерфейс в отдельной
рабочей задаче.

## Проверьте это

Для контрольного запуска должны выполняться предметные инварианты:

```text
входной grain       -> уникален (cohort_month, period_index)
выбранная популяция -> одна когорта 2026-01-01
горизонт             -> period_index 0, 1, 2
порядок              -> по возрастанию period_index
фиксированный размер -> cohort_size = 4 во всех строках
результат            -> 3 строки, не 4 и не 7
```

Behavioral tests дополнительно проверяют четыре слоя.

**Параметры и результат:**

- смена `cohort_month` меняет популяцию без изменения SQL;
- смена `max_period` меняет горизонт;
- строка с SQL-подобным текстом остаётся значением;
- placeholder не превращает имя столбца в идентификатор.

**Состояние connection:**

- запрос не видит DataFrame до явного `register`;
- relation снимается после успеха и после ошибки;
- переданная connection остаётся открытой;
- две отдельные in-memory connection не разделяют регистрацию.

**Контракты данных:**

- проверяются точные значения, порядок и grain;
- проверяются входные и выходные столбцы;
- проверяются pandas-dtypes;
- исходный DataFrame не мутирует.

**Граница решения:**

- артефакт не использует default `duckdb.sql()`;
- в нём нет CLI и regex-обещания read-only;
- SQL читает зарегистрированную relation, а не возвращается к сырому CSV.

Запустите тесты только этого урока:

```bash
uv run --locked python -m unittest discover -s tests
```

Успешный тест подтверждает поведение reference-артефакта. Освоение урока означает, что вы
можете объяснить, почему каждый из этих инвариантов находится именно на границе между
двумя инструментами.

## Поставьте результат

Главный артефакт — `outputs/duckdb_dataframe_query.py`.

Он пригоден, когда аналитическому Python-коду нужно:

1. передать уже типизированный DataFrame в DuckDB;
2. выполнить над ним доверенный SQL-asset с меняющимися значениями;
3. получить компактный DataFrame с явной схемой;
4. не оставить после себя скрытую relation и не закрыть чужую connection.

SQL-пример `outputs/cohort_activity_slice.sql` показывает ожидаемую форму доверенного
asset: комментарий с входным и выходным контрактом, фиксированная структура,
параметры-значения и детерминированный порядок.

CLI здесь сознательно не добавляется. Новый результат урока — корректная программная
граница DuckDB ↔ pandas, а не интерфейс командной строки. Если у расчёта появится реальный
внешний потребитель, формат запуска следует проектировать вместе с доставкой, обработкой
ошибок и наблюдаемостью, а не добавлять `argparse` ради единообразия.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| `DuckDBPyConnection` | Необязательная переменная перед `execute` | Контекст базы, временного состояния, зарегистрированных объектов и выполнения запросов |
| Connection ownership | Кто последним вызвал `execute`, тот и закрывает | Создавший ресурс определяет его lifecycle и закрывает после всей связанной работы |
| Default connection | То же самое, что переданный объект | Неявная connection модуля, состояние которой не видно в сигнатуре функции |
| Parameter binding | Подстановка любого SQL-фрагмента | Передача типизированного значения отдельно от структуры SQL |
| Identifier | Любая строка в запросе | Имя таблицы, столбца или другого объекта, являющееся частью SQL-структуры |
| Trusted SQL asset | Запрос, начинающийся с `SELECT` | Версионируемый и проверенный текст программы, которому разрешено выполняться |
| Relation registration | Постоянное копирование DataFrame в базу | Явное имя, под которым Python-объект доступен запросам конкретной connection |
| Replacement scan | Обычный поиск таблицы в каталоге | Неявное связывание SQL-имени с Python-объектом из окружающего namespace |
| `fetchdf()` | Ленивое представление результата | Материализация всех строк текущего результата как pandas DataFrame |
| Boundary contract | Проверка только названий столбцов | Явные columns, порядок, dtypes, grain и допустимый объём на границе движков |

- [EN · DuckDB: Python API overview](https://duckdb.org/docs/stable/clients/python/overview) — откройте разделы про базы в памяти, постоянные базы и `Connection Object and Module`. Сопоставьте вызовы через глобальный модуль `duckdb` с явным объектом соединения и обратите внимание на скрытое разделяемое состояние.
- [EN · DuckDB: Python Client API reference](https://duckdb.org/docs/stable/clients/python/reference/) — найдите на странице методы `register`, `unregister`, `execute`, `fetchdf` и `fetch_df_chunk`. Это точная сверка интерфейса, использованного в артефакте урока, включая симметричную очистку временно зарегистрированного имени.
- [EN · DuckDB: SQL on Pandas](https://duckdb.org/docs/stable/guides/python/sql_on_pandas) — разберите короткий пример с replacement scan: DuckDB умеет найти `DataFrame` по имени переменной Python. Затем сравните этот удобный неявный механизм с явным `register`, у которого граница и жизненный цикл видны в коде.
- [EN · DuckDB: Conversion between DuckDB and Python](https://duckdb.org/docs/stable/clients/python/conversion) — прочитайте разделы `Object Conversion` и `Result Conversion`, особенно части про pandas и Arrow. Они помогают отделить преобразование входных значений от материализации результата и выбрать между целым `DataFrame`, порциями и Arrow.
- [RU · YDB: параметризованные запросы](https://ydb.tech/docs/ru/reference/ydb-sdk/parameterized_queries) — начните с определения параметризованного запроса и сравнения двух коротких примеров. YDB использует другой SQL-диалект и собственный синтаксис `DECLARE`, поэтому переносите в DuckDB не код, а принцип: данные передаются отдельно от неизменной структуры запроса.
- [EN · PEP 249: Python Database API Specification 2.0](https://peps.python.org/pep-0249/) — прочитайте `paramstyle`, `Connection Objects`, а также `execute` и `fetch*` в разделе про курсоры. Так вы увидите, какие части интерфейса DuckDB следуют общему контракту Python DB API, а какие являются расширениями конкретной библиотеки.
- [RU · PostgreSQL: функции исполнения команд libpq](https://postgrespro.ru/docs/postgresql/current/libpq-exec) — найдите `PQexecParams` и прочитайте описание до `PQprepare`. Несмотря на C API, этот первичный источник точно показывает границу между SQL-командой и значениями параметров, объясняет, зачем она нужна, и отдельно предупреждает об ограничении на одну команду.
- [EN · OWASP: SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html) — сосредоточьтесь на `Prepared Statements` и `Allow-list Input Validation`. Первая часть объясняет связывание значений, вторая — почему имена таблиц, столбцов и направлений сортировки нельзя подставлять тем же способом и для них нужен закрытый список допустимых вариантов.
- [RU · PostgreSQL: обзор расширенного выполнения запросов](https://postgrespro.ru/docs/postgresql/current/protocol-overview) — для углубления прочитайте только подраздел «Обзор расширенного выполнения запросов». Модель `Parse → Bind → Execute` наглядно разделяет SQL-структуру, значения параметров и выполнение; детали сетевого протокола PostgreSQL и его синтаксис к DuckDB не относятся.
