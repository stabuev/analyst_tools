# Планы запросов и стоимость

> Сначала докажите, что новый запрос отвечает на тот же вопрос, затем ищите в плане
> лишнюю работу и только после этого измеряйте скорость.

**Тип:** Learn
**Треки:** Core
**Пререквизиты:** 04/11
**Время:** ~90 минут
**Результат:** проверяет эквивалентность SQL-вариантов, читает план DuckDB снизу вверх,
отличает оценки `EXPLAIN` от фактов `EXPLAIN ANALYZE` и формулирует ограниченный данными
вывод о лишней работе.

## Цели обучения

После урока вы сможете:

- объяснить разницу между результатом запроса, физическим планом и наблюдаемым
  выполнением;
- читать дерево DuckDB от источников данных к итоговому оператору;
- различать оценочную cardinality с `~` и фактическое число строк;
- находить повторное чтение источника и проверять, сохранился ли аналитический результат;
- объяснить, почему один `Total Time` не доказывает устойчивое ускорение;
- передать коллеге самостоятельный JSON-отчёт с SQL-вариантами, планами, scope и
  ограниченным выводом.

## Проблема

Нужно посчитать две метрики для события `order_paid`:

1. число физических строк события;
2. число уникальных активных пользователей.

Первый запрос выглядит прямолинейно: отдельный scalar subquery для каждой метрики.

```sql
SELECT
    (
        SELECT count(*)
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        WHERE event_name = ?
    ) AS event_rows,
    (
        SELECT count(DISTINCT user_id)
        FROM read_csv(?, header = true, all_varchar = true, nullstr = '')
        WHERE event_name = ?
    ) AS active_users;
```

На tiny-файле он возвращает правдоподобный результат:

| event_rows | active_users |
|---:|---:|
| 6 | 3 |

Шесть строк включают технический дубль `E0005`; это осознанная семантика метрики
`event_rows`. Второй показатель считает три разных `user_id`. В этом уроке мы не меняем
политику дублей — иначе одновременно изменились бы и запрос, и бизнес-вопрос.

Проблема не видна в результате: каждый subquery независимо обращается к одному CSV.
На маленьком файле разница во времени теряется в шуме запуска, а на большом повторное
чтение может стать заметной работой. По длине SQL нельзя надёжно определить, что
действительно выполнит движок: оптимизатор имеет право перестроить выражения.

Нужны два доказательства:

```text
semantic evidence: оба варианта возвращают один и тот же результат
plan evidence:      кандидат действительно устраняет повторное чтение
```

Только после них имеет смысл задавать отдельный вопрос о времени.

## Концепция

### Результат, SQL и план — разные уровни

Один и тот же результат можно получить разными SQL-текстами. Один SQL-текст, в свою
очередь, не является буквальной инструкцией «сделай операции в написанном порядке»:
DuckDB анализирует выражение и выбирает физический план.

```text
бизнес-вопрос
    ↓
проверяемый результат: одна строка с event_rows и active_users
    ↓
SQL: декларативное описание результата
    ↓
physical plan: дерево операторов, которое выбрал DuckDB
    ↓
execution: конкретный запуск этого плана на конкретных данных
```

Поэтому у каждого уровня свой вопрос:

| Уровень | Контрольный вопрос |
|---|---|
| Результат | Ответили ли оба варианта на один аналитический вопрос? |
| План | Какие источники и операторы реально выбрал движок? |
| Выполнение | Сколько строк прошло через операторы и что наблюдалось по времени? |

Быстрый запрос с другим результатом не является оптимизацией. Красивый план без
контрольного результата тоже не доказывает корректность.

### Физический план — дерево потока строк

В обычном выводе DuckDB `EXPLAIN` показывает physical plan — дерево физических
операторов. Для первого чтения полезно идти снизу вверх:

```text
нижний узел      откуда появляются строки
      ↓
следующий узел   что происходит с потоком
      ↓
...
      ↓
верхний узел     какой результат возвращается
```

В этом уроке достаточно четырёх семейств операторов:

| Оператор | Человеческий вопрос |
|---|---|
| `READ_CSV` / `TABLE_SCAN` | Какой источник читается и какие столбцы нужны? |
| `FILTER` или условие в `PROJECTION` | Какие строки или признаки проходят дальше? |
| `PROJECTION` | Какие выражения и столбцы формируются? |
| `UNGROUPED_AGGREGATE` | Как поток строк превращается в одну итоговую строку? |

Название зависит от версии DuckDB и режима вывода. Например, статический план может
показывать `READ_CSV`, а профиль выполнения — `TABLE_SCAN` с полем
`Function: READ_CSV`. Поэтому строка `TABLE_SCAN` сама по себе не является универсальным
API-контрактом. Артефакт сохраняет полный текст и считает узкий, заранее объявленный
маркер `Function: READ_CSV` только для этого учебного эксперимента.

### Сначала нарисуйте ожидаемую работу

Для двух scalar subquery ожидаем две независимые ветви:

```text
READ_CSV #1 -> filter order_paid -> count rows -----------\
                                                           -> одна строка результата
READ_CSV #2 -> filter order_paid -> count distinct users -/
```

Кандидат объединяет метрики в одном агрегате:

```sql
SELECT
    count(*) FILTER (WHERE event_name = ?) AS event_rows,
    count(DISTINCT user_id) FILTER (WHERE event_name = ?) AS active_users
FROM read_csv(?, header = true, all_varchar = true, nullstr = '');
```

Ожидаемая работа теперь такая:

```text
READ_CSV -> два булевых условия -> один aggregate -> одна строка результата
```

Это пока гипотеза. Даже очевидную схему нужно сверить с `EXPLAIN`, потому что движок
может встроить фильтр в scan, объединить выражения, переиспользовать подвыражение или,
наоборот, создать дополнительную ветвь.

### `EXPLAIN`: план и оценки без выполнения

```sql
EXPLAIN
SELECT ...;
```

Обычный `EXPLAIN` не выполняет целевой запрос. Он показывает выбранный план и оценочную
cardinality — сколько строк, по мнению оптимизатора, будет выдавать оператор.

В DuckDB оценка отмечается тильдой:

```text
~31 rows
```

Это не обещание и не скрытый точный `count(*)`. Оценка строится до выполнения по
статистике и эвристикам. Она нужна оптимизатору, чтобы сравнивать варианты плана.

Для tiny CSV урока scan фактически читает 16 строк, но `EXPLAIN` может показать
`~31 rows`. Это полезный контраст:

```text
~31 rows  = estimate before execution
 16 rows  = observed cardinality in this execution
```

Расхождение не означает автоматически неверный результат. Оно становится сигналом для
диагностики, особенно если ошибка оценки многократно раздувается перед `JOIN` или
агрегацией.

### `EXPLAIN ANALYZE`: запрос действительно выполняется

```sql
EXPLAIN ANALYZE
SELECT ...;
```

`EXPLAIN ANALYZE` запускает целевой запрос и добавляет:

- фактические числа строк операторов;
- наблюдаемые времена операторов;
- общий `Total Time`;
- сведения о реально прочитанных файлах.

Это важная граница безопасности. Для нашего доверенного `SELECT` выполнение только
читает данные. Для `INSERT`, `UPDATE`, `DELETE`, `COPY` или внешней функции
`EXPLAIN ANALYZE` может произвести реальные эффекты. Слово `EXPLAIN` перед запросом не
превращает произвольный SQL в безопасный preview.

### Cardinality относится к выходу узла

Cardinality оператора — число строк, которое этот узел выдаёт родителю, а не
универсальное «сколько данных было дорого обработано».

Например:

```text
scan читает 16 строк
aggregate выдаёт 1 строку
```

Одна строка на выходе aggregate не означает, что оператору была доступна только одна
входная строка. При чтении плана задавайте два вопроса:

1. сколько строк пришло снизу;
2. сколько строк узел передал вверх.

Для `JOIN` особенно важно сопоставить размеры обеих сторон и выходную cardinality:
резкий рост может быть ожидаемым many-to-many результатом или признаком fanout из 04/05.

### «Стоимость» не равна одному runtime

Название урока использует стоимость в рабочем смысле: объём наблюдаемой работы, который
помогает объяснить поведение запроса. В DuckDB-плане этого эксперимента мы смотрим на:

- число чтений источника;
- поток строк между операторами;
- ширину проекции, видимую по выбранным столбцам;
- фактические времена как диагностические наблюдения.

Нельзя делать вывод:

```text
0.003 s < 0.019 s -> кандидат всегда быстрее в 6.3 раза
```

Один запуск смешивает собственно выполнение с прогревом, файловым кэшем, компиляцией,
нагрузкой машины и малым объёмом данных. Кроме того, времена операторов могут быть
накопительными, а при параллельной работе перекрываться; их не следует безусловно
складывать.

Допустимый вывод по этому уроку уже:

> На DuckDB указанной версии и данном входе варианты вернули одинаковые две метрики.
> В плане кандидата один узел чтения `READ_CSV` вместо двух. Это подтверждает устранение
> повторного чтения в данном workload; устойчивый коэффициент ускорения не измерялся.

Если решение действительно зависит от скорости, после план-аудита нужен отдельный
benchmark-протокол из 02/09: representative data, фиксированный scope, warm-up, повторы,
распределение времени и сведения об окружении.

## Соберите это

### Шаг 1. Зафиксируйте semantic contract

До планов запишите результат обеих метрик на tiny:

```text
input: ../data/tiny/events.csv
event_name: order_paid
result grain: одна строка на весь выбранный файл
event_rows: 6
active_users: 3
```

`event_rows` и `active_users` проверяются отдельно. Одного совпавшего общего числа
недостаточно: компенсирующие ошибки могли бы скрыть изменение population.

### Шаг 2. Нарисуйте план карточками

Не копируйте вывод DuckDB. Сначала предскажите минимальное дерево для каждого SQL:

| Вариант | Чтения источника | Фильтры | Итоговая cardinality |
|---|---:|---:|---:|
| `two_scans` | 2 | по одному в каждой ветви | 1 строка |
| `one_scan` | 1 | два условия одного aggregate | 1 строка |

Теперь у `EXPLAIN` есть проверяемый вопрос: совпал ли выбранный движком plan shape с
ожиданием?

### Шаг 3. Получите статический план

Python API из 04/11 позволяет передать параметры и к `EXPLAIN`:

```python
plan_row = connection.execute(
    "EXPLAIN " + trusted_sql,
    parameters,
).fetchone()

plan_text = plan_row[1]
```

`trusted_sql` остаётся заранее проверенным asset. Параметры передают путь и значение
события, но не делают произвольный SQL безопасным.

Для каждого плана сохраните:

- полный текст;
- число объявленных узлов чтения источника;
- все встреченные оценки `~N rows`.

### Шаг 4. Выполните `EXPLAIN ANALYZE`

```python
analyzed_row = connection.execute(
    "EXPLAIN ANALYZE " + trusted_sql,
    parameters,
).fetchone()
```

Теперь сохраните:

- полный analyzed plan;
- фактические row markers без `~`;
- `Total Time` как наблюдение;
- число фактических чтений источника.

Не сравнивайте времена до semantic gate.

### Шаг 5. Сначала сравните результаты

Оба SQL выполняются отдельно и возвращают именованные поля:

```python
{
    "event_rows": 6,
    "active_users": 3,
}
```

Логика решения:

```text
results differ
-> stop: candidate is not an optimization of the same calculation

results equal and source reads decrease
-> supported plan-shape improvement on this input

results equal but source reads do not decrease
-> inspect other operators; no improvement proved yet
```

### Шаг 6. Не закрывайте чужую connection

Публичная функция артефакта принимает `DuckDBPyConnection`:

```python
report = build_plan_report(connection, events_path)
```

Она использует, но не закрывает соединение. CLI создаёт собственную connection и закрывает
её в `finally`. Это тот же ownership contract, который был введён в 04/11.

### Шаг 7. Запустите компактную демонстрацию

```bash
uv run --locked python code/main.py
```

Вы увидите:

- совпавшие результаты;
- отдельные списки estimate и actual row markers;
- два чтения против одного;
- `safe_to_compare_work: true`;
- явный запрет превращать одно timing-наблюдение в обещание скорости.

### Как читать JSON-отчёт

```text
scope
├── engine и engine_version
├── events_path и event_name
└── claim_boundary

variants
├── two_scans
│   ├── result
│   ├── explain
│   └── explain_analyze
└── one_scan
    ├── result
    ├── explain
    └── explain_analyze

comparison
├── results_equal
├── safe_to_compare_work
├── source_reads_removed
├── timing_claim_allowed
└── conclusion
```

Полный `plan_text` важнее извлечённых счётчиков. Счётчик — удобный тест конкретного
failure mode, а текст сохраняет evidence для человека и позволяет увидеть изменение
операторов после обновления DuckDB.

## Сломайте это

### 1. Упростите план ценой другой population

Ошибочный кандидат оставляет фильтр только для `event_rows`:

```sql
SELECT
    count(*) FILTER (WHERE event_name = ?) AS event_rows,
    count(DISTINCT user_id) AS active_users
FROM read_csv(?, header = true, all_varchar = true, nullstr = '');
```

План содержит одно чтение, но результат равен `(6, 8)`, а не `(6, 3)`.
`safe_to_compare_work` обязан стать `false`. Это наиболее опасная оптимизация:
быстрый и правдоподобный ответ на другой вопрос.

### 2. Перепутайте estimate и actual

Скопируйте `~31 rows` из `EXPLAIN` в отчёт как «файл содержит 31 строку». Проверка
фактического плана покажет 16. Тильда — часть смысла, а не оформление.

### 3. Запустите `EXPLAIN ANALYZE` на неизвестном SQL

`EXPLAIN ANALYZE` выполняет запрос. Не используйте его как валидатор «read-only» для
непроверенного текста и не разрешайте произвольный SQL через CLI артефакта.

### 4. Объявите коэффициент ускорения по tiny

Даже если один запуск показывает заметную разницу, тесты не утверждают порядок времени.
На маленьком файле запуск, файловый кэш и шум могут быть сопоставимы с полезной работой.

### 5. Судите о плане по числу CTE или длине SQL

CTE может быть встроен, материализован или переиспользован в зависимости от запроса и
версии движка. Число слов `WITH` не равно числу scan. Проверяйте физический план.

### 6. Сделайте текстовый парсер универсальным обещанием

Формат pretty-printed plan может измениться между версиями. Артефакт:

- сохраняет версию DuckDB;
- хранит полный текст;
- извлекает только узкие сигналы этого эксперимента;
- не обещает совместимость счётчиков с любой СУБД.

### 7. Закройте переданную connection

Если `build_plan_report` закроет соединение, вызывающий код потеряет свой каталог и
последующие запросы. Behavioral test выполняет `SELECT 42` после аудита и подтверждает
сохранение ownership.

## Проверьте это

Запустите:

```bash
uv run --locked python -m unittest discover -s tests
```

Behavioral suite проверяет:

- точные две метрики и их эквивалентность;
- два чтения против одного в `EXPLAIN` и `EXPLAIN ANALYZE`;
- наличие оценок только в статическом evidence;
- наличие фактических строк и `Total Time` после выполнения;
- несовпадение estimate и actual на tiny CSV;
- присутствие `READ_CSV`, `PROJECTION` и `UNGROUPED_AGGREGATE`;
- блокировку кандидата с неверной population;
- нулевой сценарий для отсутствующего события;
- запрет обещания speedup по одному timing;
- версию движка и scope входа;
- сохранение caller-owned connection;
- ошибки отсутствующего файла, пустого `event_name` и неподтверждённого SQL-кандидата;
- JSON stdout, запись самостоятельного отчёта и ошибку CLI.

Тесты сознательно не содержат assertion вида:

```python
candidate_time < baseline_time
```

Такой порог был бы нестабилен и проверял бы текущую машину вместе с SQL. Здесь
автоматически проверяются результат и plan shape; скорость требует отдельного
benchmark-контракта.

## Поставьте результат

Именованный артефакт урока — `duckdb-plan-report`:

```bash
uv run --locked python outputs/plan_report.py \
  --events /path/to/events.csv \
  --event-name order_paid \
  --output plan-audit.json
```

Артефакт самодостаточен:

- принимает явный путь и значение события;
- выполняет только два встроенных доверенных SQL-варианта;
- фиксирует DuckDB version и входной scope;
- сохраняет результат, `EXPLAIN`, `EXPLAIN ANALYZE` и plan signals;
- не закрывает переданную connection в библиотечном API;
- формулирует вывод, ограниченный этим запросом, входом и версией движка.

Передавая отчёт коллеге, добавьте только внешний контекст: почему именно эти две метрики
и этот workload важны. Все технические evidence уже находятся в JSON.

## Упражнения

1. На tiny вручную подпишите каждый оператор плана кандидата вопросами «что получает?»,
   «что выдаёт?» и «сколько строк проходит?». Сверьте `~N rows` с actual rows.
2. Запустите тот же аудит на sample. Сравните только plan shape и row flow, не объявляя
   коэффициент ускорения по одному запуску.
3. Измените кандидата так, чтобы `active_users` считались по всем событиям. Объясните,
   почему один scan не проходит semantic gate.
4. Возьмите проверенный `JOIN` из 04/05 и найдите в плане два входа и выходную
   cardinality. Сопоставьте её с ранее объявленным grain, не меняя SQL ради «красивого»
   оператора.
5. После обновления DuckDB сравните сохранённые plan text. Отделите изменение оформления
   от реального изменения дерева и не подгоняйте парсер без просмотра evidence.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Query result | То же самое, что SQL-текст | Наблюдаемая таблица ответа с заявленными полями, grain и значениями |
| Physical plan | SQL, разбитый на строки | Выбранное движком дерево физических операторов |
| Operator | Любая функция в SQL | Узел плана, который получает поток данных, выполняет работу и передаёт результат родителю |
| Scan | Просто слово `FROM` | Физическое чтение таблицы, файла или другого источника |
| Cardinality | Размер файла в байтах | Число строк, выдаваемых оператором |
| Estimated cardinality | Точный предварительный `count(*)` | Оценка оптимизатора до выполнения; в DuckDB отмечается `~` |
| Actual cardinality | Универсальное свойство SQL | Наблюдаемое число строк конкретного оператора в конкретном запуске |
| `EXPLAIN` | Безопасно выполняет запрос на пробу | Показывает план и оценки без выполнения целевого запроса |
| `EXPLAIN ANALYZE` | Только добавляет детали к тексту | Действительно выполняет запрос и профилирует операторы |
| Semantic gate | Сравнение финального runtime | Доказательство, что варианты отвечают на один вопрос и дают эквивалентный результат |
| Plan shape | Число строк SQL | Источники, операторы и связи между ними в физическом дереве |
| Bounded claim | Слабый вывод без пользы | Точный вывод, явно ограниченный входом, версией, workload и собранными evidence |

## Дополнительное чтение

- [EN · DuckDB: EXPLAIN — Inspect Query Plans](https://duckdb.org/docs/stable/guides/meta/explain) — прочитайте основной пример и `Additional Explain Settings`. Сопоставьте дерево операторов и оценки cardinality с планом кандидата, но не включайте `logical`/`optimized` output в обязательную практику урока.
- [EN · DuckDB: EXPLAIN ANALYZE — Profile Queries](https://duckdb.org/docs/stable/guides/meta/explain_analyze) — разберите различие estimated и actual cardinality и предупреждение о cumulative wall-clock time. Это первичный контракт для фактических строк и границы интерпретации времени.
- [EN · DuckDB: Profiling](https://duckdb.org/docs/stable/dev/profiling) — прочитайте разделы `EXPLAIN`, `EXPLAIN ANALYZE` и `Metrics`. Они показывают, как перейти от учебного текстового плана к более подробному профилированию, когда узких сигналов отчёта недостаточно.
- [RU · PostgreSQL: использование EXPLAIN](https://postgrespro.ru/docs/postgresql/current/using-explain) — сосредоточьтесь на объяснении `rows`, узлах-потомках и разделе про `EXPLAIN ANALYZE`. Синтаксис и числа PostgreSQL не переносите в DuckDB; переносите способ чтения потока снизу вверх.
- [EN · DuckDB: Performance Guide](https://duckdb.org/docs/stable/guides/performance/overview) — используйте страницу как карту следующих диагностик: environment, import, schema, joins, file formats и workload tuning. Не применяйте все советы одновременно до локализации проблемы планом.
- [EN · DuckDB: Benchmarks](https://duckdb.org/docs/stable/guides/performance/benchmarks) — прочитайте `A Note on Benchmarks` и disclaimer. Материал углубляет причину, по которой один tiny-run и неполный workload нельзя превращать в общий performance-claim.
- [RU · YDB: структура планов запросов](https://ydb.tech/docs/ru/yql/query_plans) — разберите определения scan, filter, aggregate, join и связи между стадиями. Это полезный перенос модели дерева на распределённый движок, но названия операторов YDB не являются DuckDB API.
- [RU · YDB: оптимизация запросов](https://ydb.tech/docs/ru/concepts/query_execution/optimizer) — прочитайте введение и раздел об оценке стоимости. Обратите внимание на главное ограничение оптимизатора: альтернативный план должен оставаться эквивалентным по результату.
- [EN · DuckDB Blog: Optimizers — The Low-Key MVP](https://duckdb.org/2024/11/14/optimizers) — прочитайте введение и пример с filter pushdown. Статья разработчика DuckDB показывает, почему текстовый порядок SQL не равен физическому порядку работы и почему ручное переписывание нужно подтверждать планом.
- [EN · PostgreSQL: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) — для углубления прочитайте про estimated cost, rows, width и проверку оценок через `ANALYZE`. Этот источник помогает отделить абстрактную стоимость планировщика от фактического elapsed time.
