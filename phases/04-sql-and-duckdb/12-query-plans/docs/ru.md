# Планы запросов и стоимость

> План выполнения показывает не то, как написан SQL, а какую работу движок решил
> выполнить: откуда прочитать строки, как их преобразовать и сколько данных прошло через
> каждый оператор.

**Тип:** Learn
**Треки:** Core
**Пререквизиты:** 04/11
**Время:** ~90 минут
**Результат:** для двух эквивалентных `SELECT` читает структурированные `EXPLAIN` и
`EXPLAIN ANALYZE` снизу вверх, сопоставляет оценки с фактическими строками и находит
повторное чтение или неожиданный рост данных без вывода о скорости по одному запуску.

## Цели обучения

После урока вы сможете:

- объяснить план как дерево физических операторов, а не как пересказ SQL-текста;
- читать дерево от источников к результату и узнавать минимальный набор операторов:
  scan, filter, projection, aggregate, join и sort;
- различать оценённое число строк, фактический выход оператора и число прочитанных строк;
- объяснить, почему `EXPLAIN` не выполняет запрос, а `EXPLAIN ANALYZE` выполняет;
- до сравнения планов проверить точное равенство результата, его колонок, порядка и
  dtypes;
- найти две независимые scan-ветви и сравнить их с одним чтением того же входа;
- использовать JSON-план DuckDB вместо разбора изменчивого текстового оформления;
- отделить диагностику формы плана от полноценного benchmarking, который появится в
  фазе 12.

## Проблема

После `04/11` у нас есть типизированная таблица месячной когортной активности. Одна строка
означает один наблюдаемый период одной когорты:

```text
grain -> (cohort_month, period_index)
```

Для январской когорты нужны два контрольных числа:

- сколько периодов присутствует в таблице;
- какова сумма месячных значений `active_users` по этим периодам.

Вторую величину мы намеренно называем `active_user_period_sum`, а не «числом уникальных
пользователей». Один пользователь мог быть активен в нескольких месяцах, а агрегированная
когортная таблица уже не содержит `user_id`. Название метрики сохраняет её единицу:
пользователь-периоды.

Первый запрос выглядит естественно: каждая метрика вычисляется отдельным scalar subquery.

```sql
SELECT
    (
        SELECT count(*)
        FROM cohort_activity
        WHERE cohort_month = $cohort_month::DATE
    ) AS cohort_period_rows,
    (
        SELECT sum(active_users)::BIGINT
        FROM cohort_activity
        WHERE cohort_month = $cohort_month::DATE
    ) AS active_user_period_sum;
```

Он возвращает правильный результат:

| cohort_period_rows | active_user_period_sum |
|---:|---:|
| 4 | 9 |

Второй запрос получает те же числа из одной relation:

```sql
SELECT
    count(*) FILTER (
        WHERE cohort_month = $cohort_month::DATE
    ) AS cohort_period_rows,
    CAST(
        sum(active_users) FILTER (
            WHERE cohort_month = $cohort_month::DATE
        ) AS BIGINT
    ) AS active_user_period_sum
FROM cohort_activity;
```

По результату запросы неразличимы. По SQL-тексту можно предположить, что первый читает
вход дважды, а второй один раз. Но предположение о работе движка ещё не является
наблюдением. Оптимизатор может перестроить выражения, объединить или разделить этапы.

Нужен способ ответить на три разных вопроса:

1. Возвращают ли запросы один и тот же результат?
2. Какой физический план выбрал DuckDB для каждого запроса?
3. Что фактически произошло при выполнении?

## Концепция

### Между SQL и результатом есть план

SQL описывает желаемый результат декларативно. Мы говорим, какие строки и столбцы нужны,
но обычно не задаём точный алгоритм выполнения.

Упрощённая цепочка выглядит так:

```text
SQL-текст
-> логические операции
-> оптимизированный физический план
-> выполнение операторов
-> результат
```

Для этого урока достаточно различать три уровня.

| Уровень | Главный вопрос | Пример |
|---|---|---|
| SQL-текст | Что попросил автор? | два scalar subquery |
| Физический план | Как движок решил это выполнить? | два scan или один scan |
| Профиль выполнения | Что произошло на этих данных? | прочитано 7 строк, оператор вернул 4 |

Мы не изучаем все промежуточные стадии компилятора SQL. Термин «логический» здесь нужен
только для контраста: `WHERE`, `JOIN` и `GROUP BY` описывают смысл операций, а
`PANDAS_SCAN`, `HASH_JOIN` и `UNGROUPED_AGGREGATE` — выбранные DuckDB физические
операторы.

### План — дерево движения данных

У дерева есть:

- **листья** — источники данных, обычно scan-операторы;
- **промежуточные узлы** — фильтры, проекции, соединения, агрегаты и сортировки;
- **корень** — оператор, после которого получается итог запроса.

Текстовый план DuckDB рисуется корнем сверху, но смысл удобнее восстанавливать снизу
вверх:

```text
PANDAS_SCAN
-> FILTER
-> PROJECTION
-> UNGROUPED_AGGREGATE
-> итоговая строка
```

Читаем это как историю:

1. взять строки из pandas relation;
2. проверить условие;
3. оставить или вычислить нужные выражения;
4. свернуть строки в один итог;
5. вернуть результат.

Если у узла два ребёнка, у операции два входа. Так устроены, например, join и объединение
двух независимых scalar subquery.

### Минимальный словарь операторов

Названия зависят от движка и версии. Запоминать полный каталог не нужно. Важно узнавать
роль оператора.

| Семейство | Человеческий смысл | Что проверить |
|---|---|---|
| `*_SCAN` | Прочитать relation, таблицу или файл | сколько входов и строк прочитано |
| `FILTER` | Оставить строки по условию | сколько строк вошло и вышло |
| `PROJECTION` | Выбрать или вычислить выражения | не изменился ли смысл столбцов |
| `*_AGGREGATE` | Свернуть строки до нового grain | ожидаемое ли число групп или итоговых строк |
| `*_JOIN` | Сопоставить две ветви | не выросло ли число строк неожиданно |
| `ORDER_BY` / `SORT` | Установить порядок | действительно ли downstream нужен этот порядок |
| `CROSS_PRODUCT` | Сочетать строки двух входов | ожидалось ли такое сочетание |

`PROJECTION` может появляться несколько раз, даже если в SQL один `SELECT`. Оптимизатор
создаёт технические выражения и перестраивает дерево. Это не ошибка само по себе.

### Одна строка SQL не равна одному оператору

Нельзя надёжно посчитать scans по числу `FROM`, CTE или упоминаний имени таблицы в тексте.

Например, CTE может быть встроен в основной запрос, материализован или иначе перестроен.
Scalar subquery может получить дополнительные операторы, которые проверяют контракт
«не более одной строки». Условие из `FILTER` может оказаться вычисляемой projection, а не
отдельным узлом `FILTER`.

Поэтому правильный порядок такой:

```text
прочитать SQL
-> предсказать крупные ветви
-> открыть план
-> объяснить фактическое дерево
```

План не заменяет понимание SQL, а проверяет предположение о его выполнении.

### Cardinality — сколько строк выходит из оператора

**Cardinality** в плане — количество строк на определённой границе дерева. Важно всегда
уточнять, о какой величине идёт речь.

| Поле | Смысл | Не означает |
|---|---|---|
| `estimated_rows` | Сколько строк оптимизатор ожидал до выполнения | точный факт о данных |
| `actual_rows` | Сколько строк оператор фактически отдал следующему узлу | сколько строк было физически просмотрено |
| `rows_scanned` | Сколько строк прочитал scan-оператор | число строк итогового результата |

Пусть scan прочитал семь строк, а filter оставил четыре:

```text
scan rows_scanned = 7
scan actual_rows  = 7
filter actual_rows = 4
```

Агрегат затем может отдать одну строку:

```text
aggregate actual_rows = 1
```

Все три числа правильны, но отвечают на разные вопросы.

### Оценка — не обещание

До выполнения оптимизатор не знает фактический результат каждого условия. Он использует
доступную статистику и правила оценки.

Если `EXPLAIN` ожидает одну строку после filter, а `EXPLAIN ANALYZE` показывает четыре,
это не автоматически ошибка запроса и не автоматически плохой план. Это наблюдение:

```text
estimated_rows = 1
actual_rows    = 4
```

Для маленького примера расхождение нужно уметь назвать. Исследование причин больших
ошибок оценки, статистики таблиц и порядка сложных joins относится к углублённой работе
с производительностью.

### `EXPLAIN` и `EXPLAIN ANALYZE` отвечают на разные вопросы

| Команда | Выполняет исходный запрос | Что показывает | Когда нужна |
|---|---:|---|---|
| `EXPLAIN` | нет | выбранный план и оценки | безопасно рассмотреть предполагаемую форму работы |
| `EXPLAIN ANALYZE` | да | план, фактические строки и метрики выполнения | сопоставить ожидания с реальным запуском |

В DuckDB используем структурированный формат:

```sql
EXPLAIN (FORMAT JSON)
SELECT ...;
```

и:

```sql
EXPLAIN (ANALYZE, FORMAT JSON)
SELECT ...;
```

Слово `ANALYZE` принципиально: исходный запрос действительно выполняется. Поэтому
артефакт урока принимает только уже проверенные statements. Он не является SQL-песочницей
и не пытается определить безопасность запроса регулярным выражением.

В учебной практике мы анализируем только `SELECT`. Не запускайте `EXPLAIN ANALYZE` над
изменяющим данные statement, если не готовы к его реальному эффекту.

### План не доказывает корректность результата

План может показать:

- повторное чтение;
- число входных ветвей;
- фактический рост строк вокруг join;
- раннее или позднее сокращение данных;
- тяжёлую сортировку или агрегацию.

Но он не знает, что одна строка должна означать один заказ или один когортный период. Если
неверный join размножил выручку, оператор честно покажет выросшее число строк, но не
назовёт его бизнес-ошибкой.

Поэтому сравнение начинается с result gate:

```text
одинаковые колонки
+ одинаковый порядок колонок
+ одинаковые dtypes
+ одинаковые строки и их порядок
+ одинаковые значения
-> только затем сравниваем планы
```

Быстрый запрос с другим результатом — не оптимизация.

### Время оператора — наблюдение, а не готовый benchmark

`EXPLAIN ANALYZE` сообщает timing. Это полезный сигнал, но один запуск маленькой таблицы
не отвечает на вопрос «какой вариант быстрее в работе».

На результат влияют:

- прогрев процесса и библиотек;
- cache;
- размер и распределение данных;
- число потоков;
- файловый формат и устройство хранения;
- конкурирующая нагрузка;
- повторное выполнение запроса самим диагностическим кодом.

Кроме того, времена отдельных операторов нельзя бездумно складывать: часть метрик может
быть накопительной, а работа параллельных операторов способна перекрываться по wall time.

В этом уроке timing сохраняется в таблице операторов, но артефакт не выбирает победителя
по времени. Воспроизводимые повторы, warm-up, cache policy, медианы и интерпретация
разброса изучаются в `12/01 «Корректный benchmarking»`.

Под «стоимостью» сейчас понимаем наблюдаемую форму работы:

```text
сколько входных ветвей
сколько scan-операторов
сколько строк прочитано
сколько строк вышло из ключевых операторов
```

Это необходимый минимум до полноценного измерения производительности.

## Соберите это

Сначала построим уменьшенную модель плана вручную. DuckDB появится после того, как мы
сможем предсказать крупные ветви и контрольный результат.

### Шаг 1. Зафиксируйте входной grain

Используем знакомый типизированный результат `04/10` и `04/11`:

| cohort_month | activity_month | period_index | active_users |
|---|---|---:|---:|
| 2026-01-01 | 2026-01-01 | 0 | 4 |
| 2026-01-01 | 2026-02-01 | 1 | 3 |
| 2026-01-01 | 2026-03-01 | 2 | 2 |
| 2026-01-01 | 2026-04-01 | 3 | 0 |
| 2026-02-01 | 2026-02-01 | 0 | 3 |
| 2026-02-01 | 2026-03-01 | 1 | 2 |
| 2026-02-01 | 2026-04-01 | 2 | 1 |

Всего семь строк. Январской когорте принадлежат четыре строки.

### Шаг 2. Рассчитайте результат без плана

Для `cohort_month = 2026-01-01`:

```text
cohort_period_rows      = 4
active_user_period_sum  = 4 + 3 + 2 + 0 = 9
result grain            = одна строка на выбранную когорту
```

Эти значения становятся oracle. Если второй запрос вернёт `3` и `9`, `4` и `8` или
поменяет dtype суммы, сравнивать его план с исходным нельзя.

### Шаг 3. Нарисуйте ветви первого запроса

Не пытаемся предсказать все технические projections. Достаточно крупных этапов:

```text
ветвь A                                ветвь B
cohort_activity                        cohort_activity
-> выбрать январь                      -> выбрать январь
-> count(*) = 4                        -> sum(active_users) = 9
          \                            /
           -> соединить два скаляра
           -> одна строка (4, 9)
```

Ожидание до запуска:

```text
scan branches = 2
rows scanned  = 7 + 7 = 14
filter output = 4 в каждой ветви
result rows   = 1
```

Это гипотеза о физическом плане. DuckDB может добавить операторы проверки scalar
subquery, но две независимые ветви должны остаться наблюдаемыми, если оптимизатор их не
объединит.

### Шаг 4. Нарисуйте ветвь второго запроса

```text
cohort_activity
-> вычислить условие cohort_month = 2026-01-01
-> count FILTER и sum FILTER
-> одна строка (4, 9)
```

Ожидание:

```text
scan branches = 1
rows scanned  = 7
aggregate output = 1
result rows   = 1
```

Обратите внимание: условие написано внутри двух `FILTER`, но это не требует двух чтений.
Одна строка входа может передать вычисленный признак обоим агрегатам.

### Шаг 5. Сформулируйте контракт сравнения

```text
обязательно:
  exact result equality = true
  result columns = [cohort_period_rows, active_user_period_sum]
  result dtypes = [int64, int64]
  result values = [(4, 9)]

плановое ожидание:
  baseline scan operators = 2
  candidate scan operators = 1
  baseline rows scanned = 14
  candidate rows scanned = 7

не утверждаем:
  candidate обязательно быстрее на tiny
```

Теперь можно переходить к DuckDB.

## Используйте это

### 1. Сохраните явную connection

Повторяем границу `04/11`:

```python
connection = duckdb.connect()
try:
    report = compare_dataframe_queries(
        connection,
        relation_name="cohort_activity",
        frame=cohort_activity,
        baseline_sql=baseline_sql,
        candidate_sql=candidate_sql,
        parameters={"cohort_month": "2026-01-01"},
    )
finally:
    connection.close()
```

Функция временно регистрирует `cohort_activity` и снимает регистрацию в `finally`.
Connection остаётся открытой до завершения внешнего блока: вложенная функция не закрывает
чужой ресурс.

### 2. Получите план без выполнения

Внутри `inspect_reviewed_query` выполняется:

```python
row = connection.execute(
    "EXPLAIN (FORMAT JSON) " + sql,
    parameters,
).fetchone()

planned = json.loads(row[1])
```

JSON содержит вложенные объекты с полями `name`, `children` и `extra_info`. Для scan в
`extra_info` находится `Estimated Cardinality`.

Упрощённо:

```json
{
  "name": "PANDAS_SCAN",
  "children": [],
  "extra_info": {
    "Estimated Cardinality": "7"
  }
}
```

Это структурированный API плана. Мы не считаем слово `TABLE_SCAN` в ASCII-рамке и не
извлекаем время регулярным выражением.

### 3. Получите фактический профиль

```python
row = connection.execute(
    "EXPLAIN (ANALYZE, FORMAT JSON) " + sql,
    parameters,
).fetchone()

analyzed = json.loads(row[1])
```

Для каждого оператора доступны, среди прочего:

```text
operator_name
operator_cardinality
operator_rows_scanned
operator_timing
children
```

Помните: на этом шаге `sql` выполняется.

### 4. Превратите дерево в таблицу evidence

Артефакт рекурсивно обходит оба дерева, присваивает узлам путь и соединяет плановые и
фактические поля:

| path | operator | estimated_rows | actual_rows | rows_scanned | timing_seconds |
|---|---|---:|---:|---:|---:|
| `0` | `PROJECTION` | 1 | 1 | 0 | наблюдение |
| `0.0` | `UNGROUPED_AGGREGATE` | — | 1 | 0 | наблюдение |
| `0.0.0` | `PROJECTION` | 7 | 7 | 0 | наблюдение |
| `0.0.0.0` | `PROJECTION` | 7 | 7 | 0 | наблюдение |
| `0.0.0.0.0` | `PANDAS_SCAN` | 7 | 7 | 7 | наблюдение |

Таблица хранится корнем вперёд, но читаем её от самого глубокого пути:

```text
0.0.0.0.0 -> scan прочитал и отдал 7 строк
0.0.0.0   -> вычислены выражения
0.0.0     -> подготовлены входы агрегатов
0.0       -> агрегат отдал 1 строку
0         -> результат приведён к объявленным типам
```

Точное число `PROJECTION` не является учебным инвариантом. Значимы одна входная ветвь,
один scan семи строк и одна итоговая строка.

### 5. Сравните два плана только после result gate

`compare_reviewed_queries` сначала выполняет оба statements и использует точное
`assert_frame_equal`:

```text
columns
dtypes
row order
values
```

При различии функция останавливается:

```text
candidate result differs from baseline; plans are not comparable
```

Только после этого формируется сравнение:

```json
{
  "scope": {
    "engine": "duckdb",
    "engine_version": "зафиксированная версия окружения",
    "relation_name": "cohort_activity",
    "input_rows": 7
  },
  "baseline": {
    "scan_operators": 2,
    "rows_scanned": 14
  },
  "candidate": {
    "scan_operators": 1,
    "rows_scanned": 7
  },
  "scan_operators_removed": 1,
  "timing_is_observation_not_verdict": true
}
```

Каждый statement фактически выполняется дважды: один раз для результата и второй раз
внутри `EXPLAIN ANALYZE`. Это осознанная цена учебного аудита и ещё одна причина не
считать полученный timing benchmark-результатом.

Запустите пример:

```bash
uv run --locked python code/main.py
```

### 6. Перенесите способ чтения на join

Пусть есть две маленькие relation:

```text
cohorts(cohort_id unique, cohort_size)
segments(cohort_id unique, segment)
```

Запрос:

```sql
SELECT c.cohort_id, c.cohort_size, s.segment
FROM cohorts AS c
INNER JOIN segments AS s USING (cohort_id)
ORDER BY c.cohort_id;
```

Крупная форма плана:

```text
scan cohorts ----\
                  -> HASH_JOIN -> ORDER_BY -> result
scan segments ---/
```

Читаем:

1. найти два scan-листа;
2. проверить actual rows каждого входа;
3. найти join-узел;
4. проверить actual rows после join;
5. сопоставить число строк с заявленной cardinality `one-to-one`.

Если справа появится дубликат `cohort_id`, join может отдать три строки вместо двух. План
сделает рост наблюдаемым, но смысл нарушения по-прежнему определяется контрактом ключа из
`04/05`.

Названия `HASH_JOIN`, build side и probe side относятся к физической реализации. Для
этого урока достаточно увидеть две входные ветви, тип join и изменение числа строк.

## Сломайте это

### 1. Сравните разные результаты

Добавьте к сумме единицу:

```sql
CAST(sum(active_users) FILTER (...) AS BIGINT) + 1
    AS active_user_period_sum
```

Если сначала смотреть только на scan count, такой кандидат покажется «лучше». Result gate
должен остановить сравнение до обсуждения плана.

### 2. Посчитайте scans по SQL-тексту

Число `FROM`, CTE или упоминаний relation не является физическим планом. Оптимизатор
может перестроить запрос. Сначала сформулируйте ожидание, затем проверьте дерево.

### 3. Примите estimate за факт

В зафиксированном примере filter может иметь:

```text
estimated_rows = 1
actual_rows = 4
```

Фраза «после фильтра точно одна строка» неверна. Оценка существовала до выполнения.

### 4. Перепутайте output rows и rows scanned

Агрегат возвращает одну строку, но это не означает, что запрос прочитал одну строку.
Ищите scan-узел и его `rows_scanned`.

### 5. Назовите победителя по одному timing

На семи строках различия сопоставимы с накладными расходами. Даже если candidate timing
меньше, формулировка остаётся ограниченной:

> В этом запуске candidate использовал одну scan-ветвь вместо двух. Ускорение на рабочем
> объёме не измерялось.

### 6. Запустите `EXPLAIN ANALYZE` как безопасный preview

`ANALYZE` выполняет исходный statement. Артефакт не проверяет первое слово SQL и не
обещает read-only. Передавайте только проверенные `SELECT`-assets.

### 7. Объявите любой `CROSS_PRODUCT` ошибкой

В baseline он объединяет два скалярных результата `1 × 1` и отдаёт одну строку. Это
ожидаемая форма. Опасность определяется cardinality входов и бизнес-смыслом, а не одним
названием оператора.

### 8. Оптимизируйте количество технических projections

Число `PROJECTION` может меняться с версией DuckDB и преобразованием типов. Не ставьте
цель «уменьшить каждый узел». Сначала найдите наблюдаемую дорогую или подозрительную
работу: повторное чтение, рост строк, позднее сокращение или сортировку.

## Проверьте это

Behavioral tests фиксируют содержательные инварианты.

**Эквивалентность результата:**

```text
columns = [cohort_period_rows, active_user_period_sum]
dtypes  = [int64, int64]
values  = [(4, 9)] для января
values  = [(3, 6)] для февраля
values  = [(0, NULL)] для отсутствующей когорты
```

**Форма основного плана:**

```text
baseline scan operators = 2
baseline rows scanned = 14
candidate scan operators = 1
candidate rows scanned = 7
scan operators removed = 1
```

**Оценки и факты:**

- таблица содержит отдельные `estimated_rows`, `actual_rows` и `rows_scanned`;
- baseline filters фактически отдают четыре январские строки;
- timing не превращается в поле `faster_query` или иной автоматический вердикт.
- scope сохраняет версию DuckDB, relation, размер, columns и dtypes входа, а каждый
  вариант — SQL и параметры.

**Перенос на join:**

- план содержит два scan-входа;
- между ними найден `HASH_JOIN`;
- one-to-one пример отдаёт две строки после join.

**Программная граница:**

- relation снимается после успеха и после ошибки;
- переданная connection остаётся открытой;
- невалидный relation name и не-DataFrame отклоняются;
- артефакт использует JSON и не разбирает ASCII-план регулярным выражением;
- CLI отсутствует.

Запустите только тесты урока:

```bash
uv run --locked python -m unittest discover -s tests
```

Успешные тесты подтверждают reference implementation. Освоение урока означает, что вы
можете взять новый план, начать со scan-листьев, проследить изменение строк и отделить
наблюдение от вывода о производительности.

## Поставьте результат

Главный артефакт — `outputs/duckdb_plan_audit.py`.

Он предоставляет три уровня повторного использования:

- `inspect_reviewed_query` — получить результат, JSON-планы и таблицу операторов одного
  проверенного statement;
- `compare_reviewed_queries` — сначала проверить точную эквивалентность, затем сравнить
  два плана внутри уже подготовленной connection;
- `compare_dataframe_queries` — временно зарегистрировать один типизированный DataFrame,
  выполнить сравнение и гарантированно снять регистрацию.

SQL-assets:

- `outputs/repeated_scan.sql` — baseline с двумя ветвями;
- `outputs/single_scan.sql` — эквивалентный кандидат с одной ветвью.

Минимальный вызов:

```python
report = compare_dataframe_queries(
    connection,
    relation_name="cohort_activity",
    frame=cohort_activity,
    baseline_sql=repeated_scan_sql,
    candidate_sql=single_scan_sql,
    parameters={"cohort_month": "2026-01-01"},
)
```

Артефакт пригоден для review двух проверенных аналитических запросов, когда нужно
зафиксировать:

```text
результаты эквивалентны
-> планы получены в одном контексте
-> scan-ветви и строки наблюдаемы
-> timing не выдан за доказанное ускорение
```

CLI сознательно не добавляется. Новый инструмент используется внутри Python-проверки,
ноутбука или следующего интеграционного pipeline; командная оболочка не делает чтение
дерева понятнее.

## Упражнения

   число строк после каждого filter baseline. Затем сверьтесь с таблицей операторов.
2. Измените candidate так, чтобы он считал только периоды `period_index <= 2`. Объясните,
   почему один scan не даёт права сравнивать планы, и покажите срабатывание result gate.
3. В join-примере добавьте в `segments` второй ряд для `cohort_id = 1`. Предскажите
   actual rows после `HASH_JOIN`, затем объясните рост через cardinality из `04/05`.
4. Возьмите знакомую агрегацию из `04/04`. До `EXPLAIN` нарисуйте scan, filter и aggregate,
   затем сопоставьте ручную модель с фактическими операторами, не требуя совпадения числа
   технических projections.

## Что сознательно не входит в урок

- **Benchmark harness.** Warm-up, повторы, cache policy, медиана и разброс изучаются в
  `12/01`.
- **CPU и memory profiling.** Это отдельный результат `12/02`.
- **Parquet pushdown, row groups и файловый layout.** Они появляются в `12/04`, где есть
  подходящая задача и рабочий объём.
- **Статистика таблиц, join order и настройка оптимизатора.** Для первого чтения плана
  достаточно заметить оценки и фактические строки.
- **Полный каталог операторов.** Названия движка меняются; важнее роли scan, filter,
  aggregate, join и sort.
- **Автоматическая SQL-безопасность.** Артефакт принимает только проверенные statements и
  не изображает sandbox.
- **CLI.** Результат урока — способ чтения и сравнения планов, а не внешний интерфейс.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Query plan | Переформатированный SQL | Дерево операторов, выбранных движком для выполнения |
| Physical operator | Ключевое слово SQL | Конкретный шаг чтения или преобразования данных |
| Scan | Любое упоминание таблицы в тексте | Физический оператор чтения relation, таблицы или файла |
| Cardinality | Размер файла | Число строк на выходе определённого оператора |
| Estimated cardinality | Точное число строк | Оценка оптимизатора до выполнения |
| Actual cardinality | Число прочитанных строк | Фактическое число строк, отданных оператором дальше |
| Rows scanned | Число строк результата | Строки, просмотренные scan-оператором |
| `EXPLAIN` | Пробный запуск запроса | Получение плана без выполнения исходного statement |
| `EXPLAIN ANALYZE` | Безопасный preview | Реальное выполнение с фактическими метриками операторов |
| Result gate | Сравнение только итоговой суммы | Точная проверка columns, dtypes, порядка и значений до планов |
| Plan shape | Точное время запроса | Ветви и отношения физических операторов в дереве |
| Benchmark | Любой timing из профиля | Воспроизводимое измерение с контролем входа, окружения и повторов |

Отдельно зафиксируйте два ограничения: запрос действительно выполняется, а времена параллельных операторов нельзя просто складывать и сравнивать с общим временем.
- [EN · DuckDB: Profiling](https://duckdb.org/docs/current/dev/profiling) — прочитайте разделы `Statements`, `FORMAT Option` и `Query Graphs`. Они связывают учебный текстовый план с JSON-профилем, который использует артефакт урока; настройки detailed profiling оставьте для более глубокой диагностики.
- [EN · DuckDB: Metrics](https://duckdb.org/docs/current/dev/metrics) — найдите `OPERATOR_CARDINALITY`, `OPERATOR_ROWS_SCANNED`, `OPERATOR_TIMING` и cumulative metrics. Сопоставьте их с таблицей операторов отчёта и проверьте, какие показатели относятся к одному узлу, а какие включают его дочернее поддерево.
- [RU · Postgres Pro: использование EXPLAIN](https://postgrespro.ru/docs/postgrespro/current/using-explain) — прочитайте «Азы EXPLAIN» и начало раздела `EXPLAIN ANALYZE`: там особенно ясно объяснены дерево плана, scan-листья и различие оценок и фактов. Переносите способ рассуждения, но не PostgreSQL-специфичные стоимости, индексы и названия узлов в DuckDB.
- [RU · YDB: использование планов при оптимизации запросов](https://ydb.tech/docs/ru/dev/query-execution-optimization/query-plans-optimization) — разберите введение и первый план до добавления индекса. Проследите путь от `TableFullScan` через `Filter` к корню и сравните его с правилом чтения снизу вверх; команды YDB и индексный рецепт к практике DuckDB не относятся.
- [RU · YDB: структура планов запросов](https://ydb.tech/docs/ru/yql/query_plans) — используйте страницу как справочник по общим ролям `Filter`, `Aggregate`, `Join`, `Sort` и scan-операторов. Разделы о распределённых `Connection`, `Broadcast` и `HashShuffle` можно отложить: они выходят за необходимый минимум этого урока.
- [EN · DuckDB Blog: Optimizers — The Low-Key MVP](https://duckdb.org/2024/11/14/optimizers) — прочитайте введение и пример с filter pushdown. Статья показывает, почему порядок конструкций в SQL не равен физическому порядку работы и почему гипотезу о «лучшем» переписывании нужно проверять результатом и планом.
- [EN · DuckDB: My Workload Is Slow](https://duckdb.org/docs/current/guides/performance/my_workload_is_slow) — пройдите диагностический список целиком и найдите пункт о плане запроса. Он помогает удержать правильную границу: странный план — лишь одна из возможных причин, рядом с памятью, диском, типами, файлами и параллелизмом.
- [EN · DuckDB: Benchmarks](https://duckdb.org/docs/current/guides/performance/benchmarks) — прочитайте `A Note on Benchmarks` и disclaimer. Материал объясняет, почему один timing из `EXPLAIN ANALYZE`, tiny-набор или неполный workload нельзя превращать в общий вывод об ускорении; полноценный benchmark появится в фазе 12.
