# Агрегации и уровни детализации

> `GROUP BY` не просто сокращает таблицу: он задаёт новую единицу строки, а каждый
> агрегат обязан сохранять понятный знаменатель, единицу измерения и политику пропусков.

**Тип:** Case
**Треки:** Core
**Пререквизиты:** 04/03
**Время:** ~90 минут
**Результат:** по бизнес-вопросу строит SQL-агрегацию с явным grain, знаменателями и
NULL-политикой, различает `WHERE`, `FILTER` и `HAVING` и сверяет результат с ручной
таблицей.

## Цели обучения

После урока вы сможете:

- объявить входной и выходной grain до написания `GROUP BY`;
- перенести знакомую модель pandas `groupby` в SQL;
- выбирать между `COUNT(*)`, `COUNT(expression)` и `COUNT(DISTINCT expression)`;
- объяснить, какие строки используют `SUM`, `AVG`, `MIN` и `MAX` при наличии `NULL`;
- отличить `NULL` в ключе группы от `NULL` в измеряемом значении;
- распределить условия между `WHERE`, агрегатным `FILTER` и `HAVING`;
- не выдавать сумму известных частей за доказанно полный денежный итог;
- не складывать деньги с разными единицами измерения;
- проверить каждую группу по ручной таблице, знаменателям и reconciliation-инвариантам.

## На что опирается урок

Агрегация как идея уже подробно изучена в pandas. Здесь не нужно начинать с нуля:
нужно перенести знакомую модель в SQL и добавить правила самого языка.

| Уже освоено | Где | Что переносим |
|---|---|---|
| grain и ключ определяются смыслом строки | `03/01`, `03/05`, `04/01` | заранее объявляем grain результата |
| `groupby` меняет единицу анализа | `03/05` | группирующие выражения становятся ключом новой таблицы |
| `size`, `count`, `nunique`, `sum`, `mean` отвечают на разные вопросы | `03/05` | выбираем соответствующий SQL-агрегат |
| пропуск не равен нулю | `03/02`, `03/05`, `04/03` | не маскируем неизвестную часть через `COALESCE` |
| `WHERE` сохраняет только строки с результатом `TRUE` | `04/02`, `04/03` | определяем популяцию до группировки |
| явная проекция, типы и порядок — часть результата | `04/02` | фиксируем схему и `ORDER BY` агрегированной таблицы |

Короткий перевод знакомых операций:

| pandas | SQL | Смысл |
|---|---|---|
| `groupby("currency")` | `GROUP BY currency` | одна группа на валюту |
| `size()` | `COUNT(*)` | все строки группы |
| `count()` по `amount` | `COUNT(amount)` | строки с известной суммой |
| `nunique()` по `user_id` | `COUNT(DISTINCT user_id)` | разные известные пользователи |
| `sum()` | `SUM(amount)` | сумма известных значений |
| `mean()` | `AVG(amount)` | среднее известных значений |

Новая часть урока — логический порядок SQL, агрегатный `FILTER`, `HAVING` и точное
взаимодействие агрегатов с `NULL`.

## Проблема

В relation `orders` одна строка описывает один заказ:

```text
входной grain -> одна строка на order_id
ключ          -> order_id
amount        -> DECIMAL(18, 2), NULL разрешён
currency      -> единица измерения amount
```

Нужно построить отчёт по валютам. Для каждой валюты заказчик хочет видеть:

- сколько всего заказов было в исходной популяции;
- у скольких заказов известна сумма;
- сколько заказов оплачено;
- у скольких оплаченных заказов известна сумма;
- сколько оплаченных сумм отсутствует;
- сумму и среднее известных оплаченных сумм.

Естественный выходной grain:

```text
одна строка -> одна currency
ключ        -> currency
```

Для tiny-набора получаются четыре денежные суммы:

```text
EUR -> 1625.00 EUR
KZT ->  500.00 KZT
RUB -> 2700.00 RUB
USD ->  180.00 USD
```

Их нельзя сложить в число `5005` и назвать общей выручкой. У слагаемых разные единицы
измерения. Такой итог синтаксически возможен и внешне убедителен, но не имеет
аналитического смысла без отдельного курса конвертации, даты курса и правила округления.

Есть и менее заметная опасность. `SUM(amount)` обычно игнорирует `NULL`. Если у одного
оплаченного заказа сумма отсутствует, SQL может вернуть аккуратную сумму остальных
заказов. Без отдельного знаменателя она выглядит полной.

Значит, хороший агрегированный отчёт обязан сохранять не только итог, но и evidence:

```text
сколько строк было всего
сколько строк участвовало в сумме
сколько обязательных значений отсутствует
в какой единице измерения записано число
```

## Концепция

### 1. `GROUP BY` создаёт новую relation и новый grain

До группировки `currency` может повторяться:

```text
O1001 -> RUB
O1002 -> RUB
O1005 -> RUB
```

После:

```text
RUB -> одна строка с агрегатами трёх заказов
```

Группирующие выражения определяют ключ результата. Поэтому фраза:

```sql
GROUP BY currency
```

читается как обещание:

> Одна строка результата будет описывать одну валюту.

Если написать:

```sql
GROUP BY currency, status
```

обещание изменится:

> Одна строка результата будет описывать одну комбинацию валюты и статуса.

Это не дополнительная сортировка и не косметическая детализация. Это другой grain и
другая таблица.

В обычном агрегированном `SELECT` каждое выражение должно быть:

1. ключом группировки;
2. либо агрегатом над строками группы.

Например, запрос:

```sql
SELECT currency, status, count(*)
FROM orders
GROUP BY currency;
```

не определяет, какой единственный `status` показать для группы из разных статусов.
Корректное решение — либо добавить `status` в grain, либо убрать его из результата,
либо задать осмысленный агрегат.

### 2. Агрегация без `GROUP BY` имеет grain всей популяции

`GROUP BY` не обязателен:

```sql
SELECT count(*) AS order_rows
FROM orders;
```

Результат содержит одну строку:

```text
grain -> вся выбранная популяция orders
```

Если до агрегата есть `WHERE`, строка результата описывает уже отфильтрованную
популяцию. Это важно проговаривать: «одна строка» ещё не объясняет, какие наблюдения
вошли в число.

На пустой популяции `COUNT(*)` возвращает `0`, а `SUM` и `AVG` обычно возвращают
`NULL`: строк нет, поэтому сумма или среднее не доказаны самим агрегатом.

### 3. Один универсальный `COUNT` не существует

Рассмотрим группу из трёх заказов:

| `order_id` | `user_id` | `amount` |
|---|---|---:|
| A | U1 | 100.00 |
| B | U1 | `NULL` |
| C | `NULL` | 50.00 |

Результаты:

```text
COUNT(*)                 = 3
COUNT(amount)            = 2
COUNT(user_id)           = 2
COUNT(DISTINCT user_id)  = 1
```

Каждое число правильно, но отвечает на свой вопрос:

| Агрегат | Вопрос |
|---|---|
| `COUNT(*)` | Сколько строк в группе? |
| `COUNT(amount)` | Для скольких строк известна сумма? |
| `COUNT(user_id)` | Для скольких строк известен пользователь? |
| `COUNT(DISTINCT user_id)` | Сколько разных известных пользователей? |

Имена результата должны сохранять знаменатель:

```text
order_rows
known_amount_rows
known_user_rows
distinct_known_users
```

Название `orders` для `COUNT(amount)` опасно: оно скрывает заказы с неизвестной суммой.

### 4. Числовые агрегаты обычно пропускают `NULL`

Для значений:

```text
100.00, NULL, 50.00
```

получатся:

```text
SUM(amount) = 150.00
AVG(amount) = 75.00
MIN(amount) = 50.00
MAX(amount) = 100.00
```

`AVG` использует знаменатель `COUNT(amount)`, а не `COUNT(*)`:

```text
AVG(amount) = SUM известных amount / COUNT известных amount
            = 150 / 2
            = 75
```

Это может быть нужной статистикой известных наблюдений. Но она не является средним по
всем трём строкам и не доказывает, что пропущенная сумма равна нулю.

Если все аргументы группы равны `NULL`, то:

```text
COUNT(*)       -> число строк группы
COUNT(amount)  -> 0
SUM(amount)    -> NULL
AVG(amount)    -> NULL
MIN(amount)    -> NULL
MAX(amount)    -> NULL
```

Именно пара `COUNT(*)` и `COUNT(amount)` показывает, что группа существует, но измерение
для неё не известно.

### 5. `NULL` в ключе и `NULL` в значении играют разные роли

Если `currency` равна `NULL`, SQL не выбрасывает строку из `GROUP BY`. Все строки с
пропущенной валютой образуют отдельную `NULL`-группу.

Это не означает, что выражение `NULL = NULL` стало `TRUE`. Группировка использует
специальное правило для формирования групп.

Для аналитика такая группа полезна как сигнал:

```text
currency = NULL -> сумма есть, но единица измерения неизвестна
```

В этом уроке политика контракта — сохранить её для аудита. Автоматически переименовывать
её в `'UNKNOWN'` необязательно: это уже бизнес-метка, которая может совпасть с реальным
значением источника.

`NULL` в `amount` не меняет ключ группы. Заказ остаётся в своей валюте, но не входит в
`COUNT(amount)`, `SUM(amount)` и `AVG(amount)`.

### 6. Сумма известных частей не доказывает полноту

Пусть в RUB-группу добавили оплаченный заказ с `amount = NULL`.

До добавления:

```text
paid_order_rows          = 2
paid_known_amount_rows   = 2
known_paid_revenue       = 2700.00
```

После:

```text
paid_order_rows          = 3
paid_known_amount_rows   = 2
paid_missing_amount_rows = 1
known_paid_revenue       = 2700.00
```

Сумма не изменилась. Без счётчиков можно ошибочно решить, что новые данные подтвердили
тот же полный итог.

Поэтому артефакт использует осторожное имя `known_paid_revenue` и публикует рядом:

```text
paid_missing_amount_rows
paid_amount_complete
```

`paid_amount_complete = TRUE` означает только одно: у каждой оплаченной строки этой
группы есть `amount`. Это не доказывает корректность валюты, статуса или исходного
бизнес-правила.

`COALESCE(SUM(amount), 0)` не исправляет частичную группу. Он влияет только на случай,
когда агрегат вернул `NULL`, и может превратить полностью неизвестную сумму в
доказанный ноль. Использовать его можно лишь после отдельного предметного решения:
например, когда отсутствие подходящих строк действительно означает нулевой результат.

### 7. `WHERE`, `FILTER` и `HAVING` отвечают на разные вопросы

Упрощённый логический порядок запроса:

```text
FROM
-> WHERE
-> GROUP BY
-> вычисление агрегатов и FILTER
-> HAVING
-> SELECT
-> ORDER BY
```

#### `WHERE` выбирает исходную популяцию

```sql
FROM orders
WHERE status = 'paid'
GROUP BY currency
```

Неоплаченные строки исчезают до построения групп. После этого:

- `COUNT(*)` считает только оплаченные заказы;
- нельзя одновременно показать полный размер исходной группы;
- валюты без оплаченных строк вообще не появятся.

Из `04/03` уже известно: `WHERE` сохраняет только `TRUE`. Строка с `status = NULL` не
считается подтверждённо оплаченной.

#### `FILTER` выбирает строки одного агрегата

```sql
count(*) FILTER (WHERE status = 'paid')
```

Relation остаётся на полной популяции, но конкретный агрегат использует только строки,
для которых условие `TRUE`.

Поэтому в одной строке можно сопоставить:

```sql
count(*) AS order_rows,
count(*) FILTER (WHERE status = 'paid') AS paid_order_rows
```

Внутреннее слово `WHERE` является частью синтаксиса `FILTER`; оно не равно общему
предложению `WHERE` всего запроса.

#### `HAVING` выбирает уже построенные группы

```sql
GROUP BY currency
HAVING count(*) FILTER (WHERE status = 'paid') >= 3
```

Сначала SQL строит все валютные группы и считает оплаченные строки, затем оставляет
группы с тремя и более оплаченными заказами.

`HAVING` не меняет определение grain: строка по-прежнему означает одну валюту. Он меняет
набор опубликованных групп.

Практическое правило:

| Нужно решить | Место условия |
|---|---|
| Какие исходные строки участвуют во всех расчётах? | `WHERE` |
| Какие строки участвуют только в одном агрегате? | `FILTER` |
| Какие готовые группы публиковать? | `HAVING` |

### 8. Единица измерения ограничивает аддитивность

`SUM` умеет складывать числа, но не знает, совместимы ли их единицы.

Допустимо:

```text
1200 RUB + 1500 RUB = 2700 RUB
```

Недопустимо:

```text
2700 RUB + 180 USD + 1625 EUR + 500 KZT
```

Группировка по `currency` защищает единицу результата. Но если затем бездумно сложить
столбец `known_paid_revenue`, защита исчезнет.

Для общего денежного итога понадобилась бы отдельная модель:

- целевая валюта;
- источник курса;
- дата или временной интервал курса;
- правило для отсутствующего курса;
- порядок конвертации и округления.

Этой модели в данных нет, поэтому урок не изобретает её.

Средние тоже нельзя бездумно складывать или усреднять. Чтобы объединить групповые
средние, нужны исходная сумма и соответствующий знаменатель. Иначе маленькая и большая
группы получат одинаковый вес.

## Соберите это

Сначала не пишите SQL. Вручную постройте ту таблицу, которую должен вернуть запрос.

### Шаг 1. Объявите входной и выходной grain

```text
вход:
одна строка на order_id

выход:
одна строка на currency

популяция:
все 12 проверенных заказов

денежная единица:
currency текущей группы
```

### Шаг 2. Разложите строки по группам

```text
EUR:
O1006 paid      25.00
O1008 cancelled NULL
O1009 paid     900.00
O1012 paid     700.00

KZT:
O1007 paid     500.00

RUB:
O1001 paid    1200.00
O1002 refunded 800.00
O1005 paid    1500.00

USD:
O1003 paid      75.00
O1004 pending   NULL
O1010 paid      60.00
O1011 paid      45.00
```

Проверьте, что каждый `order_id` попал ровно в одну группу.

### Шаг 3. Для каждой группы ответьте на одинаковые вопросы

Для EUR:

```text
order_rows                 = 4
known_amount_rows          = 3
paid_order_rows            = 3
paid_known_amount_rows     = 3
paid_missing_amount_rows   = 0
known_paid_revenue         = 25 + 900 + 700 = 1625.00 EUR
average_known_paid_amount  = 1625 / 3 ≈ 541.67 EUR
```

Повторите расчёт для остальных валют. Получится полный ручной oracle:

| `currency` | `order_rows` | `known_amount_rows` | `paid_order_rows` | `paid_known_amount_rows` | `paid_missing_amount_rows` | `paid_amount_complete` | `known_paid_revenue` | `average_known_paid_amount` |
|---|---:|---:|---:|---:|---:|---|---:|---:|
| EUR | 4 | 3 | 3 | 3 | 0 | `TRUE` | 1625.00 | 541.6667 |
| KZT | 1 | 1 | 1 | 1 | 0 | `TRUE` | 500.00 | 500.00 |
| RUB | 3 | 3 | 2 | 2 | 0 | `TRUE` | 2700.00 | 1350.00 |
| USD | 4 | 3 | 3 | 3 | 0 | `TRUE` | 180.00 | 60.00 |

Числа в строках сравниваются только внутри одной валюты. Столбец денежных итогов не
получает общей суммы.

### Шаг 4. Запишите независимые инварианты

Счётчики можно свернуть обратно, потому что валютные группы не пересекаются:

```text
sum(order_rows)               = 12
sum(known_amount_rows)        = 10
sum(paid_order_rows)          = 9
sum(paid_known_amount_rows)   = 9
sum(paid_missing_amount_rows) = 0
```

Для каждой группы:

```text
paid_order_rows
= paid_known_amount_rows + paid_missing_amount_rows
```

Денежный контроль устроен иначе:

```text
EUR SQL == EUR ручной расчёт
KZT SQL == KZT ручной расчёт
RUB SQL == RUB ручной расчёт
USD SQL == USD ручной расчёт
```

Общего сравнения денежных значений между валютами нет.

## Используйте это

Готовый SQL-артефакт повторяет ручную таблицу:

```sql
SELECT
    currency,
    count(*) AS order_rows,
    count(amount) AS known_amount_rows,
    count(*) FILTER (WHERE status = 'paid') AS paid_order_rows,
    count(amount) FILTER (WHERE status = 'paid') AS paid_known_amount_rows,
    (
        count(*) FILTER (WHERE status = 'paid')
        - count(amount) FILTER (WHERE status = 'paid')
    ) AS paid_missing_amount_rows,
    (
        count(*) FILTER (WHERE status = 'paid')
        = count(amount) FILTER (WHERE status = 'paid')
    ) AS paid_amount_complete,
    sum(amount) FILTER (WHERE status = 'paid') AS known_paid_revenue,
    avg(amount) FILTER (WHERE status = 'paid') AS average_known_paid_amount
FROM orders
GROUP BY currency
ORDER BY currency ASC NULLS LAST;
```

Каждый столбец сохраняет смысл:

| Столбец | Что доказывает |
|---|---|
| `currency` | единицу строки и денежных значений |
| `order_rows` | полный размер группы |
| `known_amount_rows` | сколько сумм известно независимо от статуса |
| `paid_order_rows` | сколько строк подтверждённо оплачено |
| `paid_known_amount_rows` | знаменатель денежных агрегатов оплаченных строк |
| `paid_missing_amount_rows` | сколько оплаченных сумм отсутствует |
| `paid_amount_complete` | все ли оплаченные строки имеют сумму |
| `known_paid_revenue` | сумму известных оплаченных значений, не обещание полной выручки |
| `average_known_paid_amount` | среднее известных оплаченных сумм |

`ORDER BY currency ASC NULLS LAST` не влияет на агрегацию. Он делает опубликованную
таблицу воспроизводимой и помещает диагностическую `NULL`-группу в конец.

### Когда нужен общий `WHERE`

Если отчёт действительно должен описывать только оплаченные заказы:

```sql
SELECT
    currency,
    count(*) AS paid_order_rows,
    count(amount) AS paid_known_amount_rows,
    sum(amount) AS known_paid_revenue
FROM orders
WHERE status = 'paid'
GROUP BY currency;
```

Теперь `COUNT(*)` имеет другой знаменатель: неоплаченных заказов во входной популяции
агрегата уже нет. Это корректный запрос для другого контракта, но он не заменяет
основной отчёт, где нужны и полный размер группы, и оплаченная часть.

### Когда нужен `HAVING`

Оставить только валюты минимум с тремя оплаченными заказами:

```sql
SELECT
    currency,
    count(*) FILTER (WHERE status = 'paid') AS paid_order_rows
FROM orders
GROUP BY currency
HAVING count(*) FILTER (WHERE status = 'paid') >= 3
ORDER BY currency ASC NULLS LAST;
```

На tiny-наборе останутся EUR и USD. `HAVING` применяется после расчёта группового
счётчика; `WHERE` не может заменить его без изменения исходной популяции.

### Когда нужен `COUNT(DISTINCT ...)`

Если вопрос звучит «сколько разных пользователей платили в каждой валюте»:

```sql
count(DISTINCT user_id) FILTER (WHERE status = 'paid')
    AS distinct_known_paid_users
```

Такой агрегат считает разные известные `user_id`, а не заказы. Его знаменатель и grain
нужно назвать отдельно; один пользователь может сделать несколько заказов.

## Сломайте это

### Поломка 1. Сложить разные валюты

```text
2700 + 180 + 1625 + 500 = 5005
```

SQL посчитает число, но у него нет денежной единицы. Проверка должна запрещать такой
итог, а не сравнивать его с ещё одной реализацией той же ошибки.

### Поломка 2. Назвать `COUNT(amount)` числом заказов

Для USD:

```text
COUNT(*)      = 4
COUNT(amount) = 3
```

`O1004` существует, но его сумма неизвестна. Название `order_rows` для
`COUNT(amount)` потеряет заказ из знаменателя.

### Поломка 3. Добавить оплаченный заказ с неизвестной суммой

После добавления в RUB:

```text
O1999 paid RUB NULL
```

результат должен стать:

```text
paid_order_rows          = 3
paid_known_amount_rows   = 2
paid_missing_amount_rows = 1
paid_amount_complete     = FALSE
known_paid_revenue       = 2700.00
```

Неизменившаяся сумма теперь явно помечена как сумма известных частей.

### Поломка 4. Заменить неизвестную сумму нулём

```sql
sum(coalesce(amount, 0)) FILTER (WHERE status = 'paid')
```

Число останется `2700.00`, но evidence о пропуске исчезнет. Ноль утверждает известное
значение, поэтому такая замена требует бизнес-правила, которого в контракте нет.

### Поломка 5. Перенести условие из `FILTER` в общий `WHERE`

```sql
WHERE status = 'paid'
```

Теперь `order_rows` перестанет считать полный размер валютной группы. Запрос может быть
корректен, но отвечает на другой вопрос.

### Поломка 6. Фильтровать групповой результат в `WHERE`

```sql
WHERE count(*) >= 3
```

`WHERE` выполняется до группировки, поэтому группового `count(*)` ещё нет. Для условия
на готовый агрегат используется `HAVING`.

### Поломка 7. Добавить лишний ключ

```sql
GROUP BY currency, status
```

Результат перейдёт на grain «одна строка на валюту и статус». Сравнивать его построчно с
таблицей «одна строка на валюту» уже нельзя.

### Поломка 8. Потерять `NULL`-группу

Если у заказа неизвестна `currency`, он всё равно должен войти в `order_rows` отдельной
диагностической группы. Удаление такой строки без отчёта нарушит reconciliation.

### Поломка 9. Усреднить групповые средние

```text
average(EUR average, KZT average, RUB average, USD average)
```

Так группы из одного и четырёх заказов получат одинаковый вес. Для объединения нужны
суммы и знаменатели, причём денежные значения сначала должны иметь общую валюту.

## Проверьте это

### Контрольная таблица

SQL-результат должен совпасть с ручным oracle по каждой валюте, каждому счётчику и
каждому денежному значению. Для EUR среднее сравнивается с допустимой точностью, потому
что `AVG(DECIMAL)` DuckDB возвращает как `DOUBLE`.

### Входной контракт

- relation называется `orders`;
- входной grain — одна строка на непустой уникальный `order_id`;
- `status` и `currency` имеют тип `VARCHAR`;
- `amount` имеет тип `DECIMAL(18,2)`;
- `status`, `currency` и `amount` могут быть `NULL`;
- runner не нормализует значения повторно внутри SQL-артефакта.

### Выходной контракт

- одна строка соответствует одной `currency`, включая возможную `NULL`-группу;
- столбцы и их порядок фиксированы;
- счётчики имеют тип `BIGINT`;
- completeness имеет тип `BOOLEAN`;
- `known_paid_revenue` остаётся `DECIMAL(38,2)`, а не превращается во `float`;
- результат упорядочен по валюте с `NULL` в конце;
- денежный итог между разными валютами отсутствует.

### Reconciliation-инварианты

```text
sum(order_rows) == count(*) источника
sum(known_amount_rows) == count(amount) источника
sum(paid_order_rows) == count(*) источника при status = 'paid'
sum(paid_known_amount_rows) == count(amount) при status = 'paid'
paid_order_rows == paid_known_amount_rows + paid_missing_amount_rows
```

Для каждой валюты:

```text
SQL known_paid_revenue == ручная сумма известных paid amount той же валюты
AVG * paid_known_amount_rows ≈ known_paid_revenue
```

Последнее равенство не превращает среднее в денежный total: оно только проверяет
согласованность числителя и знаменателя одной группы.

- поведение `UNKNOWN` внутри `FILTER`;

- отказ от общего денежного итога;
- нарушение входного grain повторным `order_id`.

## Упражнения

1. Измените grain на `currency, status`. До SQL предскажите число строк и объясните,
   почему это другая таблица, а не более подробный вариант прежней строки.
2. Добавьте `COUNT(DISTINCT user_id)` для оплаченных заказов. Сравните число пользователей
   с числом заказов и объясните различие знаменателей.
3. Добавьте оплаченный RUB-заказ с `amount = NULL`. Проверьте, что сумма известных
   значений не изменилась, а completeness стала `FALSE`.
4. Через `HAVING` оставьте валюты минимум с тремя оплаченными заказами. Убедитесь, что
   grain остался прежним, а набор групп изменился.
5. Добавьте строку с `currency = NULL`. Сохраните диагностическую группу и проверьте
   reconciliation всех исходных строк.
6. Добавьте валюту, у которой единственный оплаченный заказ имеет `amount = NULL`.
   Объясните сочетание `COUNT(*) = 1`, `COUNT(amount) = 0`, `SUM(amount) = NULL`.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Group key | Столбец для сортировки | Выражение, определяющее группы и grain результата |
| Aggregate | Любая функция в `SELECT` | Функция, сворачивающая строки группы в итог |
| `COUNT(*)` | Число известных значений | Число строк независимо от `NULL` в отдельных столбцах |
| `COUNT(expression)` | Число строк | Число не-NULL результатов выражения |
| `COUNT(DISTINCT expression)` | Число строк без дублей | Число разных известных результатов выражения |
| `FILTER` | Фильтр всего запроса | Условие участия строк в одном агрегате |
| `HAVING` | Вариант `WHERE` | Фильтр уже построенных групп |
| Denominator | Техническая деталь среднего | Популяция наблюдений, на которую относится метрика |
| Known total | Доказанно полный итог | Сумма доступных значений, полнота которой проверяется отдельно |
| Additivity | Возможность сложить любые числа | Допустимость суммирования при совместимых grain и единицах |
| Reconciliation | Повторить ту же формулу | Независимо сверить строки, знаменатели и значения до и после смены grain |

## Что будет дальше

В `04/05` появятся таблицы разного grain. Перед соединением товарные позиции придётся
агрегировать до одной строки на `order_id`, иначе суммы заказов размножатся. Этот урок
даёт необходимый механизм: объявить новый grain, выбрать агрегаты и доказать, что строки
и знаменатели не потерялись.
