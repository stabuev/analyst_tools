# Joins без размножения метрик

> До `JOIN` нужно предсказать, какие пары строк он создаст. После `JOIN` нужно доказать,
> что результат сохранил задуманный grain, нужные строки и единицы измерения метрик.

**Тип:** Case
**Треки:** Core
**Пререквизиты:** `04/04`
**Время:** ~105 минут
**Результат:** перед `JOIN` фиксирует grain, ключ, ожидаемое число совпадений и политику
unmatched-строк, а после проверяет целевой grain и сохранение метрик в их исходных
единицах.

## Зачем этот урок аналитику

Аналитические данные редко находятся в одной таблице. Заказ хранится отдельно от
пользователя, товарных позиций, платежей и обращений в поддержку. Чтобы ответить на
рабочий вопрос, аналитик соединяет эти факты.

Синтаксически правильный `JOIN` при этом может вернуть правдоподобный, но неверный
результат:

- строк стало больше, и сумма заказа повторилась на каждой товарной позиции;
- строк стало меньше, потому что часть ключей не нашлась в справочнике;
- две таблицы соединили по неполному составному ключу;
- `NULL` в ключе приняли за обычное совпадающее значение;
- дубликат в справочнике превратил ожидаемую связь many-to-one в fanout;
- денежные итоги сверили одним числом, хотя в данных несколько валют.

База данных не знает, является ли это ошибкой. Она честно создаёт все пары строк,
которые удовлетворяют условию `ON`. Поэтому безопасность соединения — часть
аналитической методологии, а не свойство ключевого слова `JOIN`.

## Цели обучения

После урока вы сможете:

- до запроса назвать grain обеих сторон, ключ соединения и целевой grain;
- предсказать число строк по частотам ключей;
- отличить multiplicity совпадений от покрытия ключей;
- осознанно выбрать `INNER`, `LEFT`, `SEMI` или `ANTI JOIN`;
- понять, почему `LEFT JOIN` тоже может размножить строки;
- предварительно агрегировать дочернюю таблицу до grain родителя;
- отличить отсутствующую ссылку от ссылки на несуществующую строку;
- проверить unmatched-ключи в обоих направлениях;
- сверить метрики после соединения, не смешивая валюты и не теряя `NULL`;
- диагностировать fanout по данным, а не по ощущению от запроса.

Урок не начинает тему связей с нуля. Мы переносим уже знакомую модель в SQL:

## Проблема

Нужно построить витрину с grain:

> одна строка на заказ.

В ней нужны:

- сведения из `orders`;
- число и сумма товарных позиций из `order_items`;
- признак того, найден ли пользователь в `users`;
- состояние сверки `orders.amount` и суммы позиций.

Исходные таблицы имеют разные grain:

| Relation | Grain | Ключ |
|---|---|---|
| `orders` | одна строка на заказ | `order_id` |
| `order_items` | одна строка на товарную позицию заказа | `(order_id, product_id)` |
| `users` | одна строка на пользователя | `user_id` |

Наивный запрос выглядит естественно:

```sql
SELECT
    o.order_id,
    o.currency,
    o.amount,
    i.product_id
FROM orders AS o
INNER JOIN order_items AS i
    ON o.order_id = i.order_id;
```

Но результат уже имеет grain товарной позиции. Для заказа `O1001` есть две позиции:

```text
orders
order_id  amount
O1001     1200.00

order_items
order_id  product_id  line amount
O1001     P01          1000.00
O1001     P02           200.00
```

После соединения:

```text
order_id  product_id  amount
O1001     P01          1200.00
O1001     P02          1200.00
```

Сумма `orders.amount` для этого заказа стала `2400.00`, хотя сам заказ не изменился.
Ошибка появилась не в `SUM`. Она появилась раньше, когда метрику grain заказа перенесли
на grain позиции.

## Концепция

### JOIN создаёт пары строк

Для каждого значения ключа SQL берёт все подходящие строки слева и все подходящие строки
справа. Затем создаёт все пары между ними.

Если для ключа `K`:

- слева `L(K)` строк;
- справа `R(K)` строк;

то `INNER JOIN` создаст:

```text
L(K) × R(K)
```

строк для этого ключа.

Пример:

```text
слева 2 строки с K
справа 3 строки с K
результат 2 × 3 = 6 строк
```

Это не случайное «размножение базы данных». Это точное следствие условия совпадения.

Для `LEFT JOIN` каждая левая строка:

- создаёт по одной строке на каждое совпадение справа;
- остаётся одной строкой с правыми `NULL`, если совпадений нет.

Поэтому для одного ключа число строк можно записать так:

```text
L(K) × max(R(K), 1)
```

Главное следствие:

> `LEFT JOIN` гарантирует, что левая строка не исчезнет, но не гарантирует, что она
> останется единственной.

### Четыре разных вопроса перед соединением

Перед каждым `JOIN` ответьте на четыре вопроса отдельно:

| Вопрос | Пример ответа |
|---|---|
| Каков grain каждой стороны? | заказ и товарная позиция заказа |
| По какому полному ключу сопоставляются строки? | `order_id` |
| Сколько совпадений допустимо для одной строки? | справа может быть много позиций |
| Каков целевой grain результата? | одна строка на заказ |

Тип `LEFT` или `INNER` не отвечает на остальные три вопроса. Он задаёт только политику
для строк без пары.

### Cardinality зависит от направления

Одну и ту же связь можно описать по-разному в зависимости от того, откуда мы смотрим:

| Левая сторона | Правая сторона | Ожидание среди совпавших строк |
|---|---|---|
| `orders` | `order_items` | one-to-many |
| `order_items` | `orders` | many-to-one |
| `orders` | `item_totals` | one-to-one среди совпавших строк; справа может не быть строки |
| `orders` | `users` | many-to-one |

Фраза one-to-one или many-to-one описывает multiplicity — сколько строк может
совпасть. Она не обещает, что совпадение вообще существует.

Например, `users.user_id` может быть уникальным, но заказ `O1010` с `user_id = 'U999'`
всё равно не найдёт пользователя. Поэтому отдельно проверяются:

1. **Uniqueness:** не больше ли одного совпадения там, где ожидается одно.
2. **Coverage:** нашлась ли хотя бы одна пара там, где она нужна.

### Target grain выбирает аналитик

Прямой `orders JOIN order_items` не является неправильным сам по себе. Он корректен,
если нужен результат «одна строка на товарную позицию».

Ошибка возникает, когда:

1. нужен grain заказа;
2. соединение создаёт grain позиции;
3. поля и метрики заказа продолжают использовать так, словно они остались уникальными.

Для нашей витрины нужен grain заказа. Значит, `order_items` сначала надо привести к одной
строке на `order_id`:

```text
order_items
одна строка на (order_id, product_id)

        GROUP BY order_id
                ↓

item_totals
одна строка на order_id
```

После этого у одного заказа справа будет не более одной строки.

### Деньги сохраняют единицу измерения

В `orders` одновременно находятся RUB, USD, EUR и KZT. Числа:

```text
2700 RUB
180 USD
1625 EUR
500 KZT
```

нельзя сложить в один осмысленный денежный итог без курса и правила конвертации.
Поэтому fanout проверяется отдельно внутри каждой валюты.

Для исходных данных:

| Валюта | Оплаченная сумма в `orders` | После прямого JOIN к позициям | Лишнее из-за fanout |
|---|---:|---:|---:|
| EUR | 1625.00 | 1625.00 | 0.00 |
| KZT | 500.00 | 500.00 | 0.00 |
| RUB | 2700.00 | 5400.00 | 2700.00 |
| USD | 180.00 | 180.00 | 0.00 |

Разница появилась только в RUB: оплаченные заказы `O1001` и `O1005` имеют по две
позиции. Общие числа `5005` и `7705` здесь не публикуются, потому что смешивают валюты.

### `ON` и `USING`

Если ключи называются одинаково, короткая запись допустима:

```sql
FROM orders
LEFT JOIN item_totals USING (order_id)
```

Более явная запись:

```sql
FROM orders AS o
LEFT JOIN item_totals AS i
    ON o.order_id = i.order_id
```

В учебном артефакте используется `ON`, потому что в нём видны:

- левая и правая стороны;
- точные столбцы;
- все части составного условия.

Для составного ключа нужно перечислить каждую часть:

```sql
FROM order_lines AS l
LEFT JOIN prices AS p
    ON l.order_id = p.order_id
   AND l.product_id = p.product_id
```

Если оставить только `order_id`, каждая позиция заказа может совпасть с ценой другой
позиции того же заказа.

Не используйте `NATURAL JOIN` в аналитической модели. Он выбирает одноимённые столбцы
неявно, поэтому добавление нового одноимённого поля способно изменить смысл запроса.

### Основные типы JOIN

#### `INNER JOIN`: нужны только совпавшие пары

```sql
SELECT
    o.order_id,
    u.plan
FROM orders AS o
INNER JOIN users AS u
    ON o.user_id = u.user_id;
```

Заказ `O1010` исчезнет, потому что `U999` отсутствует в `users`. Это подходит, только
если бизнес-вопрос действительно требует отбросить unmatched-заказы. Для аудита
качества такое исчезновение опасно.

#### `LEFT JOIN`: сохраняем левую population

```sql
SELECT
    o.order_id,
    u.plan
FROM orders AS o
LEFT JOIN users AS u
    ON o.user_id = u.user_id;
```

`O1010` останется, а `u.plan` будет `NULL`. Это делает проблему наблюдаемой. Но если
`U001` окажется в `users` дважды, все его заказы повторятся дважды.

#### `SEMI JOIN`: оставить строки, для которых существует пара

```sql
SELECT o.order_id
FROM orders AS o
SEMI JOIN users AS u
    ON o.user_id = u.user_id;
```

`SEMI JOIN` возвращает только столбцы и строки левой стороны. Даже если справа несколько
совпадений, левая строка возвращается один раз. Он полезен для вопроса:

> Какие заказы ссылаются на существующего пользователя?

#### `ANTI JOIN`: оставить строки, для которых пары нет

```sql
SELECT
    o.order_id,
    o.user_id
FROM orders AS o
ANTI JOIN users AS u
    ON o.user_id = u.user_id
WHERE o.user_id IS NOT NULL;
```

Это прямой аудит orphan-ссылок. Условие `WHERE o.user_id IS NOT NULL` отделяет orphan
от отсутствующей ссылки:

- `user_id IS NULL` — ссылка не заполнена;
- непустой `user_id`, которого нет в `users` — orphan reference.

`RIGHT JOIN` симметричен `LEFT JOIN`: обычно запрос проще прочитать, если поменять стороны
местами. `FULL OUTER JOIN` полезен для двусторонней сверки, но в основной практике этого
урока достаточно двух `ANTI JOIN` — слева направо и справа налево.

### Как ведёт себя `NULL` в ключе

Из `04/03` известно:

```sql
NULL = NULL
```

возвращает `UNKNOWN`, а не `TRUE`. Значит, при обычном условии:

```sql
ON left.key = right.key
```

две строки с `NULL` не совпадут.

Не надо автоматически заменять это на:

```sql
ON left.key IS NOT DISTINCT FROM right.key
```

Такое условие считает два `NULL` совпавшими, но отсутствующие идентификаторы обычно не
означают одну и ту же сущность. Используйте его только при явном бизнес-правиле, которое
действительно приравнивает отсутствующие значения.

## Соберите это

### Шаг 1. Запишите план соединения

До SQL заполните маленькую таблицу:

| Поле решения | `orders` + позиции | `orders` + пользователи |
|---|---|---|
| Левая population | все заказы | все заказы |
| Grain слева | `order_id` | `order_id` |
| Grain справа до подготовки | `(order_id, product_id)` | `user_id` |
| Ключ соединения | `order_id` | `user_id` |
| Допустимые совпадения справа | много до агрегации, не более одного после | не более одного |
| Политика без пары | заказ сохранить | заказ сохранить и пометить |
| Целевой grain | `order_id` | `order_id` |

Здесь видно, что прямое соединение с позициями несовместимо с целевым grain. Его нужно
подготовить.

### Шаг 2. Предскажите число строк вручную

В `orders` каждый `order_id` встречается один раз. В `order_items`:

- `O1001` встречается два раза;
- `O1005` встречается два раза;
- остальные десять заказов — по одному разу.

Для прямого `INNER JOIN`:

```text
1 × 2
+ 1 × 2
+ 10 × 1
= 14 строк
```

Это ожидаемый результат, а не проверка после факта. Если SQL вернёт другое число,
предположение о данных неверно или изменилось покрытие ключей.

### Шаг 3. Верните позиции к grain заказа

Из `04/04` уже известен `GROUP BY`:

```sql
SELECT
    order_id,
    count(*) AS item_rows,
    count(quantity * unit_price) AS known_item_amount_rows,
    sum(quantity * unit_price) AS item_total,
    count(*) = count(quantity * unit_price) AS item_amount_complete
FROM order_items
GROUP BY order_id
ORDER BY order_id;
```

Результат называется `item_totals` и имеет одну строку на `order_id`.

Контрольные строки:

```text
order_id  item_rows  known rows  item_total  complete
O1001     2          2           1200.00     true
O1005     2          2           1500.00     true
```

`known_item_amount_rows` сохраняет знаменатель суммы. Если у позиции неизвестны
`quantity` или `unit_price`, выражение `quantity * unit_price` станет `NULL`, а `SUM`
пропустит его. Числовой `item_total` тогда является только суммой известных частей.
Признак `item_amount_complete` не позволяет назвать такую частичную сумму полной.

Важно: предварительная агрегация не является универсальным рецептом. Она правильна
сейчас, потому что итоговая витрина должна иметь grain заказа и нам нужны именно число
позиций и их сумма. Если аналитический вопрос требует категорию каждой позиции,
агрегировать её без отдельного правила нельзя.

### Шаг 4. Опишите состояния до запроса

Одного булева `matched = true/false` недостаточно. Для пользователя нужны три состояния:

| Состояние | Смысл |
|---|---|
| `matched` | ссылка заполнена и пользователь найден |
| `missing_reference` | `orders.user_id IS NULL` |
| `orphan_reference` | ссылка заполнена, но пользователя нет |

Для сверки суммы нужны отдельные состояния:

| Состояние | Смысл |
|---|---|
| `matches` | обе суммы известны и равны |
| `differs` | обе суммы известны, но различаются |
| `order_amount_missing` | сумма заказа неизвестна |
| `item_total_missing` | позиции заказа не найдены |
| `item_total_incomplete` | позиции есть, но сумма хотя бы одной позиции неизвестна |
| `both_missing` | неизвестны обе стороны |

Так `NULL` не исчезает из проверки и не превращается автоматически в «расхождений нет».

## Используйте это

### 1. Выполните предварительную агрегацию

Запрос находится в:

```text
outputs/item_totals.sql
```

Учебный runner предоставляет его результат следующему запросу как relation
`item_totals`. Техническое связывание двух запросов не является результатом урока.
Именованные CTE и композицию шагов вы построите в `04/06`.

### 2. Соберите витрину на grain заказа

Основной артефакт:

```sql
SELECT
    o.order_id,
    o.user_id,
    o.status,
    o.currency,
    o.amount,
    i.item_rows,
    i.known_item_amount_rows,
    i.item_total,
    i.item_amount_complete,
    CASE
        WHEN i.order_id IS NULL THEN 'no_items'
        ELSE 'matched'
    END AS item_match_state,
    CASE
        WHEN o.user_id IS NULL THEN 'missing_reference'
        WHEN u.user_id IS NULL THEN 'orphan_reference'
        ELSE 'matched'
    END AS user_match_state,
    CASE
        WHEN i.order_id IS NULL AND o.amount IS NULL THEN 'both_missing'
        WHEN i.order_id IS NULL THEN 'item_total_missing'
        WHEN NOT i.item_amount_complete THEN 'item_total_incomplete'
        WHEN o.amount IS NULL THEN 'order_amount_missing'
        WHEN o.amount = i.item_total THEN 'matches'
        ELSE 'differs'
    END AS amount_reconciliation_state
FROM orders AS o
LEFT JOIN item_totals AS i
    ON o.order_id = i.order_id
LEFT JOIN users AS u
    ON o.user_id = u.user_id
ORDER BY o.order_id;
```

Почему здесь нет `SELECT *`:

- одинаковые имена перестают быть неоднозначными;
- схема результата не меняется при добавлении столбца в источник;
- видно, какие значения относятся к заказу, позициям и пользователю;
- тип и смысл каждого выходного поля можно проверить.

### 3. Прочитайте результат как evidence

Несколько показательных строк:

| order_id | amount | item rows | known rows | item total | complete | user state | amount state |
|---|---:|---:|---:|---:|---|---|---|
| O1001 | 1200.00 | 2 | 2 | 1200.00 | true | matched | matches |
| O1004 | NULL | 1 | 1 | 50.00 | true | matched | order_amount_missing |
| O1008 | NULL | 1 | 1 | 80.00 | true | matched | order_amount_missing |
| O1010 | 60.00 | 1 | 1 | 60.00 | true | orphan_reference | matches |

`O1004` и `O1008` не являются расхождениями известных сумм, но их нельзя объявить
совпавшими. Состояние `order_amount_missing` сохраняет эту разницу.

Если числовой `item_total` случайно совпадёт с `orders.amount`, но одна из позиций не
вошла в сумму из-за `NULL`, состояние всё равно будет `item_total_incomplete`, а не
`matches`.

### 4. Проверьте unmatched-ключи в обе стороны

Заказы без позиций:

```sql
SELECT o.order_id
FROM orders AS o
ANTI JOIN order_items AS i
    ON o.order_id = i.order_id;
```

Позиции без заказа:

```sql
SELECT
    i.order_id,
    i.product_id
FROM order_items AS i
ANTI JOIN orders AS o
    ON i.order_id = o.order_id;
```

Нулевая первая проверка не доказывает нулевую вторую. Покрытие связи нужно смотреть в
обоих направлениях, если обе стороны должны быть согласованы.

## Сломайте это

### Поломка 1. Сумма после прямого JOIN

```sql
SELECT
    o.currency,
    sum(o.amount) FILTER (WHERE o.status = 'paid') AS paid_amount
FROM orders AS o
INNER JOIN order_items AS i
    ON o.order_id = i.order_id
GROUP BY o.currency;
```

Запрос синтаксически корректен, но RUB завышен с `2700.00` до `5400.00`. Проверка
одного общего денежного числа скрыла бы ещё одну ошибку — смешение валют.

### Поломка 2. Дубликат в `users`

Пусть `U001` появился в справочнике дважды. У него два заказа: `O1001` и `O1005`.
Обычный `LEFT JOIN` создаст по две строки для каждого из них. Число строк вырастет с 12
до 14.

Поэтому до many-to-one JOIN проверяется правый ключ:

```sql
SELECT
    user_id,
    count(*) AS rows_per_key
FROM users
GROUP BY user_id
HAVING count(*) > 1;
```

Ожидаемый результат — ноль строк.

### Поломка 3. `INNER JOIN` скрывает плохую ссылку

Если соединить `orders` с `users` через `INNER JOIN`, заказ `O1010` исчезнет. Итог станет
аккуратнее, но ошибка качества данных пропадёт из наблюдения.

Сначала определите политику:

- сохранить и пометить;
- исключить с измеримым числом исключений;
- остановить расчёт.

Молчаливое исчезновение политикой не является.

### Поломка 4. `DISTINCT amount`

Иногда fanout пытаются исправить так:

```sql
sum(DISTINCT o.amount)
```

Это неверно. Два разных заказа могут иметь одинаковую сумму:

```text
O1  100.00
O2  100.00
```

Правильная сумма равна `200.00`, а `sum(DISTINCT amount)` вернёт `100.00`. Исправлять
нужно grain входа в агрегацию, а не совпадение числовых значений.

### Поломка 5. Неполный составной ключ

Если grain таблицы цен равен `(order_id, product_id)`, условие только по `order_id`
соединит позицию с ценами всех позиций того же заказа:

```sql
-- Недостаточно
ON l.order_id = p.order_id
```

Нужно:

```sql
ON l.order_id = p.order_id
AND l.product_id = p.product_id
```

Ключ соединения выбирается из смысла сущности, а не из первого похожего имени.

### Поломка 6. `NULL` приняли за совпавший ключ

Две отсутствующие ссылки не доказывают, что строки относятся к одной сущности. При
обычном `=` они не совпадут. Не заменяйте эту семантику на null-safe equality без
явного предметного правила.

## Проверьте это

### До JOIN

Для каждой стороны проверьте:

1. заявленный grain действительно уникален;
2. обязательные части ключа не содержат `NULL` и пустых строк;
3. типы ключей совместимы;
4. правый ключ уникален, если ожидается не более одного совпадения;
5. частоты ключа объясняют ожидаемое число строк;
6. известно, что делать с unmatched-ключами.

### После JOIN

Для витрины на grain заказа проверьте:

1. число строк равно числу заказов;
2. `count(*) = count(DISTINCT order_id)`;
3. набор `order_id` до и после совпадает;
4. orphan и missing references посчитаны отдельно;
5. заказы без позиций и позиции без заказов проверены отдельно;
6. денежные суммы сверены по валютам;
7. неизвестные и частичные суммы не названы совпавшими;
8. денежные значения сохранили точный `DECIMAL`.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Join key | Любые одноимённые столбцы | Полный набор полей, по которым предметно сопоставляются строки |
| Cardinality | Общее число строк таблицы | Допустимое число соответствий между строками сторон |
| Fanout | Любое увеличение числа строк | Повторение левой или правой строки из-за нескольких совпадений |
| Target grain | Grain автоматически выбирает JOIN | Единица строки, которую аналитик хочет получить |
| Coverage | Уникальность ключа | Наличие хотя бы одной пары для нужных ключей |
| Unmatched key | Строка, которую надо удалить | Ключ без пары, для которого требуется явная политика |
| Orphan reference | Любой `NULL` в foreign key | Заполненная ссылка на отсутствующую родительскую строку |
| Pre-aggregation | Способ ускорить запрос | Приведение дочерних данных к grain, совместимому с результатом |
| Semi join | INNER JOIN без выбранных столбцов справа | Фильтрация левой стороны по существованию хотя бы одной пары без fanout |
| Anti join | `NOT IN` для любого случая | Строки левой стороны без пары справа, с явной семантикой JOIN |
