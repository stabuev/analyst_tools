# Оконные агрегаты и рамки: накопительные и скользящие расчёты

> Раздел отвечает, какие строки относятся к одной задаче; порядок — где находится
> текущая строка; рамка — какие строки относительно неё прямо сейчас входят в агрегат.

**Тип:** Build
**Треки:** Core
**Пререквизиты:** 04/07
**Время:** ~120 минут
**Результат:** сохраняет grain заказов, строит общий, накопительный и скользящий агрегаты
с явной рамкой, контролирует включение текущей строки и `NULL`-знаменатель и объясняет
различие `ROWS`, `RANGE` и рамки по умолчанию.

## Цели обучения

После урока вы сможете:

- превратить знакомые `SUM`, `AVG` и `COUNT` в оконные агрегаты, не сворачивая строки;
- отдельно сформулировать partition, order и frame для рабочего вопроса;
- отличить итог всей partition от накопительного итога до текущей строки;
- построить скользящий расчёт по последним N строкам через `ROWS`;
- явно решить, входит ли текущая строка в её собственный baseline;
- объяснить, почему рамка на начале или конце partition может содержать меньше N строк;
- публиковать размер frame и число известных значений рядом со средним;
- предсказать скачок неявной `RANGE`-рамки на строках-peers;
- выбрать между позиционной семантикой `ROWS` и диапазоном значений `RANGE`;
- проверить, что оконный расчёт сохранил grain, типы, единицы измерения и порядок.

### На что опирается урок

Это не второй независимый обзор оконных функций. Урок продолжает конкретные механизмы,
которые уже были построены:

| Что уже известно | Где пройдено | Как используется сейчас |
|---|---|---|
| grain описывает смысл одной строки | 03/01, 04/01 | до и после окна остаётся одна строка на оплаченный `order_id` |
| `NULL` не равен нулю или пустой строке | 04/03 | неизвестная сумма не подменяется нулём внутри rolling average |
| `COUNT(*)` и `COUNT(amount)` имеют разные знаменатели | 04/04 | различаем размер frame и число известных сумм |
| `SUM` и `AVG` пропускают `NULL`-аргументы | 04/04 | рядом с агрегатом публикуем число известных значений |
| суммы разных валют нельзя складывать вместе | 04/04, 04/05 | денежные окна разделяются по `currency` |
| CTE — именованный этап со своим population и grain | 04/06 | сначала выбираем оплаченные заказы, затем добавляем оконные столбцы |
| окно сохраняет строки, а `PARTITION BY` задаёт независимые разделы | 04/07 | агрегаты добавляются к заказам без `GROUP BY` |
| оконный `ORDER BY` задаёт положение, но не порядок выдачи | 04/07 | расчёт и опубликованная сортировка проверяются отдельно |
| peers равны по всем ключам оконного порядка | 04/07 | объясняем, почему `RANGE` может включить несколько строк одновременно |
| tie-breaker делает позиционную последовательность однозначной | 04/07 | `ROWS` использует порядок `ordered_at, order_id` |

`ordered_at` снова приходит в артефакт уже типизированным как `TIMESTAMPTZ`. Мы используем
его только как сравнимый ключ порядка. Разбор строк, выбор бизнес-timezone и календарные
дни начнутся в следующем уроке. Поэтому здесь нет временных рамок вроде
`RANGE BETWEEN INTERVAL 7 DAYS PRECEDING ...`: сначала нужно понять frame без второй
одновременно новой темы.

## Проблема

Таблица `orders` имеет grain:

```text
одна строка = один order_id
```

Для каждой оплаченной покупки нужно сохранить сам заказ и добавить:

1. общую известную сумму оплаченных заказов в той же валюте;
2. накопительную известную сумму к моменту текущего заказа;
3. среднюю известную сумму текущего и двух предыдущих заказов в валюте;
4. среднюю сумму трёх **предыдущих** заказов, не включая текущий;
5. количество строк и известных сумм в каждом скользящем расчёте.

Здесь независимый поток задаёт `PARTITION BY currency`. Поэтому «предыдущие заказы» —
это предыдущие оплаченные заказы **всего магазина в той же валюте**, независимо от
покупателя. `user_id` остаётся в результате для идентификации заказа, но не входит в
partition. Такой расчёт описывает недавний уровень заказов магазина, а не личную историю
пользователя.

Для вопроса о предыдущих покупках конкретного человека понадобился бы другой контракт,
например `PARTITION BY user_id, currency`, и достаточная история каждого пользователя.
Менять partition незаметно нельзя: вместе с ним меняется смысл метрики.

Эти вопросы похожи, но используют разные множества строк:

```text
вся currency partition
начало partition ... текущая строка
две предыдущие строки ... текущая строка
три предыдущие строки ... одна предыдущая строка
```

### Почему `GROUP BY` недостаточно

Так можно получить итог по валюте:

```sql
SELECT
    currency,
    sum(amount) AS total_known_amount
FROM orders
WHERE status = 'paid'
GROUP BY currency;
```

Но grain изменится:

```text
до:    одна строка на order_id
после: одна строка на currency
```

У результата больше нет `order_id`, времени и текущей суммы. Такой итог полезен как
отдельная витрина, но не позволяет показать, каким был накопительный результат на каждой
строке.

Оконный агрегат использует знакомую функцию, но добавляет `OVER`:

```sql
sum(amount) OVER (
    PARTITION BY currency
) AS currency_total_known_amount
```

Теперь итог валюты повторяется рядом с каждой строкой этой валюты. Заказы не
сворачиваются.

### Почему одного partition и order уже недостаточно

Из предыдущего урока знакомо окно:

```sql
PARTITION BY currency
ORDER BY ordered_at, order_id
```

Оно отвечает:

- какие строки не смешиваются между собой;
- какая строка первая, вторая и следующая.

Но оно ещё не отвечает, что должен увидеть `AVG`:

- всю валютную partition;
- всё от начала до текущего заказа;
- только последние три заказа;
- только три заказа перед текущим;
- текущую строку и одну следующую;
- строки в определённом диапазоне значений времени или другого ключа.

Эту третью часть контракта задаёт **window frame — рамка окна**.

### Правдоподобные ошибки

Ошибки frame опасны тем, что SQL выполняется и возвращает аккуратные числа:

- накопительная сумма без явной рамки скачком включает все строки с одинаковым ключом;
- «последние три заказа» на первой строке фактически содержат одну строку, но публикуются
  как полноценное трёхстрочное окно;
- `AVG(amount)` по трём строкам получает знаменатель два из-за одного `NULL`, а название
  говорит «среднее трёх заказов»;
- baseline «предыдущие три заказа» включает текущий заказ и становится зависимым от
  значения, с которым его сравнивают;
- без `PARTITION BY currency` складываются рубли, доллары, евро и тенге;
- `last_value(order_id)` считается последней строкой пользователя, хотя функция видит
  только frame до текущей строки;
- `ROWS` и `RANGE` используются как взаимозаменяемые варианты синтаксиса, хотя отвечают
  на разные вопросы.

Поэтому в этом уроке рамка является частью бизнес-контракта, а не необязательной
настройкой функции.

## Концепция

### 1. Обычный агрегат и оконный агрегат используют одну функцию по-разному

Сравните две формы:

```sql
-- Новый grain: одна строка на currency
SELECT
    currency,
    sum(amount)
FROM paid_orders
GROUP BY currency;
```

```sql
-- Исходный grain: одна строка на order_id
SELECT
    order_id,
    currency,
    amount,
    sum(amount) OVER (
        PARTITION BY currency
    ) AS currency_total_known_amount
FROM paid_orders;
```

Во втором запросе `SUM` не стал другой арифметической функцией. Изменился контекст:

```text
GROUP BY:
несколько строк -> одна строка результата

SUM(...) OVER (...):
для каждой текущей строки определить контекст
-> посчитать агрегат по этому контексту
-> записать значение к текущей строке
```

Поэтому оконные `SUM`, `AVG`, `COUNT`, `MIN` и `MAX` сохраняют строки, если другие части
запроса не меняют их. Но они не исправляют grain входа: если предыдущий `JOIN` уже
размножил заказ по товарным позициям, окно честно агрегирует размноженные строки.

### 2. У оконного агрегата три независимых вопроса

Полный контракт удобно читать сверху вниз:

```sql
avg(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

| Часть | Вопрос | Ответ примера |
|---|---|---|
| `PARTITION BY` | какие строки относятся к независимым задачам? | заказы одной валюты |
| `ORDER BY` | где находится текущая строка? | хронология с tie-breaker `order_id` |
| `ROWS BETWEEN ...` | какие позиции около текущей участвуют? | текущая и две предыдущие |

Короткая модель:

```text
partition = весь отдельный коридор
order     = координата строки в коридоре
frame     = подвижный участок коридора для текущего расчёта
```

Partition обычно одна для многих строк. Frame пересчитывается для каждой текущей строки.

### 3. Frame движется вместе с текущей строкой

Пусть внутри одной currency строки уже упорядочены:

```text
A -> B -> C -> D -> E
```

Для:

```sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

рамки будут:

```text
current=A: [A]
current=B: [A, B]
current=C: [A, B, C]
current=D: [B, C, D]
current=E: [C, D, E]
```

Это не один общий набор из трёх строк. Для каждой текущей строки окно сдвигается.

На границе partition рамка **обрезается**. SQL не создаёт две вымышленные строки перед
`A`. Поэтому первые строки имеют неполную историю:

| Текущая строка | Запрошенный размер | Реальный размер |
|---|---:|---:|
| A | 3 | 1 |
| B | 3 | 2 |
| C | 3 | 3 |

Если полнота истории важна для сравнения, её нужно проверить явно:

```sql
count(*) OVER recent_3_rows AS recent_3_order_rows
```

### 4. Границы frame читаются относительно текущей строки

Основные обозначения:

| Граница | Обычный смысл |
|---|---|
| `UNBOUNDED PRECEDING` | самое начало partition |
| `3 PRECEDING` | позиция или значение на расстоянии три назад |
| `1 PRECEDING` | непосредственно предыдущая позиция или диапазон |
| `CURRENT ROW` | текущая позиция; для `RANGE` также её peers |
| `1 FOLLOWING` | следующая позиция или диапазон |
| `UNBOUNDED FOLLOWING` | самый конец partition |

Frame задаётся началом и концом:

```sql
ROWS BETWEEN <начало> AND <конец>
```

Начало не может находиться после конца. Например, конструкция от `1 FOLLOWING` до
`CURRENT ROW` противоречива.

### 5. Четыре полезных контракта не являются синонимами

#### Итог всей partition

```sql
sum(amount) OVER (
    PARTITION BY currency
)
```

При отсутствии оконного `ORDER BY` default frame охватывает всю partition. Все строки
одной валюты получают один и тот же итог.

#### Накопительный итог

```sql
sum(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Каждая строка видит всё от начала валютной последовательности до себя.

#### Текущая и две предыдущие строки

```sql
avg(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

Текущий `amount` входит в своё скользящее среднее.

#### Только три предыдущие строки

```sql
avg(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
)
```

Текущая строка исключена. В нашем контракте такой frame сравнивает покупку с недавним
потоком заказов магазина в той же валюте. Иначе baseline уже содержит проверяемое
значение. Это не baseline личного поведения покупателя: для него нужна partition по
`user_id`.

### 6. `ROWS` считает позиции

`ROWS` выбирает физические позиции в логическом оконном порядке:

```sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

означает:

```text
не более двух предыдущих строк + текущая строка
```

Это **не** означает:

- два предыдущих дня;
- значения ключа в пределах двух единиц;
- две предыдущие группы peers;
- обязательно три строки на границе partition.

Позиционная рамка требует однозначного порядка. Поэтому основной артефакт использует:

```sql
ORDER BY ordered_at, order_id
```

`ordered_at` задаёт бизнес-хронологию, а уникальный `order_id` разрешает одинаковые
timestamps. Без tie-breaker непонятно, какая из равных строк является «предыдущей
позицией».

### 7. `RANGE` выбирает диапазон значений порядка

Для маленького числового примера:

```sql
ORDER BY sort_key
RANGE BETWEEN 1 PRECEDING AND CURRENT ROW
```

строка с `sort_key = 4` видит строки, у которых:

```text
sort_key находится от 3 до 4
```

Если в данных нет ключа 3, предыдущая физическая строка с ключом 2 не входит.

При тех же данных:

```sql
ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
```

возьмёт текущую строку с ключом 4 и физически предыдущую строку с ключом 2.

Следовательно:

```text
ROWS  -> расстояние в позициях
RANGE -> расстояние в значениях ORDER BY
```

Для `RANGE` с числовым или временным смещением DuckDB требует ровно одно выражение
порядка, поддерживающее вычитание. Несколько выражений допустимы, когда используются
только границы `UNBOUNDED PRECEDING`, `UNBOUNDED FOLLOWING` и `CURRENT ROW`. Поэтому в
эксперименте `RANGE` со смещением использует только `sort_key`; `row_id` нельзя добавить
как косметический tie-breaker — он изменил бы смысл peers и не соответствовал бы
контракту диапазона.

### 8. `CURRENT ROW` ведёт себя по-разному для `ROWS` и `RANGE`

Пусть есть:

| row_id | sort_key | amount |
|---|---:|---:|
| A | 1 | 10 |
| B | 1 | 20 |
| C | 2 | 5 |

`A` и `B` — peers по единственному ключу `sort_key`.

Для `ROWS ... CURRENT ROW` текущая строка означает одну конкретную позицию. Если порядок
дополнен `row_id`, накопительная сумма может быть:

```text
A -> 10
B -> 30
C -> 35
```

Для `RANGE ... CURRENT ROW` текущая граница включает всех peers:

```text
A -> 30
B -> 30
C -> 35
```

Оба результата корректны, но отвечают на разные вопросы:

- `ROWS`: итог после каждой отдельной, однозначно упорядоченной записи;
- `RANGE`: итог на уровне значения ключа, общий для равных ключей.

### 9. Default frame зависит от наличия `ORDER BY`

Это правило нельзя оставлять скрытым.

#### Без оконного `ORDER BY`

```sql
sum(amount) OVER (
    PARTITION BY currency
)
```

Default frame — вся partition.

#### С оконным `ORDER BY`

```sql
sum(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at
)
```

В DuckDB default frame соответствует:

```sql
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

Текущая граница включает peers. Поэтому две покупки с одинаковым `ordered_at` могут
войти в накопительный итог одновременно.

Если в `ORDER BY` добавить уникальный `order_id`, peers исчезнут и на текущих данных
default `RANGE` может дать те же числа, что явный `ROWS`. Но это совпадение результата не
делает контракты одинаковыми. Удаление tie-breaker или изменение бизнес-вопроса снова
проявит разницу.

Правило артефакта:

```text
если порядок влияет на агрегат, frame записывается явно
```

Так ревьюер видит не только число, но и намерение автора.

### 10. Размер frame и знаменатель агрегата — разные величины

Пусть frame содержит:

```text
1200, NULL, 1500
```

Тогда:

```text
COUNT(*)      = 3
COUNT(amount) = 2
SUM(amount)   = 2700
AVG(amount)   = 1350
```

Среднее не равно:

```text
2700 / 3 = 900
```

Потому что `AVG(amount)` пропускает неизвестный аргумент и использует:

```text
SUM известных amount / COUNT известных amount
```

Если опубликовать только `AVG`, читатель не знает:

- frame действительно содержал две строки;
- frame содержал три строки, но одна сумма неизвестна;
- frame был обрезан границей partition;
- все суммы в frame неизвестны.

Поэтому артефакт выпускает рядом:

```sql
count(*)     OVER recent_3_rows AS recent_3_order_rows,
count(amount) OVER recent_3_rows AS recent_3_known_amounts,
avg(amount)  OVER recent_3_rows AS recent_3_known_amount_avg
```

`COALESCE(amount, 0)` здесь не является техническим исправлением. Нулевая покупка и
неизвестная сумма имеют разный смысл.

#### Тип результата `AVG` нужно проверить отдельно

Входной `amount` имеет точный фиксированный тип `DECIMAL(18, 2)`. В DuckDB:

```text
SUM(amount) -> DECIMAL(38, 2)
AVG(amount) -> DOUBLE
```

Среднее содержит деление, а деление фиксированных десятичных чисел не всегда даёт
конечную десятичную дробь. Поэтому DuckDB возвращает приближённый floating-point
результат `DOUBLE`. Это не повод превращать исходный `amount` в `DOUBLE`: точный тип
по-прежнему нужен для хранения сумм и сложения денег.

Артефакт сохраняет вычислительное среднее без скрытого округления. Поэтому значение
`1625 / 3` равно примерно `541.67`, а не точно `541.67`. Если результат поставляется как
денежное число с двумя знаками, правило публикации нужно согласовать отдельно и записать
явно, например:

```sql
cast(
    round(avg(amount) OVER currency_recent_3_rows, 2)
    AS DECIMAL(18, 2)
) AS recent_3_known_amount_avg_rounded
```

Так ревьюер видит границу между расчётом среднего и его представлением в отчёте.

### 11. Накопительная сумма на `NULL` не доказывает нулевой вклад

Если текущий `amount` неизвестен, `SUM(amount)` пропустит его. Накопительный итог может
остаться равным предыдущему:

```text
до строки с NULL:    1200
на строке с NULL:    1200
```

Это не означает, что заказ добавил ноль. Значит только:

```text
сумма известных значений пока не изменилась
```

Поэтому рядом с running sum сохраняются:

```sql
count(*) OVER currency_running_rows AS currency_running_order_rows,
count(amount) OVER currency_running_rows AS currency_running_known_amounts
```

Разница этих счётчиков показывает, сколько строк не вошло в денежный итог из-за
неизвестного значения.

### 12. Именованное окно может включать frame

В предыдущем уроке одно имя связывало partition и order. Здесь имя фиксирует полный
контракт:

```sql
WINDOW currency_recent_3_rows AS (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

Затем несколько агрегатов используют ровно один набор строк:

```sql
count(*)      OVER currency_recent_3_rows,
count(amount) OVER currency_recent_3_rows,
avg(amount)   OVER currency_recent_3_rows
```

Это важно: если среднее и его знаменатель случайно используют разные frames, проверка
перестаёт описывать сам расчёт.

В артефакте четыре имени:

| Имя | Смысл |
|---|---|
| `currency_partition` | вся валюта без порядка |
| `currency_running_rows` | от начала валюты до текущего заказа |
| `currency_recent_3_rows` | текущий и два предыдущих заказа |
| `currency_prior_3_rows` | три заказа перед текущим, без текущего |

### Необязательное углубление: `last_value` возвращает последнюю строку frame

На однозначном порядке:

```sql
last_value(order_id) OVER (
    ORDER BY sort_key, row_id
)
```

default frame заканчивается на текущей строке. Поэтому для `A`, `B`, `C`, `D` функция
может вернуть:

```text
A, B, C, D
```

Чтобы увидеть последнюю строку всей partition, frame должен доходить до конца:

```sql
last_value(order_id) OVER (
    ORDER BY sort_key, row_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
)
```

Теперь каждая строка видит `D`.

Это не обязательный новый инструмент и не результат, который нужно запоминать после
урока. Пример можно разобрать после основной практики как дополнительное доказательство:
функции `first_value`, `last_value` и оконные агрегаты зависят не только от partition и
order, но и от frame.

### 13. Входной контракт остаётся обязательным

Основной SQL ожидает:

| Поле | Контракт |
|---|---|
| `order_id` | заполненный уникальный ключ |
| `status` | каноническое значение `cancelled`, `paid`, `pending` или `refunded` |
| `user_id` | заполнен для оплаченного заказа |
| `ordered_at` | заполненный `TIMESTAMPTZ` для оплаченного заказа |
| `currency` | заполнена для оплаченного заказа |
| `amount` | `DECIMAL(18, 2)`, может быть неизвестна |

Почему:

- дубликат `order_id` создаст лишнюю позицию в `ROWS`;
- пустое время не имеет честного места в хронологии;
- пустая валюта смешает несопоставимые суммы в диагностической `NULL`-partition;
- неканонический `status` незаметно изменит population;
- строковый `amount` не является готовой денежной мерой;
- исходный `DOUBLE` вместо `DECIMAL` может изменить точность денежных сумм;
- выходной `AVG(DECIMAL)` отдельно требует осознанной политики округления.

Артефакт не загружает и не чистит данные. Эти обязанности остаются у внешнего слоя.

### Что сознательно остаётся за границей

В обязательный результат не входят:

- `GROUPS` frames — расстояние в группах peers;
- `EXCLUDE CURRENT ROW`, `EXCLUDE GROUP` и другие варианты исключения;
- `DISTINCT` и `FILTER` внутри оконных агрегатов;
- `nth_value`, percentile- и distribution-функции;
- временные `RANGE` с `INTERVAL`;
- centered rolling windows;
- sessionization;
- оптимизация и стоимость оконного оператора;
- rolling features для прогнозирования и защита от temporal leakage.

После текущего урока эти темы можно понять, но они не нужны для минимальной уверенной
работы аналитика с накопительными и скользящими SQL-расчётами. Календарные интервалы
появятся после времени в SQL, а leakage-free rolling features — в фазе временных рядов.

## Соберите это

Сначала рассчитаем два маленьких результата вручную. Первый показывает движение frame,
второй связывает механизм с заказами.

### Шаг 1. Постройте frame experiment

Даны четыре строки:

| row_id | sort_key | amount |
|---|---:|---:|
| A | 1 | 10 |
| B | 1 | 20 |
| C | 2 | 5 |
| D | 4 | 40 |

У данных есть две особенности:

- `A` и `B` — peers по `sort_key`;
- между ключами 2 и 4 есть разрыв.

Они нужны не для сложности, а чтобы `ROWS` и `RANGE` перестали случайно давать один
ответ.

### Шаг 2. Накопите сумму по позициям

Для однозначного порядка:

```text
sort_key, row_id
```

и frame:

```sql
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

получаем:

| current | Строки frame | Сумма |
|---|---|---:|
| A | A | 10 |
| B | A, B | 30 |
| C | A, B, C | 35 |
| D | A, B, C, D | 75 |

### Шаг 3. Накопите сумму по диапазону

Для:

```sql
ORDER BY sort_key
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

получаем:

| current | Значения sort_key | Строки frame | Сумма |
|---|---|---|---:|
| A | до 1 включительно | A, B | 30 |
| B | до 1 включительно | A, B | 30 |
| C | до 2 включительно | A, B, C | 35 |
| D | до 4 включительно | A, B, C, D | 75 |

Первая строка сразу получает 30, потому что `CURRENT ROW` для `RANGE` включает peer
`B`.

### Шаг 4. Сравните расстояние 1

Теперь два контракта:

```sql
ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
```

```sql
RANGE BETWEEN 1 PRECEDING AND CURRENT ROW
```

Ручной oracle:

| row_id | `ROWS` сумма | `RANGE` сумма | Почему различаются |
|---|---:|---:|---|
| A | 10 | 30 | `RANGE` включает peer B |
| B | 30 | 30 | обе строки с ключом 1 входят |
| C | 25 | 35 | `ROWS` берёт B и C, `RANGE` — все ключи 1 и 2 |
| D | 45 | 40 | `ROWS` берёт C и D, в диапазоне ключей 3..4 есть только D |

Если эта таблица понятна до запуска SQL, различие механизмов уже не сводится к
запоминанию синтаксиса.

### Шаг 5. Постройте oracle для заказов EUR

В оплаченной EUR-partition:

| order_id | ordered_at | amount |
|---|---|---:|
| O1006 | 2026-02-20 | 25 |
| O1009 | 2026-03-07 | 900 |
| O1012 | 2026-04-05 | 700 |

Общая известная сумма:

```text
25 + 900 + 700 = 1625
```

Ручной результат:

| order_id | total | running | recent rows | recent avg | prior rows | prior avg |
|---|---:|---:|---:|---:|---:|---:|
| O1006 | 1625 | 25 | 1 | 25 | 0 | `NULL` |
| O1009 | 1625 | 925 | 2 | 462.5 | 1 | 25 |
| O1012 | 1625 | 1625 | 3 | ≈ 541.67 | 2 | 462.5 |

Проверьте смысл:

- `total` одинаков на всех строках partition;
- `running` растёт вместе с текущей позицией;
- `recent` включает текущую строку;
- `prior` заканчивается на предыдущей строке;
- первые frames меньше трёх строк;
- отсутствие предыдущих строк даёт `COUNT(*) = 0` и `AVG = NULL`.

### Шаг 6. Зафиксируйте четыре оконных контракта

До запуска заполните:

| Выход | Partition | Order | Frame |
|---|---|---|---|
| общий итог | `currency` | нет | вся partition |
| накопительный итог | `currency` | `ordered_at, order_id` | от начала до текущей |
| среднее текущего и двух предыдущих | `currency` | `ordered_at, order_id` | две предыдущие и текущая |
| среднее трёх предыдущих | `currency` | `ordered_at, order_id` | три предыдущие до одной предыдущей |

Population и grain:


### Этап 2. Получить итог всей partition

```sql
sum(amount) OVER currency_partition AS currency_total_known_amount
```

Именованное окно:

```sql
currency_partition AS (
    PARTITION BY currency
)
```

Оконного порядка нет, потому что итог всей валюты не должен зависеть от позиции заказа.
Здесь «валюта» означает общий поток заказов магазина: строки разных пользователей входят
в одну последовательность, если `currency` совпадает.

### Этап 3. Получить накопительный итог

```sql
sum(amount) OVER currency_running_rows AS currency_running_known_amount,
count(*) OVER currency_running_rows AS currency_running_order_rows,
count(amount) OVER currency_running_rows AS currency_running_known_amounts
```

Окно:

```sql
currency_running_rows AS (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Три столбца вместе отвечают:

- сколько строк прошло;
- для скольких была известна сумма;
- чему равна сумма известных значений.

### Этап 4. Получить rolling-3 с текущей строкой

```sql
count(*) OVER currency_recent_3_rows AS recent_3_order_rows,
count(amount) OVER currency_recent_3_rows AS recent_3_known_amounts,
avg(amount) OVER currency_recent_3_rows AS recent_3_known_amount_avg
```

```sql
currency_recent_3_rows AS (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

Название говорит именно «последние три заказа», а не «последние три дня».

### Этап 5. Получить prior-3 без текущей строки

```sql
count(*) OVER currency_prior_3_rows AS prior_3_order_rows,
count(amount) OVER currency_prior_3_rows AS prior_3_known_amounts,
avg(amount) OVER currency_prior_3_rows AS prior_3_known_amount_avg
```

```sql
currency_prior_3_rows AS (
    PARTITION BY currency
    ORDER BY ordered_at, order_id
    ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
)
```

Это baseline для сравнения текущей покупки с предыдущими заказами магазина в той же
валюте. Он не описывает историю конкретного пользователя. На первой строке partition
frame пуст, поэтому оба счётчика равны 0, а среднее — `NULL`.

### Этап 6. Опубликовать детерминированный результат

```sql
ORDER BY currency, ordered_at, order_id
```

Финальный порядок не меняет frames. Он только позволяет читателю увидеть валютные
последовательности в том же удобном порядке.

## Сломайте это

### Ошибка 1. Заменить окно на `GROUP BY`

Итог по валюте станет корректным, но `order_id` исчезнет. Это другая витрина с другим
grain.

Проверка:

```text
число оплаченных строк до окна = число строк после окна
order_id остаётся уникальным
```

### Ошибка 2. Положиться на default frame

Хрупкая форма:

```sql
sum(amount) OVER (
    PARTITION BY currency
    ORDER BY ordered_at
)
```

На уникальных timestamps она может выглядеть как обычный running sum. После добавления
двух peer-строк один timestamp получит общий скачок.

Исправление: сначала решить, нужен `ROWS` или `RANGE`, затем записать frame явно.

### Ошибка 3. Убрать partition по валюте

```sql
sum(amount) OVER (
    ORDER BY ordered_at, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

Такой запрос складывает числа с разными единицами. Результат не становится осмысленным
только потому, что тип всех сумм — `DECIMAL`.

Исправление текущей задачи:

```sql
PARTITION BY currency
```

### Ошибка 4. Использовать `ROWS` без полного порядка

```sql
ORDER BY ordered_at
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

При двух заказах в один момент неизвестно, какая строка является предыдущей позицией.
Разные планы могут менять rolling average.

Исправление:

```sql
ORDER BY ordered_at, order_id
```

Это детерминированная договорённость, но не доказательство истинной очередности
одновременных событий.

### Ошибка 5. Считать `ROWS 7 PRECEDING` семью днями

`ROWS` считает строки. Если в один день было 100 заказов, семь позиций могут покрыть
несколько минут. Если заказов не было неделю, соседние строки могут быть разделены
десятью днями.

Для календарного вопроса нужна временная модель и `RANGE` с интервалом либо предварительно
построенный полный календарный ряд. Это будет осмысленно после урока о датах.

### Ошибка 6. Считать начальную рамку полной

На первой строке:

```sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

содержит одну строку, а не три.

Исправление: публиковать `COUNT(*) OVER same_frame` и вводить политику полноты там, где
она влияет на сравнение.

### Ошибка 7. Назвать `AVG(amount)` средним всех строк frame

При одном `NULL`:

```text
frame rows   = 3
known values = 2
AVG denominator = 2
```

Исправление: выпускать `COUNT(*)`, `COUNT(amount)` и `AVG(amount)` из одного именованного
окна.

### Ошибка 8. Подменить неизвестную сумму нулём

```sql
avg(coalesce(amount, 0)) OVER (...)
```

Так среднее отвечает на новую задачу, где отсутствие измерения объявлено реальным нулём.
Это допустимо только при отдельном бизнес-правиле, а не как автоматическая очистка.

### Ошибка 9. Включить текущую строку в prior baseline

Если текущий заказ сравнивается с:

```sql
ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
```

его собственная сумма уже влияет на baseline.

Для трёх предыдущих заказов:

```sql
ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
```

Эта граница особенно важна позже для аномалий, прогнозов и признаков моделей.

### Необязательный пример. Принять `last_value` за конец partition

Default frame с `ORDER BY` обычно заканчивается на текущей строке или её peers.
`last_value` возвращает конец именно этого frame.

Проверка: сравнить default-вариант с явным:

```sql
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
```

### Ошибка 10. Запустить окно после fanout

Если заказ размножен по позициям, `ROWS 2 PRECEDING` считает позиции товара, а не три
заказа.

Перед окном:

- назовите grain;
- проверьте уникальность `order_id`;
- при необходимости сначала агрегируйте позиции до заказа;
- затем применяйте оконный расчёт.

### Ошибка 11. Спрятать пустое время через `NULLS LAST`

Заказ без `ordered_at` не имеет честной позиции в хронологии. `NULLS LAST` технически
разместит его, но не объяснит, когда он произошёл и какие rows должны попасть в frame.

Текущий входной контракт отклоняет оплаченный заказ без времени.

### Позитивные инварианты

- девять оплаченных заказов остаются девятью уникальными `order_id`;

### Негативные fixtures

- дубликат `order_id` блокируется до оконного расчёта;

4. Для `A, B, C, D` предскажите обе рамки расстояния 1.
5. Объясните, почему `COUNT(*) = 3`, а `COUNT(amount) = 2`.

Необязательное углубление: объясните, почему `last_value` зависит от конца frame.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Оконный агрегат | агрегат, который возвращает одну строку | агрегат, вычисленный в контексте каждой строки и сохраняющий её в результате |
| Partition | текущий frame | весь независимый раздел строк, внутри которого движется frame |
| Frame | вся partition | подмножество partition относительно текущей строки |
| Текущая строка | последняя строка файла | строка, для которой сейчас вычисляется оконное значение |
| `UNBOUNDED PRECEDING` | бесконечное число пустых строк | начало текущей partition |
| `UNBOUNDED FOLLOWING` | конец всей таблицы | конец текущей partition |
| `ROWS` | диапазон дней или значений | расстояние в позициях оконного порядка |
| `RANGE` | другое написание `ROWS` | диапазон значений выражения оконного порядка с включением peers |
| Default frame | всегда вся partition | вся partition без `ORDER BY`, но range-like frame до текущей peer group при наличии `ORDER BY` |
| Partial frame | ошибка данных | рамка, обрезанная границей partition и потому содержащая меньше запрошенных позиций |
| Frame size | знаменатель любого агрегата | число строк frame; агрегат по nullable-выражению может использовать меньше значений |
| `AVG(DECIMAL)` в DuckDB | обязательно остаётся `DECIMAL` | возвращает `DOUBLE`; округление поставляемого результата задаётся отдельно |
| Prior-only frame | frame с текущей строкой | контекст, конечная граница которого находится до текущей строки |
| Running total | итог partition | накопительный агрегат от начала до текущей границы |
| Rolling aggregate | обязательно календарная метрика | агрегат по движущемуся frame; его единицей могут быть строки, значения или время |
| `last_value` | последняя строка partition | значение последней строки текущего frame |

## Дополнительное чтение

- [DuckDB: Window Functions](https://duckdb.org/docs/current/sql/functions/window_functions) — начните с разделов `Evaluation`, `Framing` и `Aggregate Window Functions`: сверьте default frame, поведение `CURRENT ROW`, обрезание рамки у границ partition и ограничение одного выражения порядка для `RANGE` со смещением.
- [Антон Жиянов: «Оконные функции SQL»](https://antonz.ru/window-functions/) — пройдите русскоязычные главы «Скользящие агрегаты», «Фрейм», «Фрейм по умолчанию» и блоки `ROWS`/`RANGE`; интерактивные примеры полезны, чтобы ещё раз увидеть движение рамки, а не только прочитать синтаксис.
- [Postgres Pro: «Оконные функции»](https://postgrespro.ru/docs/postgrespro/current/tutorial-window) — перечитайте короткое русскоязычное введение от обычного агрегата к оконному и пример накопительной суммы с равными значениями порядка; он закрепляет, почему peers получают общий результат при default frame.
- [DuckDB: Aggregate Functions](https://duckdb.org/docs/current/sql/functions/aggregates) — изучите `Handling NULL Values` и строки `avg`, `count`, `sum`: сопоставьте правило пропуска `NULL`, результат пустой группы и различие `count()`/`count(arg)` с опубликованными знаменателями урока.
- [DuckDB: Numeric Types](https://duckdb.org/docs/current/sql/data_types/numeric) — прочитайте `Fixed-Point Decimals` и `Floating-Point Types`, затем объясните, почему денежные суммы хранятся и складываются как `DECIMAL`, а деление внутри `AVG` приводит к приближённому результату и отдельной политике округления.
- [Postgres Pro: «Оконные функции общего назначения»](https://postgrespro.ru/docs/postgresql/current/functions-window) — используйте русскоязычное предупреждение о default frame у `first_value`, `last_value` и `nth_value` как необязательное закрепление того, что функция видит frame, а не автоматически всю partition.
- [PostgreSQL: Window Function Calls](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS) — разберите точный `frame_clause`: допустимый порядок границ, смысл `CURRENT ROW` для разных режимов и требования к смещению `RANGE`; это справочник для ревью SQL, а не материал для заучивания.
- [SQLite: Window Functions](https://www.sqlite.org/windowfunctions.html#frame_specifications) — прочитайте только раздел `2.2. Frame Specifications`: подробные таблицы хорошо показывают различие позиций, peer-групп и диапазонов значений; примеры выполняются в другом диалекте, поэтому переносите контракт, а не код вслепую.
- [BigQuery: Window function calls](https://cloud.google.com/bigquery/docs/reference/standard-sql/window-function-calls) — сравните правила numeric `RANGE`, именованных окон и допустимых границ в распространённом облачном диалекте; зафиксируйте различия до переноса DuckDB-запроса в production.
- [DuckDB: Catching up with Windowing](https://duckdb.org/2025/02/10/window-catchup) — после основной практики прочитайте объяснения `ROWS`, `RANGE`, peers, `GROUPS` и frame exclusion; последние две возможности нужны только как карта дальнейшего развития и не входят в результат урока.
