## Проблема

Заказчику нужен небольшой список оплаченных заказов в рублях. Для каждой строки нужно
показать:

- идентификатор заказа и пользователя;
- исходную сумму;
- сумму после добавления сервисного сбора 5%;
- категорию `large`, если исходная сумма не меньше 1300 рублей, иначе `regular`.

В результате сначала должны идти более дорогие заказы. Если суммы совпали, порядок
должен однозначно определяться по `order_id`.

Запрос на первый взгляд прост:

```sql
SELECT *
FROM orders
WHERE status = 'paid';
```

Но он не является ответом на поставленную задачу:

- в результат попали все валюты;
- состав столбцов зависит от текущей схемы источника;
- вычисляемых полей нет;
- правило `large` не записано;
- порядок строк не обещан;
- по тексту запроса нельзя восстановить полный контракт результата.

Правдоподобные числа ещё не делают результат проверяемым. До выполнения запроса нужно
уметь ответить:

```text
что означает одна строка результата;
какие исходные строки должны остаться;
какие столбцы и типы получит новая таблица;
как вычисляется каждый новый столбец;
какой порядок считается правильным.
```

## Что уже известно

Урок не начинает работу с таблицами заново. Меняется язык, но не способ рассуждения.

| Уже освоено | Где | Перенос в SQL |
|---|---|---|
| grain и ключ результата | `04/01` | объявляем одну строку на `order_id` до запроса |
| выбор столбцов и булева маска | `03/03` | `SELECT` задаёт столбцы, `WHERE` оставляет строки |
| производные столбцы | `03/04` | выражение с `AS` создаёт вычисляемый столбец |
| явные типы и строгая граница преобразования | `03/02` | проверяем типы входа и результата, не надеемся на случайный cast |
| воспроизводимый порядок | `03/07` | задаём `ORDER BY` с tie-breaker |
| добавление однотипных партий и provenance | `03/07` | `UNION ALL` складывает строки совместимых relations и сохраняет источник обычным столбцом |
| проверяемый handoff | `03/12` | SQL и контракт результата передаются вместе |

Короткая карта переноса:

```text
frame[["order_id", "amount"]] -> SELECT order_id, amount
frame.loc[mask]               -> WHERE <predicate>
frame.assign(total=...)       -> <expression> AS total
frame.sort_values(...)        -> ORDER BY ...
pd.concat([january, february]) -> SELECT ... FROM january
                                  UNION ALL
                                  SELECT ... FROM february
```

Это не утверждение, что Pandas и SQL устроены одинаково. Карта нужна только как мост:
знакомое аналитическое действие получает новый синтаксис и новые границы.

## Концепция

### 1. Результат запроса — новая таблица

`SELECT` не «показывает часть файла». Он формирует новую relation с собственным
контрактом.

Для нашей задачи контракт выглядит так:

```text
популяция  -> оплаченные RUB-заказы из orders
grain      -> один заказ
ключ       -> order_id
столбцы    -> order_id, user_id, currency, amount,
              amount_with_fee, amount_band
типы       -> VARCHAR, VARCHAR, VARCHAR, DECIMAL(18,2),
              DECIMAL(18,2), VARCHAR
порядок    -> amount DESC, затем order_id ASC
```

Фильтрация уменьшает популяцию, но не обязана менять grain:

```text
до фильтра  -> одна строка на заказ
после фильтра -> одна строка на оплаченный RUB-заказ
```

Если один `order_id` неожиданно повторяется, `SELECT` не исправляет модель данных.
Нарушение ключа останется нарушением и в результате.

### 2. Текстовый и логический порядок — не одно и то же

Запрос обычно записывают так:

```sql
SELECT ...
FROM ...
WHERE ...
ORDER BY ...
```

Для предсказания результата полезно читать его в другом порядке:

```text
1. FROM     -> откуда берутся строки
2. WHERE    -> какие строки остаются
3. SELECT   -> какие столбцы и выражения строятся
4. ORDER BY -> как упорядочивается готовый результат
5. LIMIT    -> сколько первых строк упорядоченного результата оставить
```

Это **логический порядок**. Движок может физически оптимизировать выполнение, но
наблюдаемый смысл запроса должен соответствовать этой модели.

Практическое следствие: alias, созданный в `SELECT`, логически ещё не существует на
шаге `WHERE`. В переносимом SQL не следует строить фильтр на предположении, что новый
alias уже доступен. Именованные стадии для таких случаев появятся в `04/06` вместе с
CTE.

### 3. `SELECT` задаёт проекцию

**Проекция** — выбор столбцов и выражений, которые войдут в результат.

```sql
SELECT
    order_id,
    user_id,
    amount
FROM orders;
```

Порядок элементов в select list становится порядком столбцов результата:

```text
order_id -> user_id -> amount
```

`SELECT *` означает «возьми все столбцы, которые источник имеет сейчас». Это удобно
при разовом просмотре, но слабо как контракт:

- производитель добавил `internal_note` — потребитель внезапно получил новый столбец;
- изменился порядок исходных столбцов — изменилась схема выгрузки;
- тяжёлый или чувствительный столбец ушёл downstream без явного решения;
- по запросу нельзя понять, какие поля действительно нужны.

Для поставляемого результата используем явный select list.

### 4. Выражение вычисляет значение для строки

**Выражение** может состоять из:

- ссылки на столбец: `amount`;
- литерала: `1.05`, `'large'`;
- оператора: `*`, `+`, `>=`;
- функции: `round(...)`;
- других выражений.

Например:

```sql
round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2)
```

Для каждой выбранной строки это означает:

```text
взять amount
-> умножить на точный десятичный коэффициент 1.05
-> округлить результат до двух знаков
```

Вычисление не меняет число строк. Оно добавляет новое значение к прежнему grain.

### 5. Alias является частью интерфейса

Без имени вычисляемый столбец получает техническую подпись, зависящую от текста
выражения. Потребителю неудобно и ненадёжно обращаться к такому полю.

```sql
round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2) AS amount_with_fee
```

`AS amount_with_fee` — **alias**, или стабильное имя результата выражения.

Хороший alias:

- описывает смысл, а не реализацию;
- не меняется без причины;
- согласован с контрактом и downstream-кодом;
- не скрывает единицы измерения или валюту.

Переименование `amount_with_fee` в `total` может не изменить числа, но всё равно сломать
контракт потребителя.

### 6. Тип выражения тоже входит в контракт

Денежная сумма в учебном контракте имеет тип `DECIMAL(18,2)`. Он хранит точное
десятичное значение с двумя знаками после запятой.

В запросе коэффициент записан явно:

```sql
CAST(1.05 AS DECIMAL(4, 2))
```

Это делает намерение видимым: мы считаем денежное выражение в десятичной арифметике, а
не превращаем сумму в приблизительный floating-point результат.

При этом сам `amount` не нужно заново разбирать из строки в каждом аналитическом
запросе. Урок принимает типизированную relation `orders`. Если источник всё ещё хранит
непроверенный текст, преобразование и отказ на неразбираемом значении должны происходить
на входной границе, а не случайно внутри каждого отчёта.

После выполнения проверяем не только значения:

```text
amount          -> DECIMAL(18,2)
amount_with_fee -> DECIMAL(18,2)
amount_band     -> VARCHAR
```

### 7. `CASE` создаёт условное поле

Для бизнес-категории используем searched `CASE`:

```sql
CASE
    WHEN amount >= CAST(1300 AS DECIMAL(18, 2)) THEN 'large'
    ELSE 'regular'
END AS amount_band
```

Читаем обычным языком:

```text
если amount не меньше 1300.00 -> large
иначе                         -> regular
```

Граница включена в верхнюю категорию:

| amount | amount_band |
|---:|---|
| 1299.99 | regular |
| 1300.00 | large |
| 1500.00 | large |

Условия `WHEN` проверяются сверху вниз, и используется первая подходящая ветка.
`ELSE` фиксирует поведение для всех остальных допустимых значений.

В этом уроке есть входное предположение: у выбранного оплаченного RUB-заказа сумма
известна. Tiny-набор ему соответствует, а runner проверяет его отдельно. Что SQL делает
с отсутствующим значением внутри сравнения и почему простой `ELSE` может дать опасную
классификацию, подробно разберём в `04/03`.

### 8. `WHERE` оставляет только строки с подходящим условием

**Predicate**, или предикат, — выражение, которое используется как условие.

```sql
WHERE status = 'paid'
  AND currency = 'RUB'
```

Обе части должны выполняться одновременно:

```text
status является paid
И
currency является RUB
```

`WHERE` меняет набор строк, но не создаёт столбцы результата.

#### Скобки сохраняют бизнес-смысл

Предположим, нужны оплаченные заказы в RUB или EUR:

```text
status = paid AND (currency = RUB OR currency = EUR)
```

Правильная запись:

```sql
WHERE status = 'paid'
  AND (currency = 'RUB' OR currency = 'EUR')
```

Без скобок:

```sql
WHERE status = 'paid'
  AND currency = 'RUB'
   OR currency = 'EUR'
```

условие читается как:

```text
(paid AND RUB) OR EUR
```

и пропустит любой EUR-заказ, включая отменённый. Синтаксис останется корректным, а
аналитический ответ — нет.

### 9. `ORDER BY` создаёт наблюдаемый порядок

Relation не обещает «естественного» порядка строк. Порядок CSV, текущий план выполнения
или результат вчерашнего запуска не являются контрактом.

```sql
ORDER BY amount DESC, order_id ASC
```

Читаем:

1. сначала большая сумма;
2. при равной сумме — меньший `order_id`.

Второй столбец является tie-breaker. Без него два заказа с одинаковой суммой могут
меняться местами между запусками.

`LIMIT` выбирает первые строки только после логической сортировки:

```sql
ORDER BY amount DESC, order_id ASC
LIMIT 10
```

`LIMIT 10` без `ORDER BY` обещает не «десять крупнейших» и не «первые по времени», а
только не более десяти строк неопределённого состава.

### 10. `UNION ALL` переносит `concat` на relations

`JOIN` сопоставляет столбцы разных ролей по ключу. `UNION ALL` добавляет строки
однотипных relations друг под другом. Это прямой перенос задачи `03/07`, где январская и
февральская партии имели один grain и одну схему.

```sql
SELECT
    order_id,
    user_id,
    amount,
    '2026-01' AS source_batch
FROM january_orders

UNION ALL

SELECT
    order_id,
    user_id,
    amount,
    '2026-02' AS source_batch
FROM february_orders

ORDER BY source_batch, order_id;
```

До объединения проверьте три контракта:

1. обе ветви возвращают одинаковое число столбцов в одинаковом смысловом порядке;
2. типы соответствующих столбцов совместимы;
3. обе relations описывают строки одного grain.

`source_batch` сохраняет provenance. Без него после объединения нельзя восстановить,
откуда пришла строка, и исследовать пересечение бизнес-ключей.

`UNION ALL` сохраняет все строки, включая одинаковые. Обычный `UNION` дополнительно
удаляет дубликаты **всей выходной строки**. Это не проверка ключа:

- две партии с одним `order_id`, но разными значениями останутся двумя строками;
- две полностью одинаковые ошибочные доставки исчезнут из evidence;
- стоимость дедупликации появится даже тогда, когда бизнес-контракт разрешает повторы.

Поэтому безопасный базовый выбор для партий — `UNION ALL`, а пересечение ключей
проверяется отдельно. Если ключ `order_id` должен быть глобально уникальным:

```sql
SELECT
    order_id,
    count(*) AS rows_per_key
FROM combined_orders
GROUP BY order_id
HAVING count(*) > 1;
```

`GROUP BY` и `HAVING` подробно появятся в `04/04`; сейчас достаточно понимать контракт
проверки. Финальный `ORDER BY` относится ко всему объединённому результату. Порядок строк
в отдельных ветвях не является порядком поставки.

## Соберите это

Сначала решим задачу вручную. Код пока не нужен.

Возьмём четыре строки, достаточные для проверки фильтра:

| order_id | user_id | status | currency | amount |
|---|---|---|---|---:|
| O1001 | U001 | paid | RUB | 1200.00 |
| O1002 | U002 | refunded | RUB | 800.00 |
| O1003 | U003 | paid | USD | 75.00 |
| O1005 | U001 | paid | RUB | 1500.00 |

### Шаг 1. Зафиксируйте контракт результата

```text
grain   -> одна строка на оплаченный RUB-заказ
key     -> order_id
columns -> order_id, user_id, currency, amount,
           amount_with_fee, amount_band
order   -> amount DESC, order_id ASC
```

### Шаг 2. Примените фильтр

Проверяем две части отдельно:

| order_id | status = paid | currency = RUB | Остаётся |
|---|---|---|---|
| O1001 | да | да | да |
| O1002 | нет | да | нет |
| O1003 | да | нет | нет |
| O1005 | да | да | да |

После фильтра остаются `O1001` и `O1005`.

### Шаг 3. Вычислите новые поля

Для `O1001`:

```text
amount_with_fee = 1200.00 * 1.05 = 1260.00
amount_band     = regular, потому что 1200.00 < 1300.00
```

Для `O1005`:

```text
amount_with_fee = 1500.00 * 1.05 = 1575.00
amount_band     = large, потому что 1500.00 >= 1300.00
```

### Шаг 4. Постройте проекцию

Оставляем только шесть полей контракта:

| order_id | user_id | currency | amount | amount_with_fee | amount_band |
|---|---|---|---:|---:|---|
| O1001 | U001 | RUB | 1200.00 | 1260.00 | regular |
| O1005 | U001 | RUB | 1500.00 | 1575.00 | large |

### Шаг 5. Примените порядок

Сортируем `amount DESC`. Итоговая ручная таблица:

| order_id | user_id | currency | amount | amount_with_fee | amount_band |
|---|---|---|---:|---:|---|
| O1005 | U001 | RUB | 1500.00 | 1575.00 | large |
| O1001 | U001 | RUB | 1200.00 | 1260.00 | regular |

Теперь у нас есть полный oracle: ожидаем не просто две строки, а конкретные строки,
столбцы, типы, значения и порядок.

## Используйте это

SQL-артефакт решает ту же задачу:

```sql
SELECT
    order_id,
    user_id,
    currency,
    amount,
    round(amount * CAST(1.05 AS DECIMAL(4, 2)), 2) AS amount_with_fee,
    CASE
        WHEN amount >= CAST(1300 AS DECIMAL(18, 2)) THEN 'large'
        ELSE 'regular'
    END AS amount_band
FROM orders
WHERE status = 'paid'
  AND currency = 'RUB'
ORDER BY amount DESC, order_id ASC;
```

Разберите его по логическим стадиям:

| Стадия | Фрагмент | Что меняется |
|---|---|---|
| источник | `FROM orders` | появляется популяция исходных заказов |
| фильтр | `status = 'paid' AND currency = 'RUB'` | остаются две строки tiny-набора |
| проекция | шесть выражений после `SELECT` | фиксируются столбцы результата |
| вычисление | `round(amount * ..., 2)` | появляется точная сумма со сбором |
| классификация | `CASE ... END` | появляется категория заказа |
| порядок | `amount DESC, order_id ASC` | строки получают воспроизводимую последовательность |

Запустите reference runner:

```bash
uv run --locked python code/main.py
```

Runner выполняет только инфраструктурную работу:

1. создаёт типизированную relation `orders` из учебного CSV;
2. запускает `outputs/paid_rub_orders.sql`;
3. читает `outputs/select_result_contract.json`;
4. сравнивает столбцы, типы, grain и порядок;
5. сопоставляет SQL-результат с ручной таблицей.

Python DB API, параметры и управление connection не являются материалом этого урока.
Здесь достаточно запустить runner и изучать SQL-артефакт. Программную границу DuckDB
разберём в `04/11`.

Успешный запуск заканчивается:

```json
{
  "matches_manual": true
}
```

Не ограничивайтесь этим флагом. Откройте полный JSON и вручную подтвердите:

- сначала идёт `O1005`, затем `O1001`;
- суммы равны `1575.00` и `1260.00`;
- категории равны `large` и `regular`;
- шесть столбцов совпадают с контрактом;
- денежные поля остались `DECIMAL(18,2)`.

## Сломайте это

### Поломка 1. Замените проекцию на `SELECT *`

Добавьте в источник технический столбец:

```sql
ALTER TABLE orders ADD COLUMN internal_note VARCHAR;
```

При `SELECT *` он попадёт в результат без решения автора запроса. Явный select list
сохранит прежние шесть столбцов.

### Поломка 2. Уберите скобки из смешанного `AND` / `OR`

Сравните:

```sql
WHERE status = 'paid'
  AND (currency = 'RUB' OR currency = 'EUR')
```

и:

```sql
WHERE status = 'paid'
  AND currency = 'RUB'
   OR currency = 'EUR'
```

Во втором случае найдите `cancelled` или `refunded` EUR-строку, которая неожиданно
прошла фильтр.

### Поломка 3. Попробуйте «исправить» ключ через `DISTINCT`

Скопируйте строку `O1001` в источник и добавьте:

```sql
SELECT DISTINCT ...
```

Точный дубль может исчезнуть из текущей проекции, но причина не устранена:

- источник всё ещё нарушает grain;
- изменение одного непроецируемого столбца снова проявит две строки;
- автор не решил, какая версия заказа правильная;
- `DISTINCT` скрыл evidence дефекта.

Сначала проверяют ключ и происхождение дубля. `DISTINCT` применяют только когда
уникализация является объявленной операцией результата.

### Поломка 4. Уберите tie-breaker

Добавьте заказ `O1000` с суммой `1500.00`. При:

```sql
ORDER BY amount DESC
```

относительный порядок `O1000` и `O1005` не закреплён. Полный контракт:

```sql
ORDER BY amount DESC, order_id ASC
```

### Поломка 5. Измените alias или тип

Переименуйте `amount_with_fee` в `total` либо приведите его к `DOUBLE`. Число может
выглядеть тем же, но контракт схемы должен остановить поставку.

### Поломка 6. Добавьте выбранную строку без amount

Создайте оплаченный RUB-заказ с отсутствующей суммой. Входной контракт должен
остановить расчёт до классификации. Не превращайте такую сумму в ноль и не отправляйте
её автоматически в `regular`. Механизм `NULL` и трёхзначную логику разберём в следующем
уроке.

## Проверьте это

Проверка охватывает вход и результат.

### Входные инварианты

- relation называется `orders`;
- одна строка означает один заказ;
- `order_id` не повторяется;
- необходимые столбцы существуют и типизированы;
- у выбранного оплаченного RUB-заказа известна сумма.

### Инварианты результата

- grain остаётся одной строкой на `order_id`;
- столбцы и их порядок точно совпадают с контрактом;
- `amount` и `amount_with_fee` имеют тип `DECIMAL(18,2)`;
- ручные и SQL-значения совпадают;
- граница `1300.00` относится к `large`;
- при равной сумме `order_id` задаёт tie-breaker;
- новый исходный столбец не протекает в проекцию;
- дубликат ключа не маскируется как корректный результат.

Запустите behavioral tests:

```bash
uv run --locked python -m unittest discover -s tests
```

Тесты проверяют наблюдаемое поведение, а не наличие определённых слов в SQL. Другой
запрос допустим, если он сохраняет тот же контракт, значения и границы.

## Поставьте результат

Урок поставляет два связанных файла:

```text
outputs/paid_rub_orders.sql
outputs/select_result_contract.json
```

`paid_rub_orders.sql` — исполняемый SQL-артефакт. Он ожидает типизированную relation
`orders` и строит согласованную таблицу результата.

`select_result_contract.json` фиксирует:

- входной и выходной grain;
- обязательные входные столбцы;
- бизнес-правила фильтра и вычислений;
- имена и типы выходных столбцов;
- полный порядок строк.

Чтобы переиспользовать результат:

1. подготовьте relation `orders` с совместимым контрактом;
2. выполните SQL-файл;
3. проверьте результат по JSON-контракту;
4. при изменении бизнес-правила обновите SQL, контракт и контрольный пример вместе.

Отдельный CLI здесь не нужен: поставляемым механизмом является запрос. Явную программную
границу DuckDB ↔ pandas разберём в `04/11`.

## Ключевые термины

| Термин | Распространённое заблуждение | Точное значение |
|---|---|---|
| Relation результата | Временный вывод на экран | Новая таблица со своим grain, схемой и ограничениями |
| Projection | Выбор строк | Выбор столбцов и выражений результата |
| Select list | Все столбцы источника | Упорядоченный список выражений после `SELECT` |
| Expression | Только арифметика | Столбцы, литералы, функции и операторы, вычисляющие значение |
| Literal | Имя столбца | Значение, записанное прямо в SQL, например `'paid'` или `1.05` |
| Alias | Косметическая подпись | Стабильное имя выражения в выходном контракте |
| Predicate | Любое выражение | Условие, по которому `WHERE` решает судьбу строки |
| `CASE` | Отдельный цикл | Условное выражение, возвращающее одно значение |
| Deterministic order | Текущий порядок файла | Порядок, полностью определённый `ORDER BY` и tie-breaker |
| `DISTINCT` | Автоматическое исправление дублей | Операция уникализации полной проекции, не доказательство правильного grain |
| `UNION ALL` | SQL-вариант `JOIN` | Добавление строк совместимых relations без удаления повторов |
| `UNION` | Безопасная версия `UNION ALL` | Set operation с дедупликацией полной выходной строки, которая может скрыть evidence |
